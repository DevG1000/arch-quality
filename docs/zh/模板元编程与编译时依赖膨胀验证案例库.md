## 1. 编译时扇入（MLR-013：热模板头文件）

### 1.1 案例：OpenFOAM `Tensor.H` 被大量编译单元包含

- **项目**：OpenFOAM（v2106 及更早版本）
- **领域**：计算流体力学（CFD）
- **问题描述**：`Tensor.H` 定义了张量运算的核心模板类。由于它被 `vector.H`、`symmTensor.H`、`sphericalTensor.H` 等头文件包含，而后者又被几乎所有求解器和工具包含，导致 `Tensor.H` 出现在超过 120 个编译单元的依赖树中。修改该头文件中的任意一行会触发全量重编译，耗时从数分钟增至数小时。
- **依赖关系**：
  ```cpp
  // Tensor.H
  template<class Cmpt>
  class Tensor { ... };
  
  // vector.H
  #include "Tensor.H"
  class vector : public Tensor<scalar> { ... };
  
  // solver.C
  #include "vector.H"  // 间接包含 Tensor.H
  ```
- **检测方法**：使用 `clang -ftime-trace` 获取包含链，聚合统计每个头文件的编译单元数量。
- **预期输出**：
  ```
  [MLR-013] 热模板头文件 (HIGH)
  头文件: src/OpenFOAM/primitives/Tensor/Tensor.H
  被包含编译单元数: 127 (阈值=50)
  Top 包含者: solverPimpleFoam.C, solverSimpleFoam.C, meshCheck.C ...
  建议: 将 Tensor 的实现拆分，使用 PIMPL 或前置声明减少传播。
  ```

### 1.2 案例：Gmsh 的 `gmsh.h` 轻量头文件（反例，无告警）

- **项目**：Gmsh
- **领域**：网格生成
- **问题描述**：对外头文件 `gmsh.h` 仅包含函数声明（无模板实现），通过前置声明和指针类型隐藏细节。被包含的编译单元数量 < 20。
- **预期输出**：无 MLR-013 告警。


## 2. 模板实例化重复率（MLR-014 + MLR-019）

### 2.1 案例：Eigen `Matrix<double, 3, 3>` 在多个编译单元重复实例化

- **项目**：基于 Eigen 的 CAE 求解器
- **领域**：线性代数库
- **问题描述**：`Eigen::Matrix<double, 3, 3>` 被 47 个 `.cpp` 文件使用，每个都独立实例化，未使用 `extern template`。
- **代码片段**：
  ```cpp
  // solverA.cpp, solverB.cpp ... 47 个类似文件
  #include <Eigen/Dense>
  void f() { Eigen::Matrix<double,3,3> m; ... }
  ```
- **检测方法**：使用 `clang -Xclang -ast-dump=json` 提取模板特化并统计。
- **预期输出**：
  ```
  [MLR-014] 模板重复实例化 (HIGH)
  特化: Eigen::Matrix<double,3,3>
  实例化次数: 47 (唯一=1) → 重复率 97.9%
  建议: 在头文件中添加 "extern template class ..."。
  
  [MLR-019] 未使用 extern template 优化 (LOW)
  相同特化重复率 >30% 且未使用 extern template。
  ```

### 2.2 案例：deal.II 的显式实例化管理（反例）

- **项目**：deal.II
- **领域**：有限元库
- **问题描述**：deal.II 官方文档明确指出，“实例化复杂类和函数模板在编译时间和磁盘空间上都非常昂贵”，因此其设计策略将模板分为三类：
  1. 已知固定实例化数量（如 `template <int dim>`，仅为 dim=1,2,3 显式实例化）
  2. 少量已知实例化（如线性代数类仅支持 `double`, `float`, `complex<double>`）
  3. 用户自定义实例化（提供头文件供高级用户显式实例化非标准类型）

  这一策略将实例化时机从应用编译时移至库编译时，使库用户编译时间大幅缩减。
- **预期输出**：无 MLR-014/019 告警。评估工具应能识别 deal.II 头文件中已在库内部显式实例化的模板，不在用户代码中重复计数。


## 3. 头文件影响半径（MLR-015 + MLR-024）

### 3.1 案例：BRL-CAD `common.h` 的传染性包含

- **项目**：BRL-CAD（v7.0 之前）
- **领域**：CAD/几何建模
- **问题描述**：`common.h` 包含大量系统头文件和内部定义，被超过 200 个源文件直接或间接包含。修改它导致几乎全项目重编译，影响半径 R > 150，并存在包含循环。
- **检测方法**：生成 `#include` 依赖图，统计可达编译单元数量，检测强连通分量。
- **预期输出**：
  ```
  [MLR-015] 头文件传染链过长 (MEDIUM)
  头文件: src/common/common.h
  影响半径 R: 187 (直接 89，传递 98)
  
  [MLR-024] 头文件包含循环 (HIGH)
  循环: common.h -> config.h -> platform.h -> common.h
  建议: 拆分 common.h，使用前置声明打破循环。
  ```

### 3.2 案例：LLVM 的模块化头文件（反例）

- **项目**：LLVM
- **领域**：编译器基础设施
- **问题描述**：LLVM 严格遵循“每个头文件只包含它直接需要的声明”，通过 `llvm/Support/Compiler.h` 等细粒度头文件避免传染，影响半径通常 < 30。
- **预期输出**：无 MLR-015 告警。


## 4. 模板嵌套深度（MLR-016 + MLR-022）

### 4.1 案例：Boost.MPL 中的类型列表递归

- **项目**：使用 Boost.MPL 的遗留 CAE 软件（如旧版 OpenFOAM）
- **领域**：元编程库
- **问题描述**：`boost::mpl::fold` 递归实例化深度随类型列表长度线性增长。某模块深度 D_max = 42，编译时间从 2 秒增至 3 分钟，内存峰值超 2GB。
- **代码片段**（简化）：
  ```cpp
  template<typename Seq, typename State, typename Op>
  struct fold_impl {
      typedef typename fold_impl<...>::type type; // 递归
  };
  ```
- **检测方法**：分析模板实例化链，计算最大深度 D_max。
- **预期输出**：
  ```
  [MLR-016] 模板嵌套深度过大 (MEDIUM)
  最大深度 D_max = 42 (阈值=10)
  最深链: boost::mpl::fold_impl<...> → ... (42层)
  建议: 使用 C++17 折叠表达式或 constexpr 函数替代。
  
  [MLR-022] 递归模板无限实例化风险 (HIGH)
  递归模式: template<int N> struct A : A<N+1> (无终止)
  ```

### 4.2 案例：MOOSE 框架 AD（自动微分）模板系统

- **项目**：MOOSE (Multiphysics Object-Oriented Simulation Environment)
- **领域**：多物理场仿真框架
- **问题描述**：MOOSE 的 AD 系统通过**模板元编程**实现精确导数计算，替代了传统符号微分的表达式膨胀问题和数值微分的截断误差。一个典型实现如 `ADRealVectorValue ad_curl = adCurlSln(u)`，使开发者无需手动推导复杂的雅可比矩阵。

  然而，自动微分的底层依赖大量模板递归和类型推导。在复杂本构关系或非线性材料（如非线性磁导率、超导体临界态模型、磁致伸缩耦合效应）场景下，嵌套深度可随自由度数量急剧增长。团队需主动控制深度，避免编译时间失控。
- **与规则 MLR-016 的关联**：MOOSE 案例说明了模板嵌套深度的两面性——它是实现零成本抽象和开发者效率提升的核心技术，但也需架构层面的深度控制机制。
- **检测要点**：对 AD 生成的模板实例化链进行深度分析，识别可能的指数增长模式。

### 4.3 案例：C++17 `std::visit` 的 constexpr 深度（反例，无告警）

- **项目**：现代 C++ 代码
- **问题描述**：`std::visit` 内部使用递归模板处理 variant 类型，但深度通常为 variant 中的类型数量（很少超过 10），且编译器对 constexpr 递归有优化。深度 < 5。
- **预期输出**：无 MLR-016 告警。


## 5. 二进制膨胀率（MLR-017 + MLR-023）

### 5.1 案例：OpenFOAM 中 `Tensor` 多精度实例化导致的膨胀

- **项目**：OpenFOAM
- **领域**：CFD
- **问题描述**：OpenFOAM 同时实例化 `Tensor<scalar>`（double）、`Tensor<vector>` 等，多精度和复杂参数组合导致模板生成大量重复代码。使用 `bloaty` 分析 libOpenFOAM.so，模板生成符号占比超过 45%。
- **检测方法**：`nm --demangle --size` 过滤模板符号，计算占比；跨库检测重复实例化。
- **预期输出**：
  ```
  [MLR-017] 二进制膨胀超标 (MEDIUM)
  模板代码占 .text 比例: 47% (阈值 35%)
  最大贡献者: Tensor<double>::operator+ (1.2 MB)
  
  [MLR-023] 同一模板在多个库中重复实例化 (MEDIUM)
  特化: Tensor<double> 出现在 libOpenFOAM.so, libfiniteVolume.so, libmeshTools.so
  建议: 将通用实例化集中在一个基础库中，其他库使用 extern template。
  ```

### 5.2 案例：Trilinos 模板实例化膨胀与编译资源耗尽

- **项目**：Trilinos
- **领域**：线性代数求解器库
- **问题描述**：Trilinos 中大量使用模板化包（如 Belos、Amesos2、Ifpack2、MueLu）。由于显式模板实例化（ETI）使用不足，某些示例因直接包含模板头文件而消耗“大量编译器时间和系统内存”。xSDK 项目（面向科学计算的可组合软件栈）因编译时间过长，被迫修改安装程序以移除 Trilinos 的模板化包。

  为此，Trilinos 框架建立了顶层选项（如浮点类型、复数类型的启用/禁用），要求每个模板化包必须基于请求的类型实现 ETI，以大幅减少编译和重编译时间。这成为工业级模板库治理的经典案例。
- **检测方法**：结合编译时间和内存监控，对模板化包进行 ETI 使用率统计。
- **预期输出**：
  ```
  [MLR-017] 二进制膨胀超标 (MEDIUM)
  Trilinos 包: Belos
  未使用 ETI 导致编译内存峰值: 3.8GB
  建议: 按 Trilinos 框架要求启用 ETI 选项，基于请求的浮点类型集中实例化。
  ```

### 5.3 案例：Google 的 `-fvisibility=hidden` 实践（反例）

- **项目**：Abseil / Google 内部代码
- **领域**：基础库
- **问题描述**：默认隐藏符号，仅导出必要接口，大幅减少模板生成代码在最终二进制中的暴露。膨胀率通常 < 20%。
- **预期输出**：无 MLR-017 告警。

- **案例**：某项目中 `list_utils.h` 定义了仅被同一头文件内辅助函数使用的私有模板 `detail::quick_sort`，导致传播到 30 个编译单元。

## 9. 附录：模板实例化组合爆炸与诊断方法

### 9.1 典型数值：组合爆炸与编译时间增长

- **STL容器组合效应**：一个模板类 `Container<T, Allocator, Policy>` 有 3 个模板参数：`T` 有 5 种常用类型，`Allocator` 有 2 种，`Policy` 有 3 种，理论实例化组合为 5 × 2 × 3 = 30 种。再乘以 50 个编译单元，即 1500 次实例化。在涉及递归模板的场景下，这个开销会进一步指数放大。
- **诊断方法**：
  1. 使用 `-ftime-trace` 获取每个编译单元的模板实例化时间线
  2. 通过 `nm --demangle --size` 统计模板符号占 `.text` 段比例
  3. 使用 `bloaty` 分析二进制体积来源
  4. 结合 CI 门禁监控编译时间趋势

### 9.2 工业级解耦模式：非模板基类隔离法

- **原理**：将模板类中与类型参数无关的部分（如链表节点 `next/prev` 操作）抽离为**非模板基类**，模板派生类仅负责类型相关的数据存储。无论数据类型如何，底层拓扑逻辑只编译一次，既减少体积又提高缓存效率。
- **示例**：
  ```cpp
  struct NodeBase {
      NodeBase *next, *prev;
      void hook(NodeBase* pos);
      void unhook();
  };
  template<typename T>
  struct Node : public NodeBase {
      T data;
  };
  ```
- **对应规则**：这一工业最佳实践可直接用于优化 MLR-017 和 MLR-023 相关的膨胀问题，也是检测“不必要的模板化”的正面参照。


本案例库基于 11 个开源工业软件的真实演进历史及典型工程反模式构建，为《模板元编程与编译时依赖膨胀评估指南》提供了可验证的基准。通过本库的阳性/阴性对照，评估工具可以验证其对六大子维度和十二条规则的检测正确性与抗干扰能力。
