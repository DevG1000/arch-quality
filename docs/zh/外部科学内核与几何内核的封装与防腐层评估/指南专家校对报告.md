## 三、新发现（需在 WP-4 实施前处理）

### P1-1：ACL-001 / ACL-007 / ACL-012 的"白名单外引用"检测信号重叠

**相悖点**：
- ACL-001（§五）检测"wrapper 目录白名单**之外**引用内核符号（`TopoDS_*`/`BRep*`/`Handle_*`）"
- ACL-007（§五）检测"import/export 模块白名单**之外**引用格式符号（`STEPControl_*`/`IGESControl_*`/IFC）"
- ACL-012（§五）检测"格式符号在专用模块**外**的引用密度"

三者都以"白名单外符号引用"为检测信号。实务中同一处违规可能**同时触发多规则、造成双重计分**：

| 示例 | ACL-001 | ACL-007 | ACL-012 |
|:-----|:-------:|:-------:|:-------:|
| 业务模块直接 `STEPControl_Reader` | ⚠️ 若 IRC 头文件含 `Handle_*` 也可能命中 | ✅ ERROR | ✅ WARNING（密度超阈值）|
| 业务模块直接 `BRepAlgoAPI_Fuse` | ✅ ERROR | — | — |

**建议**：WP-4 实现前明确**信号归属**——内核符号（`TopoDS_*/BRep*/Handle_*`）只归 ACL-001；格式符号（`STEPControl_*/IGESControl_*/IFC`）只归 ACL-007/012（007 管形态、012 管密度）。在指南加强"边界说明"：ACL-012 仅在**已由 ACL-007 判定为散落**的场景下叠加密度计数，避免同一散落既扣 ERROR 又扣 WARNING 的重复惩罚。

### P1-2：ACL-005 vs ACL-011 错误处理检测点重叠

**相悖点**：
- ACL-005（§五）检测"内核调用点失败处理"，检测逻辑含"`BRep*`/`TopoDS_*`/**求解器 API**"
- ACL-011（§五）检测"reader/writer 调用点错误处理"

数据交换场景中 `STEPControl_Reader.ReadFile()` 属于"reader 调用点"（ACL-011），但同时也是外部内核 API 调用点（若按 ACL-005 的"求解器 API"信号解释）。同一处 `ReadFile` 无 `IFSelect_ReturnStatus` 检查，可能**同时触发 ACL-005 与 ACL-011**。

**建议**：在 ACL-005 检测逻辑明确**排除 reader/writer 调用点**（"格式读写调用点归 ACL-011，不重复触发"），在两规则加边界说明（对齐 GCS-002/004 去重先例）。

### P1-3：内核/格式符号清单未集中定义

**发现**：ACL-001 符号清单（`TopoDS_*/BRep*/Handle_*`）写在规则描述中，ACL-007 的（`STEPControl_*/IGESControl_*/IFC`）写在另一处——全文未集中列出，WP-4 实现时需从两处手工提取，易漏项或两边不一致。

**建议**：在指南 §七 工具集成或新增一节集中定义"外部符号清单"（内核符号集 + 格式符号集 + wrapper/import-export 白名单），作为 WP-4 检测正则的单一事实来源。
