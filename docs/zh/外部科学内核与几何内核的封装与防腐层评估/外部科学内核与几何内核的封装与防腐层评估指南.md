# 外部科学内核与几何内核的封装与防腐层评估指南（1.3版）

> **版本**：1.3（专家校对 3 项 P1 修订后）
> **编制**：AI 辅助编制（编制流程见《AI 架构评估文档编制指南 1.8》）
> **状态**：通过 AI 专家自评（P0 清零）+ 专家校对（PASS with observations，3 项 P1 已修订），达到可用版本（作 WP-4 引擎实施基准）
> **适用范围**：通过封装/防腐层接入第三方几何内核（OCCT、CGAL 等）、科学计算库、或进行外部数据交换（STEP/IGES/IFC）的 CAE/工业软件

---

## 概述

### 评估目标

本指南定义**外部科学内核与几何内核的封装与防腐层（Anti-Corruption Layer）**评估维度（注册表维度⑧，引擎前缀 **ACL**）。评估对象是接入外部内核/科学库/数据交换标准的代码库，衡量其在以下方面的架构健康度：

1. **外部内核访问防腐**：业务代码是否绕过 wrapper 直连内核 API（ACL-001）；内核类型是否泄漏进 wrapper 公开接口（ACL-004）；内核调用失败是否被封装层处理（ACL-005）
2. **Wrapper 覆盖度与演进守卫**：核心内核 API 是否都有 wrapper 声明（ACL-002）；是否存在 `#if OCC_VERSION` 版本守卫隔离升级影响（ACL-003）
3. **数据交换防腐**：STEP/IGES/IFC 读写是否集中在 import/export 模块而非散落业务模块（ACL-007）；读写错误是否被处理（ACL-011）；是否存在绕过封装的格式直连（ACL-012）
4. **保真度与外部标准一致性**：是否存在 round-trip 往返保真度测试（ACL-006）；单位/公差换算是否集中（ACL-008/009）；是否守卫外部标准版本 AP203/214/242（ACL-010）

本维度**不评估**：外部内核自身的功能正确性（归③ NVR）、外部内核对象生命周期（归④ GCS-004）、数据转换机制统一性（归⑤ MPR-012）、绑定代码自身质量（归① 多语言）。

### 适用范围

- **适用**：引用外部几何内核/科学库（`TopoDS_*`/`Handle_*`/`BRep*`/`CGAL`/`STEPControl_*` 等）或进行外部标准数据交换（STEP/IGES/IFC）的代码库
- **不适用**：不接入任何外部内核/数据交换标准的纯业务代码（此时引擎应判定不适用并返回 None）

> **当前版本作用域声明（WP-3）**：本指南的检测符号与 12 条规则落地**暂限于几何内核封装（OCCT/CGAL 系列符号）与外部标准数据交换（STEP/IGES/IFC）**。科学内核（PETSc、deal.II、VTK 等）当前仅作概念层面覆盖（§8 启用条件未含科学内核符号），其**专属符号集与检测点列入后续版本**，不阻塞 WP-4 实现。与《设计依据》§2.1 作用域声明一致。

### 行业标准映射

| 标准 | 对应关切 |
|:-----|:---------|
| ISO/IEC 25010 可移植性（替换性）/互操作性 | 外部依赖接入形态、可替换性、数据交换 |
| Domain-Driven Design（Evans）| **防腐层（Anti-Corruption Layer）** 战术模式本体论 |
| ISO 10303（STEP）AP203/AP214/AP242 | 数据交换防腐、标准版本守卫（ACL-007/010）|
| OCCT DataExchange 模块化设计 | 集中读写/错误处理/单位换算的正面参照（ACL-006/007/011）|

## 置信度说明

本指南对每条规则与每个检测方法标注**三级置信度**：

| 置信度 | 含义 | 检测方式 | 使用建议 |
|:------:|:-----|:---------|:---------|
| **高** | 检测结果准确可靠，无需人工复核 | 精确符号匹配、文件存在性、白名单外引用 | 可作 CI 阻断（ERROR）|
| **中** | 检测结果基本可靠，边界情况需人工确认 | 结构检查、调用点上下文、白名单 | 建议 WARNING 或需人工复核 |
| **低** | 检测为启发式推断，需人工复核 | 模式/关键词匹配、正则推断 | 仅 INFO，不阻断 |

**使用建议**：高置信度规则可纳入门禁；中置信度规则作为告警；低置信度规则仅作为参考信息。详见§七。

## 一、子维度与权重分配

外部科学内核与几何内核的封装与防腐层评估由以下 **4 个子维度** 加权合成：

| 子维度 | 权重（默认）| 覆盖规则 | 置信度 | 对应风险 |
|--------|-------------|:--------:|:------:|---------|
| 外部内核访问防腐 | 30% | ACL-001/004/005 | 中 | 直连内核 API、类型泄漏、失败未封装 |
| Wrapper 覆盖度与演进守卫 | 15% | ACL-002/003 | 低 | 核心 API 无 wrapper、内核升级冲击全局 |
| 数据交换防腐 | 30% | ACL-007/011/012 | 中 | STEP/IGES/IFC 读写散落、错误未处理、格式直连 |
| 保真度与外部标准一致性 | 25% | ACL-006/008/009/010 | 低 | 无往返保真测试、单位/公差魔法因子、无标准版本守卫 |

**权重设计依据**（WP-3 阶段 1 用户确认 30/15/30/25）：
- **外部内核访问防腐**（30%）与**数据交换防腐**（30%）权重并列最高：它们是防腐蚀的**直接目标**——直连内核与交换读写散落是外部依赖变更冲击业务体系的两条主路径。
- **保真度与外部标准一致性**（25%）次之：在防腐蚀基础上进一步保证"不丢语义"（round-trip/单位/公差/版本）。
- **Wrapper 覆盖度与演进守卫**（15%）权重最低：其影响面向量间接（覆盖度与版本守卫决定升级影响面，但以访问防腐为前提）。

**权重来源标注**：默认权重为**工程经验校准（待定）**，将在 WP-7 交叉验证后定案（H2 决策：激活子集归一化实施归 H3，本维度以候选权重占位展示）。

## 二、子维度定义与评分算法

### 2.1 外部内核访问防腐（30%）

**定义**：评估业务代码是否绕过防腐边界（wrapper）直连外部内核 API、外部类型是否泄漏进 wrapper 公开接口、外部内核调用的失败是否被封装层正确处理。外部内核访问防腐是外部依赖隔离的**必要条件**。

**置信度**：中

**设计依据**：
- **DDD 防腐层（Evans 2003）**：防腐层隔离外部子系统，业务层只依赖稳定接口——直连等于破坏防腐
- **类型泄漏危害**：外部类型（`TopoDS_Shape`）出现在 wrapper 公共签名，等于把内核数据模型暴露给业务层，升级即风暴
- **失败语义差异**：异常型内核（C++ 异常）与状态码型内核（`IsDone()` 返回码）要求不同封装策略，未封装则失败静默吞没

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 无直连内核 API（wrapper 白名单外无内核符号）| wrapper 目录白名单 + 内核符号清单（`TopoDS_*`/`BRep*`/`Handle_*`/`STEPControl_*`）| 40分 | **高** |
| 内核类型无泄漏（wrapper 公开签名隔离）| 检测 wrapper 头文件 public 签名中的外部类型 | 30分 | **中** |
| 内核调用失败已封装（区分异常型/状态码型）| 调用点上下文 try/catch 或错误码检查 | 30分 | **中** |

```
外部内核访问防腐得分 = sum(各检查项得分)
```

**置信度说明**：
- 直连检测基于"wrapper 白名单 + 内核符号清单"精确符号匹配，但白名单需项目配置，置信度为**高**。
- 类型泄漏需解析 wrapper 公开头文件签名，依赖声明的可见性判断，置信度为**中**。
- 失败封装检测需区分异常型/状态码型内核的检查形态，跨函数传递无法追踪，置信度为**中**。

**对应行业实践**：
- SALOME GEOM 通过 `GEOMImpl` 封装 OCCT，业务层不直接碰 `TopoDS_*`
- FreeCAD 的 Part/PartDesign 模块隔离了 OCCT 内核访问

**代码坏味道：直连内核 + 类型泄漏（Direct Kernel Access & Type Leakage）**

- **描述**：业务层直接调用内核 API，或 wrapper 公共接口把外部类型当作普通参数暴露。
- **典型表现**：业务模块直接 `#include <BRepAlgoAPI_Fuse.hxx>`；wrapper 头文件 `TopoDS_Shape do_stuff(TopoDS_Shape in);`。
- **危害**：内核升级 API/符号变化冲击全局业务代码；类型泄漏使防腐层形同虚设。

**算例**：
- 正例：业务层只依赖 `Wrapper::Result`，wrapper 内部 `TopoDS_Shape` 不越界，失败统一 `std::runtime_error`
- 负例：业务层直接 `BRepAlgoAPI_Fuse op(a,b); return op.Shape();`，未检查 `IsDone()` 且接口直接透出 `TopoDS_Shape`

### 2.2 Wrapper 覆盖度与演进守卫（15%）

**定义**：评估核心外部内核 API 在封装层是否有对应声明（覆盖度），以及是否存在版本守卫把内核升级影响显式隔离。覆盖度与版本守卫决定升级影响面的可管理性。

**置信度**：低（启发式）

**设计依据**：
- **覆盖度完整性**：wrapper 只封装核心 API 时，业务层被迫为冷门 API 直连，防腐出现缺口
- **版本守卫实践**：`#if OCC_VERSION >= 70800` 类条件编译是隔离内核多版本差异的标准手段

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 核心 API wrapper 覆盖度 | 外部内核核心类清单 vs wrapper 声明引用比对 | 50分 | **低** |
| 内核版本守卫存在性 | 检测 `#if OCC_VERSION`/`VERSION` 条件编译 + 守卫密度 | 50分 | **低** |

```
Wrapper 覆盖度与演进守卫得分 = sum(各检查项得分)
```

**置信度说明**：
- "核心 API 清单"需人工维护，覆盖度比对为启发式，置信度为**低**。
- 版本守卫存在性可检测宏引用，但"守卫是否覆盖全部版本差异点"无法静态判定，置信度为**低**。

**对应行业实践**：
- OCCT 自身用 `OCC_VERSION` 宏管理跨版本 API 差异
- 商业 CAD 平台在 wrapper 内维护 `#if OCC_VERSION` 兼容分支表

**代码坏味道：防腐缺口（Anti-Corruption Gap）**

- **描述**：核心内核 API 无 wrapper 覆盖，或版本差异点无守卫，升级影响面失控。
- **典型表现**：`PySide`/业务层直调 20% 未封装的热门 API；`#if OCC_VERSION` 只出现 1 处而内核跨 3 个主版本演进。
- **危害**：升级时影响面放大；防腐层覆盖不全时用户绕行直连。

**算例**：
- 正例：wrapper 对全部核心内核操作类有声明，业务层 0 直连；版本差异统一 `#if OCC_VERSION` 块隔离
- 负例：核心 API 90% 无 wrapper，业务层被迫直连；无任何 `OCC_VERSION` 守卫

### 2.3 数据交换防腐（30%）

**定义**：评估 STEP/IGES/IFC 等外部标准数据交换是否集中在专用 import/export 模块（而非散落业务模块）、读写调用是否有错误处理、是否存在绕过封装的格式直连。数据交换防腐是外部标准接入的**必要条件**。

**置信度**：中

**设计依据**：
- **OCCT DataExchange 模块化**：`TKDESTEP`/`TKDECIGES`/`TKDEIFC` 分层设计，读写与文档管理集中在数据交换模块
- **ISO 10303 语义**：STEP 文件携带单位制/公差/版本（AP203/214/242），散落读写即绕过统一换算与版本守卫
- **错误处理必要性**：reader/writer 失败（文件损坏/版本不兼容）若未处理则静默进入内部数据

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| STEP/IGES/IFC 读写集中（专用模块外无直出）| import/export 模块白名单 + 格式符号（`STEPControl_*`/`IGESControl_*`/IFC）引用定位 | 45分 | **高** |
| 导入导出错误已处理 | reader/writer 调用点上下文错误码/try/catch 检查 | 30分 | **中** |
| 无格式直连（引用密度阈值内）| 格式符号在专用模块外的引用密度统计 | 25分 | **中** |

```
数据交换防腐得分 = sum(各检查项得分)
```

**置信度说明**：
- 读写集中度依托"import/export 模块白名单 + 符号引用定位"，精确可判，置信度为**高**。
- 错误处理检测依赖调用点上下文，需区分内部解包与业务错误，置信度为**中**。
- 格式直连为引用密度统计，阈值需 WP-4 校准，置信度为**中**。

**对应行业实践**：
- OCCT 的 `STEPControl_Writer`/`STEPControl_Reader` 集中在数据交换工具层
- SALOME GEOM 的 `STEPPlugin`/`IGESPlugin`/`BREPPlugin` 插件集中承载数据交换

**代码坏味道：数据交换散落（Data Exchange Scatter）**

- **描述**：格式读写符号散落各业务模块，绕过集中 import/export；不同模块各自换算单位/公差。
- **典型表现**：`STEPControl_Reader` 出现在 6 个业务文件；导入错误 `IFSelect_ReturnStatus` 未检查。
- **危害**：单位/公差语义漂移、版本不兼容静默吞没、导出结果不一致。

**算例**：
- 正例：所有 STEP 读写经 `import_step()`/`export_step()` 集中接口，错误统一抛出
- 负例：业务模块直接 `STEPControl_Reader reader; reader.ReadFile(x);` 后直接 `reader.OneShape()` 且无错误检查

### 2.4 保真度与外部标准一致性（25%）

**定义**：评估数据交换的往返保真度测试存在性、单位/公差换算是否集中管理、外部标准版本（AP203/214/242）是否守卫。本子维度为**增强层**，在防腐蚀基础上进一步保证"不丢语义"。

**置信度**：低（启发式）

**设计依据**：
- **round-trip 测试**：写出→读回→数据一致性比较，验证数据交换不丢语义（面/实体/拓扑/装配）
- **单位/公差换算集中**：`inch→mm`、`tol*` 魔法因子散落是 STEP 交换最常见的数据失真源
- **标准版本语义**：AP203（配置管理）vs AP214（汽车）vs AP242（新一代，聚合），文档必须声明并守卫所支持版本

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| round-trip 往返保真度测试存在（加分项）| 检测往返测试符号（`round_trip`/`write+read` 比对断言）| 40分 | **高** |
| 单位换算无魔法因子（集中工具函数）| 换算魔法因子启发式（25.4/0.0254/3.28084 等）| 20分 | **低** |
| 公差换算无魔法因子 | 公差换算因子启发式 | 20分 | **低** |
| 外部标准版本守卫 | 检测 AP203/AP214/AP242 版本声明/守卫 | 20分 | **低** |

```
保真度与外部标准一致性得分 = sum(各检查项得分)

# 递进扣分（WP-3 阶段 1/2 用户确认）：基础层任一 < 60 时，增强层折半
if 子维度 2.1（外部内核访问防腐）< 60 或 子维度 2.3（数据交换防腐）< 60:
    得分 = int(得分 * 0.5)
```

**递进扣分说明**：保真度与外部标准一致性（2.4）为**增强层**，其价值（round-trip/单位/公差/版本）依赖基础层防腐蚀成立。当任一基础层 < 60（外部依赖未隔离或数据交换未防腐）时，2.4 得分折半——对齐设计依据 §2.1 层级主张。两基础层取**更严格**的折半（任一 < 60 即折半）。

**置信度说明**：
- round-trip 测试存在性可精确检测（符号 + 断言模式），置信度为**高**。
- 单位/公差换算魔法因子为启发式，置信度为**低**。
- 版本守卫检测宏/声明存在性，但"守卫是否覆盖各版本差异"无法静态判定，置信度为**低**。

**对应行业实践**：
- OCCT 自带的测试套件（`TKDETEST`）包含 STEP round-trip 验证
- 商业 CAD 平台对 STEP 导出做 AP242 版本声明并配往返校验

**代码坏味道：语义失真（Semantic Loss）**

- **描述**：数据交换无往返保真度校验、单位/公差换算散落、标准版本未声明守卫。
- **典型表现**：导出→导入后面尺寸漂移；`double* coords` 乘 `25.4` 散落 5 处；无任何 AP 版本声明。
- **危害**：跨系统数据交付损坏，追责无据。

**算例**：
- 正例：`round_trip_test()` 断言写回读出一致；单位统一 `unit::convert()`；导出标注 `AP242`
- 负例：无 round-trip 测试，`coords[i]*25.4` 散落多处，无版本守卫

## 三、综合分

```
综合分 = Σ(子维度得分 × 子维度权重)
       = 2.1×30% + 2.2×15% + 2.3×30% + 2.4×25%
```

> 注：2.4 得分已含递进扣分（2.1 或 2.3 < 60 时折半，见 §2.4）。评分区间为 0-100。

## 五、内置规则

### 规则清单总览

| 规则 | 名称 | severity | output_level | 置信度 | 所属子维度 |

### 规则详细描述

#### ACL-001：直连内核 API

- **严重级别**：HIGH
- **检测置信度**：高
- **描述**：检测业务代码在 wrapper 目录白名单**之外**直接引用外部内核头文件/API 符号（`TopoDS_*`/`BRep*`/`Handle_*`）。
- **检测逻辑**：
  1. 识别 wrapper 目录白名单（项目配置）
  2. 扫描内核符号清单在**白名单外**的引用 → 触发 ERROR
  3. wrapper 目录内引用不触发（该目录是防腐边界的合法位置）
- **边界说明**（专家校对 P1-1 修订）：与 ACL-007/012 的信号归属划分——**内核符号**（`TopoDS_*`/`BRep*`/`Handle_*`）只归 ACL-001；**格式符号**（`STEPControl_*`/`IGESControl_*`/IFC）只归 ACL-007/012。两清单互斥，同一符号引用不会重复触发 ACL-001 与 ACL-007。与 ④ GCS-012（数据访问封装）区分——GCS-012 管内核/数据结构内部成员访问，ACL-001 管外部内核 API 访问形态（是否绕过 wrapper）。
- **置信度说明**：白名单 + 符号清单精确匹配，但白名单需项目配置正确，置信度为**高**。
- **建议修复**：业务层依赖统一 wrapper 接口，内核调用收敛到防腐边界内。

#### ACL-002：核心 API wrapper 覆盖度

- **严重级别**：LOW
- **检测置信度**：低
- **描述**：检测外部内核核心 API 类是否在 wrapper 中有对应声明（覆盖度启发式）。
- **检测逻辑**：
  1. 外部内核核心类清单（人工维护）vs wrapper 头文件声明引用比对
  2. 覆盖度 < 阈值 → 触发（INFO）
- **置信度说明**：核心 API 清单需要人工维护，比对为启发式，置信度为**低**。
- **建议修复**：将核心内核 API 全部收敛到 wrapper，避免业务层为冷门 API 直连。

#### ACL-003：内核版本守卫

- **严重级别**：LOW
- **检测置信度**：低
- **描述**：检测是否存在 `#if OCC_VERSION` 类版本守卫把内核升级影响隔离。
- **检测逻辑**：
  1. 检测 `OCC_VERSION`/`VERSION` 条件编译宏引用存在性
  2. 守卫密度过低（跨多版本演进但仅 1 处守卫）→ 触发（INFO）
- **置信度说明**：宏存在性可检测，但"守卫覆盖全部版本差异点"无法静态判定，置信度为**低**。
- **建议修复**：将内核版本差异统一用 `#if OCC_VERSION` 块隔离在 wrapper 内维护。

#### ACL-004：内核类型泄漏

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检测外部内核类型（`TopoDS_Shape`/`Handle_*`）出现在 wrapper**公开**头文件签名中。
- **检测逻辑**：
  1. 解析 wrapper 头文件 public 类/函数签名
  2. 签名中出现外部内核类型 → 触发 WARNING
  3. wrapper **内部实现**中出现的类型不触发（正常）
- **置信度说明**：需解析声明可见性，依赖 header 结构，置信度为**中**。
- **建议修复**：wrapper 公开接口用自有值类型/映射类型，内部再转换到内核类型。

#### ACL-005：错误处理封装

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检测外部内核调用点的失败处理是否被封装层正确捕获（区分异常型/状态码型内核）。
- **检测逻辑**：
  1. 识别内核调用点（`BRep*`/`TopoDS_*`/求解器 API）
  2. 异常型内核：无 try/catch → 触发
  3. 状态码型内核：无错误码检查（`IsDone()`/错误返回码）→ 触发
  4. **格式读写调用点（`STEPControl_Reader/Writer` 等）明确排除**，归 ACL-011（专家校对 P1-2 修订），不重复触发
- **置信度说明**：需区分内核失败形态与检查模式，跨函数传递无法追踪，置信度为**中**。
- **建议修复**：在 wrapper 内统一捕获内核失败并转换为业务异常/错误码，业务层不感知内核失败语义。

#### ACL-006：数据交换往返保真度测试存在性（加分项）

- **严重级别**：LOW（非违规扣分规则）
- **检测置信度**：高
- **描述**：检测项目是否包含数据交换 round-trip（写出→读回→比较）保真度测试。
- **检测逻辑**：
  1. 扫描往返测试符号（`round_trip`/`write+read` 比对断言/导出导入对比测试）
  2. 存在 → 加分；缺失 → INFO 提示"缺少数据交换往返保真度测试"
- **置信度说明**：存在性可静态判定（符号 + 断言模式），但"测试是否覆盖全部数据类型"无法确认，置信度为**高**。
- **建议修复**：为核心数据交换路径补充 round-trip 保真度测试。

#### ACL-007：STEP/IGES/IFC 读写防腐

- **严重级别**：HIGH
- **检测置信度**：高
- **描述**：检测外部标准读写符号（`STEPControl_*`/`IGESControl_*`/IFC）是否出现在专用 import/export 模块**之外**。
- **检测逻辑**：
  1. 识别 import/export 模块白名单（项目配置）
  2. 格式符号在**白名单外**引用 → 触发 ERROR
  3. 与 ACL-012（格式直连，引用密度）区分：ACL-007 管**读写封装形态**（符号位置，ERROR），ACL-012 管**直连引用计数**（密度，WARNING）
- **边界说明**（专家校对 P1-1 修订）：ACL-012 仅在**已由 ACL-007 判定为散落**的场景下叠加密度计数；格式符号在业务模块出现时以 ACL-007 为主判定（ERROR），ACL-012 仅提示散落规模，避免同一散落既扣 ERROR 又扣 WARNING 的重复惩罚。
- **置信度说明**：import/export 白名单 + 符号定位精确可判，但白名单需配置正确，置信度为**高**。
- **建议修复**：所有格式读写收敛到集中 import/export 模块，业务层经统一接口交换数据。

#### ACL-008：单位换算魔法因子

- **严重级别**：LOW
- **检测置信度**：低
- **描述**：检测数据交换上下文的单位换算魔法因子（25.4/0.0254/3.28084 等）。
- **检测逻辑**：
  1. 扫描数据交换文件中的换算魔法因子
  2. 未调用统一换算工具函数 → 触发（INFO）
- **边界裁决**：数据交换场景单位换算归 ACL-008；内核操作场景归 GCS-006（④）；**不重复计分**。
- **置信度说明**：魔法因子为启发式，低置信度。
- **建议修复**：单位换算集中为统一工具函数（如 `unit::convert()`）。

#### ACL-009：公差换算魔法因子

- **严重级别**：LOW
- **检测置信度**：低
- **描述**：检测数据交换上下文公差换算魔法因子。
- **检测逻辑**：
  1. 扫描公差换算魔法因子
  2. 未集中管理 → 触发（INFO）
- **置信度说明**：启发式，低置信度。
- **建议修复**：公差换算与单位换算统一集中管理。

#### ACL-010：标准版本守卫

- **严重级别**：LOW
- **检测置信度**：低
- **描述**：检测外部标准版本（AP203/AP214/AP242）是否被声明与守卫。
- **检测逻辑**：
  1. 检测 AP 版本声明/守卫存在性
  2. 无声明或未区分版本 → 触发（INFO）
- **置信度说明**：存在性可检测，但"守卫覆盖各版本语义差异"无法静态判定，置信度为**低**。
- **建议修复**：数据交换模块显式声明支持的标准版本并加守卫。

#### ACL-011：导入导出错误处理

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检测 reader/writer 调用点是否有错误处理。
- **检测逻辑**：
  1. 识别格式读写符号调用点（`STEPControl_Reader.ReadFile`/`IGESControl_*` 等）
  2. 调用点后无错误码检查（`IFSelect_ReturnStatus`/异常）→ 触发 WARNING
- **边界说明**（专家校对 P1-2 修订）：格式读写调用点的错误处理**只归 ACL-011**；ACL-005 明确排除此类调用点，两者不重复触发。
- **置信度说明**：依赖调用点上下文，需区分内部解包与业务错误，置信度为**中**。
- **建议修复**：每次读写后检查 `IFSelect_ReturnStatus`/异常并统一处理。

#### ACL-012：格式直连检测

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检测格式符号在专用模块外的**直接引用密度**（与 ACL-007 区分：007=读写封装形态，012=直连引用计数）。
- **检测逻辑**：
  1. 统计格式符号在 import/export 模块白名单外的引用密度
  2. 密度 > 阈值（WP-4 校准）→ 触发 WARNING
- **置信度说明**：引用密度统计，阈值需校准，置信度为**中**。
- **建议修复**：消除专用模块外的格式符号直连，收敛到统一接口。

### 7.1 外部符号清单（专家校对 P1-3 修订，WP-4 单一事实来源）

检测信号集中于下表，作为 WP-4 检测正则与白名单的**唯一事实来源**。两清单**互斥**（对齐 ACL-001 与 ACL-007 边界）：

| 清单 | 符号 | 归属规则 | 白名单 |
|:-----|:-----|:---------|:-------|
| **内核符号集** | `TopoDS_*`、`BRep*`、`Handle_*`、`CGAL` | 仅 ACL-001（直连）/004（类型泄漏）/005（错误处理）| wrapper 目录 |

- ACL-001/006/007：高置信度，精确符号匹配 + 白名单 + 存在性检测
- ACL-004/005/011/012：中置信度，调用点上下文 + 错误处理检查 + 引用密度统计

### 7.3 门禁设置

### 7.4 置信度使用指南

- 高置信度（ACL-001/006/007）可直接门禁

## 九、豁免注解体系

### 9.1 为什么需要豁免

12 条 ACL 规则均以"项目通过防腐层消费外部内核/数据交换标准"为前提。实际工程中存在两类该前提不成立的场景：

1. **被评估对象本身即外部内核/封装修复层**（vendored 内核源码、第三方 SDK 目录）——内核自身实现必然存在直接 API 调用、类型透出，不应按防腐缺陷扣分
2. **已认证的第三方封装/数据交换模块**（独立组件、无法改动）——其接入形态已固化，豁免避免误报

### 9.2 防腐边界目录排除（引擎内建）

| 项 | 内容 |
|:---|:-----|
| 匹配目录 | wrapper/封装层目录、import/export 模块目录（项目配置声明）|
| 作用域 | 全部 ACL 规则中涉及"白名单外直连/散落"的判定（ACL-001/007/012）|
| 目的 | 把默认防腐边界（wrapper/import-export）设为引擎内建，业务侧非法位置一目了然 |

> 与 GCS §9.2（内核目录排除）口径统一：路径级排除只针对防腐边界自身实现，不掩盖业务层问题。

### 9.3 注解类型

| 注解 | 用途 | 格式 | 作用域 |
|:-----|:-----|:-----|:-------|
| `@acl_exempt` | 文件级防腐排除（vendored 内核/第三方 SDK）| 文件头 `/* @acl_exempt: reason */` | **全部 12 条规则** |
| `@acl_waiver` | 声明受控的直连/散落（性能或历史债务）| 行尾 `// @acl_waiver: reason` | **仅指定规则**（默认 ACL-001/012）|

### 9.4 与其它引擎豁免语义的差异（必读）

GCS 的两个注解均影响 scoring（缩小统计范围）。**ACL 同之**：

| 注解 | 为何必须影响 scoring |
|:-----|:-------------------|
| `@acl_exempt` | 语义即"把该文件移出防腐评估集"（vendored 内核实为内核自身），无法用降级表达 |
| `@acl_waiver` | 默认已 INFO/受控，单纯降级无效果；真实痛点是受控直连/散落使计数超阈值、拿不到对应分 |

### 9.5 验证规则

- **reason 必填**：缺 reason 的注解**无效**（`/* @acl_exempt */`、`// @acl_waiver` 不生效），在 `waiver_audit.invalid_waivers` 留痕告警
- 作用域为**同文件**，不跨文件传播
- 注解须写在注释中（`/* */` 或 `//`）；引擎在剥离注释**之前**采集注解
- 目录级与注解级为 **OR** 关系，任一命中即排除

### 9.6 反滥用守卫

`@acl_exempt` 可将文件移出防腐统计，滥用会退化为空评估。守卫与 GCS 一致：

| 守卫项 | 阈值 | 行为 |
|:-------|:-----|:-----|
| `@acl_exempt` 排除占比 | **> 30%** | 输出 `waiver_audit.abuse_warning` 告警，提示 12 规则覆盖度可能失真 |
| 防腐边界目录覆盖占比 | **> 30%** | 类 GCS 过度排除守卫：项目整体被声明为 wrapper/import-export，防腐评估失真 |

审计输出（`all_metrics().waiver_audit`）：`acl_exempt`/`acl_waiver`/`boundary_dir_exclusion`（count/ratio/scope/files）、`invalid_waivers`、`abuse_limit`、`abuse_warning`。

### 9.7 门禁关系

§7.2 的门禁分级**不因豁免而放宽**：`@acl_exempt` 排除的文件不产生违规，自然不触发门禁；`@acl_waiver` 影响指定规则（默认 ACL-001/012 INFO/WARNING 级，本不阻断）。不存在通过豁免绕过 ERROR 级规则（ACL-001/007）的路径——除非滥用 `@acl_exempt`，该行为由 9.6 的 30% 上限告警暴露。
