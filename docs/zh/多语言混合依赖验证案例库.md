# 多语言混合依赖评估指南·验证案例库

> 本案例库为《多语言混合依赖评估指南》的配套基准测试集，针对6个核心子维度及12条内置规则，提供真实开源工业软件中的正例（架构良好，不应报错）与反例（存在架构债务，应触发警告）。每个案例均包含**代码片段/问题描述**、**检测方法**和**预期工具输出**，可用于验证评估工具的敏感度与抗噪能力。

## 1. 跨语言调用强度（热耦合）

### 1.1 反例：OpenFOAM `fvMatrix` 被大量Python绑定调用

- **项目**：OpenFOAM（通过 `swak4Foam` 或 `foam-extend` 的Python绑定）
- **问题描述**：`fvMatrix` 是有限体积法核心类，通过多个独立的Python工作台（如 `pyFoam`、`swak4Foam`）被数百个脚本直接调用。每个脚本在循环中频繁调用 `fvMatrix.solve()`，导致C++侧与Python侧形成**热耦合**。
- **代码片段**（概念）：
  ```python
  # pyFoam 脚本中典型循环
  for t in range(1000):
      fvMatrix = solver.fvMatrix()
      fvMatrix.solve()   # 跨语言调用
  ```
- **检测方法**：静态分析计算每个C++函数的**入向跨语言调用边**。`fvMatrix.solve()` 的入边数 > 50，触发MLR-006。
- **预期工具输出**：
  ```
  [MLR-006] 热耦合模块 (MEDIUM)
  模块: src/finiteVolume/fvMatrix/fvMatrix.C::solve()
  跨语言调用强度: L=87 (入边85，出边2)
  建议: 将Python中的循环移至C++侧，提供批量求解接口。
  ```

### 1.2 正例：Gmsh C++ 几何内核仅通过统一API暴露给Python

- **项目**：Gmsh
- **优势描述**：Gmsh的C++几何内核仅通过一个**薄API层**（约50个函数）暴露给Python，且每个Python函数对应唯一的C++实现。没有“直通”内部私有方法，跨语言调用强度L均 ≤ 3。
- **代码片段**（概念）：
  ```cpp
  // 唯一暴露的API函数
  int gmshModelAddPoint(double x, double y, double z) {
      return gmsh::model::addPoint(x, y, z);
  }
  ```
- **检测方法**：统计每个C++符号的跨语言入边数，最大值为3。
- **预期工具输出**：无MLR-006警告。

## 2. 跨语言影响半径（炸药模块）

### 2.1 反例：BRL-CAD `rt_bot` 几何基元

- **项目**：BRL-CAD
- **问题描述**：`rt_bot`（几何体素）是核心几何基元之一。修改其内部数据结构（如 `struct rt_bot_internal` 增加字段）会通过Tcl脚本、C命令处理器和至少15个C++工具影响超过120个文件。历史上任何改动都需要同步更新数十个模块。
- **影响半径计算**：依赖图中从 `rt_bot` 出发，沿跨语言边（Tcl→C→C++）可达节点数 R = 135。
- **检测方法**：BFS遍历依赖图（深度≤5），统计受影响模块数。
- **预期工具输出**：
  ```
  [MLR-007] 炸药模块 (MEDIUM)
  模块: src/librt/primitives/bot/bot.c
  影响半径: R=135 (>10)
  建议: 将rt_bot拆分为抽象接口层，使用工厂模式隔离具体实现。
  ```

### 2.2 正例：Gmsh 模型容器 `gmsh::model`

- **项目**：Gmsh
- **优势描述**：`gmsh::model` 类是模型的顶层容器，其公共接口仅包含 `addPoint`、`addLine` 等约15个稳定方法。修改内部数据结构（如 `model::_points` 存储方式）时，受影响模块仅限于 `model` 类内部和自动生成的API绑定代码，影响半径 R=3～5。
- **检测方法**：计算影响半径 R=3（仅内部函数和绑定生成器）。
- **预期工具输出**：无MLR-007警告。

## 3. 跨语言调用深度（回调地狱）

### 3.1 反例：FreeCAD FEM工作台回调链

- **项目**：FreeCAD
- **问题描述**：FEM工作台中，Python脚本调用C++ `Fem::Solver`，该求解器再回调Python材料定义函数 `material_callback`，后者又调用C++ `Part::Feature` 获取几何，形成深度3的跨语言链：`Py → C++ → Py → C++`。
- **代码片段**（概念）：
  ```python
  # fem.py
  def run_simulation():
      solver = FemSolver()
      solver.setMaterialCallback(material_callback)  # 注册回调
      solver.solve()  # C++内部会调用 material_callback
  def material_callback():
      part = Part.getShape()  # 再次进入C++
  ```
- **检测方法**：提取连续跨语言调用链，计算最大深度。
- **预期工具输出**：
  ```
  [MLR-005] 跨语言调用深度过大 (MEDIUM)
  链: Fem.py::run_simulation() [Py] → FemSolver::solve() [C++] → material_callback() [Py] → Part::getShape() [C++]
  深度: 3 (≥3)
  建议: 将material_callback实现移到C++端，或改用异步消息队列。
  ```

### 3.2 正例：Gmsh 单层API调用

- **项目**：Gmsh
- **优势描述**：所有Python API调用都是**单层**的：`gmsh.model.addPoint(1,2,3)` 直接调用对应的C++函数，无回调反向。最大跨语言深度 = 1。
- **预期工具输出**：无MLR-005警告。

## 4. 绑定层契约一致性（绑定漂移）

### 4.1 反例：KiCad 7.0 Python API 破坏（见上文案例1）

- **项目**：KiCad
- **问题描述**：`CONNECTIVITY_DATA.GetNetItems` 从接受列表改为不接受列表，导致Python代码崩溃。
- **检测方法**：对比KiCad 6.0和7.0的API签名（通过解析 `.i` 文件或pybind11注册代码），发现签名不匹配。
- **预期工具输出**：
  ```
  [MLR-003] 绑定层签名不匹配 (HIGH)
  函数: CONNECTIVITY_DATA::GetNetItems
  原生签名: (int, const std::vector<int>&)
  绑定签名: (int, const std::initializer_list<int>&)
  差异: 参数2类型从vector变为initializer_list，Python列表不再可接受
  建议: 添加转换适配器，保持类型兼容；或使用py::arg 进行自动转换。
  ```

### 4.2 正例：Gmsh 自动生成API

- **项目**：Gmsh
- **优势描述**：Gmsh的C++/Python/Julia API均从 `gmsh/api/gmsh_api.api` 自动生成。修改原生接口时，构建系统强制重新生成绑定，确保签名100%匹配。
- **检测方法**：检查是否有统一的API描述文件及代码生成规则。
- **预期工具输出**：无MLR-002/003警告。

## 5. 脚本?引擎边界清晰度（越狱脚本）

### 5.1 反例：BRL-CAD Tcl 直接访问C全局变量

- **项目**：BRL-CAD
- **问题描述**：数千个Tcl脚本通过 `::bu::` 命名空间直接访问C全局变量（如 `::bu::argv0`），而非通过API函数。
- **代码片段**（实际）：
  ```tcl
  # mged.tcl 中典型违规
  set mode $::bu::global_debug_mode
  bu::set_debug 1   # 这是封装API，合规
  ::bu::log_file $::bu::log_name   # 直接访问内部变量，违规
  ```
- **检测方法**：正则匹配 `::[a-z_]+::[a-z_]+` 模式，且该符号不在预定义白名单API列表中。
- **预期工具输出**：
  ```
  [MLR-004] 脚本层直接访问引擎内部 (HIGH)
  文件: src/tclscripts/mged.tcl:245
  违规: 直接访问 ::bu::log_name
  建议: 改用 bu::get_log_name() API。
  ```

### 5.2 正例：FreeCAD Python工作台仅通过官方API

- **项目**：FreeCAD
- **优势描述**：FreeCAD的Python工作台（Workbench）均通过 `FreeCAD` 模块（如 `FreeCAD.ActiveDocument`）访问C++对象，没有直接引用 `_Internal` 或 `cpp_ptr` 等内部结构。
- **检测方法**：扫描Python文件，检查是否存在 `from FreeCAD import _Internal` 或直接访问 `cpp_ptr` 属性。
- **预期工具输出**：无MLR-004警告。

## 6. 跨语言循环依赖（多语言面条依赖）

### 6.1 反例：ElmerFEM 热-电流双向耦合（应被标注为“合理循环”）

- **项目**：ElmerFEM
- **问题描述**：`HeatSolve` 与 `StatCurrentSolve` 在求解器中相互调用，形成静态循环依赖。但这是多物理场耦合的需求，属于合理设计。
- **检测方法**：强连通分量检测会发现 `HeatSolve → StatCurrentSolve → HeatSolve` 环。
- **预期工具输出**（若未加领域标注）：
  ```
  [MLR-001] 跨语言循环依赖 (HIGH)
  循环: HeatSolve (Fortran) → StatCurrentSolve (Fortran) → HeatSolve
  但这是多物理场耦合所需，请通过 @allowed_coupling 标注豁免。
  ```
- **正确处理**：工具应支持注解 `// @allowed_coupling thermal_electric`，将此类循环降级为INFO级别。

### 6.2 正例：Gmsh 无循环依赖

- **项目**：Gmsh
- **优势描述**：Gmsh的模块依赖是严格分层的（Geometry → Mesh → Solver → PostProcessing），无任何循环依赖（包括同语言和跨语言）。
- **检测方法**：依赖图中SCC数量为0。
- **预期工具输出**：无MLR-001警告。

## 7. 补充规则案例

### 7.1 MLR-008（跨语言回调死锁风险）

- **反例**：FreeCAD 早期版本中，C++线程回调Python时未释放GIL，导致死锁（已修复）。
- **检测方法**：识别模式 `Python → C++ (持有GIL) → Python callback`，并检查C++回调点前是否有 `py::gil_scoped_release`。
- **预期工具输出**：
  ```
  [MLR-008] 跨语言回调死锁风险 (HIGH)
  位置: src/Mod/Fem/FemSolver.cpp:256
  调用链: PyFemSolver.solve() → FemSolver::run() → Py::callback()
  风险: 回调时仍持有GIL，若回调函数再调用C++锁可能死锁。
  建议: 在调用 callback 前插入 py::gil_scoped_release release;。
  ```

### 7.2 MLR-010（FFI内存所有权模糊）

- **反例**：CalculiX 中C代码 `malloc` 数组传递给Fortran子例程，Fortran内 `DEALLOCATE`。
- **检测方法**：静态分析标记跨语言传递的指针，检查分配和释放是否在同一语言域。
- **预期工具输出**：
  ```
  [MLR-010] FFI内存所有权模糊 (HIGH)
  分配: calc.c:123  malloc()
  释放: solver.f90:456 DEALLOCATE
  风险: 跨语言释放导致堆损坏。
  建议: 遵循“谁分配谁释放”原则，或在C侧提供释放函数。
  ```

### 7.3 MLR-012（未使用ISO_C_BINDING的Fortran接口）

- **反例**：Code_Aster 中大量Fortran子例程没有 `bind(c)` 属性。
- **检测方法**：扫描 `.f90` 文件，查找 `subroutine` 且无 `use, intrinsic :: iso_c_binding`。
- **预期工具输出**：
  ```
  [MLR-012] 未使用 ISO_C_BINDING 的 Fortran 接口 (MEDIUM)
  文件: src/aster_f_modules/utilitai.f90:150
  子例程: calcep
  建议: 添加 bind(c, name="calcep") 并明确参数类型。
  ```
