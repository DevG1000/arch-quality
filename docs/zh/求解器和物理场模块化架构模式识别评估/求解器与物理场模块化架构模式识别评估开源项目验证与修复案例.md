## 摘要

依据架构质量评估技能开发指南的验证流程，在九个开源工业仿真软件上验证评估工具，发现多类误报与漏报，核心是求解器可替换性漏报。目标是定位并修复检测偏差，确认正确判定与已知边界。最终修复九项误报漏报、确认一项正确判定、记录三项已知边界，九十二项测试全通过、九个项目回归二十八项通过、三方一致性六项全过。

## 1. 问题描述

### 1.1 背景

评估工具用纯静态分析（正则匹配 + 依赖图分析）识别工业仿真软件中求解器与物理场的模块化架构模式，输出 4 个子维度评分（边界清晰度 25%、耦合架构 30%、插件扩展 25%、数据交换 20%）与 12 条 MPR 规则告警。

开发指南的 A3.5 质量门禁要求工具先在真实开源工业仿真软件上过一遍（B3.5 开源项目验证），让检测逻辑既别过度告警（误报）也别漏掉真问题（漏报）。

### 1.2 验证对象

按开发指南 B3.5 要求选了 9 个开源工业仿真软件做验证。其中 5 个是验证案例集指定的 A 类项目（MOOSE/OpenFOAM/SU2/preCICE/deal.II 按指定版本验证），4 个是本地补充的（Kratos/MFEM/ElmerFEM/FreeFEM，凑齐 C++/Fortran/Python 语言体系和不同架构风格）：

| 项目 | 版本 | 语言 | 架构特征 | 类别 | 案例集指定 MPR |
|:-----|:-----|:-----|:---------|:-----|:--------------|
| MOOSE | master | C++ | 多应用插件框架、MultiApp 耦合 | A 类 | MPR-004/005/006 |
| OpenFOAM | v2512 | C++ | 场数据类库、多求解器 | A 类 | MPR-004/010 |
| SU2 | v7.5 | C++ | 多物理场求解器族、FSI | A 类 | MPR-004 |
| preCICE | v3.0 | C++ | 通用耦合库、分区耦合 | A 类 | MPR-006/010 |

### 1.4 核心案例现象（SU2）

SU2 评估结果中，耦合架构维度子项 `solver_replaceability`（求解器可替换性，15 分）得 **0 分**，两个判定均为 false：

```
solver_replaceability: {
  "score": 0,
  "has_abstract_solver": false,
  "has_virtual_solve": false
}
```

但人工核查时发现，SU2 的抽象求解器架构其实很标准：

- `SU2_CFD/include/solvers/CSolver.hpp`：类声明 `class CSolver {`，含 **864 个 virtual 关键字、14 个纯虚函数**（`= 0`）
- 求解管线虚方法：`Preprocessing`、`Postprocessing`、`SetTime_Step`、`Centered_Residual`、`Upwind_Residual`、`coefficient` 等
- 派生求解器族：CEulerSolver、CAdjNSSolver、CFEASolver、CFEM_DG_EulerSolver 等（6 个直接继承 CSolver 的类，经 CFVMFlowSolverBase/CFEASolverBase 等中间基类再派生具体求解器）
- 迭代器抽象：`CIteration` 含 `virtual void Solve(...)`

**矛盾就在这里**：一个抽象求解器接口完备的项目，被工具判成"无虚拟求解接口"。

## 2. 分析过程

### 2.1 理论分析：模式识别工具的三类失败模式

跑完 B3.5 多项目验证，把静态模式识别工具的失败模式归成三类：

| 失败模式 | 定义 | 本质 |
|:---------|:-----|:-----|
| **命名差异** | 工具正则固化某命名（如 `solve`），真实框架用其他命名（如 `Solve`、`Preprocessing`） | 大小写/命名空间差异 |
| **语言体系差异** | 工具面向 C++，Fortran/CUDA/DSL 等语言机制无法识别 | 语言盲区 |
| **语义误判** | 正则命中表面关键词，但语义不符（自然语言、接口文档、第三方目录） | 正则过宽/上下文缺失 |

### 2.2 实验过程：LLM 漏报探查三步法

对 SU2 漏报按三步探查：

**第一步——提出候选模式**（靠 LLM 领域知识）：
SU2 由 SU2code 基金会维护，是多物理场 CFD/FSI 求解器。大致结构是：
- `CSolver` 基类 + 派生求解器族（Euler/NS/FEA/Heat/DiscAdj）
- `CIteration` 迭代器 + `CIntegration` 集成器
- 虚方法可能叫 `Preprocess`/`Iterate`/`Solve`/`Update`

**第二步——本地实测归因**（认证据，不认假设）：

| 候选 | 实测 | 结果 |
|:-----|:-----|:-----|
| 小写 `solve(` | 正则检索 `CSolver.hpp`：0 次 | 排除 |
| 大写 `Solve(` | `CIteration.hpp`：`virtual void Solve(` 1 次 | **命中** |
| 纯虚函数 `= 0` | `CSolver.hpp`：14 个，但无 `solve` 命名 | 部分命中 |
| 求解管线虚方法 | `Preprocessing`/`SetTime_Step`/`Upwind_Residual` 等 | 补充证据 |

**第三步——根因定位**（看工具代码）：

```
修复前 VIRTUAL_SOLVE_PATTERN = \bvirtual\b.*\bsolve\s*\(
```

两个缺陷：
1. `\bsolve\b` **大小写敏感**——`Solve`（大写）配不上小写 `solve`；
2. `.*` 没有边界——会跨方法误匹配：比如 MFEM 里 `virtual void GetInverseMatrix() { Factors::solve(); }` 的 `solve` 调用会被当成虚拟求解接口。

### 2.3 实验验证：修复方案的影响评估

定精确模式之前，先算了下各候选方案对 9 个基线的影响：

| 方案 | 模式 | SU2 | Kratos | MFEM | 结论 |
|:-----|:-----|:---:|:------:|:----:|:-----|
| 现状 | `\bvirtual\b.*\bsolve\s*\(` | ✗ | ✗ | ✗ | 全部漏报 |
| 方案 A | 加 `re.IGNORECASE` | ✓ | ✓ | ✓(误) | MFEM 误命中（GetInverseMatrix）|
| 方案 B | `\bvirtual\b[^;(]*?[sS]olve\s*\(` | ✓ | ✓ | ✓ | 全部正确 |

方案 B 用 `[^;(]` 把方法结束符 `;` 和参数列表 `(` 都挡在外面，匹配被限在**同一声明内**：
- SU2：`virtual void Solve(` ✅
- Kratos `LinearSolver`：`virtual bool Solve(` / `virtual void Solve(` ✅
- MFEM `Factors`：`virtual void Solve(int m, int n, real_t *X)` ✅（是真求解方法，不是误报）
- 跨方法误匹配也没了（MFEM `GetInverseMatrix` 里的 `solve` 调用不再命中）

### 2.4 仿真验证：全套测试回归

修复后跑全量验证：
- 单元/集成/E2E/变异测试：**92 passed**
- 9 项目回归：**28 passed + 3 skipped**
- 三方一致性：**PASS 6/6**

SU2 评分变化：耦合架构 60→70，综合 61.0→64.0，`has_virtual_solve` 从 false 变 true，MPR-004 正确触发。

## 3. 解决措施

### 3.1 分类处置策略

| 处置 | 数量 | 措施 | 依据 |
|:-----|:----:|:-----|:-----|
| **修复工具** | 9 | 修正正则、补检测逻辑、扩展命名列表 | 实测确认工具缺陷 |
| **确认正确判定** | 1 | Kratos FMI 0 分保留 | CoSimIO 非 FMI 标准，符合指南 |
| **记录已知边界** | 3 | preCICE/FreeFEM/OpenFOAM 记录待开发 | 设计层面的语义局限 |

### 3.2 具体修复方案

#### 修复 1：SU2 大写 Solve 漏报（核心案例）

**问题代码**（`arch_metrics_solver_physics.py:70`）：

```python
VIRTUAL_SOLVE_PATTERN = re.compile(r'\bvirtual\b.*\bsolve\s*\(', re.MULTILINE)
```

**修复代码**：

```python
# B3.5 SU2 漏报探查修复：SU2 CIteration 用大写 Solve()，
# 原 \bsolve\b 大小写敏感且 .* 跨方法误匹配/漏匹配。
# 精确模式限定同一声明（[^;(] 排除方法结束 ; 与参数列表 (），兼容 Solve/solve。
VIRTUAL_SOLVE_PATTERN = re.compile(r'\bvirtual\b[^;(]*?[sS]olve\s*\(', re.MULTILINE)
```

**新增单元测试**（防以后改坏）：
- `test_virtual_solve_uppercase_detection`：验证大写 `Solve()` 能被认出来
- `test_virtual_solve_same_declaration_only`：验证跨方法误匹配被排除

#### 修复 2~9：其余误报/漏报（概要）

> 表格编号与 1.3 节现象表编号一一对应（编号 n 对应现象 #n，其中 #1 与 #2 同批次修复）：

| # | 修复 | 方案 |
|:-:|:-----|:-----|
| 1 | MOOSE Makefile 误报 | 修复构建配置扫描逻辑 |
| 2 | MPR-004 正则误报 5 处 | 收紧 `fixed.point`/`file.*based`/`MPI`/`one.way` 正则，要求明确耦合语义 |
| 3 | 抽样计数失真 | 增加 `_sample_ratio` + `_sum_matches_extrapolated` 计数外推；结构检测走全量、布尔检测天然稳健 |
| 4 | 耦合收敛混淆 | 收敛关键词须与耦合上下文同现（文件级）；`residualControl` → 耦合收敛；单求解器内部 → 部分分 5 |
| 5 | 第三方循环误报 | 增加 `THIRD_PARTY_DIR_NAMES` + `_is_project_file`/`_is_project_abs_path` |
| 6 | Fortran 插件盲区 | 新增 `_detect_fortran_plugin`（GetProcAddr，≥3 文件或双特征）|
| 7 | 统一接口基类漏报 | 扩展 `INTERFACE_BASE_CLASSES`：MooseObject/KratosApplication/Process |
| 8 | Kratos 第三方误报 | format_conversion 纳入第三方目录排除 |

### 3.3 正确判定保留（Kratos FMI）

探查 Kratos `has_fmi_co_sim=false`（FMI 协同仿真 0 分）时发现：
- CoSimulationApplication 含 `co_sim_io.hpp`（`Connect`/`Disconnect`/`Hello`）——**CoSimIO 自定义接口**
- 标准 FMI 函数（`fmi2DoStep`/`modelDescription.xml`）零命中

**判定**：指南 §2.4 要求的是"运行时是否支持 **FMI 协同仿真标准**进行数据交换"，CoSimIO 是自定义协同仿真接口，**不是 FMI 标准** → `false` 是正确判定。保留，不把它固化成 FMI 的等价物（这和 Fortran 语言盲区不是一回事——那是工具正则真漏检，这是接口类型本来就不同、工具判得对）。

### 3.4 已知边界记录

| 边界 | 原因 | 后续计划 |
|:-----|:-----|:---------|
| preCICE MPR-004 架构误判 | 通用耦合库多模式（explicit 18 vs iterative 4 命中均属接口文档），单一架构判定不适用；多数投票反而更误判 | 多模式语义处理（待评估）|

## 4. 启示与推广

### 4.1 方法论价值：LLM 漏报探查机制

这次验证最有价值的产出，是把 **LLM 漏报探查三步法**跑通了：

```
触发点发现 → LLM 候选模式提出 → 本地实测归因 → 命中则修复 / 未命中则放弃
```

这套流程之所以好用：
1. **认证据**：LLM 领域知识只当**假设**，不当**结论**，判定要落到仓库文档或本地实测上（`co_sim_io.hpp` 内容、`CIteration.hpp` 的 `Solve(`、`SerialCouplingScheme.hpp` 的 "staggered execution" 注释）
2. **按类处置**：命名差异→扩命名列表；语言体系差异→新增检测；工具误报→修正则；正确判定→保留并记下理由
3. **不过度修**：对"非漏报"（Kratos FMI）明确保留，不因为"看着像问题"就硬固化一个错误等价

### 4.2 通用性推广

这套探查方法还能挪到**其他维度评估工具**（多语言混合依赖、模板元编程、数值精度）的 B3.5 验证里用：
- 多语言项目（Python/C++/Fortran 混合）的命名与语言体系差异
- 同名的"标准接口"（FMI）和"自定义等价接口"（CoSimIO）怎么划边界
- 构建系统（CMake/Makefile/SCons）与目录命名策略的差异

### 4.3 工具落地价值

- **验证案例集 A 类项目全部覆盖**：5 个指定 A 类项目（MOOSE/OpenFOAM/SU2/preCICE/deal.II）按指定版本（含 Git 标签）建立回归基线
- **9 项目基线 + 回归护栏**：评分偏移容忍（综合 ±2.0 / 维度 ±5.0），防止后续工具改动引入回归
- **测试金字塔完整**：51 单元 + 6 抽样 + 11 集成 + 14 E2E + 10 变异 + 28 回归 + 6 一致性

## 5. 结论

B3.5 开源项目验证在 9 个真实工业仿真软件上发现并修复了 9 项误报/漏报。核心案例是 SU2 大写 `Solve()` 命名导致的求解器可替换性漏报——走完"LLM 候选 → 实测归因 → 精确正则修复"三步后，SU2 耦合架构评分从 60 提到 70，MPR-004 正确触发。验证同时确认 Kratos FMI 判定正确（自定义 CoSimIO 不是 FMI 标准），并记下 3 项已知边界（preCICE 多模式架构、FreeFEM 目录命名、OpenFOAM 配置字典）。

质量指标：92 项测试全部通过、9 项目回归 28 项通过、三方一致性 6/6 通过。按开发方案流程，可以进 C 阶段（部署）了。
