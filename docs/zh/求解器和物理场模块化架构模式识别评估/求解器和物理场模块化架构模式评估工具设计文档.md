## 第 1 章 设计概览

### 1.1 设计目标

将《求解器与物理场模块化架构模式识别评估指南》中 4 个维度的评分算法，工程化为可执行的静态代码分析工具。指南定义"应该评估什么、如何评分"（算法规范），本工具将其实现为可复现的检测逻辑。

### 1.2 架构定位

作为 `ComprehensiveReport` 的结构质量增强维度，在多物理场项目自动启用：

```
ComprehensiveReport.generate()
  ├── StandardMetrics (基础结构质量)
  ├── MultilangMetrics (多语言增强)
  ├── TemplateMetaprogrammingMetrics (模板增强)
  ├── NumericalAccuracyMetrics (数值精度增强)
  └── SolverPhysicsMetrics (本工具) ← 4 维度 + 11 MPR
```

多增强激活时权重归一化（基础 + 各增强权重和 = 100%）。

### 1.3 技术选型

| 项 | 选型 | 理由 |
|:---|:-----|:-----|
| 分析方式 | 纯静态（正则 + glob + 图分析）| 零外部依赖，可离线运行 |
| 文件扫描 | `FileIndex`（arch_core 共享）| 统一语言识别与编码处理 |
| 图分析 | `DepGraph.detect_same_lang_cycles()` | 复用既有循环检测 |
| 权重来源 | skill.md 运行时解析（方案D）| 权重与文档同步 |
| 性能控制 | 文件抽样 + 结果缓存 + 正则预编译 | 支持 20k+ 文件大型项目 |

## 第 2 章 整体架构

### 2.1 类结构

```python
class SolverPhysicsMetrics:
    def __init__(self, root):
        self.index = FileIndex(root)        # 文件索引
        self.weights = {}                   # 4 维度权重（skill.md 解析）
        self._all_contents = {}             # 扫描到的源码内容缓存
        self._module_dirs = {}              # 模块目录映射
        self._solver_dirs = set()           # 识别出的求解器目录
        self._cache = {}                    # 维度/正则结果缓存
        self._is_multiphysics = False       # 项目检测结果

    def _detect_multiphysics(self): ...     # 多物理场项目检测
    def calc_boundary_integrity(self): ...  # 维度 1 (25%)
    def calc_coupling_architecture(self): ... # 维度 2 (30%)
    def calc_extension_support(self): ...   # 维度 3 (25%)
    def calc_data_transfer(self): ...       # 维度 4 (20%)
    def check_mpr_rules(self): ...          # 11 条 MPR
    def calc_overall(self): ...             # 综合评分
    def all_metrics(self): ...              # 完整结果
```

### 2.2 缓存机制

所有检测结果通过 `_cache` 缓存，避免 `check_mpr_rules` 重复调用 `calc_xxx()` 时的重复计算：

| 缓存方法 | 用途 | 示例 |
|:---------|:-----|:-----|
| `_cached(name, fn)` | 维度结果缓存 | `boundary_integrity` |
| `_any_match(pattern)` | 全文件"任一命中"缓存 | `has_fmi` |
| `_sum_matches(pattern)` | 全文件"匹配总数"缓存 | `internal_access_count` |
| `build_config` | 构建配置检测结果缓存 | CMake/Makefile 扫描 |

### 2.3 数据流

```
FileIndex 扫描
   ↓
_detect_multiphysics() → 是否多物理场项目
   ↓（是）
_scan_files() → 抽样读取源码内容到 _all_contents
   ↓
calc_boundary_integrity → calc_coupling_architecture → calc_extension_support → calc_data_transfer
   ↓（各维度缓存）
check_mpr_rules() → 基于维度 detail 触发 11 条 MPR
   ↓
all_metrics() → {overall, dimensions, mpr_violations}
```

### 2.4 性能优化

| 优化 | 说明 |
|:-----|:-----|
| 文件抽样 | `_MAX_SCAN_FILES = 2000`，按模块均匀抽样（MOOSE 22321 文件 → 扫描 1344）|
| 结果缓存 | 维度 + 正则双重缓存，`all_metrics` 二次调用 0s |
| 构建文件扫描缓存 | `os.walk` 结果缓存，避免多维度重复遍历 |
| 正则预编译 | 命名正则常量在模块级预编译 |

### 2.5 抽样质量保证

**为什么抽样**：大型项目（20k+ 文件）全量读取 + 正则扫描耗时过长。抽样将 I/O 和扫描限制在 2000 个文件内（分层抽样：按模块均匀取样，保证各物理场模块都有代表性文件）。

**抽样对检测的影响**（关键设计考量）：

| 检测类型 | 抽样影响 | 质量保证措施 |
|:---------|:---------|:-------------|
| 布尔型检测（has_fmi/has_plugin）| 低 | 任一命中即判定，天然稳健 |
| 阈值型检测（独立单元/API 档位）| 低 | 结构检测走全量路径（构建文件扫描）|
| **计数型检测**（内部访问数/转换站点数）| **高** | **按抽样比例外推**（见下）|
| **比值型检测**（耦合占比）| 中 | 分子外推，分母用全量源文件数 |

**计数外推机制**：

```python
# 抽样比例 = 扫描文件数 / 全量源文件数
self._sample_ratio = len(source_files) / max(1, total)

# 计数型检测外推（internal_access_count / convert_site_count / coupling_file_count）
extrapolated = int(raw_count / self._sample_ratio)
```

**修复的检测点**：

| 检测点 | 修复前（抽样低估）| 修复后（外推）|
|:-------|:------------------|:-------------|
| 内部数据结构封装性 | `internal_access_count` 低估 → 得分虚高 | 按 `1/sample_ratio` 外推 |
| 数据格式转换散布 | `convert_site_count` 低估 → MPR-012 漏报 | 外推 |
| 耦合文件占比 | 分子抽样、分母全量，比值失真 | 分子外推 |
| MMS 覆盖 | 内容级抽样可能漏检 | 目录级检测（全量 os.walk）为主判据 |

**detail 中标注外推信息**：

```json
"encapsulation": {"internal_access_count": 14228, "_sampled": {"sample_ratio": 0.103, "estimated": true}}
```

**抽样质量验证**：`tests/test_solver_physics_sampling.py` 保证——
- 抽样比例记录正确
- 计数外推误差受控（全量 vs 半抽样外推一致）
- 布尔型检测在抽样下判定不变

## 第 3 章 维度 1：物理场模块边界完整性（25%）

### 3.1 指南算法原文（§2.1）

| 检查项 | 检测方法 | 分值 | 置信度 |
|:-------|:---------|:----:|:------:|
| 模块是否以独立编译单元存在 | 检测是否存在独立的库文件或可执行文件 | 20 | 高 |
| 公共接口是否精简（暴露符号数量合理）| 统计导出的公共 API 数量 | 20 | 中 |
| 模块是否具备独立数值验证套件（含 MMS）| 检测测试目录中 `*_mms*`、`*_verification*` 文件 | 30 | 中 |
| 模块内部实现细节是否对外隐藏 | 检测直接访问内部数据结构的代码模式 | 30 | 低 |
| 模块是否支持独立 FMU（FMI 模型交换）| 检测 FMI/FMU 接口实现 | +10 | 高 |

公式：`边界完整性得分 = sum(子项得分) + 加分项`

### 3.2 工具实现映射（检测正则级别）

| 指南检查项 | 工具方法 | 分值逻辑 | 检测正则/机制 |
|:-----------|:---------|:---------|:---------------|
| 独立编译单元 | `_calc_boundary_integrity_impl` s1 | `20 if has_independent else 0` | `_scan_build_config_files()`：CMake `add_subdirectory` ≥1 或同文件 `add_library` ≥2；或 Makefile 体系 ≥2 子目录 |
| 公共接口精简 | s2 | `≤50→20, ≤100→10, >100→5` | API 正则：`(?:virtual\s+)?(?:void|int|double|...)\s+(\w+)\s*\(` |
| 独立数值验证套件 | s3 | `覆盖率≥80%→30, >0→15, 0→0` | `MMS_PATTERN`：`\b(mms|manufactured.solution|verification|order.of.accuracy)\b` + 目录 glob |
| 内部数据结构封装 | s4 | `0处→30, ≤3→20, ≤10→10, >10→0` | `DIRECT_MEMBER_ACCESS`：`(?:\w+)\s*->\s*(?:[a-z]\w*)\s*[=;]`；`INTERNAL_ACCESS_PATTERN`：`(?:\w+)\s*\.\s*(?:data_|internal_|private_)\w+\s*[=;]` |
| FMI 模型交换 | fmi_support | `有FMI→+10` | `FMI_FUNCTIONS_PATTERN`：`fmi2DoStep|fmi2GetXXX|fmi2SetXXX|fmi2Instantiate|...` |

### 3.3 工程化偏差说明

| 指南描述 | 工具实现 | 偏差原因 |
|:---------|:---------|:---------|
| "独立的库文件或可执行文件" | 识别 CMake `add_subdirectory`/`add_library` 或 Makefile 多子目录 | 静态分析无法执行构建，用构建配置语法作为代理 |
| "统计导出的公共 API 数量" | 从 `.h`/`.hpp` 头文件用正则提取函数声明 | 无法精确解析 C++ 符号导出，用声明计数近似 |
| "暴露符号数量合理"（默认 50）| `≤50→20, ≤100→10, >100→5` 三档 | 指南为二值判定，工程化为三档连续评分 |

**设计决策记录（B3.5 验证修复）**：

```
问题：MOOSE（Makefile 体系，无根 CMakeLists.txt）被判为"无独立编译单元"
修复：_scan_build_config_files() 增加 Makefile 体系识别
  - ≥2 个子目录有 Makefile = 多独立编译目标
  - 识别 MOOSE 风格 APPLICATION_NAME/libmesh 多模块应用
教训：构建体系多样性（CMake/Makefile/自定义）需一并识别
```

## 第 4 章 维度 2：求解器耦合架构合理性（30%）

### 4.1 指南算法原文（§2.2）

**耦合强度判定方法**（四维度投票）：

| 判定依据 | 强耦合特征 | 弱耦合特征 | 检测方法 |
|:---------|:-----------|:-----------|:---------|
| 数据交换频次 | 每时间步内多次交换（迭代）| 每时间步一次或隔步 | 检测耦合迭代次数配置 |
| 数据交换方向 | 双向耦合（相互影响）| 单向耦合（A→B）| 检测求解器间数据流向 |
| 附加质量效应 | 强耦合存在附加质量 | 弱耦合可忽略 | 检测附加质量矩阵 |
| 收敛反馈效应 | 存在内迭代 | 可顺序执行 | 检测迭代收敛机制 |

**评分算法**（6 子项）：

| 检查项 | 分值 | 置信度 |
|:-------|:----:|:------:|
| 耦合架构形态与耦合强度匹配 | 20 | 中 |
| 耦合逻辑是否与求解器核心逻辑分离 | 20 | 中 |
| 求解算法是否可替换 | 15 | 中 |
| 收敛稳定性与误差累积 | 15 | 中 |
| 标准耦合接口支持度 | 15 | 中 |
| 系统级验证完整性 | 15 | 中 |

### 4.2 工具实现映射（检测正则级别）

**耦合强度判定**（`_judge_coupling_strength`，投票制）：

| 指南判定维度 | 工具投票正则 | 命中 → 票 |
|:-------------|:-------------|:---------:|
| 收敛反馈（内迭代）| `(?:while|for)\s*\([^)]*[0-9]+\s*<[^)]*\w*[Cc]oupling\w*` 或 `[Ss]taggered` 或 `strong[_ -]?coupling` 或 `inner[_ -]?iter\b` | strong |
| 数据交换方向（双向）| `(?:exchange|transfer|coupl(?:e|ing))[^;\n]{0,60}(?:both|two[- ]way|bi[- ]directional|mutual|reciprocal)` | strong |
| 矩阵结构（非对称）| `(?:asymmetric|non[- ]symmetric|unsymmetric)\s*(?:matrix|jacobian|system)` | strong |
| 数据交换方向（单向）| `one[- ]way.{0,30}coupl` 或 `uni[- ]directional.{0,30}coupl` 等 | weak |
| 数据交换频次（单次）| `(?:once|single)[^;\n]{0,40}(?:exchange|transfer).{0,20}(?:field|data|coupl)` 等 | weak |

判定：`strong_votes > weak_votes → "strong"`，反之 `"weak"`，`strong>0 → "medium"`，否则 `"unknown"`。

**架构类型识别**（`_detect_coupling_architecture`，顺序匹配）：

| 架构类型 | 检测正则 |
|:---------|:---------|
| monolithic | `\bmonolithic\b\|monolith\b` |
| partitioned_iterative | `\b(partitioned.{0,20}iterative\|iterative.{0,20}coupling\|staggered\|fixed[_ -]?point\|picard)\b` |
| partitioned_loose | `\b(partitioned.{0,20}loose\|loose.{0,20}coupling\|explicit.{0,20}coupling)\b` |
| fully_loose | `\b(fully[- ]loose\|file[- ]based.{0,20}coupl\|external.{0,20}coupl)\b` |

**匹配判定**（`_matches_architecture`）：

| 耦合强度 | 匹配架构 |
|:---------|:---------|
| strong | monolithic, partitioned_iterative |
| medium | partitioned_iterative, partitioned_loose |
| weak | partitioned_loose, fully_loose |

**6 子项评分**：

| 指南子项 | 工具方法 | 分值逻辑 | 检测机制 |
|:---------|:---------|:---------|:---------|
| 架构与强度匹配 | s1 | `匹配→20, 部分→10, 0` | `_judge_coupling_strength + _detect_coupling_architecture + _matches_architecture` |
| 耦合逻辑分离 | s2 | `占比<10%→20, <30%→10, 0` | `_find_coupling_files`：目录名含 coupling/fsi/interface + 内容含 coupling/transfer/exchange |
| 求解算法可替换 | s3 | `抽象基类→15, 虚函数→10, 0` | `ABSTRACT_SOLVER_PATTERN`：`class ... virtual solve()=0`；`VIRTUAL_SOLVE_PATTERN`：`virtual.*solve(` |
| 收敛稳定性 | s4 | `耦合收敛→15, 仅单求解器收敛→5, 无→0` | `CONVERGENCE_PATTERN`：`residual|tolerance|relativeTolerance|maxIter|nIter`；须与耦合上下文同现（`COUPLING_CONTEXT_PATTERN`：coupl/fsi/transfer/multi-app/picard/fixed-point）；`ITERATION_LIMIT_PATTERN`：`(maxIter|nIter|maxIterations|iterMax)\s*[=:]\s*(\d+)`（供 MPR-006 迭代上限检查）|
| 标准耦合接口 | s5 | `有FMI→15, 0` | `FMI_FUNCTIONS_PATTERN` |
| 系统级验证 | s6 | `有→15, 0` | `V_AND_V_PATTERN`：`verification.*validation|system.*test|integration.*test` |

### 4.3 工程化偏差说明

| 指南描述 | 工具实现 | 偏差原因 |
|:---------|:---------|:---------|
| "检测耦合迭代次数配置" | 用内迭代/定点迭代关键词投票 | 静态分析无法读配置运行值 |
| "检测求解器间数据流向" | 用 exchange/transfer + 方向词正则 | 无法精确建调用图，用关键词近似 |
| "附加质量矩阵" | 未实现（指南为强/弱判定参考）| 需物理知识，静态不可判 |
| "收敛稳定性"（耦合级）| 收敛关键词须与耦合上下文同现 | 单求解器内部 residual/tolerance（FEM 残差、线性迭代容差）不属耦合评估范畴 |

**设计决策记录（B3.5 验证修复）**：

```
问题1：fixed.point 未转义点，误匹配 "fixed-point notation"（JSON 打印格式）
修复：转义 + 限定为 fixed[_ -]?point，并移出强耦合投票

问题2：fixed_point（Picard 定点迭代）被误当强耦合标志
修复：Picard 定点迭代属于 partitioned_iterative 架构，移入架构判定

问题3：send/receive.*both 误匹配 MPI 广播（"sends both count"）
修复：要求 exchange/transfer/coupl 语义，排除并行通信基础设施

问题4：one.way 误匹配自然语言（"One way to think of MatrixType"）
修复：要求 one[- ]way.{0,30}coupl 耦合语义

问题5：file.*based 误匹配注释（"file-names based"）
修复：限定 file[- ]based.{0,20}coupl 耦合语义

问题6：收敛稳定性误判单求解器内部收敛
背景：residual/tolerance/maxIter 在单求解器内部普遍存在（FEM 单元残差、线性迭代容差）
修复：收敛关键词须与耦合上下文（coupl/fsi/transfer/multi-app/picard）同现
  仅耦合收敛 → 15 分；仅单求解器收敛 → 5 分（部分分）；无 → 0 分
效果：MOOSE 96 个收敛命中中 91 个为单求解器内部，被正确排除
已知边界：OpenFOAM 的耦合收敛控制配置在 fvSolution 字典文件（无源码扩展名），
  静态分析只能检测源码中的收敛参数，可能漏检 → MPR-006 需人工确认

教训：数值计算/并行计算库中的通用词（exchange/transfer/staggered/fixed point）
与多物理场耦合语义高度混淆，正则必须限定到耦合上下文
```

### 5.3 工程化偏差说明

| 指南描述 | 工具实现 | 偏差原因 |
|:---------|:---------|:---------|
| "通过标准接口动态加载" | 检测注册宏/接口基类关键词 | MOOSE 用 `MooseObject` 统一基类 + `registerMooseObject` 宏，原正则只认 Plugin/Module/Application/Solver → 曾误判"无统一接口"。B3.5 LLM 漏报探查发现，实测 196 个继承，已固化 `MooseObject` 到 `INTERFACE_BASE_CLASSES` |

**可扩展接口模式库**：`INTERFACE_BASE_CLASSES` 列表驱动正则生成。B3.5 LLM 漏报探查发现的框架特定命名模式，经人工审查 + 防误报验证（其他项目无此类继承）后追加到列表。当前包含：Plugin、Module、Application、Solver、MooseObject、KratosApplication、Process。
| "依赖关系形式化" | 检测构建文件依赖声明 | 部分项目依赖声明在代码内（如 pkg-config），漏检 |

**第三方依赖目录排除**：循环依赖检测（及模块级检测）排除第三方依赖目录，防止误报。

| 项 | 说明 |
|:---|:-----|
| 问题 | B3.5 验证 ElmerFEM 发现：31 个循环 100% 来自根目录 `umfpack` 第三方求解器库的头文件互引用，被误判为项目模块循环依赖 |
| 方案 | `THIRD_PARTY_DIR_NAMES` 常量 + `_is_project_file()` 排除 umfpack/contrib/vendor/external 等目录 |
| 效果 | ElmerFEM cycle_count 31→0，MPR-008 消除，ext_score 25→37 |
| 扩展 | `_is_project_abs_path()` 支持绝对路径（用于 `_all_contents` 遍历）；`THIRD_PARTY_DIR_NAMES` 补充 `external_libraries`（Kratos 的 vexcl/pybind11 所在目录）|

**Kratos 格式转换误报修复**：B3.5 验证 Kratos 时发现，`format_conversion` 的唯一命中来自第三方库 vexcl（`external_libraries/vexcl/fft.hpp` 的 transform 词），且被抽样外推放大为 `convert_site_count=5` → 得 0 分。修复后格式转换检测排除第三方目录 → 项目自身 0 命中 → 得 20 分满分。data_score 65→85，overall 62.25→66.25。

**ElmerFEM LLM 漏报探查结论（统一接口）**：

| 候选模式 | 实测证据 | 结论 |
|:---------|:---------|:-----|
| C++ 类继承（Plugin/Module/Application/Solver）| 全部 0 命中 | 放弃（ElmerFEM 非 C++ 类继承架构）|
| Fortran `Procedure` 插件加载 | `GetProcAddr` + `ExecSimulationProc` + `Procedure =`（10 处）| ✅ 真实插件机制，但为语言盲区 |
| Fortran `abstract interface` | Lua.F90 中为回调接口，非统一插件接口 | 放弃 |

**归因**：ElmerFEM 用 Fortran 过程指针动态加载求解器（`GetProcAddr`），但工具统一接口检测完全面向 C++ 类继承。这是**语言体系差异**（C++ 类继承 vs Fortran 过程指针），非命名差异。

**固化决策：新增独立的 Fortran 插件机制检测（已实施）**：

| 项 | 说明 |
|:---|:-----|
| 检测方法 | `_detect_fortran_plugin()`：扫描 Fortran 文件（.f90/.f/.f03/.f08/.f95）中的过程指针动态加载 |
| 正则 | `FORTRAN_GET_PROC_ADDR`（GetProcAddr/dlsym/dlopen）、`FORTRAN_PROC_POINTER`（ExecSimulationProc/CallProc）、`FORTRAN_ISO_C`（c_funloc/iso_c_binding）|
| 判定规则 | ① GetProcAddr ≥3 文件 ② GetProcAddr+ProcPointer 双特征 ③ iso_c+GetProcAddr |
| **语言限定** | 仅扫描 Fortran 文件，排除 C++ 的 GetProcAddr（B3.5 验证 OpenFOAM 的 POSIX 系统接口误报）|
| 合并逻辑 | 作为 C++ 统一接口的等价替代，不叠加（`has_effective_interface = has_interface or has_fortran_plugin`）|
| 效果 | ElmerFEM dl_score 15→30，ext_score 37→45，overall 54→56 |
| 防误报 | OpenFOAM 的 C++ GetProcAddr（POSIX 接口）被语言过滤排除 |
| 防误报验证 | MOOSE/OpenFOAM/deal.II/MFEM 循环数无变化（无此类第三方目录或循环在自身模块）|

**Kratos LLM 漏报探查结论（统一接口）**：

| 候选模式 | 实测证据 | 结论 |
|:---------|:---------|:-----|
| `KratosApplication` 基类 | 10 个 `KratosXxxApplication : public KratosApplication`，核心基类 `kratos/includes/kratos_application.h`，`Register` 注册方法 | ✅ 统一插件接口 |
| `Process` 基类 | 202 个继承（全库），抽样内 26 命中 | ✅ 核心统一接口 |

**固化**：`KratosApplication` 和 `Process` 追加到 `INTERFACE_BASE_CLASSES`。防误报验证：其他 5 项目均无这两类继承。

**效果**：Kratos `has_unified_interface` false→true，dl_score 15→30，ext_score 40→55，overall 58.5→62.25。

**抽样启示**：`KratosApplication`（10 继承）全在抽样外，但 `Process`（202 继承）抽样内命中。统一接口检测受抽样影响——基类继承文件可能未被抽到，需在基类定义文件命中时辅助判定（未来改进）。
