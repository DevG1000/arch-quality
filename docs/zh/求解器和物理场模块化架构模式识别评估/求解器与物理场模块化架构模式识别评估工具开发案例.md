## 摘要

依据架构质量评估技能开发指南的十六步流程，开发第四个结构质量增强维度——多物理场耦合系统模块化架构评估——的静态分析工具。目标是把指南四个维度、十二条模块化模式识别规则落地为可执行检测，并保证指南、技能文件、工具三方算法一致。产出工具实现一千四百余行，九十二项单元、抽样、集成、端到端、变异测试全部通过，解决权重运行时解析、抽样计数外推、指南公式静态化、多增强权重归一化四个工程问题。

---

## 1. 问题描述

### 1.1 背景

arch-quality 的结构质量评估有 4 个增强维度，前三个（多语言混合依赖、模板元编程、数值算法精度）都已实现并集成进 `ComprehensiveReport`。本工具是第 4 个——针对工业仿真软件里求解器和物理场模块的架构质量。

评估对象是 CAD/CAE/CAx/CFD 这类软件里的多物理场耦合系统。这类系统的架构问题往往出在四件事上：物理场模块边界不清、耦合架构选型不当、插件扩展机制缺失、跨场数据传递混乱。指南把它们定成 4 个维度，配 12 条 MPR 规则。

### 1.2 开发目标与约束

| 属性 | 值 |
|:-----|:-----|
| 层级 | 第 3 层（Prompt + Skills + Commands）|
| 角色 | 结构质量增强维度，多物理场项目自动启用 |
| 启用条件 | 目录结构含多物理场特征（同时存在 structural/thermal/fluid 求解器目录，或目录名含 multiphysics）|
| 维度权重 | 25% / 30% / 25% / 20% |
| 规则数 | 12 条 MPR |
| 关键约束 | 权重从 skill .md 运行时解析（方案D），三方评分算法一致，不硬编码 |

开发不是从零开始——指南、设计依据、验证案例集、可参考工具库四份文档都已完稿，工具要做的就是把它们翻译成可执行代码。

### 1.3 关键难点

动手之前，先想清楚这块硬骨头在哪：

1. **评分算法翻译**：指南里"边界完整性得分 = 独立编译单元(20分) + API精简度(20分) + MMS验证基准(30分) + 内部封装性(30分) + FMI加分(+10分)"是自然语言，要变成可执行的分段函数，每条分支要有明确条件、评分区间严格 0-100。
2. **规则可检测性**：12 条 MPR 规则里的代码坏味道（如"耦合逻辑分散""模块边界模糊"），有的靠目录结构能看出来，有的得靠正则扫源码，还有的（如 FMI 合规性）需要解包校验——每条规则的检测手段和置信度要提前定清楚。
3. **大项目性能**：MOOSE、OpenFOAM 这类项目上万文件，全量扫一遍太慢，需要抽样；但抽样又会让计数型检测失真，得做外推。
4. **多增强权重归一化**：多个增强维度同时激活时，各自权重要等比缩放凑成 100%，跟既有增强（multilang/template/numacc）协同不打架。

## 2. 分析过程

### 2.1 三方制品体系

整个开发围绕"指南 → Skill → 工具"三层派生关系展开：

```
指南（已完稿）→ 定义 4 维度 + 12 MPR 规则
     ↓ 翻译为 skill .md（权重表 + 评分算法，方案D 运行时解析）
Skill（src/arch_quality/skills/solver-physics-architecture.md）
     ↓ 实现为 Python
工具（src/arch_quality/arch_metrics_solver_physics.py, SolverPhysicsMetrics 类）
```

三方评分算法必须一致，这是硬约束——改任一方都要同步另外两方（一致性检查脚本兜底）。

### 2.2 维度与评分算法设计

4 个维度，各配一组子项和分值：

| 维度 | 权重 | 子项（分值）|
|:-----|:----:|:------------|
| 物理场模块边界完整性 | 25% | 独立编译单元(20) + API精简度(20) + MMS验证基准(30) + 内部封装性(30) + FMI加分(+10) |
| 多物理场耦合架构合理性 | 30% | 架构与强度匹配(20) + 耦合逻辑集中度(20) + 求解算法可替换性(15) + 迭代收敛稳定性(15) + 标准耦合接口(15) + 系统级验证(15) |
| 插件式扩展架构支持度 | 25% | 标准接口动态加载(30) + 依赖关系形式化(25) + 无循环依赖(25) + 接口版本管理(20) |
| 跨场数据传递规范性 | 20% | 标准数据结构(20) + FMI协同仿真(15) + 格式转换统一性(20) + 时间同步(15) + 空间映射(15) + 时间步协调(15) |

每个子项的检测手段在设计时就定好置信度——高置信度的（独立编译单元、耦合逻辑集中度）用 ERROR/WARNING，中低置信度的（内部封装性、耦合强度判定）降级或加人工复核。

### 2.3 MPR 规则设计

12 条 MPR 规则，设计时坚持三个原则：

1. **severity 与 output_level 解耦**：severity 反映影响程度（HIGH/MEDIUM/LOW），output_level 反映告警等级（ERROR/WARNING/INFO）。ERROR 级用于可阻断的门禁规则（MPR-001/003/008），WARNING 级用于需人工判断的规则（MPR-002/004/005/006/007/009/010），INFO 级用于低置信度参考（MPR-012）。
2. **每条规则对应可检测的坏味道**，且有明确触发条件和豁免可能性（MPR-010 标注"是"，其余"否"）。
3. **P0-P3 优先级**：P0 是阻断性门禁（MPR-001/002/008/010），P1 高优先（MPR-003/005/007），P2/P3 参考（MPR-004/006/009/012 及 MPR-FMI 加分项）。

### 2.4 A3.5 质量门禁

规则定义完、工具实现之前，过一道 `skill-audit` 审查，查 6 个维度：结构完整性、§2 评分算法与 §5 规则一致性、设计合理性、可执行性、完整性、跨规则协调。判定标准：全部 6 项无 FAIL 才进 A4；任一项 FAIL 或 ≥2 项 WARNING 要返工。这道门禁把"规则写得好看但检测不出来"的问题拦在实现之前。

### 2.5 A4 工具实现

`SolverPhysicsMetrics` 类实现 4 个 `calc_xxx()` 方法（各返回 `(score, detail_dict)`）+ `check_mpr_rules()` + `all_metrics()`。几个实现要点：

- **正则模式定义在文件顶部常量区**，检测关键词集中管理，便于 B3.5 探查后扩展。
- **缓存机制**：`_cache` 缓存耦合强度、架构类型、耦合收敛等重复计算结果，避免反复扫全文。
- **抽样**：大项目按比例抽样扫描，`_sample_ratio` 记录抽样比。
- **依赖图**：用 FileIndex + DepGraph 做循环依赖检测（MPR-008）。

工具设计文档把"指南算法 → 工具实现"的映射落到检测正则级，每个子项都有"指南描述 / 工具实现 / 工程化偏差原因"三栏对照。

### 2.6 测试体系设计

测试按 B1→B4 逐层搭：

| 阶段 | 内容 | 数量 |
|:-----|:-----|:----:|
| B1 单元 | 每个 `calc_xxx()` 至少 2 例（正常+未命中），每条 MPR 至少 1 例 | 51 |
| B1+ 抽样 | 大项目抽样正确性（`_sample_ratio` 外推、布尔检测稳健性）| 6 |
| B2 变异 | 故意引入 10 类坏味道，验证工具能检出（MUT-SP-001~010）| 10 |
| B2.5 集成&E2E | 权重解析、报告合并、MPR 合并、多增强权重归一化；真实项目结构冒烟 | 11+14 |
| B3 回归 | 真实开源项目快照基线，评分偏移超限报警 | 28 |
| B4 一致性 | 指南↔Skill↔工具三方评分算法一致 | 6 |

## 3. 解决措施

### 3.1 权重方案D：运行时解析，不硬编码

权重不写死在代码里，而是从 `skills/solver-physics-architecture.md` 运行时解析。好处是改权重不用动代码，且权重总和必须恰好 100%，否则直接报错。产品类型还可调（求解器为核心默认 25/30/25/20，耦合场为核心 20/35/20/25，平台化为核心 30/20/30/20）。

### 3.2 抽样计数外推

大项目（MOOSE/OpenFOAM）全量扫太慢，用抽样。但抽样对计数型检测是坑——比如"耦合文件数"若按抽样比例少算了，耦合集中度评分就失真。解决办法：`_sample_ratio` 记录抽样比，计数型检测（internal_access_count / convert_site_count / coupling_file_count）按 `count / _sample_ratio` 外推回全量口径。结构检测走全量（不抽样），布尔检测（有/无）天然稳健不受抽样影响。

### 3.3 工程化偏差：指南公式 → 静态分析近似

静态分析没法执行构建、没法跑求解器，所以指南里的很多"检测"要用代理手段近似。几个典型偏差：

| 指南描述 | 工具实现 | 偏差原因 |
|:---------|:---------|:---------|
| "独立的库文件或可执行文件" | 识别 CMake `add_subdirectory`/`add_library` + Makefile 多子目录 | 静态分析无法执行构建，用构建配置语法当代理 |
| "统计导出的公开 API 数量" | 从 `.h`/`.hpp` 用正则提取函数声明 | 无法精确解析 C++ 符号导出，用声明计数近似 |
| "暴露符号数量合理"（默认 50）| `≤50 满分, ≤100 部分, >100 0 分` 三档 | 指南是二值判定，工程化为三档连续评分 |
| "检测耦合迭代次数配置" | 用内迭代/定点迭代关键词投票 | 静态分析无法读配置运行时 |
| "求解器间数据流向" | `exchange/transfer` + 方向词正则 | 无法精确建调用图，用关键词近似 |

这些偏差都记录在工具设计文档里，作为已知局限，B3.5 验证时逐条面对。

### 3.4 ComprehensiveReport 集成与权重归一化

工具结果要合并进 `arch_report.py` 的 `ComprehensiveReport`。关键是权重归一化——0/1/2/3/4 个增强维度任意组合激活时，结构质量总分都要归一成 100%。B2.5 集成测试用**精确值断言**（单独激活时 `sp_w=0.15`，4 增强全激活时每个增强 `≈0.1364`）抓出了 3 增强组合下 sp 权重被忽略的 bug，修掉后才通过。这验证了"期望值从合并公式推导、禁止从实现反推"的测试原则。

### 3.5 测试落地结果

| 指标 | 结果 |
|:-----|:----:|
| 单元/抽样/集成/E2E/变异 | 92 passed（51+6+11+14+10）|
| 回归（真实项目基线）| 28 passed + 3 skipped |
| 三方一致性 | 6/6 PASS |
| 工具代码 | 1416 行 |
| 测试代码（单元/抽样/集成/E2E/变异五件套）| 1883 行 |

## 4. 启示与推广

### 4.1 方法论价值：17 步流程 + 门禁的实操意义

这次开发把 17 步流程完整走了一遍，最有感触的是三道门禁的价值：
- **A3.5** 把"规则不可检测"的问题拦在写代码之前——审查 6 维里有一项就盯着"静态分析可行性、关键词误报风险"。
- **B2.5** 用精确断言抓装配 bug，证明"测试期望值从设计推导、不从实现反推"这条纪律值得坚持。
- **B3.5** 拿真实开源项目验证，把误报/漏报暴露出来再修（详见《开源项目验证与修复案例》）。

流程不是走形式，是每道关卡真的拦下了问题。此外 B4 一致性检查兜住"改了工具忘了改 Skill"的散落式改动。

### 4.2 可复用组件

这套工具搭在 `arch_core.py` 的共享地基上（FileIndex 文件索引、DepGraph 依赖图、read_text_smart 编码容错），这些组件被 4 个增强维度共用。抽样计数外推、三方制品派生、A3.5/B2.5/B3.5 门禁这套开发模式，下一个增强维度可以直接复用。

### 4.3 与验证案例衔接

工具开发完成 ≠ 结束。后续还有两条线：
- **验证线**：B3.5 开源项目验证已产出 9 项目回归基线，后续工具改动都受回归护栏约束（评分偏移容忍 综合 ±2.0 / 维度 ±5.0）。
- **增强线**：OpenFOAM 配置字典扫描（`_scan_config_files`，已决策待实施）、preCICE 多模式架构语义处理（待评估）、k-fold 交叉验证脚本（待创建）。

## 5. 结论

评估工具按 17 步流程从指南到可运行代码完整落地：产出 1416 行 `SolverPhysicsMetrics` 实现、12 条 MPR 规则、4 维度评分，测试体系 92 单元/抽样/集成/E2E/变异 + 28 回归 + 6 一致性全部通过。开发过程中解决了权重运行时解析、抽样计数外推、指南公式静态化、多增强权重归一化 4 个关键工程问题，并沉淀了"三方一致性 + 三道门禁"的开发方法论。工具已通过 B3.5 开源项目验证（9 个真实项目，修复 9 项误报/漏报），并已通过 B2.6 Agent Harness 验证（3 用例全部 PASS，验证 agent 编排行为），验证细节见《开源项目验证与修复案例》，并已具备进入 C 阶段（部署）的条件。
