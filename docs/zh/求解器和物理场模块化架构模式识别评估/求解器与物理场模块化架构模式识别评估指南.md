## 概述

**求解器与物理场模块化架构模式**是指：在工业软件中，不同物理场（结构、流体、热、电磁等）的数值求解器模块之间的组织方式、接口设计、数据交换机制和扩展架构的总称。这种架构模式决定了软件在多物理场耦合场景下的可维护性、可扩展性和计算效率。

在工业软件（CAD/CAE/CAx/CFD）中，多物理场耦合仿真已成为常态——从汽车碰撞分析中的结构-流体耦合，到电子散热中的热-流耦合，再到核工程中的热-力-中子耦合。然而，传统架构质量评估模型（ISO 25010、CK 度量集）仅关注单一代码库内的模块化，无法评估跨求解器、跨物理场的模块化架构质量。

本指南作为《软件架构质量评估指南》的补充，定义了一套专门针对求解器与物理场模块化架构模式的评估指标。这些指标可纳入**结构质量**中的模块化子维度（建议权重占结构质量的 10%~15%），也可作为工业软件多物理场仿真场景下的独立评估项。

**评估目标**：量化求解器与物理场模块化架构带来的可维护性风险与扩展性债务，识别物理场模块边界模糊、耦合架构失控、插件机制碎片化、数据交换架构混乱等架构风险，提升多物理场仿真平台的长期可维护性与可扩展性。


## 置信度说明

本指南中的每个评估子维度均标注**检测置信度**，用于说明该维度评分的可靠程度。置信度分为三级：

| 置信度 | 含义 | 典型检测方法 | 示例 |
|--------|------|-------------|------|
| **高** | 检测结果精确可靠，无需人工复核 | 精确测量（符号数量统计、配置文件解析、文件路径匹配） | MPR-002 公共接口符号数量统计 |
| **中** | 检测结果可靠，但存在边界情况需关注 | 结构化检查（构建配置解析、目录模式识别、依赖图分析） | MPR-001 模块边界识别 |
| **中低** | 检测结果为启发式推断，需人工复核确认 | 启发式检测（命名约定匹配、模式推断、架构形态倾向判断） | MPR-004 耦合架构形态倾向 |

**使用建议**：
- 高置信度规则的告警应**强制处理**，误报率极低。
- 中置信度规则的告警应**优先处理**，但在边界场景可能存在误报。
- 中低置信度规则的告警应**由人工复核**后决定是否处理，不作为阻断性门禁的唯一依据。


## 一、子维度与权重分配

求解器与物理场模块化架构模式识别评估由以下 **4 个子维度** 加权合成：

| 子维度 | 权重（默认） | 对应风险类型 | 置信度 |
|--------|-------------|-------------|--------|
| 物理场模块边界清晰度 | 25% | 物理场模块职责边界模糊，接口暴露过度或不足 | **中** |
| 求解器耦合架构合理性 | 30% | 耦合架构形态选择不当，耦合逻辑与求解器核心逻辑混杂 | **中** |
| 插件扩展架构完整性 | 25% | 新增物理场需修改核心代码，插件依赖关系混乱 | **中** |
| 场数据交换规范性 | 20% | 场数据传递路径混乱，格式转换缺乏统一管理 | **中高** |

**权重设计依据**：
- **求解器耦合架构合理性**权重最高（30%），因为耦合架构是多物理场仿真平台最核心的架构决策——错误的耦合选择会导致整个平台的可维护性崩溃。
- **物理场模块边界清晰度**（25%）和**插件扩展架构完整性**（25%）次之。**两者形成递进关系**——模块边界清晰是基础层，插件扩展是高级层（详见2.3节递进关系扣分规则）。
- **场数据交换规范性**（20%）权重最低，因其更多影响耦合精度和效率，对架构可维护性的直接影响相对可控。

**产品类型权重调整指引**：

不同产品定位对四个维度的敏感度不同，建议根据项目类型调整权重：

| 产品类型 | 边界清晰度 | 耦合架构 | 插件扩展 | 数据交换 | 说明 |
|---------|-----------|---------|---------|---------|------|
| **耦合为核心** | 20% | **35%** | 20% | **25%** | 耦合架构和场数据交换的合理性决定核心价值 |
| **多样性为优势** | **30%** | 20% | **30%** | 20% | 模块边界和插件架构的完整性决定扩展能力 |
| **均衡型（默认）** | 25% | 30% | 25% | 20% | 适用于两者并重的通用场景 |

**典型产品示例**：
- **耦合为核心**：ANSYS Multiphysics、COMSOL Multiphysics（多物理场耦合仿真）
- **多样性为优势**：Kratos Multiphysics、MOOSE（多物理场模块化平台）

**通用模块化与求解器模块化的层级关系**：

《软件架构质量评估指南》3.1节的“通用模块化”与本指南的“求解器模块化”处于不同的抽象层级：
- **通用模块化**：评估**目录级**结构——平均每目录文件数，适用于所有软件项目
- **求解器模块化**：评估**模块级**组织——物理场求解器的模块边界、耦合架构、插件扩展、数据交换，仅适用于多物理场仿真软件

两者是**互补而非替代**的关系。通用模块化提供基础层的目录结构健康度，求解器模块化提供专业层的多物理场模块组织健康度。在整合时，采用**“层级组合+加权”**的方式——先评估目录级结构（通用），再评估模块级组织（求解器），两者加权计算最终得分。层级说明详见第3章整合示例。


## 二、子维度定义与评分算法

### 2.1 物理场模块边界清晰度

**定义**：衡量每个物理场求解器模块（如结构求解器、流体求解器、热求解器等）的职责边界是否清晰、公共接口是否精简、是否具备独立的数值验证能力。模块边界清晰是多物理场仿真平台模块化架构的**必要条件**。

**置信度**：中

**设计依据**：
- **ASME V&V 10-2019** 提供的“组件级到系统级”层次化框架——组件级验证要求每个物理场模块可被独立验证
- **Kratos Multiphysics** 的模块化设计理念——核心框架定义公共接口，各物理场作为独立应用（Application）实现
- **FMI/FMU 标准**的封装要求——每个 FMU 是独立的功能单元，具有明确的输入输出接口

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 模块是否以独立编译单元存在 | 检测是否存在独立的库文件或可执行文件 | 20分 | **高** |
| 公共接口是否精简（暴露符号数量合理） | 统计导出的公共 API 数量 | 20分 | **中** |
| 模块是否具备独立的数值验证套件（如 MMS 测试用例） | 检测测试目录中是否存在 `*_mms*`、`*_verification*` 等模式的文件 | 30分 | **中** |
| 模块内部实现细节是否对外隐藏 | 检测是否存在直接访问其他模块内部数据结构的代码模式 | 30分 | **中** |
| **模块是否支持导出 FMU（FMI 模型交换模式）** | 检测是否存在 FMI/FMU 相关的接口实现或配置文件 | 加分项（+10分） | **中** |

```
边界清晰度得分 = sum(各检查项得分) + 加分项
```

**FMI 模型交换模式说明**：本检查项评估模块是否可作为 FMU（Functional Mock-up Unit）被其他仿真平台调用，属于**接口标准化**层面，与运行时数据交换无关（后者由 2.4 节覆盖）。

**置信度说明**：
- 编译单元检测为**高**置信度（精确测量）。
- 公共接口精简度因阈值（50个符号）依赖项目规模，置信度为**中**（阈值可配置）。
- 验证套件检测依赖命名约定（`*_mms*`），在非常规命名风格下可能漏报，置信度为**中**。
- 内部实现细节访问检测依赖代码模式匹配，存在漏报可能，置信度为**中**。
- FMI 支持检测依赖接口实现识别，置信度为**中**。

**对应行业实践**：
- Kratos Multiphysics 通过“核心框架 + 应用插件”架构确保模块边界清晰
- FMI 通过标准化的 FMU 接口实现模块封装

**代码坏味道：模块边界模糊（Fuzzy Module Boundary）**

- **描述**：物理场模块职责不清晰，暴露了过多内部实现细节，或与其他模块存在非接口级别的直接依赖。
- **典型表现**：结构求解器直接访问流体求解器的内部数据结构；模块的公共接口包含大量内部辅助函数。
- **危害**：模块难以独立演进，修改一个模块的内部实现可能破坏依赖它的其他模块。


### 2.2 求解器耦合架构合理性

**定义**：衡量多物理场耦合时求解器之间的耦合架构形态选择是否合理、耦合逻辑是否与求解器核心逻辑分离。工业实践中的耦合架构是一个连续光谱，包括整体式耦合、紧耦合迭代式、松耦合交错式和完全分离式等多种形态。

**置信度**：中

**设计依据**：
- **多物理场耦合框架实践**：模块化设计允许用户在分区求解（partitioned）与整体式（monolithic）耦合策略之间自由选择
- **ASME V&V 10-2019**：从组件级到系统级的层次化验证框架——耦合架构选择直接影响系统级验证的复杂度
- **FMI 3.0 标准**：支持协同仿真（co-simulation）和模型交换两种模式，为耦合架构提供标准化实现路径

**耦合强度判定方法**：

在实际工业软件中，“物理耦合强度”是一个需要量化的概念。建议通过以下方法综合判断：

| 判定依据 | 强耦合特征 | 弱耦合特征 | 检测方式 |
|---------|-----------|-----------|----------|
| 数据交换频次 | 每个时间步内多次交换（迭代） | 每个时间步仅交换一次或隔步交换 | 检测耦合迭代次数配置 |
| 数据交换方向 | 双向耦合（相互影响） | 单向耦合（A→B） | 检测求解器间的数据流向 |
| 附加质量效应 | 存在（如流固耦合中的附加质量） | 不存在或可忽略 | 检测物理场类型组合（如流固耦合） |
| 耦合算子结构 | 强耦合需要隐式处理，Jacobian 矩阵非对称 | 可用显式处理，无耦合 Jacobian | 检测算法实现特征 |

**耦合架构谱系**：

| 耦合架构形态 | 描述 | 适用场景 |
|-------------|------|----------|
| **整体式耦合** | 所有物理场统一为一个方程组求解 | 强耦合问题（如流固耦合中的颤振分析） |
| **紧耦合迭代式** | 每个时间步内多次迭代直到收敛 | 中等耦合强度问题 |
| **松耦合交错式** | 每个时间步仅交换一次数据 | 弱耦合问题（如热-结构耦合） |
| **完全分离式** | 通过文件或外部工具交换数据 | 单向耦合问题 |

**系统级验证可行性评估**（ASME V&V 10-2019）：

根据 ASME V&V 10-2019 的层次化验证框架，组件级验证通过不代表系统级验证通过。在多物理场耦合系统中，应评估**整个耦合系统是否可被作为整体进行验证**：

| 检查项 | 评估内容 | 说明 |
|--------|---------|------|
| 系统级测试用例是否存在 | 检测是否存在端到端的耦合系统验证测试 | 验证耦合系统整体行为的正确性 |
| 耦合系统边界条件是否可独立定义 | 检测耦合系统的整体边界条件是否可配置 | 系统级验证需要独立于组件的边界条件 |
| 耦合系统输出是否可量化验证 | 检测耦合系统是否输出可用于验证的全局量 | 如总能量、总动量等守恒量的验证 |

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 耦合架构形态选择是否与物理耦合强度匹配 | 检测耦合迭代次数配置，结合耦合强度判定方法 | 20分 | **中** |
| 耦合逻辑是否与求解器核心逻辑分离 | 检测耦合代码是否集中在独立的耦合层模块中 | 20分 | **中** |
| 耦合算法是否可插拔替换 | 检测是否存在耦合策略的抽象接口和多种实现 | 15分 | **中** |
| 耦合迭代是否考虑了舍入误差累积风险 | 检测迭代终止条件是否包含误差容忍度参数 | 15分 | **中** |
| 求解器接口对耦合算法的支持度 | 检测求解器是否暴露了足够的信息（如切向矩阵）以支持多种耦合算法 | 15分 | **中** |
| 系统级验证可行性 | 检测是否存在系统级验证测试用例和可量化的系统级输出 | 15分 | **中** |

```
耦合架构得分 = sum(各检查项得分)
```

**置信度说明**：
- 耦合架构形态识别依赖代码模式匹配和配置解析，且采用“形态倾向”而非“精确判定”的方式，置信度为**中**。
- 耦合逻辑分离度检测依赖代码结构分析，可能存在边界情况，置信度为**中**。
- 耦合算法可插拔性检测依赖抽象接口识别，置信度为**中**。
- 迭代误差风险评估依赖配置参数检测，置信度为**中**。
- 求解器接口支持度检测依赖接口定义分析，置信度为**中**。
- 系统级验证可行性检测依赖测试用例和输出配置分析，置信度为**中**。

**代码坏味道：耦合逻辑散落（Scattered Coupling Logic）**

- **描述**：多物理场耦合的逻辑代码散布在各个物理场求解器的核心代码中，而非集中在独立的耦合层。
- **典型表现**：结构求解器代码中包含“将位移传递给流体求解器”的逻辑；流体求解器代码中包含“接收来自结构求解器的载荷”的逻辑。
- **危害**：修改耦合策略需要修改多个求解器的代码，耦合架构难以演进。
- **对应行业实践**：multiRegionFoam 等框架将耦合策略作为独立的设计维度，允许用户在分区求解与整体式之间自由选择。

**耦合迭代舍入误差评估的定位说明**：

本检查项中的“耦合迭代次数与舍入误差累积风险的权衡”评估的是**耦合迭代过程是否可能放大各求解器内部已有的舍入误差**，属于**系统级误差风险评估**。这与《数值算法正确性与精度保障评估指南》2.2节“舍入误差与数值敏感度控制”评估的“求解器内部浮点运算是否稳健”（**单点误差检测**）是互补关系——前者关注耦合系统的误差放大风险，后者关注单点运算的误差控制质量。两者分别从**系统级**和**单点级**保障仿真结果的数值可靠性。

**场数据交换规范性与数值算法指南的边界说明**：

FMI 协同仿真的**误差控制机制**（如通信步长控制、误差估计等）属于《数值算法正确性与精度保障评估指南》的覆盖范围。本指南仅评估**FMI 接口的标准化程度**（如是否实现了必要的 FMI 函数、是否存在 XML 描述文件等），不重复评估数值精度。两本指南的分工如下：

| 评估内容 | 归属指南 | 说明 |
|---------|---------|------|
| FMI 接口是否完整（函数实现、XML 描述） | 本指南（MPR-010） | 接口标准化评估 |
| FMI 协同仿真的误差控制策略是否合理 | 数值算法指南 | 数值精度评估 |
| FMI 数据交换的舍入误差累积风险 | 数值算法指南 | 数值精度评估 |


### 2.3 插件扩展架构完整性

**定义**：衡量是否支持通过标准接口动态加载新的物理场或求解器模块。插件扩展架构是模块化架构的**高级形态**——在模块边界清晰的基础上，进一步实现运行时的动态扩展能力。

**置信度**：中

**设计依据**：
- **Kratos Multiphysics**：提供核心框架定义公共接口，各物理场作为“应用程序”（Applications）以插件形式工作
- **FMI 3.0 标准**：FMU 可作为独立的功能单元被仿真环境动态加载
- **工业软件平台化趋势**：基于“微内核+插件”的架构已成为新一代工业软件的标准模式

**递进关系说明**：

本子维度与“物理场模块边界清晰度”形成**递进关系**——模块边界清晰是基础层，插件扩展是高级层。**递进关系扣分规则仅适用于这一对维度**，其他维度（耦合架构合理性、场数据交换规范性）保持独立评估，不受其他维度评分影响。

**递进关系扣分规则**：
- 模块边界清晰度得分 ≥ 60 分时，插件扩展架构完整性正常计算
- 模块边界清晰度得分 < 60 分时，插件扩展架构完整性得分自动**扣减 50%**
- 扣减理由：模块边界模糊的系统难以有真正完整的插件扩展架构

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 是否支持通过标准接口动态加载新模块 | 检测是否存在插件发现和注册机制 | 30分 | **中** |
| 插件依赖关系是否显式声明 | 检测插件配置文件中的依赖声明 | 25分 | **高** |
| 是否存在插件间的循环依赖 | 分析插件依赖图，检测强连通分量 | 25分 | **高** |
| 接口变更是否向下兼容 | 检测模块接口的版本管理机制 | 20分 | **中** |

```
插件扩展得分 = sum(各检查项得分)
if 模块边界清晰度得分 < 60:
    插件扩展得分 = 插件扩展得分 × 0.5
```

**置信度说明**：
- 插件发现和注册机制检测依赖配置文件解析和代码模式识别，置信度为**中**。
- 依赖关系声明和循环依赖检测基于配置文件解析和依赖图分析，置信度为**高**。
- 接口版本管理检测依赖版本号规范识别，置信度为**中**。

**对应行业实践**：
- Kratos 通过统一的“应用程序”机制实现所有物理场模块的插件化集成

**代码坏味道：插件机制碎片化（Fragmented Plugin Mechanism）**

- **描述**：不同物理场模块通过不同的机制集成到系统中，缺乏统一的插件接口规范。
- **典型表现**：结构模块通过动态库加载，流体模块通过脚本注入，热模块直接编译进核心代码。
- **危害**：新增物理场需要理解多种集成机制，扩展成本高；插件间的依赖关系无法系统管理。


### 2.4 场数据交换规范性

**定义**：衡量物理场之间的场数据（温度场、位移场、压力场等）的传递路径、格式转换和同步机制是否规范统一。

**置信度**：中高

**设计依据**：
- **多物理场耦合平台实践**：通过数据（Field）、模块（Module）、节点（Node）和场景图（SceneGraph）的多层次框架管理多物理场耦合
- **FMI 3.0 标准**：定义了标准化的数据交换接口和时钟同步机制
- **模块化数据管理**：场数据传递应通过标准化的数据结构，而非自定义格式

**场数据交换评估边界说明**：场数据交换评估关注模块间数据接口的标准化程度和耦合代码的隔离性，不重复评估场数据映射算法的数值精度——该部分由《数值算法正确性与精度保障评估指南》覆盖（详见2.2节边界说明）。

**评分算法**：

| 检查项 | 检测方法 | 分值 | 置信度 |
|--------|---------|------|--------|
| 场数据是否通过标准化的数据结构传递 | 检测是否使用统一的 Field/Data 抽象 | 20分 | **高** |
| 运行时是否支持 FMI 协同仿真标准进行数据交换 | 检测是否存在 FMI 协同仿真接口实现 | 15分 | **中** |
| 数据格式转换是否有统一管理 | 检测是否存在统一的数据映射和转换机制 | 20分 | **中** |
| 时间同步机制是否规范 | 检测耦合时间步长管理是否统一 | 15分 | **高** |
| 网格映射架构是否独立 | 检测数据映射逻辑是否集中在独立的映射模块中 | 15分 | **中** |
| 时间步长协调策略是否合理 | 检测是否根据物理场时间尺度差异选择合适的时间协调策略 | 15分 | **中** |

```
场数据交换得分 = sum(各检查项得分)
```

**FMI 合规性检查（附加分项）**：

为体现 FMI 作为“战略参照基准”的地位，本指南将 FMI 合规性检查作为**附加分项**纳入综合分计算：

| 检查项 | 检测方法 | 分值 | 说明 |
|--------|---------|------|------|
| FMU 是否包含必要的 XML 描述文件（`modelDescription.xml`） | 检测 FMU 包结构 | +2分 | 接口描述完整性 |
| 是否实现了 FMI 标准要求的必要函数（如 `fmi2DoStep`、`fmi2GetXXX` 等） | 检测函数实现 | +2分 | 接口实现完整性 |
| 模块声称支持 FMI 与实际实现是否一致 | 对比声明与实际实现 | +1分 | 声明一致性 |

**FMI 合规性附加分规则**：
- 最高附加分为 **+5分**（三项全部满足）
- 附加分直接加在“场数据交换规范性”得分上，上限为100分
- 若模块完全不支持 FMI，该项不得分

**FMI 合规性检查说明**：合规性检查检测模块是否具备完整的 FMI 实现要素（XML 描述文件、必要函数实现等），属于**接口完整性检查**，不涉及数值精度或求解质量。合规性检查与数值质量检查是两个独立的概念——一个模块可以完全通过合规性检查，但其数值实现仍可能存在舍入误差问题。

**FMI 协同仿真模式说明**：本检查项评估模块在运行时是否使用 FMI 协同仿真标准与其他模块进行数据交换，属于**运行时数据交换标准化**层面，与 2.1 节的模型交换模式（接口导出）是独立的两个层次。

**FMI 三层评估体系**：

本指南将 FMI 标准的支持度分为三个层次：

| 层次 | 评估维度 | 检查项 | 评分方式 |
|------|---------|--------|----------|
| **L1：接口支持** | 物理场模块边界清晰度（2.1节） | 模块是否支持导出 FMU（模型交换模式） | 加分项（+10分） |
| **L2：运行时交换** | 场数据交换规范性（2.4节） | 运行时是否支持 FMI 协同仿真标准进行数据交换 | 常规检查项（15分） |
| **L3：合规性** | 场数据交换规范性（2.4节） | 模块的 FMI 实现是否合规（XML 描述文件、必要函数实现等） | 附加分项（最高+5分） |

**时间步长协调策略说明**：

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **统一时间步长** | 所有物理场使用相同时间步长 | 物理场时间尺度相近 |
| **子循环** | 快物理场使用小时间步长，慢物理场使用大时间步长 | 时间尺度差异较大 |
| **异步时间推进** | 各物理场独立推进，在耦合点交换数据 | 时间尺度差异巨大 |

**置信度说明**：
- 场数据结构统一性检测基于代码中 Field/Data 抽象的使用模式分析，置信度为**高**。
- FMI 协同仿真支持检测依赖接口实现识别，置信度为**中**。
- 数据格式转换统一性检测依赖代码模式匹配，置信度为**中**。
- 时间同步机制检测基于配置参数和代码模式识别，置信度为**高**。
- 网格映射架构独立性检测依赖代码结构分析，置信度为**中**。
- 时间步长协调策略检测依赖配置解析和代码分析，置信度为**中**。
- FMI 合规性检查基于文件结构和函数实现分析，置信度为**高**。

**对应行业实践**：
- FIND Multiphysics 通过 Field-Module-Node-SceneGraph 的多层次框架统一管理数据交换

**代码坏味道：数据交换路径混乱（Chaotic Data Exchange）**

- **描述**：场数据在求解器之间的传递路径不清晰，格式转换逻辑散布在各处。
- **典型表现**：温度场从热求解器传递到结构求解器时，经过多次格式转换，转换逻辑分散在多个文件中。
- **危害**：数据交换错误难以追踪，新增物理场时需要复制粘贴大量数据转换代码。


## 三、求解器与物理场模块化架构模式综合分

```
模块化架构综合分 = 
    物理场模块边界清晰度 × 25% +
    求解器耦合架构合理性 × 30% +
    插件扩展架构完整性 × 25% +
    场数据交换规范性 × 20%
```

**与通用模块化评估的整合**：

本指南的模块化架构综合分可与《软件架构质量评估指南》3.1节“通用模块化”得分整合，形成最终的模块化评估结果。

**层级说明**：通用模块化与求解器模块化处于不同的抽象层级——前者评估**目录级**结构（平均每目录文件数），后者评估**模块级**组织（物理场求解器的模块边界、耦合架构等）。两者是互补关系，采用**“层级组合+加权”**的方式整合。

建议的整合方式为**加权平均**，具体权重根据项目类型选择：

| 项目特征 | 通用模块化权重 | 求解器模块化权重 | 最终模块化得分 |
|---------|---------------|-----------------|---------------|
| **多物理场耦合为核心竞争力** | 20% | **80%** | `0.2×通用 + 0.8×求解器` |
| **物理场模块多样性为优势** | 40% | **60%** | `0.4×通用 + 0.6×求解器` |
| **均衡型（两者并重）** | 30% | **70%** | `0.3×通用 + 0.7×求解器` |

**整合示例**：

假设某项目通用模块化得分为75分，求解器模块化得分为65分，项目类型为“均衡型”：

```
最终模块化得分 = 0.3 × 75 + 0.7 × 65 = 22.5 + 45.5 = 68分
```

该综合分可作为**结构质量**中模块化指标的扩展项，在工业软件（尤其是多物理场仿真）场景下建议权重占结构质量总分的 15%。

**规则变更说明（1.3 版）**：

- **MPR-006**：检测逻辑从“是否存在参数”升级为“参数值是否合理”，增加容忍度与机器精度的关系检查

- **FMI 合规性**：新增附加分项（最高+5分），体现 FMI 战略基准地位

### 规则详细描述

#### MPR-001：物理场模块边界识别

- **严重级别**：HIGH
- **检测置信度**：中
- **描述**：识别物理场求解器模块是否以独立的编译单元存在。
- **检测逻辑**：
  1. 扫描项目构建配置（CMakeLists.txt、Makefile等），识别独立的库或可执行文件目标
  2. 检查每个物理场模块是否有独立的源代码目录（如 `src/solvers/structural/`）
  3. 若多个物理场混杂在同一编译单元中，触发告警
- **置信度说明**：构建配置解析可靠，但模块目录结构识别依赖命名约定，综合置信度为**中**。
- **建议修复**：将每个物理场模块拆分为独立的编译单元，通过标准接口通信。

#### MPR-002：模块公共接口精简度

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检查模块暴露的公共 API 是否精简合理。
- **检测逻辑**：
  1. 统计每个模块导出的公共符号数量
  2. 若导出符号数量超过阈值（**默认 50 个，可配置**），触发警告
  3. 检测是否存在导出内部辅助函数的情况（通过命名约定判断）
- **置信度说明**：符号数量统计为精确测量，但阈值（50个）为经验值，不同规模项目可能有差异。阈值可配置，置信度为**中**。
- **建议修复**：仅暴露最小必要的公共接口，内部实现使用隐藏符号或私有命名空间。

#### MPR-003：模块数值验证套件完备性

- **严重级别**：HIGH
- **检测置信度**：中
- **描述**：检查每个物理场模块是否具备独立的数值验证套件。
- **检测逻辑**：
  1. 检查每个模块的测试目录中是否存在 `*_mms*`、`*_verification*` 等模式的文件
  2. 检查验证套件是否可独立于模块运行
  3. 若模块缺少独立的验证套件，触发告警
- **置信度说明**：验证套件检测依赖命名约定（`*_mms*`），在非常规命名风格下可能漏报，置信度为**中**。
- **建议修复**：为每个物理场模块建立独立的 MMS 验证测试套件。

#### MPR-004：耦合架构形态倾向

- **严重级别**：MEDIUM（1.3 版从 HIGH 降级）
- **检测置信度**：中低
- **描述**：分析多物理场耦合所采用的架构形态**倾向**。通过检测代码中的耦合模式特征，判断系统倾向于哪种耦合形态。**检测结果需人工复核**。
- **检测逻辑**：
  1. 分析耦合代码中的特征模式，判断系统倾向整体式/紧耦合迭代式/松耦合交错式/完全分离式
  2. 解析配置文件，检测运行时实际使用的耦合模式配置
  3. 若耦合架构倾向明显不当（如强耦合问题倾向完全分离式），触发告警
- **置信度说明**：架构形态检测依赖代码模式匹配和配置文件解析，存在边界情况（系统可能包含多种模式的混合代码），置信度为**中低**。建议结合人工复核确认。
- **建议修复**：根据物理耦合强度重新评估耦合架构选择，必要时重构耦合策略。
- **1.3 版变更说明**：严重级别从 HIGH 降为 MEDIUM，因其置信度为“中低”，用作强制阻断依据存在风险。

#### MPR-005：耦合逻辑分离度（合并自 MPR-011）

- **严重级别**：HIGH
- **检测置信度**：中
- **描述**：检查耦合逻辑是否与求解器核心逻辑分离，且集中在耦合层。
- **子项**：耦合逻辑集中度——耦合逻辑是否集中在独立的耦合层模块中
- **评分贡献**：本规则的评分结果同时贡献给两个子维度：
  - 求解器耦合架构合理性（50%）
  - 场数据交换规范性（50%）
- **检测逻辑**：
  1. 检测求解器核心代码中是否包含跨物理场的数据访问或调用
  2. 检测耦合逻辑是否集中在独立的耦合层模块中
  3. 统计各求解器模块中的耦合相关代码行数
  4. 若耦合逻辑散布在各求解器中，触发告警
- **置信度说明**：耦合逻辑分离度检测依赖代码结构分析，可能存在边界情况，置信度为**中**。
- **建议修复**：将耦合逻辑抽取到独立的耦合层模块，求解器仅通过标准接口与耦合层交互。
- **1.2 版变更说明**：本规则合并了原 MPR-011“耦合逻辑集中度”的检查逻辑，采用**共享扣分**机制——扣分在两个子维度中各贡献 50%，避免重复扣分。

#### MPR-006：耦合迭代误差风险评估

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：评估紧耦合迭代式架构中舍入误差累积的风险。
- **检测逻辑**：
  1. 识别紧耦合迭代式架构
  2. 检查迭代终止条件是否包含误差容忍度参数，**且参数值是否合理**（不应低于机器精度的10倍，否则触发警告）
  3. 检查最大迭代次数是否设置合理上限（建议 ≤ 200）
  4. 检查容忍度是否过严导致迭代次数激增（如容忍度 < 1e-12 且迭代次数 > 100，触发警告）
  5. 若缺少误差控制机制或参数设置不合理，触发告警
- **置信度说明**：迭代误差风险评估依赖配置参数检测，置信度为**中**。
- **定位说明**：本规则评估耦合系统的**系统级误差放大风险**，与《数值算法正确性与精度保障评估指南》NVR-003/NVR-004 的**单点级误差检测**形成互补。
- **建议修复**：在耦合迭代中增加误差容忍度参数和最大迭代次数限制，确保容忍度不低于机器精度的10倍（双精度约为 1e-15，即容忍度不应低于 1e-14）。
- **1.3 版变更说明**：检测逻辑从“是否存在参数”升级为“参数值是否合理”。

#### MPR-007：插件扩展机制完整性

- **严重级别**：HIGH
- **检测置信度**：中
- **描述**：检查是否支持通过标准接口动态加载新的物理场模块。
- **检测逻辑**：
  1. 检测是否存在插件发现机制（如扫描特定目录、注册表等）
  2. 检测是否存在统一的插件接口定义
  3. 若缺少统一的插件机制，触发告警
- **置信度说明**：插件机制检测依赖配置文件解析和代码模式识别，置信度为**中**。
- **建议修复**：建立统一的插件接口规范，所有物理场模块通过该机制集成。

#### MPR-008：插件依赖关系管理

- **严重级别**：MEDIUM
- **检测置信度**：高
- **描述**：检查插件间的依赖关系是否被显式声明和管理。
- **检测逻辑**：
  1. 扫描插件的配置文件，检查是否声明了依赖关系
  2. 分析插件依赖图，检测是否存在循环依赖
  3. 若依赖关系未声明或存在循环依赖，触发告警
- **置信度说明**：配置文件解析和依赖图分析为精确测量，置信度为**高**。
- **建议修复**：在插件配置中显式声明依赖关系，打破循环依赖。

#### MPR-009：插件接口版本兼容性

- **严重级别**：MEDIUM
- **检测置信度**：中
- **描述**：检查模块接口的版本管理是否支持向后兼容，以及弃用机制是否被正确使用。
- **检测逻辑**：
  1. 检查模块是否声明了接口版本号
  2. 检查版本号变更是否与接口变更一致
  3. **检测 `@deprecated`、`@Deprecated` 等弃用标记的使用**——检查弃用接口是否在合理时间后被移除（建议 2 个主版本后）
  4. 若接口变更未更新版本号，或弃用接口长期未移除，触发告警
- **置信度说明**：版本号检测依赖版本号规范识别，弃用标记检测依赖注释解析，置信度为**中**。
- **建议修复**：遵循语义化版本规范管理模块接口版本，使用 `@deprecated` 标记弃用接口，并在合理时间后移除。
- **1.3 版变更说明**：增加对 `@deprecated`、`@Deprecated` 等弃用标记的检测。

#### MPR-010：场数据交换标准化

- **严重级别**：MEDIUM
- **检测置信度**：高
- **描述**：检查场数据是否通过标准化的数据结构传递。
- **检测逻辑**：
  1. 检测是否使用统一的 Field/Data 抽象
  2. 检测运行时是否支持 FMI 协同仿真标准进行数据交换
  3. 检查不同物理场之间是否使用相同的数据结构进行交换
  4. 若使用多种自定义数据结构，触发告警
- **置信度说明**：Field/Data 抽象使用模式分析基于代码结构解析，置信度为**高**。FMI 协同仿真检测依赖接口实现识别，置信度为**中**。
- **建议修复**：统一使用标准化的场数据结构进行跨物理场数据交换。

#### MPR-012：数据格式转换统一性

- **严重级别**：LOW
- **检测置信度**：中
- **描述**：检查场数据的格式转换是否有统一管理。
- **检测逻辑**：
  1. 识别数据格式转换的代码位置
  2. 检查转换逻辑是否集中在统一的转换模块中
  3. 若转换逻辑分散，触发提示
- **置信度说明**：数据格式转换统一性检测依赖代码模式匹配，置信度为**中**。
- **建议修复**：建立统一的数据格式转换和映射管理机制。

## 七、实施建议

### 7.1 工具集成

建议采用以下技术路径实现各检测规则：

| 检测目标 | 推荐技术路径 | 可参考工具/库 |
|---------|-------------|--------------|
| 物理场模块边界识别 | CMake/Makefile 目标解析 + 目录结构分析 | Python re + glob |
| 公共接口精简度 | 符号表导出分析（ELF/PE/Mach-O） | `nm`、`dumpbin`、Python ELF 解析 |
| 耦合架构形态倾向 | AST 分析 + 配置文件解析 | Clang AST、Python AST 模块 |
| 耦合逻辑分离度 | AST 分析 + 文件路径模式匹配 | Clang AST、PyCG（Python 调用图） |
| 插件扩展机制完整性 | 配置文件解析 + 代码模式匹配 | Python re + glob |
| 插件依赖关系管理 | 配置文件解析 + 图分析 | Python NetworkX |
| 场数据交换标准化 | AST 分析 + Field/Data 抽象使用模式识别 | Clang AST、Python AST |
| 时间步长协调策略 | 配置文件解析 + 代码模式匹配 | Python re + glob |
| 网格映射架构独立性 | 代码模式匹配 + 目录结构分析 | Python re + glob |
| FMI 合规性检查 | FMU 包结构解析 + 函数实现检测 | Python zipfile + AST |
| 弃用标记检测 | 注释解析 + AST 分析 | Python AST + re |

### 7.2 门禁设置

- MPR-001、MPR-005、MPR-007 为 HIGH 级别，建议强制阻断
- MPR-004 为 MEDIUM 级别（置信度中低），**建议人工复核后决定是否阻断**，不作为自动阻断的唯一依据
- 模块化架构综合分 < 50 时阻止合并
- 检测到插件循环依赖（MPR-008）时触发阻断
- 高置信度规则（MPR-008、MPR-010）的告警应强制处理

### 7.3 置信度使用指南

- 工具应明确标注每条告警的置信度等级
- 中低置信度告警应在报告中标注“建议人工复核”
- CI 门禁中，高置信度规则的权重应高于低置信度规则

### 7.4 遗留代码库的渐进式评估策略

对于有数十年历史的大型工业软件代码库，建议采用**分阶段评估**策略：

| 阶段 | 评估范围 | 目标 | 预期产出 |
|------|---------|------|----------|
| **第一阶段** | 仅评估新增/修改模块的模块化质量 | 确保新代码符合模块化标准，不引入新的架构债务 | 新增模块的模块化评分报告 |
| **第二阶段** | 识别核心耦合逻辑并逐步抽离 | 将散布在求解器中的耦合逻辑逐步迁移到独立耦合层 | 耦合逻辑集中度报告 + 重构优先级清单 |
| **第三阶段** | 整体评估模块化架构健康度 | 全面评估并制定长期改进计划 | 整体模块化架构评分 + 改进路线图 |

**渐进式评估的评分基准**：
- 第一阶段：仅报告新增模块的得分，**不计入整体综合分**
- 第二阶段：新增模块得分与耦合逻辑抽离进度**加权计算**（进度权重递增）
- 第三阶段：全量评估，按标准公式计算综合分

### 7.5 与现有评估体系的衔接

本指南是《软件架构质量评估指南》3.1节“模块化”指标在工业软件多物理场仿真场景下的**深化和扩展**。

**层级说明**：通用模块化与求解器模块化处于不同的抽象层级——前者评估目录级结构，后者评估模块级组织。两者是互补关系，采用“层级组合+加权”的方式整合。

**评分整合示例**：

| 项目类型 | 通用模块化权重 | 求解器模块化权重 | 最终模块化得分 |
|---------|---------------|-----------------|---------------|
| 多物理场耦合为核心 | 20% | 80% | `0.2×通用 + 0.8×求解器` |
| 物理场模块多样性为优势 | 40% | 60% | `0.4×通用 + 0.6×求解器` |
| 均衡型（默认） | 30% | 70% | `0.3×通用 + 0.7×求解器` |

**实施顺序建议**：
1. 先执行通用模块化评估（目录结构分析），获取基础得分
2. 再执行本指南的求解器模块化评估，获取专业得分
3. 根据项目类型选择权重配置，计算最终模块化得分

### 7.6 重构优先级

- **第一优先级**：MPR-001（模块边界模糊）、MPR-005（耦合逻辑散落）——风险最高
- **第二优先级**：MPR-004（耦合架构不当）、MPR-007（插件机制缺失）——影响扩展性
- **第三优先级**：MPR-006（迭代误差风险）、MPR-010/MPR-012（数据交换规范）——影响可靠性
