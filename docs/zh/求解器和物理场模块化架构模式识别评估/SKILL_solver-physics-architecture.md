## 二、维度定义与评分算法

每个维度包含：代码坏味道名称、检测方法、评分算法。评分算法从指南的文字描述中提取为可执行的分段函数。

### 2.1 物理场模块边界完整性（25%）

**代码坏味道：** "模糊模块边界（Fuzzy Module Boundary）"——物理场模块职责边界不清，对外暴露过多内部实现细节，模块之间通过非接口方式直接访问内部数据结构。

**检测方法：**
- 扫描 CMakeLists.txt/Makefile 识别独立编译目标和源目录（如 `src/solvers/structural/`）
- 统计分析各模块导出的公开 API 数量（符号表、头文件声明数）
- 检测各模块是否包含独立 MMS 验证基准文件（`*_mms*`、`*_verification*`）
- 检测跨模块直接访问内部数据结构的代码模式
- 检测 FMI/FMU 模型交换接口（加分项）

**评分算法：**

```
score = 0

# 1. 独立编译单元检测（20 分）
if 每个物理场模块有独立源目录 AND 独立 CMake 目标:
    score += 20

# 2. 公开 API 精简度（20 分）
module_api_count = 各模块导出的公开函数平均数
if module_api_count <= 50:
    score += 20
elif module_api_count <= 100:
    score += 10
else:
    score += 5

# 3. MMS 验证基准存在性（30 分）
if 每个模块有 MMS/verification 目录或文件:
    score += 30
elif 至少一个模块有:
    score += 15

# 4. 内部数据结构封装性（30 分）
跨模块直接成员访问数 = count_cross_module_direct_access()
if 跨模块直接成员访问数 == 0:
    score += 30
elif 跨模块直接成员访问数 <= 3:
    score += 20
elif 跨模块直接成员访问数 <= 10:
    score += 10

# 5. FMI 模型交换模式加分（+10 分，可选）
if 检测到 FMI/FMU 接口实现:
    score = min(score + 10, 110)

result = min(score, 100)
```

> **参考：** 指南 §2.1，案例集 §1。

### 2.2 多物理场耦合架构合理性（30%）

**代码坏味道：** "散射耦合逻辑（Scattered Coupling Logic）"——多物理场之间的耦合逻辑散落在各求解器文件中，而非集中在独立的耦合层。

**检测方法：**
- 根据数据交换频率、方向、刚度矩阵结构判定耦合强度（强/中/弱）
- 检测耦合逻辑是否集中在独立耦合层模块中
- 检测求解算法是否可通过接口替换（抽象基类 + 多实现）
- 检测迭代收敛控制参数（residual、tolerance 等）
- 检测 FMI 标准耦合接口的实现
- 检测 ASME V&V 10 系统层级验证文档或测试

**评分算法：**

```
score = 0

# 1. 耦合架构与耦合强度匹配度（20 分）
coupling_strength = judge_coupling_strength()  # strong/medium/weak
architecture_type = detect_coupling_architecture()  # monolithic/ partitioned_iterative/ partitioned_loose/ fully_loose
if matches_expected_architecture(coupling_strength, architecture_type):
    score += 20

# 2. 耦合逻辑集中度（20 分）
if 耦合逻辑集中在独立耦合层模块中:
    score += 20
elif 耦合逻辑分散在 2-3 个文件中:
    score += 10

# 3. 求解算法可替换性（15 分）
if 检测到抽象求解器基类 + 多实现:
    score += 15

# 4. 迭代收敛稳定性（15 分）
if 检测到收敛控制参数 (residual/tolerance/relative_tolerance):
    score += 15

# 5. 标准耦合接口支持度（15 分）
if 检测到 FMI 标准接口或类似标准化耦合接口:
    score += 15

# 6. 系统层级验证完整性（15 分）
if 检测到系统级验证测试或 V&V 文档:
    score += 15
```

> **参考：** 指南 §2.2，案例集 §2。

### 2.3 插件式扩展架构支持度（25%）

**代码坏味道：** "碎片化插件机制（Fragmented Plugin Mechanism）"——不同物理场模块通过不同机制集成到系统中，缺乏统一的插件接口规范。

**检测方法：**
- 检测是否存在统一的插件注册机制（目录扫描、注解、配置文件）
- 检测模块依赖关系是否形式化管理（依赖声明文件、接口定义）
- 检测依赖图中是否存在循环依赖
- 检测接口版本管理机制（`@deprecated` 注解、版本号规范）

**评分算法：**

```
score = 0

# 1. 标准接口动态加载（30 分）
if 检测到统一插件注册机制:
    score += 30

# 2. 依赖关系形式化（25 分）
if 检测到显式依赖声明（CMake target_link_libraries 或类似机制）:
    score += 25

# 3. 无循环依赖（25 分）
cycles = detect_cross_module_cycles()
if len(cycles) == 0:
    score += 25
elif len(cycles) <= 2:
    score += 10

# 4. 接口版本管理（20 分）
if 检测到 @deprecated/@Deprecated 注解使用 AND 版本号规范:
    score += 20
elif 检测到版本号规范:
    score += 10
```

**递进扣分规则**（指南 §2.3）：若 §2.1 边界完整性得分 < 60，本维度得分自动折半。

```
if 边界完整性得分 < 60:
    score = score * 0.5
```

> **参考：** 指南 §2.3，案例集 §3。

### 2.4 跨场数据传递规范性（20%）

**代码坏味道：** "混沌数据交换（Chaotic Data Exchange）"——物理场之间的场数据传递路径不统一，格式转换逻辑散落在各处。

**检测方法：**
- 检测是否使用统一的数据结构（Field/Data 基类）进行跨模块数据传递
- 检测是否支持 FMI 协同仿真标准数据交换
- 检测数据格式转换逻辑是否集中在统一转换模块中
- 检测时间同步机制是否规范（统一时间步、子循环、异步）
- 检测空间映射架构是否独立
- 检测时间步协调策略是否合理

**评分算法：**

```
score = 0

# 1. 标准化数据结构（20 分）
if 检测到统一 Field/Data 数据结构:
    score += 20

# 2. FMI 协同仿真数据传递（15 分）
if 检测到 FMI 协同仿真接口实现:
    score += 15

# 3. 数据格式转换统一性（20 分）
if 数据格式转换集中在统一转换模块中:
    score += 20
elif 分散在 2-3 个文件中:
    score += 10

# 4. 时间同步机制规范性（15 分）
if 检测到统一时间步管理或显式时间同步策略:
    score += 15

# 5. 空间映射架构独立性（15 分）
if 空间映射逻辑集中在独立映射模块中:
    score += 15

# 6. 时间步协调策略合理性（15 分）
if 检测到时间步协调策略（统一步长/子循环/异步）:
    score += 15
```

**FMI 合规性加分**（最多 +5 分，不超 100）：

| 检查项 | 检测方法 | 分值 |
|:-------|----------|:----:|
| FMU 包含 `modelDescription.xml` | zipfile 解包检查 | +2 |
| 实现必要 FMI 函数（fmi2DoStep 等） | 函数名检测 | +2 |
| 多 FMU 接口一致性 | 接口签名对比 | +1 |

```
# FMI 合规加分
fmi_bonus = check_fmi_compliance()
score = min(score + fmi_bonus, 100)
```

> **参考：** 指南 §2.4，案例集 §4。

```
模块化架构综合分 =
    物理场模块边界完整性 × 25% +
    多物理场耦合架构合理性 × 30% +
    插件式扩展架构支持度 × 25% +
    跨场数据传递规范性 × 20%
```

## 五、12 条 MPR 规则

每条规则包含：编号、名称、output_level、severity、代码坏味道描述、检测方法、豁免可能性。

| 规则 | 名称 | output_level | severity | 代码坏味道 | 豁免 | 指南§ | 案例集§ |
|:-----|:------|:------------:|:--------:|:-----------|:----:|:-----:|:-------:|
| MPR-001 | 物理场模块边界识别 | **ERROR** | HIGH | 多物理场求解器在同一编译单元中 | 否 | §5.1 | §1.1 |
| MPR-002 | 模块公开接口精简度 | **WARNING** | MEDIUM | 模块导出 > 50 个公开接口/符号 | 否 | §5.2 | §1.2 |
| MPR-003 | 模块数值验证基准完备性 | **ERROR** | HIGH | 缺少 MMS 验证文件或目录 | 否 | §5.3 | §1.3 |
| MPR-004 | 耦合架构模式判定 | **WARNING** | MEDIUM | 强耦合使用松散架构，或反之 | 否 | §5.4 | §2.1 |
| MPR-005 | 耦合逻辑集中度 | **WARNING** | HIGH | 耦合逻辑分散在各求解器文件中 | 否 | §5.5 | §2.2 |
| MPR-006 | 迭代收敛稳定性 | **WARNING** | MEDIUM | 缺少收敛控制或迭代误差参数 | 否 | §5.6 | §2.3 |
| MPR-007 | 插件扩展完整性 | **WARNING** | HIGH | 缺乏统一插件接口或注册机制 | 否 | §5.7 | §3.1 |
| MPR-008 | 跨模块依赖关系 | **ERROR** | MEDIUM | 模块间依赖图中存在循环依赖 | 否 | §5.8 | §3.2 |
| MPR-009 | 接口版本管理 | **WARNING** | MEDIUM | 接口变更未使用版本号/废弃标注 | 否 | §5.9 | §3.3 |
| MPR-010 | 跨场数据传递标准化 | **WARNING** | MEDIUM | 缺乏统一 Field/Data 数据结构 | 是 | §5.10 | §4.1 |
| MPR-012 | 数据格式转换统一性 | **INFO** | LOW | 数据格式转换逻辑散落各处 | 否 | §5.12 | §4.3 |

**注意**：output_level 与 severity 解耦（与模板 MLR 体系一致）。置信度标注见指南 §2.x 各节。

### 规则详细描述

#### MPR-001：物理场模块边界识别

- **severity**：HIGH
- **置信度**：高
- **问题**：识别物理场求解器模块是否以独立编译单元形式存在。
- **检测逻辑**：
  1. 扫描项目构建配置（CMakeLists.txt、Makefile）识别独立目标
  2. 检查各物理场模块是否有独立源目录（如 `src/solvers/structural/`）
  3. 若多个物理场求解器在同一编译单元中，触发告警
- **置信度说明**：构建配置解析可靠；目录结构识别存在一定规则假设，综合置信度为**高**。
- **改进建议**：将各物理场模块划分为独立编译单元，通过标准接口通信。

#### MPR-002：模块公开接口精简度

- **severity**：MEDIUM
- **置信度**：高
- **问题**：模块对外暴露的公开 API 数量是否精简合理。
- **检测逻辑**：
  1. 统计各模块导出的公开函数/符号数量（默认阈值 50）
  2. 若超出阈值，检查是否导出了大量内部实现函数
  3. 超出阈值时触发告警
- **置信度说明**：符号表统计为精确计数；50 阈值为经验值，置信度为**高**。
- **改进建议**：仅暴露必要的公开接口，内部实现使用匿名命名空间或私有封装。

#### MPR-003：模块数值验证基准完备性

- **severity**：HIGH
- **置信度**：中
- **问题**：各物理场模块是否具备独立的 MMS 验证基准。
- **检测逻辑**：
  1. 检查各模块的测试目录下是否存在 `*_mms*`、`*_verification*` 模式的文件
  2. 若某模块完全缺少验证基准文件，触发告警
- **置信度说明**：文件名模式匹配可能漏检非常规命名，置信度为**中**。
- **改进建议**：为各物理场模块建立独立的 MMS 验证基准套件。

#### MPR-004：耦合架构模式判定

- **severity**：MEDIUM
- **置信度**：中低
- **问题**：耦合架构模式选择是否与耦合强度匹配。
- **检测逻辑**：
  1. 通过数据分析模式判断耦合强度（强/中/弱）
  2. 通过代码模式识别耦合架构类型（monolithic/partitioned-iterative/partitioned-loose/fully-loose）
  3. 若强耦合使用松散架构（fully-loose），或弱耦合使用 monolithic，触发告警
- **置信度说明**：架构模式判断依赖启发式规则，存在边界情况，置信度为**中低**，**需人工确认**。

#### MPR-005：耦合逻辑集中度（合并原 MPR-011）

- **severity**：HIGH
- **置信度**：高
- **问题**：多物理场耦合逻辑是否集中在独立耦合层中。
- **检测逻辑**：
  1. 分析跨物理场的数据访问和函数调用关系
  2. 统计耦合逻辑在各文件中的分布情况
  3. 若耦合逻辑高度分散（非集中耦合层），触发告警
- **跨维度扣分**：同时影响耦合架构合理性（50%）和数据传递规范性（50%），不重复扣分。
- **置信度说明**：文件级调用分布可精确统计，置信度为**高**。
- **改进建议**：将耦合逻辑抽取到独立耦合层模块，各物理场通过标准接口与耦合层交互。

#### MPR-006：迭代收敛稳定性

- **severity**：MEDIUM
- **置信度**：中
- **问题**：迭代求解器缺少收敛控制或误差累积风险。
- **检测逻辑**：
  1. 检测是否配置了 residual/tolerance 等收敛参数
  2. 检查是否设置了合理的迭代次数上限
  3. 检测是否有误差累积放大风险（迭代步数 > 100 且精度 < 1e-12）
- **置信度说明**：参数存在性可检测，但参数合理性需要人工评估，置信度为**中**。

#### MPR-007：插件扩展完整性

- **severity**：HIGH
- **置信度**：高
- **问题**：是否具备统一的插件机制来支持新物理场模块的动态加入。
- **检测逻辑**：
  1. 检测是否存在插件注册机制（目录扫描、配置文件、注解等）
  2. 检测是否存在统一的插件接口定义
  3. 若缺乏统一接口或注册机制，触发告警
- **置信度说明**：代码模式和接口定义可精确检测，置信度为**高**。

#### MPR-008：跨模块依赖关系

- **severity**：MEDIUM
- **置信度**：高
- **问题**：模块间的依赖关系是否形式化管理和无循环。
- **检测逻辑**：
  1. 构建模块间依赖图
  2. 使用图算法检测是否存在循环依赖
  3. 若存在循环依赖，触发告警
- **置信度说明**：图分析为基础算法，结果精确，置信度为**高**。

#### MPR-009：接口版本管理

- **severity**：MEDIUM
- **置信度**：中
- **问题**：模块接口变更时是否使用版本号和废弃标注。
- **检测逻辑**：
  1. 检测接口定义中是否包含版本号信息
  2. 检测 `@deprecated`、`@Deprecated` 注解的使用
  3. 若接口未使用版本号且无废弃标注，触发告警
- **置信度说明**：注解检测可靠；版本号规范检测依赖模式匹配，置信度为**中**。

#### MPR-010：跨场数据传递标准化

- **severity**：MEDIUM
- **置信度**：中
- **问题**：物理场之间的场数据是否通过标准化数据结构传递。
- **检测逻辑**：
  1. 检测是否使用统一的 Field/Data 数据结构
  2. 检测不同物理场间是否使用相同数据结构进行交换
  3. 若使用自定义非标准化数据结构，触发告警
- **置信度说明**：基类使用情况可检测，但自定义结构的识别力不完全，置信度为**中**。

#### MPR-012：数据格式转换统一性

- **severity**：LOW
- **置信度**：低
- **问题**：数据格式转换逻辑是否集中在统一转换模块中。
- **检测逻辑**：
  1. 识别数据格式转换的代码位置
  2. 分析转换逻辑是否集中在统一转换层
  3. 若转换逻辑散落在各处，触发建议
- **置信度说明**：转换逻辑识别依赖模式匹配，漏检风险较高，置信度为**低**。

## 六、跨规则协调

### 6.1 MPR-005 跨维度扣分

MPR-005（耦合逻辑集中度）同时影响两个评估维度：
- 多物理场耦合架构合理性（50%）
- 跨场数据传递规范性（50%）

扣分规则：不重复扣分，每个维度各扣 50%。

### 6.2 MPR-001 → MPR-003 关联检测

模块边界模糊（MPR-001）往往伴随缺乏独立验证基准（MPR-003）：
- 若 MPR-001 触发 → 建议同时检查 MPR-003
- 若 MPR-003 触发但 MPR-001 未触发 → 虽边界清晰但验证缺失

### 6.3 MPR-004/MPR-006 与数值精度指南的边界

MPR-006（迭代收敛稳定性）关注系统级耦合算法的收敛性，与数值精度指南 NVR-007/NVR-008（关注单物理场计算级）互补：
- 系统级（本指南）：耦合算法的迭代收敛和误差累积
- 节点级（数值精度指南）：单物理场离散误差和迭代误差

### 6.4 MPR-FMI → MPR-004 协调

若项目使用 FMI 标准实现耦合，则 MPR-004 的耦合架构模式判定自动降级：
- FMI 实现自动满足"标准耦合接口支持度"子项（15 分）
- 但 FMI 不保证架构模式选择正确性，MPR-004 仍需人工确认

## 七、基线校准

### 7.1 校准方法

与模板元编程 skill §8.1 一致的统计校准流程：

```
1. 收集验证案例集的阳性案例（通过）的评分数据
2. 收集阴性案例（违规）的评分数据
3. 计算阳性案例评分分布的 5% 分位数作为及格线
4. 计算阳性案例评分分布的均值作为基准分
5. 验证阴性案例的评分是否全部低于及格线
```

## 八、豁免注解体系

### 8.1 注解类型

| 注解 | 适用规则 | 必填字段 | 说明 |
|:-----|:--------|:---------|:------|
| `@custom_data_structure` | MPR-010 | `reason`, `alternative_method`, `test_script`, `threshold` | 使用自定义数据结构的豁免声明 |
| `@coherence_approved` | MPR-004 | `reason`, `architecture_type`, `verification_case` | 耦合模式偏离但经评审通过的声明 |

### 8.2 `@custom_data_structure` 格式

```
@custom_data_structure(
    reason = "性能优化需要，统一 Field 结构无法满足 GPU 计算要求",
    alternative_method = "通过自定义 DeviceField 结构 + 显式转换函数集",
    test_script = "tests/data_transfer/device_field_test.py",
    threshold = "max_conversion_error < 1e-10"
)
```

### 8.3 验证规则

- 豁免注解必须包含所有必填字段，缺失任一字段 → output_level 不降级
- 字段值为空 → 视为缺失
- 豁免注解仅在同文件内生效，跨文件引用不作用
