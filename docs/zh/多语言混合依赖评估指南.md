# 多语言混合依赖评估指南（非优化版）

> 本指南参照 `SOFTWARE_ARCHITECTURE_QUALITY_GUIDE.md` 的结构编写，定义了一套专门用于评估多语言混合依赖的架构质量指标体系。适用于 CAD/CAE/CAx 等工业软件中 C++/Python/Fortran/Tcl 等多语言混合的场景。

---

## 概述

**多语言混合依赖**是指软件系统中不同编程语言编写的组件之间通过语言绑定、外部函数接口（FFI）、进程间通信或共享数据格式所形成的调用、数据传递或控制流关系。在工业软件（CAD/CAE/CAx）中，C++/Python/Fortran/Tcl 等多语言混合是常态，但传统架构质量评估模型（ISO 25010、CK度量集）未提供针对性的量化指标。

本指南作为《软件架构质量评估指南》的补充，定义了一套专门针对多语言混合依赖的评估指标。这些指标可纳入**结构质量**中的耦合度子维度（建议权重占结构质量的10%~15%），也可作为工业软件场景下的独立评估项。

**评估目标**：量化跨语言耦合带来的可维护性风险，识别绑定层不一致、跨语言循环依赖、FFI内存不安全等架构债务。

---

## 一、子维度与权重分配

多语言混合依赖评估由以下6个子维度加权合成：

| 子维度 | 权重 | 对应风险类型 |
|--------|------|-------------|
| 跨语言调用强度 | 15% | 过度频繁的跨语言交互导致性能与稳定性下降 |
| 跨语言影响半径 | 20% | 变更波及范围过大，回归测试成本高 |
| 跨语言回调深度 | 10% | 过深调用链导致调试困难、栈溢出风险 |
| 绑定层接口一致性 | 25% | 接口定义与绑定实现不同步，运行时崩溃 |
| 脚本越界访问 | 15% | 脚本越过防腐层直接依赖内部实现，升级困难 |
| 跨语言循环依赖 | 15% | 多种语言之间的调用环，导致紧耦合与死锁风险 |

**权重设计依据**：
- 绑定层接口一致性权重最高（25%），因为它是多语言项目中最常见且后果最严重的问题（修改C++接口后Python绑定未更新，直接导致运行时异常）。
- 影响半径（20%）次之，反映了架构模块化的核心诉求——变更影响范围应可控。
- 跨语言循环依赖（15%）虽然严重，但在工业软件中可通过架构设计避免，因此略低于前两者。
- 调用深度（10%）权重最低，因为其实际危害相对较小，且通常可通过重构缓解。

## 二、子维度定义与评分算法

### 2.1 跨语言调用强度

**定义**：衡量单个模块（文件/类/函数）参与跨语言调用的频繁程度。高强度的模块往往是系统中最脆弱的节点，因为任何跨语言边界都是潜在的错误源。

**设计依据**：
- 实证研究显示，跨语言依赖的错误密度是单语言依赖的3倍（*On the Impact of Interlanguage Dependencies*，IEEE T. Reliability）。
- 模块的扇入/扇出跨语言版本是耦合度的直接量化。

**评分算法**：
```
let L = 模块的跨语言调用总数（出边+入边，仅计数跨语言边）
if L == 0: score = 100
else if L <= 2: score = 80
else if L <= 5: score = 60 - (L-3)*5   # 60,55,50...
else if L <= 10: score = 40 - (L-6)*4  # 40,36,32,28,24
else: score = max(0, 20 - (L-11)*2)
```
**阈值说明**：0次为最佳；1-2次为可接受；3-5次需关注；>5次需重构隔离。

**代码坏味道：热耦合（Hot Cross?Language Coupling）**

- **描述**：某个模块（文件、类、函数）与另一种语言之间的跨语言调用次数过多，形成“热点”。这类模块成为系统中极度脆弱的高频交互节点，任何微小改动都可能引发连锁故障。
- **典型表现**：
  - 一个C++函数被超过10个不同的Python模块直接调用。
  - 一个Python脚本在循环中反复调用C++函数（如每帧数千次），导致性能瓶颈。
  - 绑定层代码充斥大量重复的`def(...)`注册，且缺乏抽象。
- **检测示例**：
  ```python
  # 分析依赖图：Python模块A、B、C、D、E、F都调用了同一个C++函数 `computeStress`
  # 若调用者数量 > 阈值（如5），触发“热耦合”警告。
  ```
- **危害**：
  - 任何修改C++函数的行为都需要同时修改所有依赖它的Python调用方，回归测试成本极高。
  - 跨语言调用本身有编组/解组开销，热点模块易成为性能瓶颈。
  - 违反“高内聚、低耦合”原则，模块实际上已成为多个无关功能的汇聚点。

---

### 2.2 跨语言影响半径

**定义**：当修改一个模块（如C++函数）时，通过跨语言依赖图间接影响的模块数量（包括同语言和不同语言的模块）。影响半径越大，变更风险越高。

**设计依据**：
- ISO 25010可修改性（Modifiability）要求“变更对现有组件的影响最小化”。
- 工业经验表明，跨语言影响半径超过10的模块往往导致“牵一发而动全身”。

**评分算法**：
```
R = 从该模块出发，沿跨语言边（可跨语言后继续同语言）可达的模块数量（BFS深度≤5，避免无限传播）
if R == 0: score = 100
else if R <= 3: score = 90
else if R <= 7: score = 70
else if R <= 15: score = 40
else: score = max(0, 30 - (R-15)*2)
```
**注意**：测试文件和示例代码不计入R，以降低噪声。

**代码坏味道：炸药模块（TNT Module）**

- **描述**：一个模块（尤其是基础库）被大量其他语言模块直接或间接依赖，导致其变更的“爆炸半径”极大。此坏味道是传统“上帝模块”在多语言场景下的演变。
- **典型表现**：
  - 一个C++数学工具函数被Python、Fortran、Tcl等几乎所有上层模块调用。
  - 修改该函数后，需要同步更新绑定代码、脚本调用逻辑、甚至下游的Fortran调用点，影响范围超过15个模块。
- **检测示例**：
  ```bash
  # 从依赖图中计算影响半径
  impact_radius(utils_math.cpp) = 23   # 修改它可能影响23个其他模块
  # 若 > 10 触发“炸药模块”警告
  ```
- **危害**：
  - 团队不敢轻易修改该模块，即使是性能优化或错误修复也需全员评审。
  - 技术债务逐年累积，最终该模块变成“不可触碰”的遗产代码。
  - 违背开闭原则（OCP），对扩展封闭，对修改却极端开放。

---

### 2.3 跨语言回调深度

**定义**：跨语言调用链中连续跨语言跳转的最大次数（例如：Python → C++ → Fortran 深度为2）。深度越大，调用链的可理解性和可调试性越差。

**设计依据**：
- 软件工程中的“回调地狱”（Callback Hell）反模式在多语言场景下同样成立。
- 深度超过3的调用链往往涉及复杂的同步问题（如Python GIL嵌套C++线程再回调Python）。

**评分算法**：
```
D_max = 项目中所有从根到叶的跨语言调用链的最大深度（仅统计连续跨语言边）
if D_max <= 1: score = 100
else if D_max == 2: score = 80
else if D_max == 3: score = 50
else: score = 20
```
**说明**：深度1表示仅有单层跨语言调用（如Python直接调用C++库），这是合理且常见的。深度2为可接受但需评审。深度≥3应重构为异步消息或减少边界层。

**代码坏味道：跨语言回调地狱（Callback Hell Across Languages）**

- **描述**：调用链在多种语言之间来回穿梭，形成极长的逻辑路径。常见于GUI事件、异步I/O或多物理场耦合中，导致调试和测试几乎不可行。
- **典型表现**：
  - Python工作台调用C++内核，C++内核又通过回调调用Python的Lambda，Lambda再触发Fortran数值子程序。
  - 调用深度 ≥ 4，且每次跳转都需要编组/解组数据，异常栈混乱。
- **检测示例**：
  ```
  调用链：Python:start() → C++:run() → Python:callback() → Fortran:solver()
  连续跨语言跳转次数 = 3 → 触发“跨语言回调地狱”警告
  ```
- **危害**：
  - 错误栈跨越多种运行时，堆栈信息支离破碎，开发者无法快速定位问题。
  - 资源管理复杂（如Python GIL在C++线程中回调Python容易死锁）。
  - 违反迪米特法则（最少知识原则），每个层级都需要知道下一层级的实现细节。

---

### 2.4 绑定层接口一致性

**定义**：衡量自动或手动生成的绑定代码（如pybind11、SWIG、ctypes）与原生语言（C++/Fortran）接口定义的同步程度。不一致会导致运行时`AttributeError`、参数错误或内存损坏。

**设计依据**：
- FreeCAD历史问题追踪表明，80%的跨语言缺陷源于绑定层未随C++接口更新。
- 该指标是工业软件架构治理的实际痛点。

**评分算法**：
```
total_exports = 对外暴露的原生接口数量（如C++类的公共方法）
bound_exports = 绑定代码中实际注册的接口数量
matched_signatures = 绑定接口签名与原生接口完全匹配的数量（参数类型、顺序、const修饰）

ratio_bound = bound_exports / total_exports
ratio_match = matched_signatures / bound_exports

score = (ratio_bound * 100 + ratio_match * 100) / 2
```
**扣分项**：若存在绑定接口使用了`void*`或`any`绕过类型检查，每处额外扣5分（上限20分）。

**代码坏味道：绑定漂移（Binding Drift）**

- **描述**：原生语言（C++/Fortran）的接口定义与绑定层（pybind11/SWIG/ctypes）暴露的接口逐渐失步，就像两个独立演化的副本。这是多语言项目中最常见、危害最大的坏味道。
- **典型表现**：
  - C++增加了新函数，但Python绑定未注册 → Python代码调用时报`AttributeError`。
  - C++函数修改了参数默认值，绑定代码未同步 → Python调用时参数数量不匹配。
  - C++函数重构了异常类型，绑定仍按旧异常捕获 → 异常传播错误导致程序崩溃。
- **检测示例**：
  ```cpp
  // C++ 头文件
  double compute(double a, double b = 1.0);
  ```
  ```python
  # Python 绑定（错误：默认参数丢失）
  m.def("compute", &compute);
  ```
  检测工具通过对比签名，发现`compute`在Python中丢失默认参数 → 触发“绑定漂移”警告。
- **危害**：
  - 运行时错误，且通常在压力测试或生产环境才暴露。
  - 降低了动态语言的便利性（本应灵活的Python接口变得脆弱）。
  - 严重拖累持续集成：C++接口变更后，相关Python测试大面积失败。

### 2.5 脚本越界访问

**定义**：在采用脚本语言（Python、Tcl、Lua）作为上层控制层的架构中，衡量脚本代码是否越过预设的API边界，直接依赖引擎内部实现（如全局变量、未导出的C函数）。违规越紧密，引擎重构越困难。

**设计依据**：
- BRL-CAD的Tcl脚本直接访问C引擎的`struct`成员，导致引擎升级需要修改数千个脚本。
- 防腐层模式（Anti-Corruption Layer）是领域驱动设计中的核心模式。

**评分算法**：
```
total_script_calls = 脚本中调用引擎的总次数
direct_access = 脚本中直接引用引擎内部符号的次数（通过正则匹配：全局变量、未通过API包装的函数）
violation_ratio = direct_access / total_script_calls

score = 100 - violation_ratio * 200   # 每1%违规扣2分，上限扣100分
```
**检测示例**：
- 合规：`engine_api.create_box(x, y, z)`
- 违规：`engine_internal.global_box_count` 或直接调用`_internal_func`

**代码坏味道：越狱脚本（Jailbreak Script）**

- **描述**：脚本语言（Python/Tcl/Lua）直接越过预设的API防腐层，访问引擎内部的全局变量、未导出的函数或私有数据结构。就像越狱一样绕过安全门。
- **典型表现**：
  - Tcl脚本直接读取C引擎的全局`struct`成员，而不是通过getter/setter。
  - Python使用`ctypes`调用一个以下划线开头的内部C函数（约定表示私有）。
  - Lua脚本通过内嵌C指针操作引擎的内部缓冲区。
- **检测示例**：
  ```tcl
  # 违规：直接访问C全局变量
  set count $::engine::global_counter
  ```
  ```python
  # 违规：绕过API调用内部函数
  lib = ctypes.CDLL("engine.so")
  lib._internal_reset_cache()   # 以下划线开头
  ```
  正则匹配`\$_internal_`、`::engine::`等模式 → 触发“越狱脚本”警告。
- **危害**：
  - 防腐层形同虚设，引擎内部重构必然导致无数脚本崩溃（BRL-CAD的历史教训）。
  - 安全性漏洞：脚本可能破坏引擎的不变量。
  - 锁定实现细节，阻碍技术创新（如替换底层求解器）。

---

### 2.6 跨语言循环依赖

**定义**：依赖图中存在涉及至少两种语言的循环（A语言模块调用B语言模块，B语言模块直接或间接调用回A语言模块）。这种循环打破了模块化，导致难以独立测试和部署。

**设计依据**：
- 架构坏味中的“循环依赖”在多语言场景下危害放大，因为无法通过单一语言的编译器检测。
- 学术研究发现，跨语言循环依赖与缺陷率显著正相关。

**评分算法**：
```
cycles = 检测到的所有跨语言循环依赖的数量（每个强连通分量计为一个循环）
cycle_length_sum = 所有循环的长度（节点数）之和
severity = min(100, cycles * 10 + cycle_length_sum * 2)
score = max(0, 100 - severity)
```
**补充规则**：
- 若存在任何循环，在报告中列出循环路径，并标记最高优先级修复建议。
- 若不存在循环，得100分。

**代码坏味道：多语言面条依赖（Multilingual Spaghetti）**

- **描述**：依赖图在不同语言之间形成循环，例如Python模块A调用C++模块B，C++模块B回调Python模块A，或者更长链条：Python→C++→Fortran→Python。这种依赖彻底破坏了模块化。
- **典型表现**：
  - 求解器A（C++）调用求解器B（Fortran），B又回调A的C++回调函数。
  - Python工作台注册一个C++监听器，C++监听器在事件中调用工作台的Python方法。
- **检测示例**：
  ```
  依赖环：Python:DataProcessor → C++:Solver → Fortran:LinAlg → Python:DataProcessor
  该环涉及3种语言 → 触发“多语言面条依赖”警告
  ```
- **危害**：
  - 无法独立编译、测试或部署任何一个模块（因为循环导致静态链接或动态加载死锁）。
  - 理解成本极高，新成员需要同时掌握多种语言和架构全景。
  - 循环中任何一个模块的错误都可能辐射整个环，缺陷修复极其困难。

## 三、多语言混合依赖综合分

```
多语言混合依赖综合分 = 
    跨语言调用强度 × 15% +
    跨语言影响半径 × 20% +
    跨语言回调深度 × 10% +
    绑定层接口一致性 × 25% +
    脚本越界访问 × 15% +
    跨语言循环依赖 × 15%
```

该综合分可作为**结构质量**中耦合度指标的扩展项，在工业软件场景下建议权重占结构质量总分的15%（即结构质量综合分 = 原5项加权平均 × 85% + 多语言混合依赖综合分 × 15%）。对于纯单语言项目，可忽略此维度。

|---------|------|------|----------|

## 五、内置规则

为支撑上述指标的自动化评估，本指南预定义以下 **12 条核心检测规则**。规则采用 `MLR-XXX`（Multi?Language Rule）编号体系，可按严重级别（HIGH/MEDIUM/LOW）分类管理。

### 规则清单总览

| 规则ID | 名称 | 对应子维度 / 坏味道 | 严重级别 |
|--------|------|-------------------|---------|
| MLR-001 | 跨语言循环依赖检测 | 跨语言循环依赖 / 多语言面条依赖 | **HIGH** |
| MLR-001b | 同语言模块级循环检测 | 跨语言循环依赖（同语言回退） | **MEDIUM/INFO** |
| MLR-002 | 绑定层接口缺失 | 绑定层接口一致性 / 绑定漂移 | **HIGH** |
| MLR-003 | 绑定层签名不匹配 | 绑定层接口一致性 / 绑定漂移 | **HIGH** |
| MLR-004 | 脚本层直接访问引擎内部 | 脚本越界访问 / 越狱脚本 | **HIGH** |
| MLR-004b | Tcl命名空间直接访问内部 | 脚本越界访问（Tcl） | **MEDIUM/INFO** |
| MLR-005 | 跨语言回调深度过大 | 跨语言回调深度 / 回调地狱 | **MEDIUM** |
| MLR-006 | 热耦合模块 | 跨语言调用强度 / 热耦合 | **MEDIUM** |
| MLR-007 | 炸药模块（影响半径过大） | 跨语言影响半径 / 炸药模块 | **MEDIUM** |

### 规则详细描述

#### MLR-001：跨语言循环依赖检测

- **严重级别**：HIGH
- **描述**：检测依赖图中是否存在涉及至少两种语言的循环。例如：Python → C++ → Python，或 Python → C++ → Fortran → Python。
- **检测逻辑**：
  1. 构建统一依赖图（节点 = 函数/模块，边 = 调用，边属性包含源语言和目标语言）。
  2. 计算强连通分量（SCC），若SCC内节点数 ≥ 2 且至少有一条跨语言边，则标记为循环。
  3. 输出循环路径（如 `py:mod_a.func1 → cpp:mod_b.func2 → cpp:mod_b.func3 → py:mod_a.func4`）。
- **建议修复**：
  - 将循环中的一个调用改为异步消息（队列/事件），或使用回调反转方向。
- 提取共同依赖的接口，放入第三种语言的共享库，打破直接循环。
- **评分影响**：违反此规则导致"跨语言循环依赖"子维度得分直接扣除30分（或按循环个数累加）。

#### MLR-001b：同语言模块级循环检测

- **严重级别**：MEDIUM（非第三方路径）/ INFO（第三方路径）
- **描述**：检测依赖图中同一语言内部的模块级循环依赖。此规则是MLR-001的补充，用于单语言回退场景（如Fortran `use ModuleA` → `ModuleA` → `ModuleB` → `ModuleA`），或跨语言边不足以触发MLR-001时。
- **检测逻辑**：
  1. 使用 `DepGraph.detect_same_lang_cycles(lang)` 检测指定语言内的强连通分量。
  2. 对于Fortran：解析 `use ModuleName` 和 `call SubName` 构建模块间依赖图，通过3层映射（模块声明→文件、子程序声明→文件、文件名回退）解析。
  3. 非第三方路径的循环标记为MEDIUM，第三方路径（如 `is_third_party_path()` 命中）标记为INFO。
- **建议修复**：使用 `@allowed_coupling ModuleName` 注解标记合理的循环依赖（如多物理场耦合），工具将自动降级为INFO。

#### MLR-002：绑定层接口缺失

- **严重级别**：HIGH
- **描述**：C++ / Fortran 中对外公开的接口（函数、类方法）在绑定代码（pybind11/SWIG/ctypes）中没有对应的注册。
- **检测逻辑**：
  1. 解析 C++ 头文件（或 Fortran 模块），提取所有 `public` 且非 `static` 的函数/方法，生成集合 `N_native`。
  2. 解析绑定文件（`.cpp` 中的 `PYBIND11_MODULE`、`.i` 中的 `%include`、`.py` 中的 `CDLL` 赋值），提取注册的接口名 `N_bound`。
  3. 若 `N_native - N_bound` 非空，则对每个缺失接口发出警告。
- **建议修复**：在绑定代码中添加对应的 `.def(...)` 或 `%feature` 声明。
- **例外**：明确标记 `// BINDING_EXCLUDE` 或 `__attribute__((annotate("no_bind")))` 的接口可忽略。

#### MLR-003：绑定层签名不匹配

- **严重级别**：HIGH
- **描述**：绑定的函数签名（参数类型、数量、默认值、返回值、const 修饰）与原生定义不一致。
- **检测逻辑**：
  1. 对每个已绑定的接口，获取其原生签名（通过 Clang AST 或 Fortran 解析器）。
  2. 获取绑定签名（解析 pybind11 的 `.def` 参数、SWIG 的类型映射等）。
  3. 对比以下元素：参数个数、参数类型（基本类型、指针、引用）、默认值存在性、返回值类型、const 修饰。
  4. 任何差异触发警告。
- **建议修复**：
  - 使用 `py::arg("name") = default_value` 显式声明默认参数。
  - 确保 `const` 成员函数绑定为 `.def`（而非 `.def_readwrite`）。
- **示例**：
  ```cpp
  // C++
  void set(int x, double y = 1.0);
  // 错误绑定
  m.def("set", &set);   // 丢失默认参数
  // 正确绑定
  m.def("set", &set, py::arg("x"), py::arg("y") = 1.0);
  ```

#### MLR-004：脚本层直接访问引擎内部

- **严重级别**：HIGH
- **描述**：脚本语言（Python/Tcl/Lua）代码直接引用引擎的内部符号（以下划线开头的函数、全局变量、未导出的结构体），绕过API防腐层。
- **检测逻辑**：
  - 对 Python：扫描 `.py` 文件，检测 `ctypes.CDLL` 调用中是否使用以下划线开头的符号（如 `_internal_func`），或直接访问 `module._private_var`。
  - 对 Tcl：检测 `::engine::` 后跟内部变量名，或 `$engine_global` 模式。
  - 对 Lua：检测 `ffi.C.engine_` 内联访问。
- **建议修复**：
  - 将所有内部访问迁移到官方 API 函数。
  - 如果必须保留，封装为一个稳定的“后门”模块并明确标注风险。
- **评分影响**：每处违规扣除脚本越界访问得分的2%（上限20%）。

#### MLR-004b：Tcl命名空间直接访问内部

- **严重级别**：MEDIUM（非第三方路径）/ INFO（第三方路径或白名单命名空间）
- **描述**：Tcl脚本通过 `::namespace::variable` 模式直接访问引擎内部命名空间，绕过API防腐层。此规则是MLR-004的Tcl语言特定子规则。
- **检测逻辑**：
  1. 扫描 `.tcl` 文件，检测 `::namespace::symbol` 模式（双冒号前缀的非标准命名空间访问）。
  2. 过滤25+个Tcl标准命名空间白名单（如 `::tcl::`, `::tk::`, `::string::`, `::info::` 等）。
  3. 非第三方路径的违规标记为MEDIUM，第三方路径（如 `is_third_party_path()` 命中）标记为INFO。
- **建议修复**：将Tcl命名空间直接访问替换为封装的Tcl命令API。

#### MLR-005：跨语言回调深度过大

- **严重级别**：MEDIUM
- **描述**：存在连续跨语言跳转次数 ≥ 3 的调用链（如 Python → C++ → Python → Fortran）。
- **检测逻辑**：
  1. 在依赖图中，仅考虑连续跨语言边（语言切换的边）。
  2. 使用 DFS 计算最长连续跨语言路径长度 `D_max`。
  3. 若 `D_max ≥ 3`，触发警告并输出最深的链示例。
- **建议修复**：
  - 合并多个来回调用为批量调用（如 Python 一次性传递数据，C++ 处理完再返回）。
  - 使用异步消息队列解耦，避免同步深度嵌套。
- **阈值配置**：可通过参数 `--max-depth` 调整（默认3）。

#### MLR-006：热耦合模块

- **严重级别**：MEDIUM
- **描述**：单个模块（文件/类）的跨语言调用强度（入边+出边）超过阈值（默认 > 5）。
- **检测逻辑**：
  1. 对每个节点，计算 `coupling_score = incoming_cross_edges + outgoing_cross_edges`。
  2. 若 `coupling_score > 5`，输出模块路径及其耦合详情。
- **建议修复**：
  - 将热模块拆分为多个子模块，每个子模块只负责一类跨语言交互。
  - 引入中间“代理”层，减少直接依赖数量。
- **示例**：一个 C++ 模块被 10 个 Python 工作台调用，且自身又调用 3 个 Fortran 库 → 耦合强度 13。

#### MLR-007：炸药模块（影响半径过大）

- **严重级别**：MEDIUM
- **描述**：修改一个模块通过跨语言依赖图影响到的其他模块数量 > 10。
- **检测逻辑**：
  1. 对每个节点，执行 BFS/DFS 沿所有边（包括同语言和跨语言），统计可达节点数 `R`（深度限制5）。
  2. 若 `R > 10`，触发警告。
- **建议修复**：
  - 将高影响模块拆解，抽取稳定的抽象接口。
  - 为受影响区域增加自动化回归测试，确保变更安全。
- **关联坏味道**：炸药模块（TNT Module）。

#### MLR-008：跨语言回调死锁风险

- **严重级别**：HIGH
- **描述**：存在调用链中 Python（持有 GIL）调用 C++，C++ 再回调 Python，且回调可能持有同一 GIL 导致死锁。
- **检测逻辑**：
  1. 识别模式：`Python → C++ → Python` 的调用链，且 C++ 端在回调 Python 前未释放 GIL（在 pybind11 中可通过 `py::gil_scoped_release` 释放）。
  2. 静态检查 C++ 回调代码中是否有 `py::gil_scoped_acquire` 但没有配套的 `release`，或使用同步原语（如条件变量）在持有 GIL 时等待。
- **建议修复**：
  - 在 C++ 端调用 Python 回调前，确保已释放 GIL（`py::gil_scoped_release` 作用域）。
  - 避免在持有 GIL 时进行阻塞操作（如锁等待）。
- **示例**：
  ```cpp
  // 危险代码
  void call_python_callback() {
      py::object cb = get_callback();
      cb();  // 此时仍持有 GIL，若 Python 端再调用 C++ 锁可能死锁
  }
  // 安全代码
  void call_python_callback() {
      py::gil_scoped_release release;
      // 做一些非Python操作
      py::gil_scoped_acquire acquire;
      cb();
  }
  ```

#### MLR-009：绑定层使用类型绕过

- **严重级别**：MEDIUM
- **描述**：绑定代码中使用了 `void*`、`py::object`、`ctypes.c_void_p` 或 `any` 等绕过类型系统的构造，削弱契约一致性。
- **检测逻辑**：
  - pybind11：检测 `.def` 中参数类型为 `py::object` 或返回 `void*`。
  - SWIG：检测 `%typemap` 中将类型映射为 `void*`。
  - ctypes：检测 `argtypes` 或 `restype` 为 `c_void_p`。
- **建议修复**：
  - 尽量使用具体类型映射（如 `std::vector<double>` → `list`）。
  - 如果必须绕过，添加注释说明理由，并限制在少数内部模块中。
- **评分**：每处扣减绑定层接口一致性得分的5%（上限20%）。

#### MLR-010：FFI 内存所有权模糊 (v2)

- **严重级别**：HIGH（Python FFI上下文中的malloc）/ MEDIUM（无配对free的malloc）/ LOW（有配对free的malloc）
- **描述**：一种语言的模块分配内存，而另一种语言的模块释放它（例如 C 中 `malloc`，Python 中 `free`）。这通常导致堆损坏或 double-free。
- **v2 增强**：
  - **5层过滤**：L1 Python tokenize精确提取 → L2 FFI上下文检测 → L3 跨语言调用形式判断 → L4 配对释放检测 → L5 代码生成模板过滤
  - **C/C++ malloc检测**：扫描 `.c`/`.h`/`.cpp` 文件中的 `malloc`/`calloc`/`realloc`，3级严重度：HIGH（Python FFI上下文）、MEDIUM（无配对free）、LOW（有配对free或SFREE宏）
  - **SFREE宏识别**：Fortran中的 `SFREE()` 宏视为配对释放
- **检测逻辑**：
  1. Python文件：`find_malloc_tokens_in_py()` 精确提取malloc调用（排除字符串/注释），`has_ffi_context()` 检测ctypes/pybind11上下文，`is_codegen_template()` 过滤代码生成模板，`check_paired_free()` 检测配对释放。
  2. C/C++文件：检测 `malloc`/`calloc`/`realloc` 调用，`has_pybind11_context()` 判断是否在Python扩展模块中（HIGH），`check_paired_free()` 检测 `free`/`SFREE` 配对。
  3. Fortran文件：`DEALLOCATE` 视为配对释放。
- **建议修复**：
  - 明确约定：分配内存的语言负责释放。如果必须跨语言释放，封装为 `destroy` 函数并调用正确语言的释放器。
  - 使用高级绑定（如 pybind11 的 `opaque` 或 `unique_ptr`）自动管理生命周期。

#### MLR-011：过量的跨语言小对象传递

- **严重级别**：LOW
- **描述**：在紧密循环中，频繁传递小的数据结构（如每个元素一个 Python 对象），导致编组/解组开销过大。
- **检测逻辑**：
  1. 识别循环结构（`for`, `while`）内部是否有跨语言调用。
  2. 估算每次调用传递的数据量（静态分析难以精确，可通过运行时 profiling 辅助）。
  3. 若循环体中的跨语言调用次数 > 1000 次（可配置），且每次传递数据 < 64 字节，触发建议。
- **建议修复**：
  - 批量传递（如将循环移到 C++ 侧，或者一次性传递整个数组）。
  - 使用 NumPy 或 `array` 模块共享内存，减少复制。
- **注意**：本规则依赖动态分析时更准确，静态扫描仅作为启发式。

#### MLR-012：未使用 ISO_C_BINDING 的 Fortran 接口 (v3)

- **严重级别**：MEDIUM（被C/C++直接调用的Fortran接口）/ INFO（以下降级条件任一命中）
- **描述**：Fortran 代码向 C/C++ 暴露接口时，未使用标准的 `ISO_C_BINDING` 模块，而是依赖特定编译器的名称修饰和调用约定。这导致跨语言调用极不稳定。
- **v3 增强**：
  - **第三方路径降级**：`is_third_party_path()` 命中的文件（如第三方库）自动降级为INFO
  - **F77固定格式降级**：`.f` 扩展名（Fortran 77固定格式）不支持 `iso_c_binding`，自动降级为INFO
  - **跨语言边感知**：无跨语言边的Fortran文件（即仅被同语言调用）自动降级为INFO。Code_Aster 7,968个Fortran文件全部降级为INFO
  - **`@allowed_coupling`注解**：Fortran源码中 `! @allowed_coupling ModuleName` 注解将MEDIUM降级为INFO
- **检测逻辑**：
  1. 扫描 Fortran 文件，查找 `subroutine` / `function` 声明。
  2. 检查是否包含 `use, intrinsic :: iso_c_binding`，并且具有 `bind(c)` 属性。
  3. 降级判断链：第三方路径 → INFO; F77固定格式 → INFO; 无跨语言边 → INFO; `@allowed_coupling` → INFO; 否则 → MEDIUM。
- **建议修复**：
  - 重构 Fortran 接口，使用 `ISO_C_BINDING` 定义，明确指定 `value`、`dimension` 等。
  - 对于合理的多物理场耦合依赖，使用 `! @allowed_coupling HeatSolve` 注解标记。

## 六、与现有标准/指南的映射

| 本指南指标 | 对应 ISO 25010 子特性 | 对应 CK 度量集 | 对应行业坏味 |
|-----------|----------------------|---------------|-------------|
| 跨语言调用强度 | 可耦合性（Couplability） | 无直接对应 | “热耦合” |
| 跨语言影响半径 | 可修改性（Modifiability） | RFC（类的响应集）的跨语言扩展 | “炸药模块” |
| 跨语言回调深度 | 可分析性（Analysability） | 无 | “跨语言回调地狱” |
| 绑定层接口一致性 | 可修改性 + 可测试性 | 无 | “绑定漂移” |
| 脚本越界访问 | 模块化（Modularity） | 无 | “越狱脚本” |
| 跨语言循环依赖 | 可修改性 + 模块化 | CBO（对象类间耦合）的跨语言扩展 | “多语言面条依赖” |

## 七、实施建议

1. **工具集成**：将上述算法集成到现有的架构扫描工具中（如`arch-scan`），输出每个模块的跨语言耦合得分。
2. **门禁设置**：在CI流水线中设置阈值，当多语言混合依赖综合分 < 50 时阻止合并。
3. **重构优先级**：优先处理“跨语言循环依赖”和“绑定层接口一致性”得分低于60的模块。
4. **语言组合定制**：对于不同的语言对（如C++/Python vs C/Fortran），可调整部分扣分系数（例如C/Fortran的FFI内存安全性更重要）。
