# 软件架构质量评估指南（2.3版）

本文档定义软件架构质量的评估体系，按四大分类组织：结构质量、设计质量、文档质量、演进质量。每个评估维度包含设计依据、算法说明和权重分配。


## 一、软件架构质量的定义

### 1.1 什么是软件架构质量

**软件架构质量**是指软件系统架构满足其利益相关者（开发者、维护者、测试者、运维者等）需求的程度。它不关注"功能是否正确"（功能质量），而关注"系统的结构是否健康"（结构质量）。

根据 **IEEE 1471 / ISO/IEC 42010**，软件架构是"系统的基本组织方式，体现在其组件、组件之间的关系以及与环境的关系中，并指导其设计和演进"。架构质量就是衡量这种"基本组织方式"的好坏程度。

### 1.2 架构质量的三个层次

| 层次 | 关注点 | 时间维度 | 类比 |
|------|--------|---------|------|
| **结构质量** | 代码物理结构：模块化、耦合度、内聚度 | 当前快照 | 建筑的钢筋混凝土框架 |
| **设计质量** | 设计决策质量：SOLID、设计模式、架构风格 | 当前快照 | 建筑的户型设计 |
| **演进质量** | 可持续性：技术债务、依赖健康度、活跃度 | 时间序列 | 建筑的维护记录 |

### 1.3 自动化评估的边界

本指南定义的评估体系基于**自动化静态分析**，能够测量代码的物理结构、设计模式、文档完整性和演进趋势。然而，自动化指标存在固有边界：
- **无法替代人工架构评审**：架构风格是否恰当、模块拆分是否合理、技术选型是否正确等问题，无法通过静态分析回答。
- **建议配合使用**：本指南输出应作为架构评审会议（如 ATAM 或轻量级替代方案）的输入材料，由架构师结合业务上下文进行最终判断。
- **检测置信度差异**：不同指标的检测可靠性不同——文件行数（高置信度）与设计模式识别（启发式）置信度不同，详见各章节说明。

### 1.4 评估频率与范围

本指南支持两种评估模式：
- **全量基线评估**：每月或每季度执行，覆盖全部代码，用于追踪架构健康度的长期趋势，建立历史基线。
- **增量变更评估**：每次 PR 或 MR 触发，仅分析变更文件及其直接影响范围，用于门禁检查，防止架构腐化。

两种模式应配合使用：增量评估用于日常防护，全量评估用于战略决策。

### 1.5 为什么架构质量重要

| 影响维度 | 低质量架构的后果 | 高质量架构的益处 |
|---------|----------------|----------------|
| **开发效率** | 每次改动需要理解大量耦合代码，新功能交付慢 | 模块独立开发，变更影响范围小 |
| **缺陷率** | 高耦合导致"修一个 bug 引入三个 bug" | 低耦合使变更风险可控 |
| **入职成本** | 新成员需要数月才能理解系统全貌 | 清晰的分层和文档让新成员快速上手 |
| **技术债务** | 架构腐化速度超过修复速度，最终被迫重写 | 持续重构，架构健康度可控 |
| **系统寿命** | 3-5年需重写 | 可持续演进10年以上 |

**来源**：Martin Fowler *Refactoring*、*Clean Architecture*；Lehman 软件演进定律。


## 二、软件架构质量评估的定义

### 2.1 什么是架构质量评估

**软件架构质量评估**是一套系统性方法，通过**可重复的、量化的指标**来衡量软件架构在上述三个层次上的健康程度。其核心思想是：**无法度量，就无法管理**。

### 2.2 评估的四个核心原则

| 原则 | 含义 | 来源 |
|------|------|------|
| **可重复性** | 同一项目在不同时间点运行评估，结果应可比 | SQALE 方法论 |
| **可解释性** | 每个得分的升降都能追溯到具体的代码变更 | Martin Fowler 度量哲学 |
| **多维覆盖** | 单一指标（如代码行数）不足以衡量架构质量 | ISO/IEC 25010 质量模型 |
| **可行动性** | 评估结果应指导具体的改进动作 | Google 工程实践 |

### 2.3 评估的收益

- **发现隐患**：在缺陷出现之前识别架构中的风险点（如循环依赖、高耦合）
- **跟踪趋势**：量化架构在时间维度上的变化方向（改善/恶化）
- **辅助决策**：为"是否该重构"、"是否该技术选型升级"等决策提供数据支撑
- **建立共识**：用统一的度量语言沟通架构问题，减少主观争论
- **控制债务**：让技术债务可见，驱动团队持续偿还而非累积

### 2.4 评估的局限性

| 局限 | 说明 |
|------|------|
| **代理度量** | 所有指标都是真实质量的间接近似（如用文件行数代表复杂度，而非真实的认知复杂度） |
| **无法替代人工评审** | 自动化评估无法检测"设计是否恰当"——只能检测"设计是否符合规则" |
| **上下文敏感** | 同一指标在不同项目中的意义可能不同（如20个文件的模块在微服务中可能合理，在单体中可能过度拆分） |
| **工具依赖** | 评估结果受工具实现质量影响（正则匹配的误报/漏报、Git 日志的完整性等） |

**来源**：ISO/IEC 25021（质量度量指标框架）；SonarQube 文档。

### 2.5 评估结果应用（闭环机制）

评估的价值在于驱动改进，而非仅得到一个数字。本体系采用以下闭环流程：

```
评分 → 诊断 → 改进 → 复评
```

**评分阶段**：执行自动化评估，计算各维度得分，输出结构化报告。

**诊断阶段**：对得分低于阈值的指标，自动关联诊断信息和改进建议：

| 问题指标 | 典型症状 | 标准改进动作 |
|---------|---------|-------------|
| 耦合度低 | 跨域导入比例高 | 拆分模块，引入防腐层，依赖倒置 |
| 复杂度高 | 大文件占比>30% | 按职责拆分文件，提取独立函数/类 |
| MMS验证缺失 | 求解器模块无MMS测试 | 构造制造解，执行网格收敛性研究 |
| 设计模式误用 | 模式识别但意图不符 | 人工复核，判断是否需要保留 |
| ADR覆盖率低 | 无架构决策记录 | 建立ADR模板，记录关键决策 |
| 技术债务上升 | 债务趋势比上次上涨>20% | 制定债务偿还计划，分配重构工时 |

**改进阶段**：团队根据诊断报告制定改进计划，明确负责人和时间节点。

**复评阶段**：改进完成后重新运行评估，验证得分提升，确认问题已解决。

### 2.6 本项目评估体系概要

本项目的评估体系基于上述标准和理念，采用**四维加权评分模型**：

```
总分 = 结构质量 × 30% + 设计质量 × 25% + 文档质量 × 20% + 演进质量 × 25%
```

- **结构质量**（ISO/IEC 25010 可维护性）：模块化、耦合度、内聚度、复杂度、测试覆盖度
- **设计质量**（SOLID + GoF + ISO 42010 + AntiPatterns）：SOLID原则、设计模式、架构风格、反模式
- **文档质量**（README/CHANGELOG/ADR/JSDoc 等标准）：6种文档类型
- **演进质量**（CHAOSS + Fowler + DORA 等）：历史可追溯性、技术债务趋势、依赖过时、废弃代码、增量质量、问题扣分

每个维度均有明确的评分算法、设计依据、检测方式和分数分级。

### 2.7 参考标准汇总

| 标准/框架 | 用途 | 在本体系中的角色 |
|----------|------|----------------|
| **ISO/IEC 25010:2011** | 软件产品质量模型 | 结构质量（可维护性）的5个子特性定义 |
| **ISO/IEC 42010 / IEEE 1471** | 架构描述标准 | 架构文档完整性、架构风格评估 |
| **SQALE** | 技术债务量化 | 技术债务趋势评分模型 |
| **SOLID (R.C. Martin)** | 面向对象设计原则 | 设计质量核心评估（SOLID占40%） |
| **GoF Design Patterns (1994)** | 设计模式分类 | 设计模式多样性和正确性检测 |
| **CHAOSS** | 开源社区健康度 | 历史可追溯性（Git活跃度）评分 |
| **DORA (2025 更新版)** | 部署效能指标 | 增量质量（提交粒度）评分 |
| **Keep a Changelog** | 版本变更文档规范 | CHANGELOG 完整性评估 |
| **TSDoc** | TypeScript 文档注释规范 | JSDoc 覆盖率评估 |
| **SonarQube** | 代码质量门禁 | 通用技术：注释密度阈值、死代码检测、复杂度阈值 |
| **Antipatterns (Brown et al.)** | 反模式目录 | 设计质量扣分项 |


## 总体得分

```
总分 = 结构质量 × 30% + 设计质量 × 25% + 文档质量 × 20% + 演进质量 × 25%
```

**权重分配依据**：
- 结构质量权重最高(30%)，因为它是所有软件质量的基础。结构质量以结构质量综合分为准，该综合分由模块化、耦合度、内聚度、复杂度、测试覆盖度5个维度等权合成，对应 ISO/IEC 25010 可维护性(Maintainability)的5个子特性
- 设计质量提升至25%，反映SOLID原则和架构设计在长期维护中的重要性
- 演进质量提升至25%，合并原问题扣分(15%)，将问题作为演进质量的子维度

**扩展维度**：本评估体系还包含**需求—架构映射质量**，作为架构质量的补充视角。详见独立文档 `REQUIREMENT_MAPPING_GUIDE.md`。该维度衡量需求与代码实现之间的可追溯性，评估方法包括覆盖度（命令/功能/数据/路径）、精确度、可追溯性和鲜活性四个维度。


## 三、结构质量

结构质量衡量代码的物理结构特征，是软件可维护性的基础。参考 **ISO/IEC 25010** 可维护性(Maintainability)模型，结构质量由5个子维度加权合成，每个子维度对应可维护性的一个子特性：

| ISO/IEC 25010 子特性 | 本项目指标 | 描述 |
|---------------------|-----------|------|
| 模块化 (Modularity) | 3.1 模块化 | 系统由独立组件的程度 |
| 可修改性 (Modifiability) | 3.2 耦合度 | 有效修改而不引入缺陷的程度（低耦合=高可修改） |
| 模块化的前提条件 | 3.3 内聚度 | 组件内部元素的功能相关程度（高内聚支撑有效模块化） |
| 可分析性 (Analysability) | 3.4 复杂度 | 诊断缺陷或确定修改部位的有效性（低复杂=高可分析） |
| 可测试性 (Testability) | 3.5 测试覆盖度 | 代码可被测试的程度和实际覆盖情况 |

**权重说明**：本指南默认采用等权设计（各20%），反映ISO 25010五个子特性在标准中的**并列关系**——"平衡优于突出"的设计理念。实施团队可根据业务场景调整权重：
- **快速迭代产品**（如互联网SaaS）：建议耦合度权重提升至30%，因为它直接影响变更交付速度
- **长期维护基础库**（如CAD/CAE核心引擎）：建议复杂度权重提升至30%，因为它直接影响长期维护成本
- **安全性关键系统**（如核工程、航空航天）：建议可测试性权重提升至25%，因为测试覆盖率直接影响安全认证

5个子维度加权平均合成**结构质量综合分**（参见3.6节），该综合分参与总体评分计算（结构质量 × 30%）。
在 ISO/IEC 25010 框架下，上述5个指标归类为可维护性(Maintainability)，因此结构质量综合分可类比为可维护性得分。

### 3.1 模块化 (Modularity)

**权重**: 20% of 结构质量（默认，可调整）

**定义**：模块化衡量代码库被拆分为独立、可替换模块的程度。高模块化意味着修改一个模块不需要理解或变更其他模块，降低认知负载和变更风险。

**ISO/IEC 25010 映射**：对应可维护性子特性**模块化(Modularity)**——系统由独立组件的程度，变更一个组件对其他组件影响最小。

**设计依据**：
- ISO/IEC 25010: 可分析性(Analysability)、可修改性(Modifiability)（模块化是其基础）
- Martin Fowler: 模块化架构原则

**评分算法**：
```
avgFilesPerDir = 总文件数 / 唯一目录数
modularityScore = 100 - (avgFilesPerDir - 5) × 10
```
- 理想值：每目录 5 个文件，得 100 分
- 每多/少 1 个文件扣 10 分
- 封顶 100 分，最低 0 分

**检测置信度**：高（精确测量）

**权重依据**：目录结构是模块化的最直接体现

### 3.2 耦合度 (Coupling)

**权重**: 20% of 结构质量（默认，可调整）

**定义**：耦合度衡量模块之间的依赖强度和紧密程度。低耦合意味着模块之间仅通过明确、最小的接口通信，一个模块的变更不会"涟漪式"影响其他模块。

**ISO/IEC 25010 映射**：对应可维护性子特性**可修改性(Modifiability)**——有效修改而不引入缺陷的程度。高耦合意味着一个模块的变更可能波及其他模块，降低可修改性。

**设计依据**：
- ISO/IEC 25010: 可耦合性(Couplability)（可修改性的关键度量）
- Yourdon/McConnell: 耦合度分类（内容、公共、控制、标记、数据）

**评分算法**：
```
avgImports = 内部导入总数 / 文件数
baseScore = 100 - avgImports × 10

// 类型导入加分
typeRatio = 类型导入文件占比
typeBonus = min(20, typeRatio × 200)

// 跨域扣分
crossRatio = 跨功能域导入 / 总导入
crossPenalty = min(30, crossRatio × 300)

// 双向依赖扣分
bidirectionalPenalty = min(20, 双向依赖对数 × 5)

couplingScore = baseScore + typeBonus - crossPenalty - bidirectionalPenalty
```

**检测置信度**：高（精确测量）

**权重依据**：耦合度直接影响代码的可修改性和可测试性

**说明**：
- 类型导入加分：`import type { X }` 仅依赖接口/类型，编译后不产生运行时依赖；`import { X }` 导入具体值，产生运行时依赖，耦合更紧。类型导入占比越高，加分越多。
- 跨域扣分：跨功能域的导入视为紧耦合，功能域按 `src/` 下首层目录划分，根目录文件归为 `root`
- **测试文件导入源码属于合理架构模式，不计入跨域扣分**

### 3.3 内聚度 (Cohesion)

**权重**: 20% of 结构质量（默认，可调整）

**定义**：内聚度衡量模块内部各元素（函数、类、变量）在功能上的相关程度。高内聚意味着一个模块只做一件事且做好这件事，所有内部元素都服务于同一职责。

**ISO/IEC 25010 映射**：内聚度不是 ISO 25010 可维护性的直接子特性，但它是**模块化(Modularity)的前提条件**。高内聚意味着模块内部元素高度相关、职责单一，这是有效模块化的基础。Yourdon & Constantine 的结构化设计理论指出：高内聚 + 低耦合 = 良好的软件结构。

**设计依据**：
- ISO/IEC 25010: 功能内聚(Functional Cohesion)（通过模块化间接影响可维护性）
- Yourdon/McConnell: 内聚度分类（功能、顺序、通信、过程、偶然）

**评分算法**：
```
xlargeRatio = 超过1000行的文件数 / 总文件数
cohesionScore = 100 - xlargeRatio × 200
```
- 每有 1% 超大文件扣 2 分
- 1000行为业界常用阈值

**检测置信度**：高（精确测量）

**权重依据**：大文件通常意味着职责过多，破坏内聚

**补充说明**：内聚度作为模块化的前提条件（Yourdon & Constantine，1979），ISO 25010虽未将其列为独立子特性，但它是实现高模块化的基础，因此纳入本评估体系作为补充指标。

### 3.4 复杂度 (Complexity)

**权重**: 20% of 结构质量（默认，可调整）

**定义**：复杂度衡量代码的理解和维护难度。高复杂度的代码难以阅读、调试和修改，增加了引入缺陷的概率。本项目以超过200行的文件占比作为复杂度的代理度量。

**ISO/IEC 25010 映射**：对应可维护性子特性**可分析性(Analysability)**——诊断缺陷或确定修改部位的有效性。文件越大、代码越复杂，开发者理解代码的成本越高，可分析性越低。本项目以200行文件比例作为复杂度的代理度量。

**设计依据**：
- ISO/IEC 25010: 可分析性(Analysability)
- SONARQube: 大文件复杂度阈值（通常以 200-500 行为界）

**评分算法**：
```
largeFileRatio = 超过200行的文件数 / 总文件数
complexityScore = 100 - largeFileRatio × 300
```

**检测置信度**：高（精确测量）

**说明**：这是**反向指标**，分数越低表示复杂度越高。200行为业界常用的大文件阈值。

**项目解读**：如果项目有多个超过200行的文件（如 `versionCheck.ts` 约400行），复杂度得分会显著降低，说明需考虑对这些文件进行拆分重构。

### 3.5 测试覆盖度 (Test Coverage)

**权重**: 20% of 结构质量（默认，可调整）

**定义**：测试覆盖度衡量项目的测试文件对源码的覆盖程度。从4个层级综合评估：目录覆盖（源码目录是否有对应测试目录）、语言覆盖（每种语言是否有测试文件）、文件比（测试文件与源码文件比例）、绑定层覆盖（多语言项目的绑定接口是否有测试）。

**ISO/IEC 25010 映射**：对应可维护性子特性**可测试性(Testability)**——测试准则有效性和测试执行便捷度。测试覆盖率越高，代码的可验证性越好，可维护性越高。

**设计依据**：
- ISO/IEC 25010: 可测试性(Testability)
- Google 工程实践：单元测试覆盖率
- 行业实践：多层级测试覆盖评估（目录级、语言级、接口级）

**评分算法**：

```
L1 目录覆盖得分 = 有测试的源码目录比例 × 100 (权重30%)
L2 语言覆盖得分 = 有测试文件的语言比例 × 100 (权重25%)
L3 文件比得分 = min(1.0, 测试文件数 / (源码文件数 × 0.3)) × 100 (权重25%)
L4 绑定层覆盖得分 = 有测试的绑定函数比例 × 100 (权重20%, 单语言项目重分配到L1-L3)

单语言项目: testCoverage = L1×37.5% + L2×31.25% + L3×31.25%
多语言项目: testCoverage = L1×30% + L2×25% + L3×25% + L4×20%
```

**检测置信度**：高（精确测量）

**说明**：
- 原"可测试性"算法仅按 `testRatio × 200` 评分（50%文件比即满分），不区分语言、目录、绑定层
- 升级后4层评分更精确反映实际覆盖情况
- 单语言项目无绑定层，L4权重按比例分配到L1-L3
- 名称从"可测试性"改为"测试覆盖度"，更准确反映实际测量内容

### 3.6 结构质量综合分

结构质量的最终输出由前5个子维度加权平均合成。

**设计依据**：
- 该综合分对应 ISO/IEC 25010 **可维护性(Maintainability)** 概念——即系统能被有效修改的综合能力
- 默认等权平均（各20%），体现"平衡优于突出"的设计哲学
- 实施团队可根据业务特点调整权重（见本章开头权重说明）

**评分算法**：

```
结构质量综合分 = 模块化×20% + 耦合度×20% + 内聚度×20% + 复杂度×20% + 测试覆盖度×20%
```

**说明**：
- 该综合分是"结构质量"维度的输出值，直接参与总体评分计算（参见"总体得分"公式）
- 在 ISO/IEC 25010 框架下，这5个子维度被归类为可维护性(Maintainability)，因此结构质量综合分可称为**可维护性得分**


## 四、设计质量

设计质量衡量代码的**设计决策质量**，关注代码的抽象、封装、组织和扩展方式。参考 **Robert C. Martin** 的 SOLID 原则和 **GoF** 设计模式。设计质量由4个子维度加权合成：

| 参考标准/框架 | 本项目指标 | 描述 |
|-------------|-----------|------|
| SOLID 原则 (R.C. Martin) | 4.1 SOLID 原则 | 面向对象设计的五大基本原则，决定代码的可扩展性和可维护性 |
| GoF 设计模式 (1994) | 4.2 设计模式 | 23种经典设计问题解决方案，体现代码的成熟度（启发式检测，需人工复核） |
| 架构风格 (ISO/IEC 42010, Fowler) | 4.3 架构风格 | 系统的高层组织模式，决定代码的结构范式 |
| AntiPatterns (Brown et al.) | 4.4 反模式 | 常见设计错误模式，作为扣分项 |

4个子维度加权合成**设计质量综合分**（参见4.5节），该综合分参与总体评分计算（设计质量 × 25%）。
详细算法说明参见独立文档 `DESIGN_QUALITY_METRICS.md`。

### 4.1 SOLID 原则

**权重**: 40% of 设计质量

**定义**：SOLID 是面向对象设计的五大基本原则的首字母缩写。它衡量代码在应对需求变化时的**弹性**——高 SOLID 合规意味着系统可以通过"增加代码"而非"修改已有代码"来适应新需求，从而降低回归缺陷风险。每个原则单独评分后等权平均。

**设计依据**：
- Robert C. Martin: *Agile Software Development* (2000)
- Barbara Liskov: 里氏替换原则 (1987 OOPSLA)
- Bertrand Meyer: 开闭原则 (1988)
- SQALE 方法论：扣分模型

**评分算法** — 对每个文件逐一评估，按文件大小加权平均：

| 原则 | 检测规则 | 得分公式 |
|------|---------|---------|
| 单一职责(S) | 统计文件中的职责数量（按导入模块、导出函数的业务领域跨度、私有方法操作范围判断） | `sScore = 100 - (职责数 - 1) × 25`，1职责→100分，5+职责→0分 |
| 开闭原则(O) | 6项检测：1)是否使用接口/抽象类；2)是否使用策略/函数注入；3)新功能是否需要修改此文件(反向)；4)是否使用配置/注册表；5)是否通过继承/组合扩展；6)接口变更频率(通过Git历史) | `oScore = 100 + sum(加分项) - sum(扣分项)`，接口变更频率超过阈值则额外扣分 |
| 里氏替换(L) | 检测继承层次中的三种违反：行为改变(override不调super)、参数前置条件强化、返回后置条件弱化 | 每项违反-33分 |
| 接口隔离(I) | 接口方法数 ≤ 5 且不使用 `any` 绕过类型契约 | 每多3个方法-10分，使用 `any` 额外-10分 |
| 依赖倒置(D) | 检测构造函数注入(正)、`new`具体类(反)、import抽象类型 | `dScore = constructorDI×40 + abstractImport×20 - newConcrete×20`，但 `new` 出现在 Factory/Builder 类或 `create*` 方法中时不扣分 |

```
solidScore = (S+O+L+I+D) / 5
```

**检测置信度**：中（依赖AST解析，部分启发式判断）

**权重依据**：SOLID 是面向对象设计的核心原则，决定代码长期可维护性

**设计依据汇总**：

| 原则 | 参考来源 | 核心依据 |
|------|---------|---------|
| **S** 单一职责 | Robert C. Martin *Agile Software Development* + SQALE | 一个模块一个改变理由，线性扣分模型源自 SQALE |
| **O** 开闭原则 | Bertrand Meyer 原始定义 + Robert C. Martin 抽象依赖 + SonarQube | 对扩展开放、对修改关闭，六项检测覆盖合规/反模式，新增接口变更频率检测 |
| **L** 里氏替换 | Barbara Liskov 1987 OOPSLA 定义 + SonarQube | 子类可替换父类不改变正确性，检测行为/参数/返回违反 |
| **I** 接口隔离 | Robert C. Martin *Clean Architecture* + ESLint no-explicit-any | 小接口原则，5 属性阈值，any 视为绕过类型契约 |
| **D** 依赖反转 | Robert C. Martin DIP 定义 + Angular/Spring DI 模式 + SonarQube | 依赖抽象而非具体，构造函数注入为正、new 为反（Factory模式例外） |

### 4.2 设计模式

**权重**: 15% of 设计质量（从原25%下调，反映启发式检测的局限性）

**定义**：设计模式是经过验证的、可复用的设计问题的通用解决方案。它衡量代码的**成熟度**——合理使用设计模式意味着团队经验丰富、代码结构经过深思熟虑，而非"面向过程"或"临时拼凑"。从多样性和正确性两个维度评分。

**重要说明**：当前检测基于**正则匹配（启发式）**，无法完全识别设计模式的意图和上下文，**检测结果需人工复核**。本维度得分仅供参考，不应作为阻断性门禁的唯一依据。

**设计依据**：
- GoF (Gang of Four): *Design Patterns: Elements of Reusable Object-Oriented Software* (1994)
- Brown et al.: *AntiPatterns*

**评分算法** — 正则匹配源码，从多样性和正确性两个维度合成：

```
patternCount = 检测到的不同模式种类数（上限8种）
correctUsage = 正确实现的模式数
diversityScore = patternCount × 10（每模式10分，上限80分）
correctnessScore = (correctUsage / patternCount) × 20（上限20分）

patternScore = diversityScore + correctnessScore
```

**检测置信度**：低（启发式匹配，需人工复核）

**检测模式（12种）**：

| 模式 | 检测特征 |
|------|---------|
| Singleton | `private constructor` + `static.*instance` + `getInstance()` |
| Observer | `push.*listener` / `forEach.*listener` + add/removeListener |
| Strategy | 函数数组 + 迭代调用模式 |
| Factory | `switch/if` + `new` + 类型判断创建函数 |
| Command | `switch(command)` 或命令注册表 + 处理函数映射 |
| Template Method | 一个方法调用多个 `this.xxx()` 子方法 |
| Adapter/Wrapper | 封装外部API对象 + 转发调用模式 |
| Facade | 类包含多个子组件引用 + 对外提供简化接口 |
| Decorator | `@` 装饰器 |
| Cache | 缓存对象/Map + TTL 时间戳比较 |
| Retry/Backoff | `retry` + `Math.min/Math.pow` 退避计算 |
| Callback Injection | 构造函数参数为函数类型 |

**权重依据**：设计模式体现代码的成熟度和可扩展性，但因检测方法限制（正则匹配无法识别意图），权重从25%降至15%。

### 4.3 架构风格

**权重**: 20% of 设计质量

**定义**：架构风格是系统的高层组织范式，定义了组件如何交互、数据和控制的流向。它衡量代码的**结构范式一致性**——系统是否遵循了某一明确的架构风格（如分层、事件驱动），而非无组织的"大泥球"。风格越一致，新开发者上手越快，系统行为越可预测。

**设计依据**：
- ISO/IEC 42010: 架构描述标准
- Martin Fowler: *Patterns of Enterprise Application Architecture*
- C4 Model: Simon Brown
- Robert C. Martin: *Clean Architecture*

**评分算法** — 综合检测目录模式和依赖方向：

| 风格 | 目录检测特征 | 依赖方向检测 |
|------|-------------|-------------|
| 分层架构 | 目录包含 controller/service/repository | controller→service→repository（反向则扣分） |
| 模块化 | 功能域组织 + 接口通信 | 按功能域划分，跨域导入受控 |
| 事件驱动 | 事件发布/订阅模式 | 发布者→事件总线→订阅者 |
| MVC | Model + View + Controller 分离 | Controller→Model/View，反向扣分 |
| 微内核 | 核心系统 + 插件扩展 | 核心→插件，插件间无依赖 |
| **整洁架构** | 检测 entities/use_cases/interface_adapters/frameworks_drivers 四层分离 | 依赖方向由外向内：frameworks→interface_adapters→use_cases→entities |

```
styleScore = min(100, (最常见风格实例数 / 总文件数) × 100)
```
**附加规则**：检测到依赖方向违反时（如 repository 依赖 controller），每处扣5分。

**检测置信度**：中（目录模式识别+依赖方向分析，需人工复核）

**说明**：风格检测识别项目中占主导的架构组织方式，不要求多种风格共存。

### 4.4 反模式

**权重**: 25% of 设计质量（从原15%上调，因设计模式权重降低）

**定义**：反模式是常见但有害的设计方式，短期内看似合理，长期会导致系统难以维护和演进。它衡量代码的**设计债务**——反模式越多，未来的重构成本越高。作为设计质量的扣分项，得分从100分起扣，上限扣30分。

**设计依据**：
- Brown et al.: *AntiPatterns: Refactoring Software, Architectures, and Projects in Crisis*
- SonarQube: 代码异味检测规则

**评分算法**：

| 反模式 | 检测条件 | 扣分 |
|--------|---------|------|
| God Class | 类>300行且方法>10个 | -10分/个 |
| Long Method | 函数>100行 | -5分/个 |
| 硬编码 | 应配置化的值直接写死 | -5分/处 |
| 霰弹修改 | 一个需求变化需改>3个文件 | -5分/处 |

```
smellDeduction = min(30, GodClass×10 + LongMethod×5 + hardcode×5 + shotgun×5)
antiPatternScore = Math.max(0, 100 - smellDeduction)
```

**检测置信度**：高（精确检测，但“霰弹修改”为启发式判断）

**说明**：反模式是设计质量的扣分项，上限扣30分。

### 4.5 设计质量综合分

设计质量的最终输出由前4个子维度加权合成。

**设计依据**：
- 4个子维度分别从"原则合规(SOLID)"、"解决方案成熟度(设计模式)"、"组织范式(架构风格)"、"设计债务(反模式)"四个互补视角评估设计质量
- SOLID权重最高(40%)，因为它是设计质量的根基
- 反模式权重提升至25%，因为它反映的设计债务比设计模式的出现频率更直接影响可维护性

**评分算法**：

```
设计质量综合分 = SOLID × 40% + 设计模式 × 15% + 架构风格 × 20% + 反模式 × 25%
```

### 分数分级

| 分数区间 | 等级 | 说明 |
|---------|------|------|
| ≥ 85 | ?? 优秀 | 设计成熟，SOLID合规性好，架构清晰 |
| 70-84 | ?? 良好 | 核心设计合理，部分模式可优化 |
| 50-69 | ?? 需改进 | 存在设计缺陷，需关注SOLID和反模式 |
| < 50 | ?? 差 | 设计严重不足，建议架构重构 |


## 五、文档质量

文档质量衡量项目文档的**完整性和规范性**。参考 **Keep a Changelog** 和 **TSDoc** 标准。文档质量由6个子维度加权合成。

**ISO/IEC 25010 归属说明**：文档质量参考 ISO/IEC 25010 使用质量模型中的"满意度"和"生产率"维度，并结合行业最佳实践（GitHub README、Keep a Changelog、Michael Nygard ADR、TSDoc）进行综合评估。在工业实践中，高质量的文档是软件长期可维护性的关键支撑，其重要性不因其标准归属而降低。

| 参考标准 | 本项目指标 | 描述 |
|---------|-----------|------|
| GitHub README 最佳实践 + Awesome README | 5.1 README 完整性 | 项目门户文档，决定上手效率和可信度 |
| [keepachangelog.com](https://keepachangelog.com) | 5.2 CHANGELOG 完整性 | 版本演进记录，变更沟通的核心载体 |
| Michael Nygard ADR + ThoughtWorks Radar | 5.3 ADR 覆盖率 | 架构决策上下文记录，保障项目可持续性 |
| Google Code Review + SonarQube | 5.4 代码注释密度 | 源代码的可读性和自解释程度 |
| TSDoc 标准 | 5.5 JSDoc 覆盖率 | 导出 API 的文档注释覆盖程度 |
| ISO/IEC 42010 + C4 Model | 5.6 架构文档完整性 | 系统全貌描述，降低认知负载 |

6个子维度加权合成**文档质量综合分**（参见5.7节），该综合分参与总体评分计算（文档质量 × 20%）。

### 5.1 README 完整性

**权重**: 25% of 文档质量

**定义**：README 是项目的"门面文档"，衡量项目介绍信息的**完备程度**。一个完整的 README 应包含项目简介、安装步骤、使用说明、功能列表和配置指南，帮助新开发者快速上手。

**设计依据**：
- GitHub 官方 README 最佳实践（项目简介 → 安装 → 使用 → 功能 → 配置 → 贡献）
- Awesome README 社区标准

**评分算法**：

```
readmeScore = 0~100分
  - README.md 存在 → 20分
  - 包含项目简介 → +15分
  - 包含安装说明 → +15分
  - 包含使用说明 → +15分
  - 包含功能列表 → +15分
  - 包含配置说明 → +10分
  - 包含贡献指南 → +10分
```

**检测置信度**：高（精确匹配）

**检测方式**：正则匹配 README.md 中各章节的标题关键词（`## 安装`、`## 使用`等）

### 5.2 CHANGELOG 完整性

**权重**: 15% of 文档质量

**定义**：CHANGELOG 记录项目的版本演进历史，衡量版本变更文档的**规范性**。遵循 [keepachangelog.com](https://keepachangelog.com) 格式标准的 CHANGELOG 应包含版本号、发布日期和语义化变更分类。

**设计依据**：
- [keepachangelog.com](https://keepachangelog.com) 格式标准

**评分算法**：

```
changelogScore = 0~100分
  - CHANGELOG.md 存在 → 30分
  - 包含版本号 → +20分
  - 包含日期 → +20分
  - 包含变更分类（Added/Changed/Fixed等）→ +30分
```

**检测置信度**：高（精确匹配）

**检测方式**：正则匹配 CHANGELOG.md 中的版本号、日期和语义化变更分类关键词。

### 5.3 ADR 覆盖率

**权重**: 20% of 文档质量

**定义**：ADR（架构决策记录）衡量架构决策文档的**覆盖率**。每个关键的架构决策（如框架选择、模块拆分、技术选型）应有对应的 ADR 记录其上下文、决策理由和后果，避免"为什么这么做"的信息丢失。

**设计依据**：
- Michael Nygard: *Documenting Architecture Decisions* (2007)
- ThoughtWorks Technology Radar 推荐实践

**评分算法**：

```
adrScore = 0~100分
  - ADR 模板存在 → 40分（有基础设施即可获得基础分）
  - 应记录决策总数 = min(5, 项目规模决定的决策数)
  - 已记录决策数 = 实际ADR数量
  - adrCoverage = 已记录决策数 / min(5, 应记录决策总数)
  - 得分 = 40 + (100-40) × adrCoverage
```

**检测置信度**：高（精确统计）

**说明**：新启动的小型项目（1-2个关键决策）只要建立了ADR模板即可获得40分，避免因绝对值计数导致的低分误判。

**检测方式**：统计 `.opencode/templates/` 下的 ADR 模板以及 `<project>/adr/` 或 `<project>/docs/adr/` 目录下的 ADR 记录数量。

### 5.4 代码注释密度

**权重**: 15% of 文档质量

**定义**：代码注释密度衡量源代码中解释性注释的**充足程度**。注释不是越多越好——太少则代码难以理解，太多则说明代码自解释能力不足。15%-25% 为业界公认的健康区间。

**设计依据**：
- Google Code Review 指南：代码应具备自解释能力，注释不应过度
- SonarQube 注释密度默认阈值：低于10%标记警告，高于30%提示注释过度
- 综合业界经验，**15%-25%** 为健康区间：过低说明代码难以理解，过高说明代码自解释不足

**评分算法**：

```
commentRatio = 注释行数 / 代码总行数
commentScore = 
  < 5% → 20分（注释太少）
  5%~10% → 40分
  10%~15% → 60分
  15%~25% → 100分（理想区间）
  25%~40% → 80分
  ≥ 40% → 40分（注释过多，代码自解释不足）
```

**检测置信度**：高（精确测量）

**检测方式**：对 `src/**/*.ts` 文件统计 `//`（单行注释）、`/* */`（多行注释）和 `/** */`（JSDoc）行数。

### 5.5 JSDoc 覆盖率

**权重**: 15% of 文档质量

**定义**：JSDoc 覆盖率衡量**公共 API 的文档注释覆盖程度**。仅对对外暴露的公共 API 强制要求 JSDoc，内部工具函数和测试辅助函数不作强制要求。

**设计依据**：
- TSDoc 标准（TypeScript 官方文档注释规范）
- ESLint `require-jsdoc` 规则的默认配置

**评分算法**：

```
// 区分公共API（对外暴露，如导出函数、类、接口）
publicApi = 标记为 @public 或位于 src/index.ts 的导出
internalApi = 仅模块内部使用、以 _ 开头或标记为 @internal

公共API要求：
jsdocRatio = 有JSDoc的公共API / 总公共API
jsdocScore = 
  ≥ 80% → 100分
  60%~80% → 70分
  40%~60% → 40分
  20%~40% → 20分
  < 20% → 0分

内部API：仅统计，不强制计分
```

**检测置信度**：高（精确匹配）

**检测方式**：对 `src/**/*.ts` 文件，统计 `export function`、`export const` 等导出声明，检查其上方是否有 `/**` 开头的 JSDoc 注释块。

### 5.6 架构文档完整性

**权重**: 10% of 文档质量

**定义**：架构文档衡量系统设计文档的**完整程度**。一份完整的架构文档应描述系统的目录结构、模块职责、数据流、依赖关系和关键设计决策，帮助开发者快速理解系统全貌。

**设计依据**：
- ISO/IEC 42010: 架构描述国际标准，定义架构描述应包含利益相关者关注点、架构视图、设计决策
- C4 Model 分层文档（Context → Container → Component → Code）

**评分算法**：

```
archDocScore = 0~100分
  - 架构文档存在 → +20分
  - 包含目录结构 → +15分
  - 包含模块职责 → +15分
  - 包含数据流 → +15分
  - 包含依赖关系 → +15分
  - 包含设计决策 → +20分
```

**检测置信度**：中（章节存在性检查，需人工确认内容质量）

**检测方式**：扫描 `docs/`、`architecture/`、`.opencode/` 目录下的 Markdown 文件，检查关键架构章节。

### 5.7 文档质量综合分

文档质量的最终输出由前6个子维度加权合成。

**设计依据**：
- README 权重最高(25%)，因为它是开发者接触项目的第一个入口
- ADR 权重高于注释密度(20%)，因为架构决策记录比代码注释对项目长期演进更重要
- 架构文档权重最低(10%)，因为已有 `SOFTWARE_ARCHITECTURE_QUALITY_GUIDE.md` 和 `DESIGN_QUALITY_METRICS.md` 覆盖

**评分算法**：

```
文档质量综合分 = README×25% + CHANGELOG×15% + ADR×20% + 代码注释×15% + JSDoc×15% + 架构文档×10%
```

### 设计依据汇总

| 维度 | 参考来源 | 核心依据 |
|------|---------|---------|
| README 完整性 | GitHub README 最佳实践 + Awesome README 社区标准 | 项目门面文档，影响上手效率和可信度 |
| CHANGELOG 完整性 | [keepachangelog.com](https://keepachangelog.com) 格式标准 | 版本演进记录，沟通变更的核心载体 |
| ADR 覆盖率 | Michael Nygard ADR 模式 + ThoughtWorks Technology Radar | 记录架构决策上下文，保障项目可持续性 |
| 代码注释密度 | Google Code Review 指南 + SonarQube 默认阈值 | 15%-25% 为业界公认健康区间 |
| JSDoc 覆盖率 | TSDoc 标准 + ESLint `require-jsdoc` 规则 | 公共API应有文档注释，支撑IDE提示和文档生成 |
| 架构文档完整性 | ISO/IEC 42010 + C4 模型 | 描述系统全貌和设计意图，降低认知负载 |

### 分数分级

| 分数区间 | 等级 | 说明 |
|---------|------|------|
| ≥ 85 | ?? 优秀 | 文档完整，维护良好 |
| 70-84 | ?? 良好 | 核心文档齐全，部分可改进 |
| 50-69 | ?? 需改进 | 关键文档缺失或质量不足 |
| < 50 | ?? 差 | 文档严重不足，影响项目可持续性 |


## 六、演进质量

演进质量衡量项目在**时间维度上的可持续性和健康度**。这是传统静态评估（仅看当前快照）无法覆盖的视角。演进质量由6个子维度加权合成，问题扣分作为健康度调节因子：

| 参考标准 | 本项目指标 | 描述 |
|---------|-----------|------|
| CHAOSS + GitHub 社区健康度 | 6.1 历史可追溯性 | 项目维护的持续性和团队活跃度 |
| Martin Fowler 债务象限 + SQALE | 6.2 技术债务趋势 | 代码债务的变化方向（改善/恶化） |
| Dependabot/Renovate + Sonatype | 6.3 依赖过时程度 | 第三方依赖的版本更新和安全状态 |
| SonarQube + ESLint | 6.4 废弃代码比例 | 未使用的代码对维护成本的拖累 |
| Google 小提交原则 + DORA (2025) | 6.5 增量质量 | 提交粒度对变更风险的影响 |
| 问题检测体系 | 6.6 问题扣分 | 各维度问题的严重级别综合扣分 |

6个子维度加权合成**演进质量综合分**（参见6.7节），该综合分参与总体评分计算（演进质量 × 25%）。

### 6.1 历史可追溯性

**权重**: 16% of 演进质量

**定义**：历史可追溯性衡量项目维护的**持续性和团队活跃度**。有规律的 Git 提交历史是项目"活着"的最直接证据——提交越频繁、参与人数越多，项目被持续关注和维护的可能性越高。

**设计依据**：
- GitHub 社区健康度指标（Repository Health Metrics）
- CHAOSS 项目（Community Health Analytics Open Source Software）：活跃度指标
- 项目有 Git 提交历史是衡量项目维护持续性的最直接证据

**评分算法**：

```
gitScore = 0~100分
  - 项目有 Git 仓库 → 20分
  - 最近 3 个月内有提交 → +20分
  - 最近 1 个月内有提交 → +20分
  - 最近 7 天内有提交 → +20分
  - 提交人数 > 1（团队协作）→ +10分
  - 有短期特性分支（存活<30天）→ +5分
  - 存在长期未合并分支（存活>90天）→ -5分（每分支）
```

**检测置信度**：高（精确测量）

**检测方式**：执行 `git log --oneline --since` 检查不同时间段的提交频率，`git shortlog -sn` 统计提交人数，`git branch` 统计分支存活时间。

**说明**：无 Git 仓库时返回 N/A，跳过该维度（权重按比例分配给其他非 N/A 维度）。

### 6.2 技术债务趋势

**权重**: 20% of 演进质量

**定义**：技术债务趋势衡量代码质量在时间维度上的**变化方向**。债务在减少说明架构在改善，债务在增加说明架构在腐化。单一时刻的债务点数不如趋势重要——一个从80分降到70分的项目比一个从60分升到70分的更值得警惕。

**设计依据**：
- Martin Fowler: 技术债务象限理论（"reckless vs prudent" 和 "deliberate vs inadvertent"）
- SQALE 方法论：技术债务量化追踪
- 单一时刻的债务点数不足以说明问题，**债务的变化趋势**才是关键——债务在减少说明架构在改善，在增加说明架构在腐化

**评分算法**：

```
debtTrendScore = 0~100分
  - 存在历史债务数据可对比 → 20分（有基线）
  - 债务点数相比上次评估下降 → +40分（改善中）
  - 债务点数相比上次评估持平 → +10分（稳定可控）
  - 债务点数相比上次评估上升 → -20分（腐化中）
  - 债务点数下降但新增债务速度快于偿还速度 → 额外-10分（隐性恶化）
  - 无高/中风险债务 → +20分
  - 有详细还款计划 → +20分
```

**检测置信度**：高（需历史数据，数据准确时置信度高）

**检测方式**：读取 `.opencode/arch-metrics/history.json` 中的历史债务数据，与当前 `arch-scan.js` 计算的技术债务点数对比趋势。若无历史数据，则按"无基线"处理（仅获得存在性基础分）。

**说明**：单一时刻债务点数不足以说明问题，趋势才是关键。历史数据由每次运行时自动保存。无历史数据时会降低评分但不会跳过该维度。

### 6.3 依赖过时程度

**权重**: 16% of 演进质量

**定义**：依赖过时程度衡量第三方依赖的**版本更新和安全状态**。过时的依赖不仅缺少新功能和性能改进，更关键的是缺少安全补丁，可能成为攻击入口。依赖全部保持最新是理想状态。

**设计依据**：
- Dependabot / Renovate 等依赖更新工具的告警策略
- Sonatype《软件供应链报告》：过时的依赖不仅缺少新功能，更关键的是缺少安全补丁

**评分算法**：

```
depRatio = 过时依赖数 / 总依赖数
depScore = 
  - depRatio = 0% → 100分（全部最新）
  - depRatio < 10% → 80分
  - 10% ≤ depRatio < 25% → 60分
  - 25% ≤ depRatio < 50% → 30分
  - depRatio ≥ 50% → 0分
  - 存在已知安全漏洞（npm audit 高危） → -30分
```

**检测置信度**：高（精确测量，依赖外部工具准确性）

**检测方式**：执行 `npm outdated --json` 获取过时依赖列表，执行 `npm audit --json` 获取安全漏洞信息。若项目无 `package.json` 则跳过该维度（权重分配给其他维度）。

### 6.4 废弃代码比例

**权重**: 12% of 演进质量

**定义**：废弃代码比例衡量项目中**不再被使用但仍保留的代码**的占比。废弃代码增加维护成本（需要浏览和理解无用代码）、误导新开发者（误以为这些代码仍在发挥作用），是架构腐化的隐性指标。

**设计依据**：
- SonarQube "死代码"（Dead Code）检测规则
- ESLint `@typescript-eslint/no-unused-vars` 规则
- 废弃代码增加维护成本、误导新开发者、增加编译和测试时间，是架构腐化的隐性指标

**评分算法**：

```
deadCodeScore = 0~100分
  - 检测到未使用的导出 → 每处 -10分（上限-30分）
  - 检测到未使用的导入 → 每处 -5分（上限-20分）
  - 存在空的/废弃的配置文件 → -10分
  - 存在重复/备份文件（如 *.bak, *.old）→ -10分
  - 存在被注释掉的大段代码（>10行）→ 每处 -5分（上限-15分）
  - 以上均无 → 100分
```

**检测置信度**：高（AST精确分析，但“废弃配置文件”为启发式）

**检测方式**：
- 遍历 `src/**/*.ts`，分析导出但未被其他文件导入的符号
- 检测 `import` 声明中未被使用的标识符
- 检查项目根目录是否存在 `.bak`、`.old`、`_backup` 等废弃文件
- 正则匹配文件中被注释掉的代码块（`/* ... */` 内含代码逻辑）

### 6.5 增量质量

**权重**: 16% of 演进质量

**定义**：增量质量衡量代码变更的**粒度合理性**。小步提交（每次变更50行以内）易于 review、回滚和调试，引入缺陷的概率更低；大爆炸式提交（500行以上）难以 review，往往是"一次性大量交付"的坏味道。

**设计依据**：
- Google Code Review "小提交原则"（Small CLs Are Better）：小提交易于 review，缺陷概率更低
- DORA (2025 更新版)：部署频率和变更前置时间与代码质量的相关性研究。DORA 在 2025 年已将指标从 4 项扩展到 5 项，新增“可靠性”维度。
- 平均提交大小是衡量增量质量的重要代理指标——大提交往往包含过多变更，难以 review，引入缺陷概率更高

**评分算法**：

```
avgCommitSize = 近 30 次提交的平均变更行数（insertions + deletions）
incrementalScore = 
  - avgCommitSize < 50 行 → 100分（小步提交）
  - 50 ≤ avgCommitSize < 100 → 80分
  - 100 ≤ avgCommitSize < 300 → 60分
  - 300 ≤ avgCommitSize < 500 → 30分
  - avgCommitSize ≥ 500 → 0分（大爆炸式提交）
  - 无 Git 记录 → N/A（不计入总分）
```

**检测置信度**：高（精确测量）

**检测方式**：执行 `git log --shortstat -30` 统计最近 30 次提交的变更行数，计算平均值。若无 Git 仓库则跳过该维度（权重分配给其他非 N/A 维度）。

### 6.6 问题扣分

**权重**: 20% of 演进质量

**定义**：问题扣分衡量项目整体**健康度的综合减分**，是对 ISO/IEC 25010 质量模型中各特性缺陷的汇总度量。高频、严重的问题越多，项目的稳定性越差，即使各子维度得分不低，也可能隐藏了需要立即关注的风险。

每个高严重性问题扣 5 分。

**问题类型与严重级别**：

| 问题类型 | 严重级别 | 检测条件 |
|---------|---------|---------|
| 循环依赖（跨包） | high | A→B→A，跨包依赖环 |
| 循环依赖（包内） | medium | A?B，同一包内依赖环 |
| 大文件 | high/medium | >1000行(high)/>500行(medium) |
| 高耦合 | medium | couplingScore < 60 |
| 低内聚 | medium | cohesionScore < 60 |
| 测试覆盖不足 | medium | testCoverage < 50 |
| 文档不足 | high/medium | docScore < 50/<70 |
| 设计质量不足 | high/medium | designScore < 50/<70 |

**评分算法**：

```
// 跨包循环依赖：-5分/个（high）
// 包内循环依赖：-3分/个（medium）
problemDeduction = min(100, max(0, 100 - highIssues × 5 - mediumIssues × 3 - lowIssues × 1))
```

**检测置信度**：高（精确检测）

**说明**：问题扣分作为演进质量的子维度，反映项目的健康度趋势。扣分直接纳入演进质量综合分。

### 6.7 演进质量综合分

演进质量的最终输出由前6个子维度加权合成。

**设计依据**：
- 技术债务趋势权重最高(20%)，因为债务方向比现状更重要——一个在改善的60分项目比一个在腐化的80分项目更有价值
- 问题扣分权重最高(20%)，反映“当前健康度”对演进质量的直接影响
- 历史可追溯性、依赖过时、增量质量各16%，反映“历史活跃度”、“供应链健康度”和“变更质量”同等重要
- 废弃代码权重最低(12%)，因为其对维护成本的影响相对可控

**评分算法**：

```
演进质量综合分 = 历史可追溯性×16% + 技术债务趋势×20% + 依赖过时程度×16%
                + 废弃代码比例×12% + 增量质量×16% + 问题扣分×20%
```

### 分数分级

| 分数区间 | 等级 | 说明 |
|---------|------|------|
| ≥ 85 | ?? 健康 | 项目持续演进，架构良好 |
| 70-84 | ?? 注意 | 核心指标正常，少数维度需关注 |
| 50-69 | ?? 需干预 | 多个维度存在风险 |
| < 50 | ?? 危险 | 架构严重腐化，需立即介入 |

### 演进质量问题检测

除了结构质量、设计质量、文档质量问题外，演进质量特有的问题检测如下：

| 问题类型 | 严重级别 | 检测条件 |
|---------|---------|---------|
| 依赖严重过时 | high | depScore < 40 |
| 技术债务增长 | high | 债务点数相比历史上升 > 20% |
| 项目不活跃 | high | 近 6 个月无 Git 提交 |
| 大量废弃代码 | medium | deadCodeScore < 50 |
| 大爆炸式提交 | medium | avgCommitSize > 500 |


## 七、内置规则（SAR-001 至 SAR-012）

本指南内置 12 条标准架构质量规则，覆盖结构、设计、文档、演进四大维度。
规则检测条件与评分算法章节（三至六章）中的阈值保持一致，供自动化工具统一执行。
检测条件见各子维度评分算法与第六章问题扣分表（6.6 节）。

| 规则ID | 名称 | 维度归属 | 严重级别 | 输出级别（无豁免） | 豁免后输出级别 | 检测条件 |
|--------|------|---------|---------|-------------------|---------------|---------|
| SAR-001 | 模块化失衡 | 结构质量 | MEDIUM | WARNING | 不支持豁免 | `avgFilesPerDir` 偏离理想值 5 过远（< 3 或 > 8） |
| SAR-002 | 高耦合 | 结构质量 | MEDIUM | WARNING | 不支持豁免 | `couplingScore < 60`（平均导入数超标） |
| SAR-003 | 低内聚 | 结构质量 | MEDIUM | WARNING | 不支持豁免 | `cohesionScore < 60`（超大文件占比过高） |
| SAR-004 | 高复杂度 | 结构质量 | HIGH | WARNING | 不支持豁免 | 超过 200 行的文件占比 > 30%（`largeFileRatio`） |
| SAR-005 | 测试覆盖不足 | 结构质量 | MEDIUM | WARNING | 不支持豁免 | `testCoverage < 50`（L1/L2/L3/L4 四层综合） |
| SAR-006 | God Class / God Object | 设计质量 | HIGH | WARNING | 不支持豁免 | 类 > 300 行且方法 > 10 个；文件 > 1000 行 |
| SAR-007 | Long Method | 设计质量 | MEDIUM | WARNING | 不支持豁免 | 函数 > 100 行 |
| SAR-008 | 分层依赖方向违反 | 设计质量 | MEDIUM | WARNING | 不支持豁免 | 低层模块依赖高层模块（controller/service/repository 反向） |
| SAR-009 | 接口膨胀 | 设计质量 | LOW | INFO | 不支持豁免 | 接口方法数 > 5（接口隔离原则阈值） |
| SAR-010 | 文档缺失 | 文档质量 | HIGH | WARNING | 不支持豁免 | `docScore < 50`（README/CHANGELOG/ADR 缺失组合） |
| SAR-011 | 依赖严重过时 | 演进质量 | HIGH | ERROR | 不支持豁免 | `depScore < 40`（依赖过时程度 ≥ 25%） |
| SAR-012 | 项目不活跃 | 演进质量 | HIGH | ERROR | 不支持豁免 | 近 6 个月无 Git 提交 |

**输出级别定义**（与模板元编程指南 4.0 版一致）：
- **ERROR**：阻断 CI 流水线，必须立即修复。
- **WARNING**：建议修复，可暂时忽略但需记录技术债务。
- **INFO**：仅提供信息，不阻断 CI，但建议审查。

**豁免机制**：
- 本指南 12 条规则默认**不支持豁免**（结构/设计/文档/演进维度为基础质量，无业务豁免场景）。
- 若项目确需豁免（如遗留系统迁移期），按组织豁免审批流程记录，并纳入演进质量问题扣分（6.6 节）。

**规则与问题扣分表的对应**（6.6 节 / 附录 A.6）：

## 八、可用性就绪度（轻量级检查项）

本指南主评估体系聚焦于可维护性相关的架构质量。根据 ISO 25010 产品质量模型，可用性（Usability）也是软件质量的重要维度。本检查项作为**独立附加项**，不计入综合分，供需要关注 API 可用性的团队参考。

**权重**: 不计入综合分（独立附加项）

**定义**：衡量代码库对外暴露 API 的可用性就绪程度，包括 API 文档一致性、错误处理模式等。

**设计依据**：
- ISO/IEC 25010: 可用性（Usability）——系统在指定使用条件下被有效、满意地使用的程度
- 工业实践：API 文档和错误处理是开发者体验的关键因素

**检查项**：

| 检查项 | 检测条件 | 状态 |
|--------|---------|------|
| API 文档完整性 | 导出 API 是否有 JSDoc/注释（由5.5节覆盖） | PASS / FAIL / N/A |
| 错误码/错误信息 | 检测 `throw new Error` 或错误码定义 | PASS / FAIL / N/A |
| 参数校验 | 检测导出函数中是否包含参数校验逻辑 | PASS / FAIL / N/A |
| 超时/重试机制 | 检测外部调用是否包含超时或重试逻辑 | PASS / FAIL / N/A |

**检测置信度**：中（启发式检测）

**说明**：本检查项覆盖 API 设计一致性（是否有文档、错误信息是否清晰）的基础层面。完整的可用性评估（如用户界面、交互流程）属于产品设计范畴，超出本指南的架构评估范围。如需更全面的可用性评估，建议配合 UX 评审流程。

### 9.1 工具集成

本指南的算法可通过静态分析工具实现：
- 结构质量：文件系统遍历 + AST 分析（TypeScript Compiler API）
- 设计质量：AST 分析 + 正则匹配（启发式检测需人工复核）
- 文档质量：Markdown 解析 + 正则匹配
- 演进质量：Git 日志分析 + npm 依赖分析

### 9.2 CI 门禁设置

建议将以下指标纳入 CI 门禁：
- 结构质量综合分 < 60 时阻断合并
- 存在跨包循环依赖（high 级别问题）时阻断合并
- 设计质量综合分 < 50 时触发警告

### 9.3 与 ATAM 的衔接

本指南的自动化评估输出可作为 ATAM（架构权衡分析方法）的输入材料。

**轻量级 ATAM 衔接指引**：

当自动化评估报告显示某模块得分低于阈值时，建议执行以下简化版质量属性场景分析：

1. **选择分析目标**：针对得分最低的 1-3 个模块
2. **定义质量属性场景**：为每个低分模块定义一个具体的质量属性场景（例如：“如果耦合度得分低于 40，则未来 6 个月内该模块的可修改性将显著下降，可能导致 2 人月以上的额外开发成本”）
3. **权衡分析**：识别该模块在可修改性（耦合度）与可分析性（复杂度）之间是否存在过度抽象或抽象不足的权衡
4. **决策**：根据分析结果决定是否执行重构

**完整 ATAM 场景**：如需要系统性的架构评审，建议参照 ATAM 完整方法（涉及架构师、利益相关者、质量属性场景头脑风暴等环节），本指南不替代 ATAM 流程。

### 9.4 诊断报告中的权衡警示

在诊断报告中增加“可修改性与可分析性权衡提示”：当某模块的耦合度得分高（可修改性好）但复杂度得分低（可分析性差）时，提示“该模块耦合度得分高但复杂度得分低，请检查是否存在过度抽象（过度使用设计模式或过度拆分），导致理解成本增加。”

### 9.5 诊断报告中的建议人工评审标记

在诊断报告中增加“建议人工评审”标记：当某模块同时触发三个以上低分指标（得分 < 50）时，自动标记“建议人工评审该模块的架构设计”。此标记旨在提示架构师介入，而非作为阻断性门禁。

## 附录C：常见问题（FAQ）

### Q1: 为什么文档质量不能跟结构质量、设计质量等同看待？

**问题背景**：本评估体系将文档质量作为与结构质量、设计质量并列的独立维度（各占不同权重）。有人可能会问：文档不就写在代码旁边吗？为什么不能把它当作结构质量或设计质量的一部分？

**回答**：虽然文档和代码紧密相关，但从**质量评估的视角**看，它们有本质区别：

| 维度 | 检测对象 | 是否影响运行时 | 所属 ISO 25010 模型 |
|------|---------|--------------|-------------------|
| 结构质量 | 代码本身（目录、导入、文件大小） | ? 是（依赖链影响运行时） | **产品质量模型** |
| 设计质量 | 代码本身（类、接口、继承、模式） | ? 是（多态、DI影响运行时） | **产品质量模型** |
| 文档质量 | 代码的说明（README、注释、ADR） | ? 否（完全不影响运行时） | **使用质量模型**（满意度/生产率） |

**三个根本原因**：

1. **属于不同的质量模型**：ISO/IEC 25010 将软件质量分为产品质量模型和使用质量模型。结构/设计质量属于前者，文档质量属于后者。文档影响的是"生产率"和"满意度"，而非"功能正确性"或"可维护性"——因此不能共用同一标准衡量。

2. **检测对象不同**：结构/设计质量检测的是**代码本身的属性**（模块化、耦合、继承、多态），不依赖标题和段落。文档质量检测的是**代码的描述**（README标题、CHANGELOG版本号、JSDoc覆盖率），依赖文字内容的完整性和规范性。前者是"构件质量"，后者是"说明书质量"。

3. **退化条件不同**：代码质量差时系统**运行时出错**（如循环依赖导致死循环）。文档质量差时系统照常运行，只是**人无法理解**。两者的"失效模式"完全不同，不能混为一谈。

**工业实践中的重要性**：虽然文档质量在标准分类中属于使用质量模型，但它在工业实践中的重要性不因此而降低。高质量的文档是软件长期可维护性的关键支撑——缺乏文档的系统即使代码质量再高，新成员也无法快速理解其设计意图。

**权重合理性**：文档质量占 20% 是折中结果：
- 如果低于 10% → 低估了文档对项目可持续性的影响（特别是 ADR 和 JSDoc）
- 如果高于 30% → 夸大了文档相对于代码本身的重要性（空有文档、代码一团糟也没用）

**类比**：结构/设计质量是**房屋的建筑质量**（框架是否牢固、户型是否合理），文档质量是**房屋的使用说明书**（是否有布线图、是否说明承重墙位置）。好的房屋本身质量好，但好的说明书让房屋更好用——两者是互补而非从属关系。

**相关引用**：
- ISO/IEC 25010: 产品质量模型 vs 使用质量模型
- Martin Fowler: "任何傻瓜都能写出计算机能理解的代码，优秀的程序员写的是人类能理解的代码"——但这说的是代码可读性（设计质量），而非文档完整性（文档质量）
- Google 工程实践: 文档评审与代码评审并列为独立的工程流程

### Q2: 为什么复杂度用200行文件占比而非圈复杂度？

**问题背景**：本评估体系中"复杂度"指标使用超过200行的文件占比作为计算依据，而非软件工程中更常见的圈复杂度（Cyclomatic Complexity）。这是出于什么考虑？

**回答**：选择文件行数作为复杂度的代理度量，而非圈复杂度，是基于以下原因：

**1. 工具实现可行性**：圈复杂度要求解析代码的抽象语法树（AST）或控制流图，需要集成 ESLint 的 `complexity` 规则或 SonarQube 的扫描器。文件行数仅需要 `wc -l` 或 `fs.readFileSync`，无需额外工具依赖。

**2. 维度正交性**：圈复杂度对应的是"函数内分支逻辑的复杂度"，更接近认知复杂度。文件行数对应的是"整体理解和导航的难度"——超过200行的文件无论其圈复杂度高低，都需要开发者滚动阅读。"认知复杂度"和"文件大小复杂度"是不同维度的指标。

**3. 经验阈值一致性**：200行为大宗阈值，与以下行业实践一致：
- SonarQube: 文件超过200行标记为"大文件"（Large File）
- Google 代码风格指南: 推荐文件不超过200行
- Linux 内核编码风格: 每个函数不超过100行，每个文件不超过200行

**局限性**：文件行数无法检测"一行极其复杂的表达式"或"多行但简单的配置代码"。如需更精确的复杂度分析，建议集成 ESLint 的 `complexity` 规则或使用专门的认知复杂度工具。

### Q3: 架构质量评估和代码质量评估有什么区别？

**问题背景**：既然都在分析代码，架构质量评估和常规的代码质量评估（如 SonarQube）有什么区别？

**回答**：两者在**评估对象、评估粒度、评估目标**上有本质区别：

| 维度 | 架构质量评估 | 代码质量评估 |
|------|-------------|-------------|
| **评估对象** | 模块间关系 | 模块内部质量 |
| **评估粒度** | 文件级、目录级（宏观） | 函数级、语句级（微观） |
| **关注点** | 耦合、内聚、依赖方向、分层 | 代码规范、重复、bug模式、漏洞 |
| **时间视角** | 包含演进趋势（历史对比） | 当前快照 |
| **输出形式** | 加权分数 + 趋势 + 改进建议 | 违规列表 + 修复建议 |
| **典型工具** | 本系统、Structure101、ArchUnit | SonarQube、CodeClimate、ESLint |

**类比**：
- 代码质量评估 = 检查一块砖是否合格（尺寸、强度、颜色一致性）
- 架构质量评估 = 检查一堵墙是否合理（砖的排列方式、与相邻墙的连接、是否承重）

**互补关系**：两者不互斥。一个架构质量高的项目如果没有代码质量规范，仍然会有大量细节问题。一个代码质量高的项目如果架构设计不当（如循环依赖、高耦合），仍然难以维护。因此，两者应**同时使用**。

### Q4: 同一个项目在不同运行中的评分结果不一致，为什么？

**问题背景**：同一项目连续运行两次评估，得到不同的评分结果。

**回答**：可能的原因包括：

1. **代码变更**：两次运行之间代码发生了变化（新增/修改/删除文件），这是评分变化的最正当原因
2. **依赖更新**：`npm outdated` 结果可能因为远程仓库的版本发布而变化
3. **Git 时间窗口**：`git log --since` 使用的"近7天"、"近1个月"是相对于运行时间的动态窗口，随时间推移提交可能移出窗口
4. **缓存清除**：如果 Python 版本检查缓存或依赖检查缓存被清除，第二次运行需要重新获取

**建议**：
- 在代码无变更的情况下，以第一次运行结果为基准
- 使用 `.opencode/arch-metrics/history.json` 追踪趋势，而非依赖单次运行的绝对值
- 运行前确认 `package-lock.json` 未被更新，Git 提交历史未发生变化
