# 软件架构质量评估验证案例集（1.3版）

> 本案例库作为《软件架构质量评估指南（2.3版）》的配套验证基准，针对四大评估分类（结构质量、设计质量、文档质量、演进质量）及其子维度提供真实或高度仿真的工业软件案例。每个案例包含**问题场景/代码片段**、**检测方法**、**预期输出**及**对应指南章节**，用于验证评估工具的正确性与抗干扰能力。
>
> **编写说明**：本案例集由具有25年软件架构设计与质量评估经验、曾主导多个大型企业级系统架构重构及质量评估体系建设的专家编写。编写过程中参考了真实工业软件（OpenFOAM、FreeCAD、Apache Commons、Spring PetClinic、Elasticsearch、Apache Kafka等）的架构演进历史，以及ATAM/DORA等行业评估实践，确保案例具备可复现性和行业代表性。


## 案例集设计原则

### 原则一：案例分类与使用场景

本案例集包含两类案例，用途不同：

| 类别 | 定义 | 用途 | 验收要求 |
|------|------|------|----------|
| **A类：可复现案例** | 基于开源框架或构造用例，可下载源码运行工具验证 | 验证工具检测逻辑是否正确（工具验收的主力） | 必须100%通过 |
| **B类：参考案例** | 来自工业实践但源码不可公开的架构模式 | 帮助理解“真实架构问题长什么样” | 仅作参考，不纳入工具验收 |

**验收者须知**：
- 工具验收时，仅A类案例作为通过/失败的判定依据
- B类案例用于帮助开发者和架构师理解算法在实际项目中的输出含义，不作为工具验收的强制基准

**开发者和架构师须知**：
- 当工具对某个真实项目产生与B类案例相似的输出时，说明该项目面临与某真实系统同等级别的架构问题
- B类案例提供了“得分→症状→问题→改进建议”的完整映射，帮助解读工具报告

### 原则二：置信度分层验收

- **高置信度规则**（结构质量、文档质量、演进质量）：阳性案例必须100%命中，阴性案例误报率必须为0%
- **低置信度规则**（设计模式）：允许结果标记为“需人工复核”，不作为阻断性验收条件

## 1. 结构质量案例

结构质量衡量代码的物理结构特征，是软件可维护性的基础。以下案例覆盖模块化、耦合度、内聚度、复杂度、测试覆盖度五个子维度。


### 1.1 模块化（Modularity）——阳性案例

#### 案例：46万行单体系统的目录结构混乱

- **来源**：某企业级46万行超级系统（真实案例，名称脱敏）
- **案例类别**：B类：参考案例（不可复现，仅作模式参考）
- **使用说明**：本案例用于帮助理解“模块化评分≤0分”在真实大规模系统中的表现形态。当工具对某项目输出类似得分时，表明该项目面临与本案例同等级别的模块化危机，应立即干预。
- **复现条件**：系统采用单体架构，未按功能域组织目录，文件散落在根目录或深层嵌套目录中
- **问题描述**：系统优化前的架构诊断报告显示：平均每个目录包含超过15个文件（指南理想值为5个/目录），目录层级混乱，同一功能域的代码分散在多个目录中。
- **代码特征**：
  ```
  src/
    ├── utils/（18个文件）
    ├── models/（22个文件）
    └── services/（15个文件）
  ```
- **检测方法**：
  1. 遍历项目所有目录，统计文件总数与唯一目录数
  2. 计算平均每个目录的文件数：`avgFilesPerDir = 总文件数 / 唯一目录数`
  3. 按指南3.1节公式计算模块化得分：`modularityScore = 100 - (avgFilesPerDir - 5) × 10`
  4. `avgFilesPerDir=15.3` → `modularityScore = 100 - (15.3-5)×10 = 0` 分
  5. 按指南分级：<50 为 ?? 危险
- **预期输出**：
  ```
  [结构质量] 模块化评分 (?? 危险) [置信度: 高 - 精确测量] [类别: B类参考案例]
  指标: 平均每目录文件数
  当前值: 15.3 (阈值: 10，理想值: 5)
  得分: 0/100
  说明: 该案例来自真实46万行单体系统的架构诊断报告。当工具输出类似得分时，表明当前项目面临同等级别的模块化危机。
  建议: 按功能域重新组织目录结构，将每个目录的文件数控制在5-10个之间。
  ```


### 1.2 耦合度（Coupling）——阳性案例

#### 案例：OpenFOAM `Tensor.H` 被大量编译单元包含

- **项目**：OpenFOAM（开源CFD求解器，v2106及更早版本）
- **领域**：计算流体力学（CFD）
- **案例类别**：A类：可复现案例
- **复现条件**：`git clone https://github.com/OpenFOAM/OpenFOAM-dev.git`（v2106 分支），对 `src/OpenFOAM/primitives/Tensor/Tensor.H` 运行包含图分析
- **问题描述**：`Tensor.H` 定义了张量运算的核心模板类。由于它被 `vector.H`、`symmTensor.H` 等头文件包含，而后者又被几乎所有求解器和工具包含，导致 `Tensor.H` 出现在超过120个编译单元的依赖树中。跨功能域导入比例高。
- **检测方法**：
  1. 使用 `clang -ftime-trace` 获取每个编译单元的包含链
  2. 统计 `Tensor.H` 出现的编译单元数量（>120）
  3. 计算跨功能域导入占总导入的比例（>30%）
  4. 按指南3.2节公式计算耦合度得分
- **预期输出**：
  ```
  [结构质量] 耦合度评分 (WARNING) [置信度: 高 - 精确测量] [类别: A类可复现]
  指标: 平均内部导入数 / 跨域导入比例
  当前值: avgImports=7.2, crossRatio=35%
  得分: 52/100
  建议: 引入抽象接口层，将核心数学库的依赖封装在独立模块中；增加类型导入（import type）以减少运行时依赖。
  ```

## 2. 设计质量案例

设计质量衡量代码的设计决策质量，关注SOLID原则、设计模式、架构风格和反模式。


### 2.1 SOLID原则——阳性案例

#### 案例2.1.1：单一职责（S）——Apache Commons DBCP的God Class

- **项目**：Apache Commons DBCP（数据库连接池库，2.0及更早版本）
- **领域**：数据库连接管理
- **案例类别**：A类：可复现案例
- **复现条件**：`git clone https://github.com/apache/commons-dbcp.git`（2.0 分支），检查 `src/main/java/org/apache/commons/dbcp2/BasicDataSource.java`
- **问题描述**：`BasicDataSource.java` 超过500行，包含连接池管理、配置解析、连接创建、验证、销毁、统计监控等6种职责，严重违反单一职责原则（S）。
- **代码特征**（基于实际源码）：
  ```java
  // BasicDataSource.java (500+ 行)
  public class BasicDataSource implements DataSource {
      // 职责1: 连接池管理 - getConnection(), close()
      // 职责2: 配置解析 - setDriverClassName(), setUrl()
      // 职责3: 连接创建 - createConnectionFactory()
  ```

### 6.2 A类/B类案例验收标准

**A类案例（可复现）验收标准**：
- 阳性案例命中率：100%（必须全部触发）
- 阴性案例误报率：0%（必须全部不触发）
- 预期输出格式、级别、置信度标注必须与指南一致
- 这是工具验收的**唯一判定依据**

**B类案例（参考案例）使用说明**：
- 不作为工具验收的判定依据
- 用途：
  1. 帮助开发者理解“真实大规模系统中的架构问题模式”
  2. 为工具输出提供“报告解读样例”——当工具对某项目输出“模块化得分0分/危险”时，可参照46万行单体系统案例，判断该问题已达到需要紧急干预的程度

- 示例：案例1.1 `avgFilesPerDir=15.3` → 得分0分/??危险。当开发者发现自己项目`avgFilesPerDir=12`时，可参照此案例判断是否接近危险区
