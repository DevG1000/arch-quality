## 二、新发现（1.7 版）

### P0-1：`@gcs_waiver` 无滥用上限，可全量豁免刷满 GCS-010

**相悖点**：§9.6 反滥用守卫仅监控 `@kernel_exempt`（> 30% 告警），`@gcs_waiver` **无任何上限**。由于该注解从密度**分母**中剔除文件，当项目内全部科学数据文件被豁免时 `scidata_files = 0`，密度退化为 `0 / max(1,0) = 0`，GCS-010 直接获得 35/35 满分。

**实测证据**（4 个裸数组文件全部标注 `@gcs_waiver`）：

```
density = 0.0   score = 35   waived_files = 4
abuse_warning = None          ← 守卫完全未触发
```

**相悖本质**：`@gcs_waiver` 的设计目的是"受控裸数组不扣分"，但缺少上限时它等价于"关闭 GCS-010"，且不留任何痕迹。这使 §9.7 声称的"不存在通过豁免绕过规则的路径"失效。

**建议（已采纳）**：
1. 将 30% 上限扩展至 `@gcs_waiver` 通道，与 `@kernel_exempt` 同阈值同告警格式
2. 新增 `density_undefined` 标记：当 `waived_files > 0 且 scidata_files == 0` 时置真，并输出 `caveat` 说明"本项得分不具参考意义"
3. 回归用例 `test_gcs_waiver_ratio_guard` / `test_density_undefined_when_denominator_waived_away`

### P0-2：空 reason 形式被接受为有效豁免，"reason 必填"可被绕过

**相悖点**：§9.5 规定"reason 必填，缺失 reason 的注解无效"。但原实现 `KERNEL_EXEMPT_RE` / `GCS_WAIVER_RE` 的 reason 捕获组未排除空串，且**非法形式检测正则在冒号后要求立即闭合**，导致 `/* @kernel_exempt: */` 与 `// @gcs_waiver:` 两种形式**既不匹配合法式、也不匹配非法式**，最终以空 reason 落入有效豁免。

**实测证据**（修复前）：

| 注解形式 | 修复前结果 |
|:---------|:----------|
| `/* @kernel_exempt: */` | `exempt={'src/a.cpp': ''}`，`invalid=0`，GCS-012 被静默排除 |
| `// @gcs_waiver:` | `waiver={'src/a.cpp': ''}`，`invalid=0` |

**相悖本质**：这是**虚假安心**的典型形态——用户写了注解、引擎承认了豁免、但审计链上没有任何理由记录，事后无法复核该豁免是否正当。H2 待办 H2-001 的定性（"虚假安心"）在此得到实证。

**建议（已采纳）**：合法式 reason 组改为 `\S[^*\n]*?` / `\S[^\n]*?`（首字符强制非空白）；非法式改为 `/\*\s*@kernel_exempt\s*(?::\s*)?\*/` 与 `//\s*@gcs_waiver\s*(?::\s*)?$`，覆盖"无冒号"与"有冒号但空"两种形态。回归用例 `test_empty_reason_forms_rejected`（4 种形式全覆盖）。

### P1-1：`KERNEL_SELF_DIRS` 含通用目录名，可静默误伤应用层代码

**相悖点**：`KERNEL_SELF_DIRS` 混合了两类性质不同的目录名：

| 类别 | 目录名 | 性质 |
|:-----|:-------|:-----|
| 强名 | `occt` / `opencascade` / `cascade` / `tkbool` / `tkg3d` / `tktop` | 内核发行版或内核模块专有名，命中即内核自身 |
| 弱名 | `geom` / `brep` / `geometric_engine` | 通用几何词，**应用层封装目录同名概率高** |

**实测证据**（三基线目录命中分布）：

| 基线 | 受评文件 | 内核目录排除 | 命中构成 |
|:-----|--------:|-----------:|:---------|
| OCCT | 13,445 | 753（5.6%）| `tkbool` 460、`tkg3d` 251、`brep` 42 |
| SALOME-GEOM | 861 | 28（3.3%）| `geom` 28 |
| FreeCAD | 6,512 | 0（0.0%）| — |

关键反例：SALOME-GEOM 的 `src/GEOM` 实为其**封装层源码**（正是维度④/⑧ 应当评估的对象），却被弱名 `geom` 排除。构造性验证：`src/geom/app.cpp` 中的直接成员访问访问被静默排除（GCS-012 计数 0，本应为 2）。

**建议（已采纳）**：不强删弱名（删除会破坏已校准的基线），改为**分类 + 可见化**：
1. 拆分为 `KERNEL_SELF_DIRS`（强名）与 `WEAK_KERNEL_SELF_DIRS`（弱名），并集用于判定
2. `waiver_audit.kernel_dir_exclusion` 输出 count/ratio/`strong_names`/`weak_names`，使弱名命中对用户可见
3. 内核目录排除纳入同一 30% 过度排除守卫，告警文案点明弱名风险

回归用例 `test_kernel_dir_over_exclusion_guard`。

### P2-1：reason 含 `*` 时注解静默失效（观察，不修）

`KERNEL_EXEMPT_RE` 的 reason 组为 `[^*\n]+?`（块注释不允许 `*`），当 reason 含星号（如 `性能优化*关键路径`）时不匹配 → 该文件**不被豁免**，规则照常触发。实测：GCS-012 计数 1（正确计入）。

**评估**：失效方向是**保守的**（漏豁免而非误豁免），不产生虚假安心，判定为 P2 观察项，不在本轮修改。建议后续改为非贪婪匹配 + 尾随 `\*/` 锚定，或在文档中提示 reason 避免使用 `*`。

## 三、专项核验：与递进扣分的交互（无缺陷，记录备查）

§2.4 递进扣分规则为"子维度 2.1 < 60 → 2.4 折半"。`@kernel_exempt` 与内核目录排除会**同时**改变 2.1 与 2.4 的统计基数，故存在一条间接影响链：

```
豁免某文件 → 2.1（GCS-001~004）计数变化 → 若 2.1 由 <60 升至 ≥60
          → 2.4 递进扣分被解除 → 2.4 得分 (score×0.5) 恢复为 score
```

**核验结论**：这不是缺陷（豁免本就应该影响评分），但属**非直觉的间接效应**——用户为 GCS-012 标注的豁免可能连带改变 GCS-010 的递进扣分状态。建议在 §9.6 审计说明中补一句提示，本轮以文档备注形式记录于 §9.6 的守卫表下方。
