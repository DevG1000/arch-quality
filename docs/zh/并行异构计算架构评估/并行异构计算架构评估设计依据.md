## 摘要

工业软件（CFD/FEM/多物理场）的性能与可行性越来越取决于**并行与异构执行架构**：以 MPI 做进程级域分解、OpenMP/线程做共享内存并行、以 CUDA/HIP/GPU 做设备级加速，并在此之上做 halo（ghost）交换、集合通信、负载划分与混合并行。与业务软件不同，这类架构的**正确性依赖执行配置**（进程数、线程数、设备可用性），缺陷常以**间歇性 race/deadlock、边界数据错或 CPU/GPU 数值分歧**出现，而非稳定崩溃；其价值也体现在**强/弱扩展曲线**而非单机耗时。通用质量模型（ISO/IEC 25010「性能效率」）与自动化测量标准（CK、CISQ/ISO 5055）均未定义针对**并行/异构执行面**的可度量指标，使其成为工业软件架构质量评估中长期缺位的核心维度。本文从必要性、定义、工程作用与设计逻辑四层，系统阐述「并行/异构计算架构（HPC/GPU）」作为独立评估项的**设计依据**。

## 1 建设必要性

### 1.1 通用质量模型存在理论缺口

ISO/IEC 25010 的「性能效率」仅给出**定性**子特性——时间行为、资源利用、容量。这些目标在单进程软件中可映射为响应时间、利用率；但工业软件并行/异构架构具有独特复杂性：

- **正确性依赖执行配置**：同一代码在 `rank=1` 与 `rank=1024`、不同线程数、有/无 GPU 下行为不同；通用"性能效率"无法表达"在何种配置下正确"。
- **缺陷是非确定性的**：halo 交换不成对、OpenMP 归约竞态、MPI 线程安全违规，表现为**间歇死锁或偶发数值偏差**，单次运行既不可复现、也不崩溃。
- **价值是可扩展性函数**：性能不是单点耗时，而是强/弱扩展曲线（Amdahl/Gustafson）；ISO 25010 无"扩展性"子特性。
- **异构双实现一致性**：CPU/GPU 两套实现的等价性，是任一单实现度量都无法覆盖的。

ISO 25010 只告诉我们要"高效利用资源"，却没有说明"如何度量域分解是否均衡、halo 交换是否成对、GPU 双实现是否与 CPU 数值一致、MPI 在多线程下是否安全"。

### 1.2 自动化测量标准存在适用盲区

CK 度量集（WMC/CBO/RFC/LCOM 等）基于**单语言面向对象**抽象语法树，无法跨进程/线程/设备追踪数据与执行流。CISQ/ISO 5055 提供可维护性与安全弱点的自动化规则，但范围限于同语言架构违规。对以下真实并行缺陷，测量能力为零：

- `MPI_Isend` 发出后未 `MPI_Wait`/`MPI_Test`，缓冲被复用 → 竞态或死锁；语法树无法表达"通信生命周期"。
- 多线程区调用未声明 `MPI_THREAD_MULTIPLE` 的 MPI → 未定义行为；CK 无"线程安全"概念。
- OpenMP `reduction` 缺失导致归约竞态；静态耦合度无法识别 pragma 语义。
- CUDA kernel 的 block/grid 硬编码，跨规模失效；通用度量无"launch 配置"维度。
- CPU/GPU 两套实现归约顺序不同 → 数值分歧；无单一实现度量能覆盖。

只依赖 CK/CISQ 的评估会给出**虚假的"架构健康"结论**，必须设计面向并行/异构执行面的专门度量元。

### 1.3 行业工程实践形成刚性倒逼（案例按源码实证校正）

主流开源/工业软件反复出现同一类并行架构问题（归属已按本地源码核验，锚点见 §附录 A）：

- **halo/通信配对缺陷**：OpenFOAM 的 `processorPolyPatch` 边界与 `decomposePar` 域分解中，非阻塞通信配对错误/阻塞 `Send` 未配对可致偶发死锁或边界数据错。
- **混合并行竞态**：**SU2**（MPI + OpenMP，`#pragma omp` 3 文件）与 **deal.II**（MPI + **TBB/Taskflow 线程**，局部 OpenMP）中，线程区 MPI 调用安全、残差归约竞态问题。
- **CPU/GPU 双实现分歧**：异构后端（CUDA/HIP）中归约顺序/精度差异导致结果不可比；**MFEM 以统一 `MFEM_HOST_DEVICE` 内核规避该问题（正样本）**，缺陷多见于"CPU/GPU 各写一份"的项目。
- **负载不均衡**：deal.II（`p4est` 分区）、OpenFOAM 的均分网格在非均匀算例下个别 rank 拖尾。
- **扩展性反模式**：热循环内集合通信、阻塞通信串行，随进程数超线性退化。

> **校正说明（专家校对 P0-1）**：本机 SU2 全仓 `__CUDACC__/ENABLE_CUDA/cudaMemcpy/hipMalloc` 唯一命中 `externals/catch2/catch.hpp`（第三方测试框架），**无真实 GPU 代码**；故 SU2 不作 GPU/双实现样本，GPU 样本用 **MFEM**。OpenFOAM `#pragma omp` 仅 2 文件，**≈纯 MPI**，不作混合并行样本。

这些架构问题倒逼行业承认：**并行/异构计算架构不是"性能调优细节"，而是直接影响正确性、可扩展性与可移植性的架构风险类型**，必须成为独立评估项。

## 2 内涵定义与边界划分

### 2.1 核心概念定义

**并行/异构计算架构（HPC/GPU）** 是指：工业软件将计算工作分布到**进程（MPI）、线程（OpenMP/TBB）、设备（GPU/CUDA/HIP）**，并在其间交换数据的结构性组织方式，以及该组织在正确性、一致性与可扩展性上的健康程度。它决定软件在以下方面的能力：

- **后端接口一致性**：CPU/GPU 实现是否一致、异构调用是否有设备守卫与合理 launch 配置、数据搬运是否克制；
- **MPI 域分解与 halo 交换**：域分解是否正确、halo 交换是否成对且尺寸匹配、通信是否与计算重叠；
- **负载均衡与进程拓扑**：划分是否按负载加权、进程拓扑/通信子是否合理；
- **混合并行冲突**：MPI×OpenMP 是否线程安全、共享变量/竞态是否受控、并行域嵌套是否合规。

**颗粒度定义**：

| 颗粒度层级 | 定义 | 评估方法 | 用途 |
|:--|:--|:--|:--|
| **基本颗粒度** | 并行调用单元（含 MPI/OpenMP/CUDA 调用的源码文件/函数）| 调用点上下文、pragma/directive 分析、通信配对 | 一致性/正确性评估的主要对象 |
| **辅助颗粒度** | 并行编排层（domain decomposition、通信子、solver 驱动）| 目录结构、通信/计算编排 | 辅助理解扩展性与拓扑 |

以**并行调用单元**为基本颗粒度，以**并行编排层**为辅助颗粒度；调用单元级别权重高于编排层级别。

**四子维检查项与检测方法**：

| 子维度 | 检查项 | 检测方法 |
|:--|:--|:--|
| 后端接口一致性 | CPU/GPU 双实现一致性、设备可用性守卫、launch 配置、H2D/D2H 搬运 | 双实现签名/常量比对、`#ifdef`/`cudaGetDeviceCount` 检测、launch 配置模式、`cudaMemcpy` 上下文 |
| MPI 域分解与 halo | halo 交换配对、尺寸、通信/计算重叠 | `Send/Recv`/`Isend+Irecv` 配对分析、图/邻接构建、阻塞通信上下文 |
| 负载均衡与进程拓扑 | 划分加权、拓扑/通信子 | 均分 vs 加权分区模式、`comm_split`/cartesian 使用 |
| 混合并行冲突 | 线程安全 MPI、OpenMP 共享变量、并行域嵌套 | `MPI_THREAD_MULTIPLE` 守卫、`omp` 数据作用域、`omp/MPI` 嵌套 |

**层级关系（专家校对 P1-4：不设自动折半）**：四个子维度**独立评分**（30/30/20/20）。"后端/halo/混合并行"为**基础层（正确性必要条件）**，"负载均衡"为**增强层（可扩展性）**；该划分仅用于**整改优先级指引**（先保正确性、再优化扩展性），**不实施"基础层<60 → 增强层折半"的自动扣分**（正确性与可扩展性相对正交，且阈值缺实证）。

| 层级 | 层级名称 | 评估内容 | 定位 | 对应规则 |
|:--|:--|:--|:--|:--|
| 基础层 | 后端接口一致性 | 双实现、设备守卫、launch、搬运 | 正确性**必要条件** | HPC-001~004 |
| 基础层 | MPI 域分解与 halo | 交换配对、尺寸、重叠 | 正确性**必要条件** | HPC-005~007 |
| 基础层 | 混合并行冲突 | 线程安全、共享变量、嵌套 | 正确性**必要条件** | HPC-010~012 |
| 增强层 | 负载均衡与进程拓扑 | 加权划分、拓扑/通信子 | 可扩展性**优化项** | HPC-008~009 |

> **HPC-009 定位（专家校对 P1-3）**：未使用 `comm_split`/cartesian **本身不是缺陷**（大量正确可扩展代码用 `MPI_COMM_WORLD` + 自定义邻居通信）。HPC-009 仅窄化为"多物理场/多网格存在多个通信域混用而未隔离通信子"这一具体反模式，默认 INFO；不因"未用某 API"判罚。

### 2.2 工业软件典型并行/异构架构模式

**纯 MPI 架构**：计算域经 domain decomposition 切分到多进程，进程间以 halo 交换与集合通信协作。典型代表：**OpenFOAM**（`processorPolyPatch`/`Pstream`，≈纯 MPI）。优点是扩展性好、进程隔离清晰；缺点是 halo/通信正确性与负载均衡成为主要风险。

**MPI + 线程（OpenMP/TBB）混合架构**：进程间 MPI、进程内多线程。典型代表：**SU2**（MPI + OpenMP，`#pragma omp` 3 文件）；**deal.II**（MPI + **TBB/Taskflow 线程**，局部 OpenMP）。优点是适配多核、减少 MPI 进程数；缺点是**线程安全 MPI、线程竞态、并行域嵌套**。

**单机多线程（OpenMP-only）架构**：单进程内 OpenMP 并行。典型代表：部分后处理/网格模块。优点是实现简单；缺点是无法跨节点扩展、共享变量竞态集中。

**GPU 异构 offload 架构**：CPU 主机 + GPU 设备，以 CUDA/HIP/OpenCL kernel 加速热点。典型代表：**MFEM**（`general/device.hpp`、`config/config.hpp.in` 的 `MFEM_USE_CUDA/HIP`）、CUDA 版 OpenFOAM（RapidCFD）。优点吞吐高；缺点是**双实现一致性、设备守卫、数据搬运**。

**可移植异构（性能可移植）架构**：Kokkos/RAJA/SYCL 抽象层写一次多后端运行。优点可移植；缺点是抽象层下后端一致性仍需验证。典型代表：**deal.II**（`portable_matrix_free`/step-64，Kokkos 设备后端；9.7 起取代 CUDAWrappers）。

**并行编排谱系**：

| 编排形态 | 描述 | 适用场景 | 代表 |
|:--|:--|:--|:--|
| 纯 MPI | 进程级域分解 | 跨节点大算例 | OpenFOAM |
| MPI + 线程 | 节点间 MPI、节点内线程 | 多核 cluster | SU2、deal.II |
| 单机 OpenMP | 单进程多线程 | 共享内存工作站 | 后处理模块 |
| CPU+GPU offload | 热点 kernel 下沉设备 | 加速热点 | MFEM |
| 性能可移植层 | Kokkos/RAJA/SYCL | 多后端可移植 | 新兴代码 |

**正样本参照（含锚点，见附录 A）**：
- **OpenFOAM**：`processorPolyPatch` halo（成对 `UOPstream`/`UIPstream`）+ `initInterfaceMatrixUpdate` 重叠 → HPC-005/007 **正样本（健康）**。
- **deal.II**：`p4est_wrappers`/`distributed/tria` 分区 + `PartitionWeights`/`get_cell_weights` 加权 + TBB 线程 → HPC-008 **正样本**；另 Kokkos 提供 GPU-capable（HPC-001/003 正样本方向：单一可移植内核 / 抽象 launch）。
- **MFEM**：`Device` GPU 抽象 + `MFEM_FORALL` 启动抽象 + 统一 `MFEM_HOST_DEVICE` 内核（0 `.cu/.hip`）→ HPC-002 运行期守卫参照；HPC-001/003 为**正样本（最佳实践，不应触发）**，其阳性缺陷样本需 C 类合成（见 §4.3）。
- **SU2**：`CSolver` + MPI `Allreduce` 残差归约；`MPI_Init_thread` 默认 `MPI_THREAD_FUNNELED`、`--thread_multiple` 启 `MPI_THREAD_MULTIPLE` → HPC-010 **正样本**；HPC-006 为常规每步残差 Allreduce（非必然缺陷）。

**本维度定位**：评估"**并行/异构执行组织是否健康**"，而非"是否采用某一特定并行技术"。采用 MPI 但通信不成对仍触发 HPC-005；采用 GPU 但双实现分歧仍触发 HPC-001；单机 OpenMP 项目不因"未用 MPI"被误判——规则以"缺陷模式"而非"技术选型"为判定依据。

### 2.3 与通用软件质量评估的本质差异（5 点）

1. **配置依赖的正确性**：并行软件在不同 rank/线程/设备下行为不同，需关注"配置变化下是否仍正确"。
2. **非确定性缺陷**：race/deadlock 间歇出现，通用静态度量无法表达"某次运行才出现"。
3. **可扩展性而非单点性能**：价值在强/弱扩展曲线。
4. **异构双实现一致性**：必须评估 CPU/GPU 路径数值等价。
5. **跨进程/设备数据流**：关键在 halo/通信的跨进程数据依赖，通用"耦合/内聚"不描述。

### 2.4 与相邻维度的边界裁决

| 共享关切 | 涉及维度 | 裁决 | 顺序 |
|:--|:--|:--|:--|
| 求解器模块结构 | ⑤ MPR × ⑥ | ⑤ 管模块边界/耦合/插件化；⑥ 管执行面（通信/后端/线程）| 先⑤后⑥ |
| 归约顺序/精度差异 | ③ NVR × ⑥ | NVR 管算法数值正确性；⑥ 管**并行实现引入**的差异（halo 边界、双实现）| 先③后⑥ |
| 同语言并行运行时 | ① MLR × ⑥ | MLR 管跨语言绑定；⑥ 管同语言内 MPI/OpenMP/CUDA | 先①后⑥ |
| 并行反模式债务 | 演进质量 × ⑥ | 演进管趋势；⑥ 管具体反模式 | 仅⑥计分 |

## 3 体系工程应用作用

**开发阶段**：新增并行路径（MPI 集合通信、GPU kernel、OpenMP 区）时，工具检查通信是否成对（HPC-005）、GPU 调用是否有设备守卫（HPC-002）、多线程区 MPI 是否线程安全（HPC-010）、OpenMP 归约是否受控（HPC-011）。

**架构演进阶段**：在"纯 MPI → MPI+线程 → GPU 异构"迁移时，量化双实现一致性风险、线程安全债务、数据搬运开销，支撑迁移决策。

**运维与演进阶段**：量化"并行架构债务"（未配对通信数、非线程安全 MPI 调用数、双实现分歧点）。

**多物理场集成阶段**：不同物理场可能运行于不同进程/设备，核间通信模式（集合/点对点/文件）与同步策略是耦合正确性的高风险区。

**持续集成门禁**：对新增并行模块检查通信配对（HPC-005）、线程安全 MPI（HPC-010，ERROR）；对修改并行逻辑的提交检测竞态/守卫是否被绕过。

**异构迁移决策**：引入 GPU 后端时，对比 CPU/GPU 路径的签名/常量/归约，量化"是否数值等价"。

## 4 体系设计逻辑（四层驱动催熟模型）

### 4.1 通用质量模型明确目标缺口

ISO/IEC 25010 的"性能效率"在单进程软件中已有成熟度量，但面向通用软件，无法为多进程/多线程/多设备的工业软件提供落地指导。这一层**指明方向但留下缺口**：我们知道应追求"高效并行、正确异构"，但不知道在 `MPI_Comm`/`omp parallel`/`cudaStream` 混合环境中，什么算"halo 交换正确"，什么算"线程安全"，如何度量"扩展性"。

### 4.2 自动化测量标准暴露能力盲区

CK/CISQ/ISO 5055 的前提是"所有代码能被同一抽象语法树覆盖"。当并行语义以 `MPI_Isend/MPI_Wait` 的**通信生命周期**、`#pragma omp reduction` 的**数据作用域**、`cudaMemcpy` 的**设备边界**表达时，语法树断裂、测量失效。只依赖 CK/CISQ 会忽略并行风险，给出虚假的"架构健康"结论。

### 4.3 行业实践梳理典型架构模式与风险陷阱（按源码实证校正）

**halo/通信配对缺陷**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 非阻塞 halo 交换 `MPI_Isend` 发出后未 `MPI_Wait/Test`；`Send/Recv` 不配对；halo 宽度不足以覆盖 stencil；阻塞 `Send` 在邻居环内未配对 → 竞态、死锁或边界数据错（OpenFOAM `processorPolyPatch`）|
| **解决方案** | 成对 `Isend+Irecv` + 统一 `Waitall`；halo 宽度按 stencil 阶数确定；环内通信用 `Sendrecv` 或非阻塞避免死锁 |
| **可提炼指标** | halo 交换配对（HPC-005）；通信/计算重叠（HPC-007）|

**混合并行竞态**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 多线程区调用非 `THREAD_MULTIPLE` 的 MPI；线程/`omp` 区共享变量缺 `private`/`reduction` → 数据竞争（SU2 MPI+OpenMP；deal.II TBB 线程）|
| **解决方案** | 启用 `MPI_THREAD_MULTIPLE` + 线程守卫；共享变量作用域正确；归约用 `reduction`/原子；避免线程内 fork |
| **可提炼指标** | 线程安全 MPI（HPC-010）；OpenMP 共享变量（HPC-011）；并行域嵌套（HPC-012）|

**CPU/GPU 双实现分歧**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 同一算子 CPU/GPU 两套实现，归约顺序/精度不同 → 结果不可比；设备无守卫导致无 GPU 时崩溃；launch 硬编码跨规模失效；频繁 H2D/D2H（缺陷多见于"CPU/GPU 各写一份"的项目；MFEM 用统一内核规避）|
| **解决方案** | 双实现数值等价测试；设备可用性运行时检测 + 回退；统一精度/归约；launch 按规模计算；搬运复用 |
| **可提炼指标** | 双实现一致性（HPC-001）；设备守卫（HPC-002）；launch 配置（HPC-003）；数据搬运（HPC-004）|

**负载不均衡**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 均分网格/任务，未按几何/物理量加权 → 个别 rank 拖尾（若未提供加权：deal.II p4est 支持 `PartitionWeights` 但默认按单元数；OpenFOAM decomposePar 默认均分）|
| **解决方案** | 加权分区（METIS / p4est）；动态 load balance |
| **可提炼指标** | 划分加权（HPC-008）；通信子隔离（HPC-009，窄化，默认 INFO）|

**扩展性反模式**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 热循环内**高频**集合通信（Allreduce/Bcast）、阻塞通信串行 → 随进程数超线性退化（注：每迭代残差归约是常规成本、非必然缺陷；仅当可局部化/降频而未做时计入）|
| **解决方案** | 局部化归约、通信与计算重叠、减少全局同步 |
| **可提炼指标** | 集合通信滥用（HPC-006）；强/弱扩展曲线（HPC-013 KNOWN_HOLES）|

**正样本参照**：OpenFOAM（`processorPolyPatch`/`Pstream`）、deal.II（`p4est` 分区 + TBB 线程）、MFEM（`Device`/`MFEM_FORALL`/统一内核）、SU2（`CSolver` + MPI `Allreduce`）分别提供 halo/负载/GPU/混合参照（锚点见附录 A）。注：MFEM 以统一 `MFEM_HOST_DEVICE` 内核与 `MFEM_FORALL` 抽象 launch 为**正样本**；HPC-001（双实现分歧）与 HPC-003（硬编码 launch）的**阳性缺陷示例需 C 类合成样本**（两份归约顺序不同的 CPU/GPU kernel；算法层写死 blockDim/裸 `<<<>>>`），不得以 MFEM 充当阳性。

### 4.4 行业共识推动确立核心评估项

"催熟"：当同一架构问题在多软件、多团队、多年反复造成严重危害，它从"个体痛苦经验"加速提升为"行业必需共识"。催熟三前提：**问题普遍存在**（几乎所有并行/异构工业软件都面临 halo/竞态/双实现风险）、**难以人工发现**（间歇 race、跨进程/设备）、**后果严重**（死锁、数值错、扩展性崩溃）。并行/异构评估满足三条。

**催熟三证据**：

- **学术界共识**：**MPI 标准**定义了非阻塞通信语义与线程级（`MPI_THREAD_MULTIPLE` 自 **MPI-2.0** 起定义，现行为 **MPI 4.1**）；**OpenMP 5.2** 规范定义数据作用域与归约；**Amdahl/Gustafson** 定律刻画强/弱扩展；**Roofline** 模型刻画计算/访存瓶颈；**ASME V&V 20** 提供 CFD/传热的**验证与确认方法学**（网格/时间步收敛、比较误差）——注意其为 V&V 方法学，**不专门规定并行验证/扩展性**，并行验证另循"强/弱扩展基准 + code-to-code 对比 + MPI 正确性工具"。
- **工业界实践**：OpenFOAM（域分解/halo）、deal.II（p4est 分区/线程装配）、MFEM（GPU 后端）、SU2（MPI+OpenMP）均把并行/异构正确性与扩展性作为核心工程关注；MPI/OpenMP 已成事实标准。
- **工具生态成熟**：MUST / MPI-Checker（MPI 正确性）、ThreadSanitizer / Helgrind / DRD（竞态）、CUDA compute-sanitizer（设备）、TAU / Score-P / VTune（扩展性剖析）、Intel Inspector。

## 5 与现有评估体系的衔接

| 维度 | 《软件架构质量评估指南》| 本评估项 |
|:--|:--|:--|
| **评估对象** | 通用代码目录结构与耦合度 | 并行/异构执行组织（通信/后端/线程/拓扑）|
| **评估颗粒度** | 文件/目录级 | 并行调用单元级 |
| **评估内容** | 平均每目录文件数、耦合度 | 后端一致性、halo、负载均衡、混合并行 |
| **评估方法** | 文件系统遍历 | 调用点上下文 + pragma/通信配对 + 设备边界 |

两者**互补而非替代**。本设计依据定义框架与核心维度，不定义与通用评估的合成算法（由激活子集全局归一化统一定义）；实施建议先通用评估、再并行/异构评估。

**与其他维度互补**：与 NVR ③（算法层 vs 执行层）、与 MPR ⑤（结构层 vs 执行面），先 ③/⑤ 后 ⑥，同一文件按主关切归属。

## 6 总体结论

并行/异构计算架构成为工业软件架构评估项，本质上是因传统质量模型与测量标准假设了"单进程、确定性、单后端"的纯粹世界，而工业软件的现实是**多进程/多线程/多设备协同、间歇缺陷、异构双实现已成常态**，并行执行组织直接决定软件的正确性、可扩展性与可移植性。本文从必要性出发，论证了理论缺口、测量盲区与实践倒逼；给出了定义、颗粒度、四子维检查项与典型架构模式（纯 MPI、MPI+线程、单机 OpenMP、GPU offload、性能可移植；HPC 评估"执行组织是否健康"而非"技术选型"）；明确与通用评估的本质区别；阐述开发/演进/运维/集成/CI 门禁/异构迁移的作用；通过四层催熟模型与多维证据揭示其设计逻辑；并以本地源码实证校正案例归属（SU2 无 GPU、OpenFOAM≈纯 MPI、deal.II 主用 TBB 线程、MFEM 为 GPU 样本）。

未来工具须内置并行/异构执行面的专用分析：halo 交换配对、线程安全 MPI、CPU/GPU 双实现一致性、负载划分加权、并行域嵌套。其中 HPC-005、HPC-010、HPC-001、HPC-011 应作为核心技术参照。
