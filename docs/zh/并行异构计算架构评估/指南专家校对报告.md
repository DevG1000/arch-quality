> **评审视角**：工业软件（CFD/FEM/多物理场）并行/异构架构设计与开发专家（与设计依据校对本同一专家）

## 一、总体评价

结构完整（概述/置信度/权重/评分/综合分/分级/规则/映射/实施/KNOWN_HOLES/样本），与设计依据 v0.3 的子维、规则、边界一致，适用性归一化与门禁思路正确。但**评分与严重度脱节**，存在"高危缺陷仍判优秀"的结构性缺陷，属阻断级。

## 二、问题清单

### P0（阻断，必须清零）

**P0-1 单一 HIGH / ERROR 违规仍可评"优秀"——评分稀释，severity 与分级脱节**

- **证据（算术核验）**：按指南模型（子维 30/30/20/20；规则赋分），逐条核验：

| 场景 | overall | 等级 |
|:--|:--:|:--:|
| 全通过 | 100.0 | 优秀 |
| **HPC-010（ERROR）违规** | **92.0** | **优秀** |
| HPC-005（HIGH）违规 | 85.0 | 优秀 |
| HPC-012（HIGH）违规 | 95.0 | 优秀 |
| HPC-011 违规 | 93.0 | 优秀 |
| HPC-001 违规 | 91.0 | 优秀 |
| HPC-005 + HPC-010 | 77.0 | 良好 |

- **问题**：一条 **ERROR 级**（HPC-010）或 **HIGH 级**（HPC-005/012）缺陷，因权重稀释只扣 5–15 分，仍落"优秀（≥85）"。**严重度/门禁与分数分级不一致**，会给出"高危但优秀"的误导结论。
- **修订要求**：
  1. **等级封顶**：任一 **ERROR** → 总分等级封顶"需改进"（或直接"不合格"）；任一 **HIGH** → 封顶"需改进"。
  2. **分数与门禁分离**：报告同时给"分数等级"与"门禁状态（PASS/BLOCK）"，ERROR 违规时门禁 BLOCK（不因分数高而放行）。
  3. 或在评分模型中对 HIGH/ERROR 采用**非线性扣分/子维封顶**。

**P0-2 HPC-010 设 ERROR，但静态判定条件未收紧，误报即阻断 PR**

- **问题**：HPC-010 为 ERROR（阻断），但"omp 内调 MPI = 非线程安全"需排除 `omp master/single`、封装函数、仅主线程调用等情形；静态作用域分析易误报。指南 §五检测逻辑写"且非 omp master/single"，但未定义跨函数/封装的处理，误报将直接阻断。
- **修订要求**：
  1. **收紧触发条件**：仅当"`omp parallel` 作用域内**直接**调用 `MPI_*`、**且**不在 `omp master/single` 内、**且** `MPI_Init_thread` 级别 < `THREAD_MULTIPLE`"才判 ERROR；跨函数/封装调用降为 WARNING/候选。
  2. **先校准后阻断**：新维度首期建议以 **WARNING** 上线，经阶段 4 案例校准后再升 ERROR（与"低/中置信不得 ERROR"精神一致）。

### P1（应修，影响可信度/效度）

**P1-1 HPC-005 配对检测跨函数/RAII/异步，置信度应为"中低"而非"中"**
- `MPI_Wait` 可能在另一函数、`Waitall`/`Waitany`、RAII 封装、或异步流水线中；仅看同函数易误报。建议 HPC-005 置信度降 **中低**，并限定"同函数/同作用域"判定，跨作用域记"候选"。

**P1-2 INFO / LOW 规则赋分过重，与"INFO 不阻断、低置信"语义冲突**
- HPC-009（LOW/INFO/低置信）占 S3 的 15%；HPC-007（LOW/INFO）占 S2 的 20%。INFO/LOW 应更多为"提示"，建议降到 5 分以内或仅作附加项，避免低置信规则显著左右分数。

**P1-3 指南硬编码顶层权重 0.15，违背"单一事实源"**
- §三写"候选权重 0.15"，但该项目刚在 H1/H2/H3 反复强调"权重单一事实源=registry"。且 registry 目前**尚无 `dim.hpc_gpu`**（仍 7 引擎/10 维/84 规则）。建议改为"顶层权重以 `meta_model_registry.json` 为准（待 WP-3 阶段 B 注册）"，不在指南里写死数值。

**P1-4 缺"规则可行性分级矩阵"与豁免机制**
- H3 must-adopt 要求"规则可行性分级（🟢/🟡/🔴 + KNOWN_HOLES）"。指南只有置信度，没有 🟢/🟡/🔴 的可行性分级表；也缺豁免（如 HPC-003 在基准/教学场景的 `@benchmark_ok`）。建议补矩阵与豁免规则。

**P1-5 HPC-001 检测"归约顺序分歧"静态不可判**
- 指南 §五 HPC-001 检测逻辑含"比对 reduction 顺序"，但归约顺序在编译/运行时才定，静态无法比对。建议窄化为**可静态的信号**：同算子 CPU/GPU 双实现是否存在、签名/常量是否一致、是否有数值等价对照测试；"归约顺序分歧"归运行时（KNOWN_HOLES）。

### P2（可选，精化）

- **P2-1 二元赋分粒度过粗**：规则"触发→0"导致分数跳跃（如 S1 只能取 0/15/25/30…）。建议引入阈值分级（0 处/少量/大量）或多档扣分。
- **P2-2 HPC-006 "热循环"难静态判定**：需循环嵌套/调用频次启发式，易误报；建议标注"中低置信 + 人工复核"。
- **P2-3 分级区间表述**：`70–84` 与 `≥85` 之间的 84.x 归属需明确（建议写 `70 ≤ x < 85`）。
- **P2-4 算例缺具体代码/行号**：正/负例为文字描述，建议附最小代码片段（阶段 4 案例集补）。
