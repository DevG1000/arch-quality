## 二、新发现问题

### P1（应修/须说明，影响方法学与纪律）

**P1-A 子维适用性归一化导致"跨项目不可比"，指南未标注/禁止混合比较**

- **事实**：§三 对不适用子维剔除后按剩余权重归一化（纯 MPI→仅 S2/S3 归一到 0.6/0.4；含 GPU→四子维全用）。不同项目 `is_hpc` 适用集不同，**HPC 得分的语义基线不同**。
- **风险**：把"纯 MPI 项目 82 分"与"GPU+MPI 项目 82 分"并列比较会误导（与 H2 决策 8b"子集评分与全量评分禁止混合计分"是同类问题）。
- **修订**：报告中标注 `applicability_set`（适用子维集）与 `score_scope=subset`，并声明**不同适用集不可直接比较**；跨项目排名时须先对齐适用集或分群。

**P1-B "已确认违规"未定义——封顶与 BLOCK 都依赖它**

- **事实**：v0.2 的等级封顶/门禁写"仅对**已确认**违规生效"，但全篇未定义"已确认"由谁/如何判定。
- **风险**：CI 自动运行时，规则输出是"候选"还是"确认"不清 → 封顶/BLOCK 可能形同虚设或误伤。
- **修订**：明确"已确认"= ①高置信度规则直接命中，或 ②人工/复核确认的候选；并规定自动化链路中默认按"候选"处理（不封顶、不 BLOCK），仅高置信规则可自动确认。

**P1-C HPC-008"均分有依据说明"依赖注释意图，违反"可静态实现信号"纪律**

- **事实**：HPC-008 建议修复写"加权分区**或说明均分合理**"；而编制指南 1.8 明确"每条规则须定义**可静态实现的检测信号**，**禁止依赖注释意图**"。
- **风险**：静态工具无法判定"是否已说明合理"，导致该条不可机检或误判。
- **修订**：把"说明均分合理"改为**可检信号**：例如"分区调用存在 weights 参数/加权配置（`p4est_weights`/`PartitionWeights`/METIS 权重）"才判通过；否则记"均分（INFO）"，由人工复核是否合理。即：**可检部分只判'有无加权'，'是否合理'交人工**。

### P2（精化）

**P2-A INFO 规则赋分不一致**：同为 LOW/INFO，HPC-003=15、HPC-007=10、HPC-009=5。建议统一 INFO 赋分档（如 ≤10），或说明差异理由（HPC-003 影响面更大）。

**P2-B 封顶后"数值分与等级不一致"的展示规则未定**：score=92 但封顶显示"需改进"，报告需规定呈现方式（如"分数 92（等级受封顶：需改进）"），避免读者困惑。

**P2-C HPC-002 对"GPU-only"项目可能误报**：纯 GPU 部署（无 CPU 回退需求）下"缺设备守卫"未必是缺陷；建议对"明确 GPU-only"项目降级/豁免（如 `@hpc_gpu_only`）。

**P2-D HPC-006"热循环"未定义**：应在指南给出可判定口径（如"位于时间步/非线性迭代循环体内，或调用频次 > N"），否则检测边界模糊。

## 四、修订要求 / 阶段 4 门槛

1. **P1-A**：报告增加 `applicability_set` 与"跨适用集不可比"声明。
2. **P1-B**：定义"已确认违规"，并规定自动化链路默认为"候选"（不封顶/不 BLOCK）。
3. **P1-C**：HPC-008 改为"有加权信号→通过；无→INFO，人工复核合理"。
4. P2 可选：统一 INFO 赋分、明确封顶展示、GPU-only 豁免、定义"热循环"。
5. 以上完成后进入**阶段 4（验证案例集）**，并在阶段 4 用样本实证校准阈值/赋分与 HPC-010 误报率。
