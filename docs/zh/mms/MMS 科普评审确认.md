### #2 [专家 A] 并行通信 Bug → 分区边界通量交换错误

> "并行通信 Bug"的检测描述需修正。MMS 在并行下跑出不一致结果，更常见的原因是分区边界上的 ghost cell 交换未正确实现。

**编写者确认**：✅ **采纳**，并进一步修正

原文：
> 并行通信 Bug — ❌ 偶发 — ✅ 结果不一致

改为：
> 分区边界通量交换错误 — ❌ 单元测试难覆盖 — ✅ 串并行结果不一致

理由：专家 A 指出的"ghost cell 交换"确实是 MMS 在并行场景下最常暴露的问题类型，比泛泛的"通信 Bug"更精确。

### #3 [专家 A] 3 套网格 → 推荐 4-5 套

> 三套网格是底线，推荐 4-5 套（h, h/2, h/4, h/8）。三套网格可能因两点的偶然对齐而误判为通过。

**编写者确认**：✅ **采纳**

虽然 3 套网格在理论上可以计算观察阶（`p = log(e₂/e₁) / log(h₂/h₁)`），但专家 A 指出工业实践中 3 套网格确实存在偶然风险。将修改为：

> **网格建议**：最低 3 套网格，推荐 4-5 套（h, h/2, h/4, h/8）。越多的网格层级越能排除网格质量偶然因素，观察阶的计算越可靠。

同时在 §3.1 的示例表中补充一列"超细"网格 160×160。

### #4 [专家 A] 非线性 PDE 源项推导——强调使用符号计算工具

> 非线性 PDE 的源项推导强烈建议使用符号计算工具（SymPy、Mathematica）而非手算。我在实际项目中见过多次手算失误的案例。

**编写者确认**：✅ **采纳**

这是一个非常实际的工程经验。在 §3.3 FAQ 中补充：

```
Q: 非线性 PDE 的 MMS 怎么做？
A: 可以。但注意事项：制造解代入非线性 PDE 后，源项的解析推导
   可能包含高阶导数项和混合导数项，手算极易出错。
   强烈建议使用 SymPy（Python）、Mathematica 或 Maple 等符号
   计算工具辅助推导和验证。
```

### #5 [专家 A + B] 新增两个 FAQ

> 建议增加 FAQ："MMS 验证通过是否意味着代码完全没有 Bug？" 和 "MMS 的网格需要满足什么质量要求？"

**编写者确认**：✅ **采纳**（两条都加）

将在 §3.3 中增加：

```
Q: MMS 验证通过是否意味着代码完全没有 Bug？
A: 不是。MMS 只能验证制造解覆盖的代码路径是否实现正确。
   未覆盖的代码分支（如时间步进、湍流模型、特定的边界条件类型）
   仍可能存在 Bug。MMS 应与单元测试、回归测试、基准测试等
   组合使用，构成完整的验证体系。

Q: MMS 的网格需要满足什么质量要求？
A: MMS 假设网格均匀或至少光滑变化。极度扭曲的网格会在离散误差
   之上叠加额外的几何误差，使观察阶计算失真。建议使用均匀网格
   或质量受控的结构化网格。如果必须使用非结构网格，应确保网格
   质量指标（偏斜率、正交性）在可控范围内。
```

### #8 [专家 B] 明确 MMS 是"必要条件非充分条件"

> MMS 应与单元测试、回归测试、基准测试组合使用，构成完整验证体系。

**编写者确认**：✅ **采纳**

将在文档引言或结论处增加一段明确说明：

```
MMS 是代码验证的强有力工具，但它不是万能的。
MMS 验证通过 = 制造解覆盖的代码路径实现正确 ≠ 全部代码无 Bug。
完整的代码验证体系应包含：
• 单元测试 — 验证单个函数/模块的正确性
• MMS 验证 — 验证 PDE 离散化的整体正确性
• 基准测试 — 在标准算例上对比与参考解的一致性
• 回归测试 — 防止代码修改引入退化
```
