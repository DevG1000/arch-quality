# AI 架构评估文档编制指南（1.8版）

> 本指南面向**参与评估文档创建的新手**，系统梳理了如何参照已有的四类架构评估指南（多语言混合依赖、模板元编程、数值算法、求解器模块化架构）的编制流程，创建新的工业软件架构评估文档。
>
> **核心特色**：本指南以"用户与AI助手的对话流程"为主线，每步提供可直接复制的提示词模板，强调人机协作而非单人写作。
>
> **1.7 版核心更新**：在步骤5"评审与迭代"中新增 **"5.0 AI虚拟专家初审"** 子步骤，让AI扮演多个"虚拟专家"角色（架构专家、行业专家、验证专家、标准专家）对文档进行多维度初审，帮助编写者在提交人类专家前完成自我诊断和预修正，提高正式评审效率。
>
> **1.8 版核心更新**（基于 H2 WP-1 维度④ 编制实测）：将"多轮修订-回评循环"制度化（§1.4）；新增"编写者确认记录"环节（§2.2）；规则"可检信号 + 置信度-检测难度对应"要求（§3.5）；案例-指南版本绑定（§4.1）；构造用例 API 正确性/可编译要求（§4.3）；新增"案例覆盖矩阵双向核对"（§4.4）；AI 初审"修订后回评 + 跨文档一致性"（§5.0）；专家校对"证据要求"（§5.1）。

## 一、概述

### 1.1 这份指南是为谁写的？

| 角色 | 说明 |
|------|------|
| 新手文档编写者 | 需要掌握评估文档的编制流程和规范 |
| 技术负责人 | 需要审核文档是否符合标准 |
| 架构师 | 需要了解文档内容的具体逻辑和行业背景 |
| 验证工程师 | 需要了解评估文档与评估工具的关系 |

### 1.2 系列文档的共性特征

目前已有的评估指南都遵循统一的方式：

| 指南 | 评估对象 | 内置规则 | 评估维度 |
|------|---------|---------|----------|
| 多语言混合依赖评估指南 | C++/Python/Fortran/Tcl 多语言混合 | 12 条（MLR-001～012）| 6 个维度 |
| 模板元编程与编译时依赖膨胀评估指南 | C++ 模板实例化与编译时膨胀 | 12 条（MLR-013～024）| 6 个维度 |
| 数值算法正确性与精度保障评估指南 | 数值稳定性、舍入误差、MMS 验证 | 12 条（NVR-001～012）| 6 个维度 |
| 求解器与物理场模块化架构评估指南 | 求解器模块边界、耦合架构、插件扩展 | 12 条（MPR-001～012）| 4 个维度 |

**共性模式**：4-6 个评估维度，再细分为 12 条规则 + 加权综合分 + 分数分级 + 置信度标注 + 算例交叉验证。

### 1.3 本指南的设计原则

本指南的编制遵循**职责分离**原则——AI负责生成和结构梳理，但所有关键判断（如子维度划分、权重分配、阈值设定、严重级别）的决策权归用户，AI生成的内容必须经用户确认后才可定稿。权重、阈值、关键决策等关键参数的决策权必须归用户。

### 1.4 文档成熟度阶段

本指南将评估指南及相关文档的成熟度分为三个阶段，用于指导流程推进：

| 阶段 | 版本号模式 | 说明 | 用途 |
|------|-----------|------|------|
| **初稿** | 1.0 | 首次完成编制，结构完整但未经外部审核 | 内部审阅、初步评审 |
| **可用版本** | 1.1 | 经过至少1轮专家校对并确认，内容稳定 | **可作为后续文档编制的依据** |
| **最终版本** | 1.3+ | 经过3位国际专家评审并全部确认 | 正式发布、推广实施 |

**"可用版本"的定义**：文档在完成专家校对（至少1位行业专家）后，所有重大结构性问题已解决，内容基本稳定，可作为后续依赖文档编制的依据。国际评审为"最终确认"环节，用于正式发布。

**多轮修订-回评循环（1.8 新增）**：文档编制并非单轮"自评→校对→定稿"。实测流程（H2 WP-1 维度④）表明：
- **P0 清零**：进入下一阶段（人类专家校对/发布）前，P0 级问题必须清零；
- **P1 可跨轮**：P1 问题可在后续轮次处理，但应在版本历史中登记；
- **每轮修订后回评**：任何修订（含 P0/P1 修复）后，应重新运行 AI 虚拟专家初审（见 5.0），确认 P0 已清零、无新引入矛盾；
- **版本号推进**：每轮修订推进次版本号（1.0→1.1→1.2…），版本历史须记录每轮修订原因。

## 二、AI助手能力边界与角色定义

### 2.1 AI助手的角色定义

| 方面 | 说明 |
|------|------|
| **职责** | 专门负责架构评估文档编制的AI助手 |
| **角色** | **辅助判断、拟定范围、建议权重或确定阈值**，但这些决策必须由用户确认 |
| **定位** | 逻辑整理 + 内容生成 + 一致性自检 |
| **约束** | AI生成的所有内容都必须经用户确认后才可定稿 |

### 2.2 用户与AI助手的分工

| 工作内容 | AI助手的职责 | 用户的职责 | 交互模式 |
|---------|-------------|-----------|----------|
| **需求分析与范围界定** | 整理已有材料，生成初稿 | 定义评估范围、确定评估目标 | 用户给出需求 → AI整理结构 |
| **设计依据编制** | 生成四层催化模型初稿，提供行业案例搜索 | 审核逻辑自洽性、确认行业依据准确性 | AI生成→用户审核→迭代修正 |
| **子维度与权重设计** | 提供参考案例，计算权重分配建议 | 确定子维度、确认权重合理性 | AI建议→用户决策 |
| **评分算法编写** | 生成算法框架，提供模板 | 审核阈值合理性、确认检测方法 | AI生成初稿→用户审核阈值 |
| **内置规则设计与置信度标注** | 生成规则清单和置信度标注 | 审核规则完整性、确认严重级别和置信度 | AI生成→用户审核→补充 |
| **验证案例集编制** | 搜索开源框架，生成案例初稿 | 确认案例可复现性、审核预期输出 | AI搜索→用户验证 |
| **AI虚拟专家初审** | 扮演多个虚拟专家角色，提供多维度初审反馈 | 审核初审意见、修正P0问题 | AI初审→用户修正→决定是否进入人类评审 |
| **评审与迭代** | 汇总评审意见，生成修改建议 | 判断评审意见合理性、做出决策 | AI汇总→用户决策→AI执行 |
| **编写者确认记录** | 逐条核实专家校对意见（对照仓库文档原文/实测证据）| 确认接受/提出异议、决定修订动作 | AI逐条核实→编写者确认→AI执行修订 |
| **术语统一** | 全文搜索替换、生成术语表 | 审核术语准确性 | AI执行替换→用户确认 |

### 2.3 AI助手能做什么？不能做什么？

| AI助手可以做的 | AI助手不能做的 |
|---------------|---------------|
| 读取评估指南并提取共性模式 | 做价值判断（权重分配、阈值设定等）|
| 生成评估文档的初稿结构 | 确认行业数据的准确性（需用户/专家审核）|
| 生成子维度、评分算法、规则的初稿 | 确认案例的可复现性（需用户实测验证）|
| 搜索开源框架信息，提供参考材料 | 判断哪些材料该采用（需用户决策）|
| 全文搜索并统一术语 | 替代人类专家做最终决策 |
| 生成AI虚拟专家初审报告 | 承担评审结论的责任 |
| 按用户指令修改任何内容 | 独立决定修改内容 |
| 生成设计依据的四层催化模型 | 未经用户确认就定稿 |

### 2.4 使用AI助手的最佳实践

1. **分步引导**：每一步要求AI输出对应文档结构的新增部分，不一次性生成全部
2. **提供模板**：给AI提供已有的评估指南作为模板参考
3. **人工审核**：AI生成的每个部分都需要人工审核
4. **决策留权**：权重、阈值、关键参数等决策必须由用户完成
5. **迭代完善**：根据AI生成初稿，通过多轮对话完善
6. **术语统一管理**：AI可汇总并执行全局替换，但最终审核权归用户
7. **版本管理**：所有AI生成的内容都通过Git追踪变更
8. **真实来源验证**：要求AI提供真实来源（GitHub链接、文件路径、DOI、标准编号），对关键引用进行人工核实
9. **追踪AI生成内容**：对AI生成的每份文件进行版本追踪
10. **记录AI修改内容**：记录AI生成内容、用户修改内容、修改时间、修改人

### 2.5 推荐工具

| 工具 | 用途 | 适用阶段 |
|------|------|----------|
| Claude / DeepSeek | 生成初稿、提取模式、扮演角色 | 全流程，文档编制 |
| Perplexity | 搜索真实来源、验证信息、寻找参考案例 | 内容核实、验证案例搜索 |
| Git | 版本管理、变更追踪 | 全流程 |
| Markdown 编辑器 | 编写文档 | 全流程 |

## 三、完整编制流程概览

本指南采用"分阶段、对话式"的编制流程，以**概要阶段**组织。各阶段之间存在**多轮迭代**的可能。当一份文档达到"可用版本"状态时，可以并行启动下一份文档的编制，而不是等待全部完成。

```
阶段一：内容定义与范围界定
  需求分析 → 内容清单1.0（草稿）→ 专家校对 → 内容清单1.1（可用版本）
                    ↑ 达到可用版本后，进入下一阶段编制
阶段二：评估指南编制
  3.1 子维度与权重设计
  3.2 评分算法编写
  3.3 可读性优化
  3.4 分数分级定义
  3.5 内置规则设计与置信度标注（合并原4+5）
  3.6 实施建议编写
                    ↑ 达到可用版本后，进入下一阶段编制
阶段三：验证案例集编制
  4.1 案例分类设计（A/B/C）
  4.2 A类可复现案例搜索与编写
  4.3 构造用例编写
  4.4 案例覆盖矩阵核对
                    ↑
阶段四：评审与发布
  5.0 AI虚拟专家初审（每份文档1.0完成后、提交专家前）
  5.1 专家校对（文档1.0版 → 可用版本1.1）
  5.2 评审意见汇总（AI助手）
  5.3 评审意见确认表（编写者逐条确认）
  5.4 更新文档（可用版本 → 最终版本）
  5.5 发布
```

**流程说明**：

1. **流转顺序保持不变**：内容定义 → 评估指南 → 验证案例集
2. **并行启动**：文档达到"可用版本"（经专家校对）后，即可启动下一阶段编制，无需等待全部完成
3. **多轮迭代**：文档编制过程中发现的问题，通过修改机制同步到前面阶段的文档
4. **AI虚拟专家初审**：在每份文档初稿完成后、提交专家评审前执行，用于自我诊断
5. **多轮修订-回评循环（1.8）**：文档包内任一文档修订后，应重新运行AI虚拟专家初审，并校验跨文档一致性

## 四、各步骤：用户与AI助手对话流程

### 步骤1：需求分析与范围界定

**用户角色**：技术负责人/架构师
**用户目标**：明确要评估什么、为什么评估、为谁评估

#### 第1轮对话：AI初稿生成

**提示词模板**：

> **适用条件**：当需要开始一份新的工业软件架构评估文档的编制时。
> **备选方案**：当项目已有初步范围想法时，可以结合已有的范围想法和以下提示词，让AI列出更具体的范围选项供选择。

```
请帮我创建一份新的工业软件架构评估文档，评估对象为{评估对象名称}。

需求分析要求：
1. 分析该评估对象的核心理念和关注点
2. 列出本指南可以覆盖的评估维度（参考已有指南：多语言混合依赖、模板元编程、数值算法、求解器模块化架构，每个指南4-6个维度）
3. 说明该评估对象与本指南体系的关系和边界
4. 给出评估对象的目标用户

输出格式为：内容清单 → 建议评估维度 → 边界说明 → 目标用户
```

**AI助手预期输出**：内容清单、候选维度列表、与已有指南的边界说明、目标用户信息

**用户审核要点**（以下要点的目的是验证AI是否在其能力边界内正确工作，防止AI幻觉或越界）：
- **[技术负责人]** [ ] 内容清单是否覆盖了全部关切？
- **[架构师]** [ ] 评估维度是否符合用户预期、无遗漏或重点偏移？
- **[架构师]** [ ] 与已有指南的边界是否清晰？
- **[技术负责人]** [ ] 目标用户是否明确？

#### 第N轮对话：多轮迭代完善

当AI初稿需要调整时，可追加追问：

- "维度A和维度B看起来有些重叠，如何重新划分？"
- "请参考求解器模块化指南的边界划分方式，说明维度的边界定义"
- "缺少对XXX风险的覆盖，请补充"

> **迭代终止标准**：当用户与AI达成共识后，修改幅度小于10%，且文档结构不再发生大幅变化、细节不断完善时，可视为收敛并进入用户确认阶段。

### 步骤2：设计依据编制

**用户角色**：技术负责人/架构师
**用户目标**：完成四层催化模型的编制与验证

#### 第1轮对话：AI初稿生成

**提示词模板**：

> **适用条件**：步骤1的范围界定已完成后，需要开始设计依据文档时。
> **备选方案**：当AI生成的四层催化模型不够完整时，可要求AI参照指定标准和案例补充。

```
请按照四层催化模型的框架，撰写一份{评估对象名称}的设计依据内容：

## 1 建设必要性
### 1.1 通用质量模型存在理论缺口
（ISO 25010等标准在此评估对象存在哪些缺口？为什么无法提供具体的指导？）
### 1.2 自动化测量标准存在适用盲区
（CK、CISQ、ISO 5055作为通用标准无法覆盖该维度，缺失什么？）
### 1.3 行业工程实践形成刚性倒逼
（调研至少3个行业案例，分析其出现的共性架构问题）

## 2 内涵定义与边界划分
### 2.1 核心概念定义
（给出清晰明确的定义，需要多细就多细）
### 2.2 行业实例与常见形态
（举例说明该关切在工业软件中的几种常见表现方式）
### 2.3 与通用软件质量评估的本质差异
（列举至少4个本质区别）

## 3 体系工程应用作用
（该维度在开发阶段、架构演进、运维与演进等阶段的具体应用）

## 4 体系设计逻辑（四层驱动催化模型）
（阐述四层驱动催化模型，并提供学术领域/工业领域/工具生态的多维证据）

请参考以下已有指南的表述方式：
- 多语言混合依赖评估指南中的"四层催化模型"
- 求解器与物理场模块化架构模式识别评估指南中的"四层催化模型"

每个部分必须给出论证依据、真实来源和逻辑推导，不要只写提纲。
```

**AI助手预期输出**：四层催化模型的完整定义，每个论点附带证据支撑和来源

**用户审核要点**（以下要点的目的是验证AI是否在其能力边界内正确工作，防止AI幻觉或越界）：
- **[架构师]** [ ] 第一层：标准描述是否准确？缺口论证是否成立？
- **[架构师]** [ ] 第二层：通用标准失效的描述是否准确？失效点是否具体？
- **[验证工程师]** [ ] 第三层：行业案例是否有真实溯源？（至少3个案例能否验证？）
- **[技术负责人]** [ ] 第四层：评估维度的证据是否充分？催化效应（前因后果）是否得到验证？

#### 第N轮对话：多轮迭代完善

- "四层催化模型的行业实例感觉举例不充分，请再补充"
- "第二层的通用标准失效描述比较空泛，请具体说明"
- "请参考数值算法评估指南对ASME V&V标准的引用方式，补充行业标准引用"

> **迭代终止标准**：当四层催化模型的核心主张有充分的证据支撑、真实来源可溯源、逻辑完整时，可认为四层催化模型已完成，进入专家校对阶段。

#### 创建术语表

**用户角色**：技术负责人
**用户目标**：建立统一术语体系，确保全文一致

**提示词模板**：

> **适用条件**：当设计依据的定义部分初步完成后。
> **备选方案**：当AI生成的术语与已有评估指南不一致时，需要AI扫描全文章节补充。

```
请扫描当前文档，提取所有关键术语，生成一个统一术语表。

输出格式：
| 术语 | 英文对应 | 定义 | 首次出现位置 |
|-----|---------|------|-------------|
| ... | ... | ... | ... |

请确保：
1. 每个术语只保留唯一的规范定义
2. 英文对应准确（参考相关标准和已有指南）
3. 定义简洁准确
```

**要求**：
1. 案例覆盖矩阵的每一格"✅"须能**在案例正文定位**（标注小节编号，如"4.9"）；
2. 矩阵与正文**双向核对**：矩阵声称的用例数 ≤ 正文实际用例数；
3. 规则清单（≥N 条）与案例正文（覆盖 ≥N 条）逐条比对，防虚假声称；
4. 覆盖缺口须如实标注"待补"而非占位"✅"。

## 七、常见问题（FAQ）

### Q1: 为什么需要四层催化模型？

四层催化模型提供了评估维度"为什么必须独立存在"的完整论证链——从通用质量模型的理论缺口，到自动化测量标准的能力盲区，再到行业实践的风险倒逼，最后到行业共识的催熟效应。它使评估维度的建立不再依赖主观偏好，而是有完整逻辑支撑。

### Q2: 子维度数量和规则数量如何确定？

参照已有指南，子维度一般为4-6个，内置规则一般为12条。子维度数量与规则数量的比例不要求一一对应——求解器模块化指南用4个子维度承载12条规则，数值算法指南用6个子维度承载12条规则。

### Q3: 置信度标注有什么作用？

置信度标注反映检测方法的可靠性：高置信度规则可纳入CI门禁（ERROR），中置信度规则作为告警（WARNING），低/中低置信度规则仅作为参考（INFO）。置信度必须与检测机制匹配，语义级/启发式检测不得标注"高"置信度（1.8 要求）。

### Q4: AI虚拟专家初审能替代人类专家评审吗？

不能。AI虚拟专家初审是帮助编写者快速发现盲点、修正明显问题的自检环节，其结论（P0/P1/P2）是建议性的。最终是否接受、如何修订由编写者决定，人类专家评审仍不可替代。

### Q5: 文档需要几轮修订才能定稿？

取决于初稿质量与评审发现的问题数量。实测（H2 WP-1 维度④）：经历 AI 初审两轮 + 专家校对两轮共 13 项意见后定稿为可用版本。P0 必须清零，P1 可跨轮处理，每轮修订后需回评（1.8 要求）。

### Q6: 构造用例如何保证可编译？

构造用例引用真实框架 API 时，须校验构造函数/方法签名正确性（可用仓库源码实测验证），纯示意伪代码须显式标注（1.8 要求）。实测曾发现 `new Geom_Plane()` 无默认构造函数导致用例不可编译。
