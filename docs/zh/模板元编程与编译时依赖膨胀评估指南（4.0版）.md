# 模板元编程与编译时依赖膨胀评估指南（4.0版）

> 本指南参照 `SOFTWARE_ARCHITECTURE_QUALITY_GUIDE.md` 及《多语言混合依赖评估指南》的结构编写，定义了一套专门用于评估 C++ 模板元编程及编译时依赖膨胀的架构质量指标体系。适用于 CAD/CAE/CAx 等工业软件中大量使用模板泛型编程的场景。  
> **4.0 版核心更新**：  
> - 整合 P0 改进（外部引用 URL、豁免语法规范、审计流程）。  
> - 新增第八章“高级主题”：基线校准统计方法与豁免性能数据自动化验证方案。  
> - 明确跨规则豁免协调规则与输出级别规范。  
> - 补充基线校准步骤、统计公式及 CI 集成示例。  
> - 增加 MLR-014 与 MLR-017 重叠豁免的优先级规则。

## 概述

**模板元编程与编译时依赖膨胀**是指：在 C++ 工业软件中，由于模板实例化机制、头文件包含传染性及编译时计算特性，导致模块间的**编译时耦合**显著超过运行时耦合。具体表现为：
- 头文件传递依赖爆炸（一个头文件被成百上千个编译单元包含）；
- 同一模板在不同编译单元重复实例化（实例化爆炸）；
- 编译时间随模板嵌套深度指数增长；
- 二进制体积中模板生成代码占比畸高。

**行业背景**：Google C++ 风格指南[1]明确指出“当你包含一个头文件时，你就引入了一个依赖，每当该头文件改变时，你的代码就会被重新编译”。LLVM 编码规范[2]将编译时间视为系统级性能度量。Qt 编码约定[3]强调“明智地使用模板，不要仅仅因为你能够使用而使用”。C++ Core Guidelines[4]为编译时耦合度量提供了理论框架。Effective C++ Item 44[6]专门讨论了模板代码膨胀问题。

本指南作为《软件架构质量评估指南》的补充，定义了一套专门针对模板元编程与编译时依赖膨胀的评估指标。这些指标可纳入**结构质量**中的耦合度子维度（建议权重占结构质量的 10%~15%），也可作为工业软件场景下的独立评估项。

**评估目标**：量化编译时依赖带来的可维护性风险，识别热模板头文件、重复实例化、深度嵌套、二进制膨胀等架构债务，降低变更编译成本，提升开发迭代效率。

## 一、子维度与权重分配

| 子维度 | 权重 | 对应风险类型 |
|--------|------|-------------|
| 编译时扇入（头文件包含热度） | 20% | 头文件被大量编译单元包含，修改后重编译范围大 |
| 模板实例化重复率 | 20% | 同一模板参数组合在多处重复实例化，浪费编译时间与二进制体积 |
| 头文件影响半径 | 15% | 修改一个头文件通过传递依赖影响的编译单元数量 |
| 模板嵌套深度 | 10% | 模板递归/嵌套过深，导致编译时间爆炸、错误信息不可读 |
| 二进制膨胀率 | 15% | 模板生成代码占最终二进制体积的比例，影响部署与缓存效率 |
| 不必要的模板化（虚泛型） | 20% | 从未以 ≥2 种类型实例化的模板，应降级为普通代码 |

权重设计依据详见各子维度行业引用。

## 二、子维度定义与评分算法

### 2.1 编译时扇入（头文件包含热度）

**定义**：衡量一个头文件（`.h`, `.hpp`, `.tpp`）被多少个编译单元（`.cpp`, `.cc`）直接或间接包含。扇入越高，修改该头文件导致的重编译范围越大。

**设计依据**：
- Google C++ 风格指南[1]：“当你包含一个头文件时，你就引入了一个依赖，每当该头文件改变时，你的代码就会被重新编译。……应当优先使用前置声明来减少依赖。”
- C++ Core Guidelines CP.1[4]：“将你的代码组织为逻辑上独立的模块，每个模块应有清晰的物理边界。”
- 工业案例：OpenFOAM 中 `Tensor.H` 被超过 120 个求解器文件包含，修改后全量重编译耗时数小时。

**评分算法**：
```
let I = 头文件被包含的编译单元数量（通过依赖图计算，去重）
if I == 0: score = 100
else if I <= 10: score = 100 - I * 1.5       # I=10 → 85
else if I <= 50: score = 85 - (I-10) * 0.7   # I=50 → 57
else if I <= 100: score = 57 - (I-50) * 0.5  # I=100 → 32
else: score = max(0, 32 - (I-100) * 0.3)
```
**阈值说明**：0~10 为健康；10~50 需关注；50~100 应重构；>100 为严重债务。**基线校准**：参见 8.1 节。

**代码坏味道：热模板头文件（Hot Template Header）**
- **描述**：头文件被大量编译单元包含，形成编译时依赖热点。
- **典型表现**：核心数学头文件被超过 80% 的编译单元包含；修改一行注释触发全量重编译。
- **危害**：开发迭代效率崩溃；CI 资源浪费；团队“不敢改”。

### 2.2 模板实例化重复率

**定义**：同一模板（如 `std::vector<int>`）在不同编译单元中被独立实例化的次数。重复率越高，编译时间和二进制体积浪费越大。

**设计依据**：
- C++ Core Guidelines T.68[4]：“使用模板时，注意它可能对编译时间和代码体积产生的影响。考虑使用 `extern template` 来抑制隐式实例化。”
- Effective C++ Item 44[6]：“Templated programs can result in massive object-code bloat.”
- 实测数据：OTB（基于 ITK）项目中 `extern template` 可减少编译时间约 **15%**；但在 GLM 数学库中无明显差异。

**评分算法**：
```
总实例化次数 = 对所有模板特化，统计出现次数之和
唯一实例化次数 = 去重后的模板特化数量
重复率 = (总实例化次数 - 唯一实例化次数) / 总实例化次数   # 0~1

if 重复率 == 0: score = 100
else if 重复率 <= 0.1: score = 90
else if 重复率 <= 0.2: score = 80 - (重复率-0.1)*100  # 0.2 → 70
else if 重复率 <= 0.4: score = 70 - (重复率-0.2)*150  # 0.4 → 40
else: score = max(0, 40 - (重复率-0.4)*100)
```
**说明**：重复率 <10% 为优秀，10%~20% 可接受，>40% 需强制重构。

**`extern template` 无效或低效场景清单**：
- 模板定义在头文件中完整可见（多数情况下仍需要解析完整定义）；
- 与 `-fvisibility=hidden` 同时使用导致符号导出复杂化；
- 与 LTO（链接时优化）一起使用时，重复实例化可能被优化器部分抵消；
- 对于仅包含静态成员函数或类型别名（无实际代码生成）的模板，收益极小。

**豁免条款（MLR-014 专用）**：
在多精度数值库或多维度模板场景下，若不同实例化对应不同的算法特化路径（如 SIMD 优化），开发者可使用豁免注释。豁免输出级别为 **INFO（需审查）**，而非 WARNING。详见附录 B。

### 2.3 头文件影响半径

**定义**：修改一个头文件后，通过 `#include` 传递依赖所影响的编译单元总数。影响半径越大，变更风险越高。

**设计依据**：
- C++ Core Guidelines CP.2[4]：“一个模块的变更应尽可能只影响该模块内部的实现，而不应波及依赖它的其他模块。”
- Google 风格指南[1]：“尽可能将函数定义移出头文件，放到 `.cc` 文件中。”
- 工业经验：BRL-CAD 中影响半径超过 150 的模块已成为“不可触碰”的遗产代码。

**评分算法**：
```
R = 从该头文件出发，沿 #include 边（不跨过 .cpp 边界）可达的编译单元数量
if R == 0: score = 100
else if R <= 10: score = 95
else if R <= 30: score = 85 - (R-10)*0.5   # 30 → 75
else if R <= 80: score = 75 - (R-30)*0.3   # 80 → 60
else if R <= 150: score = 60 - (R-80)*0.2  # 150 → 46
else: score = max(0, 46 - (R-150)*0.15)
```
**注意**：只统计生产代码，测试文件和示例代码不计入。

**代码坏味道：传染性头文件（Contagious Header）**
- **描述**：头文件通过多层传递依赖影响大量编译单元。
- **危害**：修改底层头文件导致大量上层重编译；破坏模块化。

---

### 2.4 模板嵌套深度

**定义**：模板定义中递归或嵌套实例化的最大深度（例如 `A<B<C<int>>>` 深度为 3）。深度过大时编译时间指数增长，错误信息不可读。

**设计依据**：
- C++ Core Guidelines T.115[4]：“避免模板递归过深。使用 `constexpr` 函数或折叠表达式代替传统模板递归。”
- LLVM 编码规范[2]：要求“模板递归深度不应超过 5 层”。
- 实测：深度 > 10 导致编译时间增长一个数量级。

**评分算法**：
```
D_max = 项目中所有模板实例化点的最大嵌套深度（通过 AST 分析）
if D_max <= 3: score = 100
else if D_max <= 6: score = 80 - (D_max-3)*5   # 6 → 65
else if D_max <= 10: score = 65 - (D_max-6)*4  # 10 → 49
else: score = max(0, 49 - (D_max-10)*3)
```
**说明**：深度 ≤3 为良好；4~6 需关注；7~10 较差；>10 不可接受。

**代码坏味道：模板递归地狱（Template Recursion Hell）**
- **危害**：编译时间指数增长；内存 OOM；错误信息长达数万行，严重拖累开发效率。

---

### 2.5 二进制膨胀率

**定义**：最终二进制文件中，由模板实例化生成的代码占 `.text` 段总大小的比例。

**设计依据**：
- Effective C++ Item 44[6]：“Templated programs can result in massive object-code bloat.”
- C++ Core Guidelines T.69[4]：“如果不同的模板参数生成的代码几乎相同，考虑使用运行时参数代替。”
- **性能与膨胀的权衡**：HPC 场景中 30–40% 膨胀率可能是换取接近手工优化代码性能（如 AllScale 达到 92–105% 手工 MPI 性能）的必要支出。指南将膨胀率高于 35% 标记为“需审查”，而非直接定为“债务”。

**评分算法**：
```
膨胀率 = (模板生成代码字节数) / (总 .text 段字节数) * 100%
if 膨胀率 <= 10%: score = 100
else if 膨胀率 <= 20%: score = 90 - (膨胀率-10)*1   # 20% → 80
else if 膨胀率 <= 35%: score = 80 - (膨胀率-20)*1.2 # 35% → 62
else if 膨胀率 <= 50%: score = 62 - (膨胀率-35)*1.5 # 50% → 39.5
else: score = max(0, 39.5 - (膨胀率-50)*0.8)
```
**说明**：膨胀率 <10% 优秀，10%-20% 可接受，>35% 需审查。嵌入式项目建议阈值 20%。

**膨胀合理性豁免机制（MLR-017 专用）**：
对于经架构评审确认的合理膨胀点，开发者可使用豁免注释，并必须附带性能测试数据。详见附录 B 及 8.2 节。

---

### 2.6 不必要的模板化（虚泛型）

**定义**：一个模板只被一种具体类型实例化（或从未实例化）。

**设计依据**：
- Qt 编码约定[3]：“Use templates wisely, not just because you can.”
- C++ Core Guidelines T.10[4]：“如果只有一种类型适用，就不需要模板。”

**评分算法**：
```
total_templates = 定义的模板总数
unnecessary_templates = 只被一种类型实例化的模板数（或从未实例化）
ratio = unnecessary_templates / total_templates
score = 100 - ratio * 150   # 每1%扣1.5分，上限扣100
```
**扣分加强**：若模板从未被实例化，额外扣 10 分（上限仍为 0 分）。

**豁免机制（MLR-018 专用）**：
对于底层库预留的扩展接口，可使用 `// @reserved_for_future_extension` 豁免。详见附录 B。

## 三、与 C++20 Modules 的衔接

### 3.1 现实约束声明

C++20 Modules 在工业软件中全面普及仍面临显著障碍：

| 维度 | 现状 |
|------|------|
| **编译器支持** | GCC 仍为 **experimental**（需 `-fmodules`）；Clang 自 16 版起逐步支持但存在 ABI 差异；MSVC 最成熟但与其他编译器不兼容。 |
| **构建系统** | CMake 3.26+ 实验性支持，配置复杂；IDE 支持不完整。 |
| **生态依赖** | 支持 Modules 的库生态占比极低（<2%）。 |
| **迁移成本** | 完整迁移需数人年投入。 |

### 3.2 各规则的 Modules 环境适配

| 规则 | 传统阈值 | Modules 环境调整 |
|------|---------|-----------------|
| MLR-013 | 扇入>50 | 暂不提供固定阈值，建议用户基于迁移后数据重新建立基线（见 8.1 节）；过渡期参考 100–150 作为试探值 |
| MLR-015 | 影响半径>80 | 替换为“模块导入图”，仅统计模块接口变更的影响半径 |
| MLR-024 | 检测包含循环 | 纯模块项目：编译器直接拒绝循环依赖，规则降级为 LOW；混合项目：仍需保留 |
| MLR-014/023 | 维持不变 | Modules 不影响此问题 |
| MLR-018 | 维持不变 | 不受 Modules 影响 |

## 四、综合分计算与指标重叠处理

### 4.1 综合分公式

```
模板依赖综合分 = 
    编译时扇入 × 20% +
    模板实例化重复率 × 20% +
    头文件影响半径 × 15% +
    模板嵌套深度 × 10% +
    二进制膨胀率 × 15% +
    不必要的模板化 × 20%
```

### 4.2 指标重叠处理策略

- **MLR-014（重复实例化）** 与 **MLR-023（跨库重复实例化）**：取两者中较严重的得分（即较低分）作为该问题的最终得分，避免双重扣分。
- **MLR-013（扇入）** 与 **MLR-015（影响半径）**：保留独立评分，但在报告中标注关联性，提示优先解决同时触犯两条规则的模块。
- **跨规则豁免协调**：若一个模板同时满足 MLR-014 豁免（多精度）和 MLR-017 豁免（性能），工具应**分别处理**：MLR-014 输出 INFO，MLR-017 仍需验证性能数据。若性能验证失败，MLR-017 仍告警。
- **SME 评审阶段**：工具输出的综合分仅作为筛选信号，最终债务认定需由架构师人工复核，特别对边界情况（如 HPC 高膨胀率）应予以豁免。

## 五、内置规则（MLR-013 至 MLR-024）

规则清单与 3.2 版相同，本版增加“输出级别规范”列：

| 规则ID | 名称 | 严重级别 | 输出级别（无豁免） | 豁免后输出级别 |
|--------|------|---------|-------------------|---------------|
| MLR-013 | 热模板头文件 | HIGH | WARNING | 不支持豁免 |
| MLR-014 | 模板重复实例化 | HIGH | WARNING | INFO（需审查） |
| MLR-015 | 头文件传染链过长 | MEDIUM | WARNING | 不支持豁免 |
| MLR-016 | 模板嵌套深度过大 | MEDIUM | WARNING | 不支持豁免 |
| MLR-017 | 二进制膨胀超标 | MEDIUM | WARNING | INFO（需审查+性能验证） |
| MLR-018 | 虚泛型（镀金模板） | HIGH | WARNING | INFO（预留接口） |
| MLR-019 | 未使用 extern template 优化 | LOW | INFO | 不支持豁免 |
| MLR-020 | 头文件包含不必要的模板定义 | MEDIUM | WARNING | 不支持豁免 |
| MLR-021 | 模板特化在错误命名空间 | LOW | INFO | 不支持豁免 |
| MLR-022 | 递归模板无限实例化风险 | HIGH | ERROR | 不支持豁免 |
| MLR-023 | 同一模板在多个库中重复实例化 | MEDIUM | WARNING | 不支持豁免（由 MLR-014 覆盖） |
| MLR-024 | 头文件包含循环 | HIGH | ERROR | 不支持豁免 |

**输出级别定义**：
- **ERROR**：阻断 CI 流水线，必须立即修复。
- **WARNING**：建议修复，可暂时忽略但需记录技术债务。
- **INFO**：仅提供信息，不阻断 CI，但建议审查。

## 七、实施建议

1. **工具集成**：使用 `clang -ftime-trace`、`include-what-you-use`、`nm`/`bloaty` 等工具采集原始数据，基于本指南算法计算得分。

2. **门禁设置**：CI 中设置模板依赖综合分 < 50 时警告（非强制），由 SME 决定是否阻断合并。ERROR 级别规则必须阻断。

3. **重构优先级**：
   - **P0**：评估 Modules 迁移可行性，优先将扇入最高的头文件模块化。
   - **P1**：处理 MLR-013、MLR-018。
   - **P2**：处理 MLR-014/023。
   - **P3**：处理深度嵌套和包含循环。

4. **基线建立**：首次评估前，按 8.1 节方法进行基线校准，确定项目专属阈值。每季度或代码库规模增长 >30% 时重新校准。

5. **SME 复核流程**：工具输出后，至少两名架构师对得分 < 60 的模块进行复核，确认是否真实债务。HPC 场景高膨胀率需附性能测试报告。

6. **豁免审计**：按附录 B 及 8.2 节管理豁免注释，每季度审计。

## 八、高级主题：基线校准与豁免验证

### 8.1 基线校准统计方法

默认阈值来源于典型工业软件经验值，但不同项目规模差异大，需基于项目自身数据进行校准。

#### 8.1.1 采样模块选择

随机抽取 **20–30 个模块**，覆盖：
- 高频修改模块（变更次数前10%）
- 低频修改模块（变更次数后10%）
- 核心基础设施模块（被依赖最多的10个头文件）
- 边缘业务模块（无外部依赖）

#### 8.1.2 采集与统计

对每个样本模块计算扇入(I)、影响半径(R)、重复率等指标，得到数据集 `{x1, ..., xn}`。计算：
- 中位数 (Median)
- 四分位距 (IQR) = Q3 - Q1
- 上四分位数 (Q3)

#### 8.1.3 设定项目专属阈值

| 指标 | 默认阈值 | 校准公式 |
|------|---------|----------|
| 扇入 | 50 | `max(10, Q3 + 1.5*IQR)` |
| 影响半径 | 80 | `Q3 + 1.5*IQR` |
| 重复率 | 40% | `Median + 2*MAD`（MAD：中位数绝对偏差） |
| 膨胀率 | 35% | `min(60%, Q3 + 1.5*IQR)`（嵌入式20%） |
| 嵌套深度 | 10 | `max(5, Q3 + IQR)` |

#### 8.1.4 验证与迭代

将新阈值应用于测试集（另20个模块）。若误报率>10%，使用 `Q3 + 2.0*IQR` 放宽；若漏报率>10%，使用 `Q3 + 1.0*IQR` 收紧。每季度或代码库增长>30%时重新校准。

### 8.2 豁免性能数据自动化验证方案

#### 8.2.1 豁免注释扩展语法

```cpp
// @allow_binary_bloat: <简要理由>;
//    performance_gain: X%;
//    compile_time_increase: Ys;
//    benchmark_script: ci/benchmarks/benchmark.cpp;
//    threshold: gain>=5% and increase<=10s
```

#### 8.2.2 CI 自动验证流程

1. 编译两个版本：启用特化 vs 基准（禁用特化）。
2. 运行性能测试各10次，取中位数计算 `gain` 和 `increase`。
3. 判定是否满足 `threshold` 条件。
4. 若不满足，阻断 MR 并输出失败报告。

#### 8.2.3 性能测试编写规范

- 确定性：固定随机种子
- 隔离性：无共享状态
- 代表性：数据规模与生产场景相当
- 版本控制：测试程序随豁免注释提交

#### 8.2.4 MLR-014 多精度豁免验证

比较 `double` 与 `float` 特化的反汇编，若指令序列相同则豁免无效。

#### 8.2.5 豁免审计增强

- 性能测试程序及日志归档到 `docs/waivers/performance_logs/`
- 每6个月自动重跑性能测试，不满足条件则提醒 SME 复查
- 项目豁免总数 >50 时触发架构委员会季度评审
