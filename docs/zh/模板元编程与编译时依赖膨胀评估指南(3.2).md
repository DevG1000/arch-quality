## 概述

**模板元编程与编译时依赖膨胀**是指：在 C++ 工业软件中，由于模板实例化机制、头文件包含传染性及编译时计算特性，导致模块间的**编译时耦合**显著超过运行时耦合。具体表现为：
- 头文件传递依赖爆炸（一个头文件被成百上千个编译单元包含）；
- 同一模板在不同编译单元重复实例化（实例化爆炸）；
- 编译时间随模板嵌套深度指数增长；
- 二进制体积中模板生成代码占比畸高。

**行业背景**：Google C++ 风格指南[1]明确指出“当你包含一个头文件时，你就引入了一个依赖，每当该头文件改变时，你的代码就会被重新编译”。LLVM 编码规范[2]将编译时间视为系统级性能度量。Qt 编码约定[3]强调“明智地使用模板，不要仅仅因为你能够使用而使用”。C++ Core Guidelines[4]为编译时耦合度量提供了理论框架。Bloomberg 开源的 BDE 库[5]提供了大规模模板治理的参考实践。Effective C++ Item 44[6]专门讨论了模板代码膨胀问题。

本指南作为《软件架构质量评估指南》的补充，定义了一套专门针对模板元编程与编译时依赖膨胀的评估指标。这些指标可纳入**结构质量**中的耦合度子维度（建议权重占结构质量的 10%~15%），也可作为工业软件场景下的独立评估项。

**评估目标**：量化编译时依赖带来的可维护性风险，识别热模板头文件、重复实例化、深度嵌套、二进制膨胀等架构债务，降低变更编译成本，提升开发迭代效率。

## 一、子维度与权重分配

| 子维度 | 权重 | 对应风险类型 |
|--------|------|-------------|
| 编译时扇入（头文件包含热度） | 20% | 头文件被大量编译单元包含，修改后重编译范围大 |
| 模板实例化重复率 | 20% | 同一模板参数组合在多处重复实例化，浪费编译时间与二进制体积 |
| 头文件影响半径 | 15% | 修改一个头文件通过传递依赖影响的编译单元数量 |
| 模板嵌套深度 | 10% | 模板递归/嵌套过深，导致编译时间爆炸、错误信息不可读 |
| 二进制膨胀率 | 15% | 模板生成代码占最终二进制体积的比例，影响部署与缓存效率 |
| 不必要的模板化（虚泛型） | 20% | 从未以 ≥2 种类型实例化的模板，应降级为普通代码 |

权重设计依据详见各子维度行业引用。

## 二、子维度定义与评分算法

### 2.1 编译时扇入（头文件包含热度）

**定义**：衡量一个头文件（`.h`, `.hpp`, `.tpp`）被多少个编译单元（`.cpp`, `.cc`）直接或间接包含。扇入越高，修改该头文件导致的重编译范围越大。

**设计依据**：
- Google C++ 风格指南[1]：“当你包含一个头文件时，你就引入了一个依赖，每当该头文件改变时，你的代码就会被重新编译。……应当优先使用前置声明来减少依赖。”
- C++ Core Guidelines CP.1[4]：“将你的代码组织为逻辑上独立的模块，每个模块应有清晰的物理边界。”
- 工业案例：OpenFOAM 中 `Tensor.H` 被超过 120 个求解器文件包含，修改后全量重编译耗时数小时。

**评分算法**：
```
let I = 头文件被包含的编译单元数量（通过依赖图计算，去重）
if I == 0: score = 100
else if I <= 10: score = 100 - I * 1.5       # I=10 → 85
else if I <= 50: score = 85 - (I-10) * 0.7   # I=50 → 57
else if I <= 100: score = 57 - (I-50) * 0.5  # I=100 → 32
else: score = max(0, 32 - (I-100) * 0.3)
```
**阈值说明**：0~10 为健康；10~50 需关注；50~100 应重构；>100 为严重债务。

**代码坏味道：热模板头文件（Hot Template Header）**
- **描述**：头文件被大量编译单元包含，形成编译时依赖热点。
- **典型表现**：核心数学头文件被超过 80% 的编译单元包含；修改一行注释触发全量重编译。
- **危害**：开发迭代效率崩溃；CI 资源浪费；团队“不敢改”。
- **对应行业共识**：Google 要求“优先使用前置声明减少 `#include`”[1]。

### 2.2 模板实例化重复率

**定义**：同一模板（如 `std::vector<int>`）在不同编译单元中被独立实例化的次数。重复率越高，编译时间和二进制体积浪费越大。

**设计依据**：
- C++ Core Guidelines T.68[4]：“使用模板时，注意它可能对编译时间和代码体积产生的影响。考虑使用 `extern template` 来抑制隐式实例化。”
- Effective C++ Item 44[6]：“Templated programs can result in massive object-code bloat.”
- 实测数据：OTB（基于 ITK）项目中 `extern template` 可减少编译时间约 **15%**；但在 GLM 数学库中，由于头文件仍完整包含模板定义，使用 `extern template` 未测量到显著差异。收益因项目结构和模板使用模式而异。

**评分算法**：
```
总实例化次数 = 对所有模板特化，统计出现次数之和
唯一实例化次数 = 去重后的模板特化数量
重复率 = (总实例化次数 - 唯一实例化次数) / 总实例化次数   # 0~1

if 重复率 == 0: score = 100
else if 重复率 <= 0.1: score = 90
else if 重复率 <= 0.2: score = 80 - (重复率-0.1)*100  # 0.2 → 70
else if 重复率 <= 0.4: score = 70 - (重复率-0.2)*150  # 0.4 → 40
else: score = max(0, 40 - (重复率-0.4)*100)
```
**说明**：重复率 <10% 为优秀，10%~20% 可接受，>40% 需强制重构。

**`extern template` 无效或低效场景清单**：
- 模板定义在头文件中完整可见（多数情况下仍需要解析完整定义）；
- 与 `-fvisibility=hidden` 同时使用导致符号导出复杂化；
- 与 LTO（链接时优化）一起使用时，重复实例化可能被优化器部分抵消；
- 对于仅包含静态成员函数或类型别名（无实际代码生成）的模板，收益极小。

**豁免条款（MLR-014 专用）**：
在多精度数值库（如同时使用 `Tensor<double>`、`Tensor<float>`）或多维度模板（如 `Matrix<3,3>` 与 `Matrix<4,4>`）场景下，若不同实例化对应不同的算法特化路径（如 SIMD 优化或稀疏结构），开发者可使用豁免注释。详见附录 B“豁免语法规范与审计流程”。

**代码坏味道：实例化爆炸（Instantiation Bloat）**
- **描述**：同一模板参数组合在数十个编译单元中独立实例化。
- **典型表现**：`std::vector<double>` 在 120 个 `.cpp` 中各实例化一次。
- **危害**：编译器重复工作；增量编译失效；CI 资源虚高。
- **对应行业实践**：LLVM 社区采用“延迟实例化”策略；Google 使用 `extern template` 集中实例化。

### 2.3 头文件影响半径

**定义**：修改一个头文件后，通过 `#include` 传递依赖所影响的编译单元总数。影响半径越大，变更风险越高。

**设计依据**：
- C++ Core Guidelines CP.2[4]：“一个模块的变更应尽可能只影响该模块内部的实现，而不应波及依赖它的其他模块。”
- Google 风格指南[1]：“尽可能将函数定义移出头文件，放到 `.cc` 文件中。”
- 工业经验：在 BRL-CAD 等历史悠久的工业软件中，头文件影响半径超过 150 的模块已成为“不可触碰”的遗产代码。

**评分算法**：
```
R = 从该头文件出发，沿 #include 边（不跨过 .cpp 边界）可达的编译单元数量
if R == 0: score = 100
else if R <= 10: score = 95
else if R <= 30: score = 85 - (R-10)*0.5   # 30 → 75
else if R <= 80: score = 75 - (R-30)*0.3   # 80 → 60
else if R <= 150: score = 60 - (R-80)*0.2  # 150 → 46
else: score = max(0, 46 - (R-150)*0.15)
```
**注意**：只统计生产代码，测试文件和示例代码不计入。

**代码坏味道：传染性头文件（Contagious Header）**
- **描述**：头文件通过多层传递依赖影响大量编译单元。
- **典型表现**：`common.h` 间接引入数千行预处理后代码。
- **危害**：修改底层头文件导致大量上层重编译；破坏模块化。
- **对应行业共识**：Google 要求“除非有明确理由，否则头文件应该只包含它直接需要的声明”[1]。

### 2.4 模板嵌套深度

**定义**：模板定义中递归或嵌套实例化的最大深度（例如 `A<B<C<int>>>` 深度为 3）。深度过大时编译时间指数增长，错误信息不可读。

**设计依据**：
- C++ Core Guidelines T.115[4]：“避免模板递归过深。使用 `constexpr` 函数或折叠表达式代替传统模板递归。”
- LLVM 编码规范[2]：在代码审查中明确要求“模板递归深度不应超过 5 层，否则需要改写成迭代形式”。
- Clang 开发者论坛指出：深度 > 10 的模板实例化会导致编译时间增长一个数量级，且错误信息膨胀到数万行。

**评分算法**：
```
D_max = 项目中所有模板实例化点的最大嵌套深度（通过 AST 分析）
if D_max <= 3: score = 100
else if D_max <= 6: score = 80 - (D_max-3)*5   # 6 → 65
else if D_max <= 10: score = 65 - (D_max-6)*4  # 10 → 49
else: score = max(0, 49 - (D_max-10)*3)
```
**说明**：深度 ≤3 为良好；4~6 需关注；7~10 较差；>10 不可接受。

**代码坏味道：模板递归地狱（Template Recursion Hell）**
- **描述**：模板元函数递归实例化深度随输入线性增长。
- **典型表现**：`Factorial<100>::value` 产生 100 层实例化。
- **危害**：编译时间指数增长；内存 OOM；错误信息可长达数万行，严重拖累开发效率（Boost 邮件列表指出模板元编程错误“extremely hard to read and parse”）。
- **对应行业修复**：C++17 折叠表达式（如 `(args + ...)`）将递归深度降为 O(1)；C++14 `constexpr` 函数彻底消除模板递归。

### 2.5 二进制膨胀率

**定义**：最终二进制文件中，由模板实例化生成的代码占 `.text` 段总大小的比例。膨胀率越高，表示模板泛型代码冗余度越大。

**设计依据**：
- Effective C++ Item 44[6]：“Templated programs can result in massive object-code bloat.”
- C++ Core Guidelines T.69[4]：“在使用模板时，要考虑代码膨胀。如果不同的模板参数生成的代码几乎相同，考虑使用运行时参数代替。”
- **性能与膨胀的权衡**：在某些高性能计算（HPC）场景中，模板的零成本抽象可能带来 30–40% 的二进制膨胀率和一定的编译时间代价，但这是换取接近手工优化代码性能（例如 AllScale 运行时系统达到 92–105% 的手工 MPI 性能）的必要支出。指南将膨胀率高于 35% 标记为“需审查”，而非直接定为“债务”。

**评分算法**：
```
膨胀率 = (模板生成代码字节数) / (总 .text 段字节数) * 100%
if 膨胀率 <= 10%: score = 100
else if 膨胀率 <= 20%: score = 90 - (膨胀率-10)*1   # 20% → 80
else if 膨胀率 <= 35%: score = 80 - (膨胀率-20)*1.2 # 35% → 62
else if 膨胀率 <= 50%: score = 62 - (膨胀率-35)*1.5 # 50% → 39.5
else: score = max(0, 39.5 - (膨胀率-50)*0.8)
```
**说明**：膨胀率 <10% 优秀，10%-20% 可接受，>35% 需审查。嵌入式项目建议阈值 20%。

**膨胀合理性豁免机制（MLR-017 专用）**：
对于经架构评审确认的合理膨胀点（如 SIMD 优化特化、零成本抽象），开发者可使用豁免注释。详见附录 B“豁免语法规范与审计流程”。

**代码坏味道：二进制肥胖（Binary Bloat）**
- **描述**：二进制文件中充斥着大量几乎相同的模板生成代码。
- **典型表现**：`Matrix<double,3,3>` 和 `Matrix<double,3,4>` 生成 90% 重复的机器码。
- **危害**：部署成本高；指令缓存效率下降；链接时间增加。
- **对应行业实践**：Google 使用 `-fvisibility=hidden` 和 `-ffunction-sections` + 链接器 GC 减少膨胀；LLVM 支持 `-fno-implicit-templates` 强制显式实例化。

### 2.6 不必要的模板化（虚泛型）

**定义**：一个模板在整个项目中只被一种具体类型实例化（或从未实例化），表明模板抽象是多余的。

**设计依据**：
- Qt 编码约定[3]：“Use templates wisely, not just because you can.”（明智地使用模板，不要仅仅因为你能够使用而使用。）社区将“只实例化一次的模板”列为典型的“镀金模板”坏味道。
- C++ Core Guidelines T.10[4]：“将模板定义为对多种类型有意义的抽象。如果只有一种类型适用，就不需要模板。”
- Google 内部代码审查准则：如果新增的模板只用于单一类型，审查员会要求改为普通函数或类。

**评分算法**：
```
total_templates = 定义的模板总数
unnecessary_templates = 只被一种类型实例化的模板数（或从未实例化）
ratio = unnecessary_templates / total_templates

score = 100 - ratio * 150   # 每1%扣1.5分，上限扣100
```
**扣分加强**：若模板从未被实例化，额外扣 10 分（上限仍为 0 分）。

**豁免机制（MLR-018 专用）**：
对于底层库预留的扩展接口（如未来可能支持新类型），开发者可使用 `// @reserved_for_future_extension` 豁免。详见附录 B。

**代码坏味道：镀金模板（Gold-Plated Template）**
- **描述**：为“可能的未来”设计的模板，实际只用于一种类型。
- **典型表现**：`template<typename T> T compute(T x)` 所有调用点使用 `double`。
- **危害**：增加头文件依赖；误导维护者；浪费编译时间。
- **对应行业共识**：Google 和 Qt 都强调“只为今天的问题编码，不为可能的明天过度设计”。

## 三、与 C++20 Modules 的衔接

### 3.1 现实约束声明

C++20 Modules 是编译模型的革命性变革，但在工业软件中全面普及仍面临显著障碍：

| 维度 | 现状 |
|------|------|
| **编译器支持** | GCC 官方 C++ 状态页仍将 Modules 标注为 **experimental**（需 `-fmodules`）；Clang 自 16 版起逐步支持，但各版本间存在 ABI 兼容差异；MSVC 实现最为成熟，但与其他编译器存在二进制接口不兼容问题。 |
| **构建系统** | CMake 3.26+ 实验性支持，但需要编译器提供 P1689R5 模块扫描协议，配置复杂；主流 IDE（如 Qt Creator、VS Code 通过 clangd）对 Modules 的支持不完整。 |
| **生态依赖** | 支持 Modules 的库生态占比极低（估算 <2%），包管理器面临二进制兼容性挑战。 |
| **迁移成本** | 将现有头文件体系完整迁移到 Modules 需要“分层重构”，通常需要数人年投入。 |

因此，本指南在 Modules 环境下的规则调整应视为**长期演进方向**，而非当前可普遍实施的硬性要求。建议项目在迁移 Modules 前仍以传统头文件评估为主。

### 3.2 各规则的 Modules 环境适配

| 规则 | 传统头文件环境阈值 | Modules 环境调整建议 | 说明 |
|------|------------------|---------------------|------|
| MLR-013（热头文件） | 扇入 > 50 | 暂不提供固定阈值，建议用户**基于自身迁移后的编译数据重新建立基线**；过渡期可参考 100–150 作为试探性上限 | 无公开实证支持具体数值，故标注“待校准” |
| MLR-015（头文件传染链） | 影响半径 > 80 | 替换为“模块导入图”，仅统计模块接口变更的影响半径 | 实现变更不传播，影响半径显著缩小 |
| MLR-024（包含循环） | 检测 `#include` 循环 | 纯模块项目：编译器直接拒绝循环依赖，规则可**降级为 LOW**（仅建议检查分区设计）；混合项目：仍需保留检测 | 头文件与模块共存时仍可能出现循环 |
| MLR-014/023（重复实例化） | 重复率 > 40% | 维持不变；`extern template` 策略在模块中同样有效 | Modules 不影响此问题 |
| MLR-018（镀金模板） | 仅实例化一次 | 维持不变 | 不受 Modules 影响 |

### 3.3 混合编译模型评分策略

在头文件与模块共存阶段：
1. **分别统计**：头文件依赖图使用原算法；模块导入图使用调整后的阈值（暂用传统阈值的 1.5 倍作为探索值）。
2. **综合评分**：最终得分 = 头文件部分得分 × (头文件编译单元占比) + 模块部分得分 × (模块单元占比)。
3. **人工复核**：由于缺乏成熟基准，建议 SME（主题专家）对过渡期报告进行复核，标记出因 Modules 不成熟导致的误报。

## 四、综合分计算与指标重叠处理

### 4.1 综合分公式（不变）

```
模板依赖综合分 = 
    编译时扇入 × 20% +
    模板实例化重复率 × 20% +
    头文件影响半径 × 15% +
    模板嵌套深度 × 10% +
    二进制膨胀率 × 15% +
    不必要的模板化 × 20%
```

### 4.2 指标重叠处理策略

- **MLR-014（重复实例化）** 与 **MLR-023（跨库重复实例化）** 度量同一问题的不同维度。在综合分计算时，评估工具应**自动合并为单一扣分项**：取两者中较严重的得分（即较低分）作为该问题的最终得分，避免双重扣分。
- **MLR-013（编译时扇入）** 与 **MLR-015（头文件影响半径）** 存在部分重叠，但扇入侧重“包含广度”，影响半径侧重“传递深度”，两者在评分中保留独立，但在最终报告中应**标注关联性**，提示团队优先解决同时触犯两条规则的模块。
- 引入 **SME 评审阶段**：工具输出的综合分仅作为筛选信号，最终的债务认定需由架构师人工复核，特别对于边界情况（如高膨胀率但高性能收益的 HPC 模块）应予以豁免。

## 七、实施建议

1. **工具集成**：使用 `clang -ftime-trace`、`include-what-you-use`、`nm`/`bloaty` 等工具采集原始数据，基于本指南算法计算得分。

2. **门禁设置**：CI 中设置模板依赖综合分 < 50 时警告（非强制），由 SME 决定是否阻断合并。随着基线建立，可逐步收紧。

3. **重构优先级**：
   - **P0**：评估 Modules 迁移可行性，优先将扇入最高的头文件模块化（需充分测试）。
   - **P1**：处理 MLR-013（热头文件）、MLR-018（虚泛型）。
   - **P2**：处理 MLR-014/023（重复实例化）——注意 `extern template` 收益有限，可结合 PIMPL 或非模板基类。
   - **P3**：处理深度嵌套和包含循环。

4. **基线建立与校准**：记录项目当前各指标得分，每月评审变化趋势。对于 Modules 迁移中的项目，每季度更新阈值。

5. **SME 复核流程**：工具输出后，由至少两名架构师对得分 < 60 的模块进行复核，确认是否真实债务。对于 HPC 场景的高膨胀率模块，需附上性能测试报告。

6. **豁免审计**：按附录 B 的规范管理豁免注释，每季度由架构组复审豁免清单。

## 附录 B：豁免语法规范与审计流程

### B.1 豁免注释语法规范

本指南定义三类豁免注释，评估工具必须识别并相应调整评分：

```cpp
// 类型1：模板重复实例化豁免（MLR-014）
// @template_specialization_required: <multi-precision | multi-dimension | performance-critical | future-extension>
// 适用场景：多精度数值库（如 Tensor<double>/Tensor<float> 并存）、多维度模板（如 3×3 与 4×4 矩阵）、性能关键路径特化

// 类型2：二进制膨胀豁免（MLR-017）
// @allow_binary_bloat: <简要理由>
// 必须包含性能测试数据，格式为 "performance_gain: X%; compile_time_increase: Ys"
// 示例：@allow_binary_bloat: SIMD optimization for 4x4 matrix; performance_gain: 40%; compile_time_increase: 2.1s

// 类型3：镀金模板豁免（MLR-018）
// @reserved_for_future_extension: <预期扩展的类型>
// 适用场景：底层库为未来预留的扩展接口
// 示例：@reserved_for_future_extension: float, int, custom_complex
```

**放置规则**：
- **MLR-014 豁免**：必须放置在模板定义处（即 `template<typename T> class ...` 声明之前），评估工具将检查该模板的所有实例化点是否实际满足豁免理由。
- **MLR-017 豁免**：必须放置在引发高膨胀率的模板特化定义处（如 `template<> class Matrix<double,4,4> { ... }`），评估工具将在检测到高膨胀率时扫描该文件是否包含对应的豁免注释。
- **MLR-018 豁免**：必须放置在模板定义处，评估工具将验证该模板的实例化类型数量是否确实为 1（预留接口不能已实例化为多种类型，否则豁免将被拒绝）。

**工具静态验证要求**：
- 评估工具应检查豁免注释的基本格式合法性（如是否包含必填字段）。
- 对于 `@allow_binary_bloat`，工具应验证 `performance_gain` 字段是否为正数，若为负数或缺失则应发出警告。
- 工具应记录所有豁免的使用位置，生成“豁免审计日志”供定期审查。

### B.2 豁免申请模板（供架构评审使用）

开发者申请豁免时，须填写以下表格（作为 PR 描述的一部分或单独文档）：

```markdown
## 模板膨胀豁免申请表

| 字段 | 填写内容 |
|------|---------|
| 豁免类型 | [ ] MLR-014 重复实例化 / [ ] MLR-017 二进制膨胀 / [ ] MLR-018 镀金模板 |
| 文件位置 | `src/math/matrix_4x4.hpp` |
| 模板定义 | `Matrix<T, 4, 4>` |
| 豁免理由 | 该特化使用 SIMD 指令集优化矩阵乘法，性能提升 40% |
| 性能数据 | 性能提升 40%（基准：非 SIMD 版本 1000 次乘法耗时 12.3ms → 优化版 7.4ms） |
| 编译时间增量 | +2.5 秒（全量编译基线：45 秒 → 优化后 47.5 秒） |
| 替代方案评估 | [ ] 无法合并相似特化：[√] 运行时参数化会导致性能下降 25%  |
| SME 批准人 | @architect_name |
| 审查日期 | YYYY-MM-DD |
```

**归档要求**：所有豁免记录须归档到项目仓库的 `docs/architecture/waivers` 目录，纳入版本控制。评估工具运行时生成豁免审计日志，由 SME 每季度复审一次。

### B.3 CI 审计流程

1. **自动检测阶段**：评估工具在 CI 中运行，扫描所有豁免注释。对于不符合语法规范的豁免（如 `@allow_binary_bloat` 缺少 `performance_gain` 字段），工具直接报错，MR 合入被阻断。

2. **批准阶段**：符合格式的豁免需要至少一名架构师（SME）在代码审查中手动批准。SME 须验证豁免理由的合理性及性能数据的真实性。

3. **定期审计阶段**：每季度由架构组对豁免清单进行复审，执行以下检查：
   - 检查是否存在“永久豁免”（豁免时间超过 6 个月而未重新评估）。
   - 对于 MLR-018 豁免，检查预留接口是否在合理时间内（如 1 年内）实际扩展为多种类型，若否，则要求开发者重新考虑是否移除模板。
   - 生成豁免审计报告，提交架构委员会。

4. **滥用防范**：若同一作者在连续两个季度中提交超过 5 个豁免申请，工具自动触发预警，提醒架构组重点关注该模块的豁免使用情况。
