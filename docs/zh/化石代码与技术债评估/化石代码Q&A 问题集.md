## 0. 速查结论

1. **为什么要独立维度**：ISO 25010 只给定性目标，CK/CISQ/SQALE 不识别 F77/`auto_ptr`/死代码/克隆；标准“演进质量”只看趋势，不做形态检测。
2. **4 个子维**：历史遗留 API/语言方言 30%、死代码/不可达 20%、克隆/重复 20%、技术债密度 30%。
3. **D1**：FOS-006 计所有成块注释（>10 行 WARNING、≤10 行 INFO）；标准 `calc_dead_code` 只保留备份文件。
4. **D2**：标准 `hardcode` 只抓 IP/密钥，FOS-008 只管跨文件常量；单文件数字魔法数仍是空白。
5. **D3**：FOS-012 只计“零测试且年龄 >5 年”的遗留模块；标准 `test_coverage` 对命中模块豁免。
6. **U1/U2/U3**：ISO 25010:**2011**、FOS-012 计分+标准豁免、`is_fossil` TODO 密度 **>5/KLOC**。
7. **12 条规则**：FOS-001~012；FOS-001/002/005 高置信，FOS-004/007/011/012 中低置信，低置信不得设 ERROR。
8. **`throw()`**：`throw(type)` C++17 移除；`throw()` 是 `noexcept(true)` 的弃用别名（至 C++20），两者不能混说。
9. **案例角色**：Code_Aster 是固定格式 Fortran 正样本；BRL-CAD 是 `register`/自有 Fortran 参照；OpenFOAM 只作 FOS-010 债务标记，**不是**遗留 API 正样本。
10. **下一步**：阶段 B（指南 + 案例集 + 专家校对）。

## 一、定位与必要性

### Q1 为什么需要独立的“化石代码与技术债”维度？

**一句话**：因为传统质量模型和自动化度量标准都假设“新代码、现代语言、单一标准”，而工业软件的现实是 20–40 年生命周期、多语言/多时代共存。

**详细解释**：

- 工业软件生命周期常达 **20–40 年**，代码中会沉淀大量“时代特定形态”：FORTRAN 77 固定格式/`COMMON`/隐式类型、`auto_ptr`/`register`/`throw(type)` 等废弃 API、K&R C 方言、死代码、复制粘贴、长期未偿还的技术债。
- 这类形态的危害是**累积且非突发**的：不一定让程序崩溃，却持续抬高理解、修改、测试、编译升级与现代化成本。
- ISO/IEC 25010 的“可维护性/可移植性”只给出**定性目标**；CK、CISQ/ISO 5055、SQALE 覆盖复杂度、结构违规与债务成本，但**不定义“F77/`auto_ptr`/死代码/克隆”等化石形态的可操作检查项**。
- 标准结构维度的“演进质量”只统计趋势/债务曲线，**不做形态检测**。因此需要一个独立维度，回答“哪些形态、多少、先改谁、成本多少”。

**证据**：Code_Aster `IMPLICIT REAL*8`、BRL-CAD `register int i;`、OpenFOAM `HACK/FIXME` 都是“新代码质量指标”难以捕捉的形态。

### Q2 化石代码维度与“演进质量”有什么区别？

| 维度 | 关注点 | 输出 | 典型问题 |
|:--|:--|:--|:--|
| 演进质量（标准） | 趋势、债务曲线、提交活跃度、依赖过时 | 趋势分/曲线 | 债务在增加还是减少？ |
| 化石代码（新维度） | 形态、数量、升级阻塞、现代化成本 | 形态清单 + 分数 | 有没有 F77/`auto_ptr`/死代码/克隆？ |

**边界**：D1~D3 明确“同一文件同一形态只判一次”；化石维度管“形态”，演进维度管“趋势”，两者不重复扣分。

**反例**：一个仓库没有任何 TODO、提交很活跃（演进分高），但仍有大量 F77 `COMMON` 和 `auto_ptr`——演进分看不出升级阻塞，化石维度能。

### Q3 化石代码是不是“代码坏味道”的子集？

**不是简单子集**。

- 代码坏味道（Fowler）偏**设计层**：长函数、上帝类、特性依恋、霰弹式修改等，现代代码也会有。
- 化石代码偏**时代/升级层**：F77 固定格式、废弃 API、K&R C、死代码、克隆、重复常量、债务标记；核心是“时代特定形态 + 升级阻塞”。
- 两者有交集（如重复代码既是坏味道也是克隆），但**不是包含关系**：一个“长函数”不一定是化石；一个 `COMMON` 块也不一定是坏味道。
- FOS-010（TODO/FIXME/HACK）更接近“债务标记”，是化石维度的债务信号，不是完整坏味道体系。

## 二、标准与理论

### Q4 ISO/IEC 25010 用 2011 还是 2023？为什么选 2011？

| 版本 | 可维护性 | 可移植性/灵活性 | 可测试性位置 |
|:--|:--|:--|:--|
| **2011** | 模块化、可重用性、可分析性、可修改性、**可测试性** | **可移植性**：适应性、可安装性、可替换性 | 在**可维护性**内 |
| **2023** | 模块化、可重用性、可分析性、可修改性 | **灵活性（Flexibility）**：适应性、可安装性、可替换性、**可测试性**、可扩展性 | 移到**灵活性**内 |

**为什么选 2011**：设计依据全文使用“可维护性含可测试性、可移植性”的表述，与 2011 完全对应；改成 2023 需要全文改“灵活性/可测试性归属”，容易造成术语漂移。v0.3 的做法是**明确写 `ISO/IEC 25010:2011`，并加 2023 变更注记**，迁移时再统一改名。

**如果用户要求 2023**：把“可移植性”改为“灵活性”，把“可测试性”从可维护性移到灵活性，并在 D3 边界说明中同步。

### Q5 SQALE 是标准吗？

**不是 ISO 标准，是方法/工具**。

- SQALE（Software Quality Assessment based on Lifecycle Expectations）由 Letouzey 提出，核心是**把规则违反映射为修复成本**，形成技术债比率。
- 它需要先定义规则，才能映射成本；对“化石形态”没有现成清单。
- 因此设计依据把 SQALE 标为“方法/工具”，FOS-011 用它做**成本代理**，不是直接引用标准条款。
- 真正可引用的自动化质量度量标准是 **CISQ / ISO/IEC 5055:2021**；CK 是 1994 年的 OO 度量集，不是标准。

### Q6 CK、CISQ、ISO 5055 各是什么？为什么覆盖不了化石形态？

| 名称 | 性质 | 覆盖 | 化石盲区 |
|:--|:--|:--|:--|
| CK（Chidamber & Kemerer 1994） | OO 度量集 | WMC/CBO/RFC/LCOM 等 | 单语言 OO 结构；无时代/废弃 API/死代码概念 |
| CISQ / ISO/IEC 5055:2021 | 自动化质量度量标准 | 可靠性、性能、安全、可维护性规则 | 结构违规为主；不识别 F77/`COMMON`/`auto_ptr` |
| SQALE | 方法/工具 | 规则违反映射修复成本 | 需先定义化石规则；无现成清单 |

**结论**：三者能回答“结构是否健康/债务多少”，但不能回答“有哪些化石形态、升级阻塞在哪”。这正是独立维度的理论缺口。

### Q7 `throw()` 到底是不是 C++17 移除的？

**不是。要区分两个东西**：

| 写法 | 状态 | 说明 |
|:--|:--|:--|
| `void f() throw(int);`（`throw(type)`） | **C++17 移除** | 动态异常规格被移除（P0003R5） |
| `void f() throw();`（`throw()`） | **保留为 `noexcept(true)` 的弃用别名** | C++17 起弃用，约 C++20 移除 |

**正确说法**：“`throw(type)` C++17 移除；`throw()` 是 `noexcept(true)` 的弃用别名（至 C++20）。” 设计依据 v0.3 已在 §2.2 加注，避免把两者混为一谈。

**替代写法**：`noexcept` / `noexcept(false)`；不要再用动态异常规格。

### Q8 其他常见废弃 API 的移除/弃用版本？

| API/关键字 | 状态 | 版本 |
|:--|:--|:--|
| `std::auto_ptr` | 移除 | C++17 |
| `register` | 移除 | C++17 |
| `std::bind1st` / `std::bind2nd` | 移除 | C++17 |
| `std::random_shuffle` | 移除 | C++17 |
| `std::result_of` | 移除 | C++20 |
| `std::strstream` | 弃用 | C++98 起 |
| `std::codecvt` / `std::iterator` | 弃用 | C++17 |
| `std::aligned_storage` | 弃用 | C++23 |
| `std::atomic_*`（shared_ptr 自由函数） | 弃用 | C++20 |
| `gets` | 移除 | C11 |

> 注：不同标准版本/编译器实现可能有差异；检测时以“目标标准 + 编译器警告”为准，不只看关键字。

## 三、定义与评分

### Q9 化石代码的定义是什么？4 个子维怎么分？

**定义**：代码中因语言/API/工具链时代变迁而沉淀的、**升级阻塞或维护成本显著**的形态，以及长期未偿还的技术债。

| 子维 | 权重 | 规则 | 层级 |
|:--|:-:|:--|:--|
| 历史遗留 API 与语言方言 | 30% | FOS-001~003 | 基础层（升级阻塞） |
| 死代码/不可达 | 20% | FOS-004~006 | 基础层（可删性） |
| 克隆/重复 | 20% | FOS-007~009 | 增强层（理解成本） |
| 技术债密度与可维护性 | 30% | FOS-010~012 | 增强层（偿还优先级） |

**为什么这样分**：前两层是“必须先识别/清除”的基础形态；后两层是“影响理解与偿还顺序”的增强信号。基础层不折半，避免“死代码多但克隆少”被平均掉。

### Q10 12 条 FOS 规则分别管什么？

| 规则 | 检查对象 | 子维 | 分值 | 备注 |
|:--|:--|:--|:-:|:--|
| FOS-001 | F77 固定格式/`COMMON`/`IMPLICIT`/`EQUIVALENCE` | 遗留 API | 40 | 高置信；需固定格式判定 |
| FOS-002 | `auto_ptr`/`register`/`throw(type)`/`strstream`/`bind1st` | 遗留 API | 40 | 高置信；剥离注释/字符串 |
| FOS-003 | K&R C 方言/非标准扩展 | 遗留 API | 20 | 高置信 |
| FOS-004 | 不可达/死代码 | 死代码 | 50 | 引用图启发式 |
| FOS-005 | 未使用函数/文件 | 死代码 | 30 | 高置信 |
| FOS-006 | 成块注释代码 | 死代码 | 20 | >10 行 WARNING；≤10 行 INFO |
| FOS-007 | 克隆代码（Type-1/2/3） | 克隆 | 50 | token 哈希/winnowing |
| FOS-008 | 跨文件重复常量/魔法数 | 克隆 | 20 | 只管跨文件 |
| FOS-009 | 失效配置/死分支 | 克隆 | 30 | 配置/分支分析 |
| FOS-010 | `TODO/FIXME/HACK/XXX` 密度 | 债务 | 25 | 债务标记 |
| FOS-011 | SQALE 修复成本比率 | 债务 | 50 | 成本代理，中低置信 |
| FOS-012 | 年龄 >5 年且零测试的遗留模块 | 债务 | 25 | 与标准覆盖率豁免联动 |

**子维内合计**：40+40+20=100；50+30+20=100；50+20+30=100；25+50+25=100。  
**KNOWN_HOLES**：FOS-013（跨语言死代码）、FOS-014（历史构建脚本）暂不评分。

### Q11 评分怎么汇总？基础层/增强层会不会折半？

- 子维内按规则分值扣减（命中即按比例/阈值扣分），子维分下限 0、上限 100。
- 总分 = Σ（子维分 × 子维权重），权重 30/20/20/30。
- **基础层/增强层不折半**：这是与 HPC 维度不同的地方；化石维度要避免“基础形态被增强层平均掉”。
- 低置信规则（FOS-004/007/011/012）以 **candidate** 输出，不直接决定 ERROR；高置信规则才可设 ERROR。
- 维度整体可给 `overall=None`（不适用），避免对非化石项目强行打分。

### Q12 为什么低置信度规则不能设 ERROR？

- 化石检测大量依赖引用图、克隆、成本代理，存在**误报**（如注释里的 `register`、模板实例化导致的“伪克隆”）。
- 一旦设 ERROR，会误伤健康项目、阻断 CI，反而降低评估可信度。
- 设计原则：**低置信 → candidate + 人工/LLM 复核**；只有 FOS-001/002/005 等高置信规则可设 ERROR。
- 这与 HPC 的 candidate/confirmed 体系一致，但化石维度的低置信比例更高，需更保守。

## 四、边界裁决 D1~D3

### Q13 D1：标准 `calc_dead_code` 与 FOS-006 怎么分工？为什么原来有“<10 行”空白？

**原来的问题**：

- 标准 `arch_metrics_standard.py:1011-1038` 的 `calc_dead_code` 统计两类：
  1. 备份文件（`*.bak`、`*_old` 等）；
  2. `/* ... if/for/class/return ... */` 形式的注释块。
- FOS-006 原设计只计 **>10 行**的成块注释。
- 结果：**≤10 行的注释代码**标准不扣、FOS-006 也不扣 → 出现空白。

**v0.3 的裁决**：

- **FOS-006 计所有成块注释**：>10 行 WARNING；≤10 行 INFO（仍输出，但不重扣）。
- **标准 `calc_dead_code` 只保留备份文件**，移除注释块扣分。
- 这样“注释代码”完全归 FOS-006，标准不再重复；短注释块也有 INFO 记录，不再落空。

**示例（`#if 0` 块，5 行）**：

```c
#if 0
if (mode == LEGACY) {
    legacy_init();
}
#endif
```
旧规则：标准只匹配 `/* ... if ... */`，不抓 `#if 0`；FOS-006 只计 >10 行 → 5 行块**两者都不抓**，形成空白。  
v0.3：FOS-006 记 INFO，标准不计注释块，归属唯一。

### Q14 标准 `calc_dead_code` 改动会影响什么？怎么保证基线不漂移？

**影响**：

- 标准结构维度的“死代码/债务”相关扣分减少，`standard_arch_quality` 等回归快照会变化。
- 若直接改代码不重设基线，回归测试会红。

**控制**：

1. 改动前记录受影响快照清单（`tests/regression/snapshots/standard_*.json` 等）；
2. 用程序化校验（分数区间、维度键、计数、确定性）确认变化方向合理；
3. 重设基线并写迁移记录（为什么变、变了多少、是否只由 D1 引起）；
4. 禁止盲刷 `ARCH_REGRESSION_UPDATE=1`。

> 这是阶段 C 的实现项；v0.3 只定设计，不改标准代码。

### Q15 D2：标准 `hardcode` 与 FOS-008 怎么分工？单文件数字魔法数为什么落空？

**现状**：

- 标准 `anti_patterns.hardcode`（`arch_metrics_standard.py:567-570`）只匹配 **IP 地址/密钥**类硬编码，不统计数字魔法数。
- FOS-008 只统计**跨文件**重复常量/魔法数。
- 结果：**单文件内的数字魔法数**（如 `if (x > 0.85)`）标准不抓、FOS-008 也不管 → 两者落空。

**为什么不在 v0.3 强行补**：

- 单文件魔法数误报率高（0/1、数组下标、物理常数都可能是合理常量）；
- 需要“高密度 + 非平凡常量”子规则，否则会把健康代码打成缺陷。

**后续**：补标准规则，或给 FOS-008 增加“单文件高密度魔法数”**INFO 子规则**；在补齐前，该空白在文档中明确标注，不假装覆盖。

### Q16 D3：FOS-012 与标准 `test_coverage` 为什么会双重扣分？怎么豁免？

**双重扣分链**：

1. 一个 10 年未改的遗留模块没有任何测试；
2. 标准 `test_coverage` 按整体覆盖率扣分；
3. FOS-012 又按“年龄 >5 年且无测试”扣分；
4. 同一事实被扣两次。

**v0.3 裁决**：

- FOS-012 只计 **“零测试且年龄 >5 年”的遗留模块**（不是“覆盖率低”）；
- 标准 `test_coverage` 对 FOS-012 命中模块**豁免重复扣分**；
- 实现方式：FOS 引擎输出 `legacy_untested_modules` 列表，标准引擎在计算覆盖率时剔除这些模块（阶段 C）。

**备选**：若跨引擎豁免实现成本过高，可把 FOS-012 降为 advisory（不计分）；但当前设计选择“计分 + 豁免”，保留债务信号。

### Q17 `is_fossil` 的激活条件是什么？为什么定 5/KLOC？

**三条件（任一成立即激活）**：

1. **遗留语言/API 信号**：F77/`COMMON`/`IMPLICIT`、`auto_ptr`/`register`/`throw(type)`、K&R C；
2. **债务密度**：`TODO/FIXME/HACK/XXX` **>5/KLOC**；
3. **死代码/克隆**超过阈值（阶段 A 校准，待定）。

**为什么 5/KLOC**：

- TODO 几乎每个项目都有，零阈值会让维度“永远激活”；
- 5/KLOC 能过滤“零星注释”，保留“债务成片”的项目；
- 该值是**启发式阈值**，阶段 B 用样本校准，可调整。

**注意**：条件 1 是“形态信号”，不要求数量；条件 3 的阈值尚未定，阶段 B 补。

## 五、检测口径

### Q18 FOS-001 怎么判定“固定格式”？

不能只看 `.f` 扩展名（`.f` 也可能按自由格式编译）。判定依据：

1. **扩展名**：`.f/.f77/.for`（优先）；
2. **列规则**：第 1–6 列有标签/续行标记，第 7 列非空/非零，代码从第 7 列后开始；
3. **编译选项**：`-ffixed-form` / `-ffixed-line-length-*`；
4. **内容信号**：`COMMON`、`IMPLICIT`、`EQUIVALENCE`、`DIMENSION` 等老式写法。

**误判控制**：自由格式 `.f90` 不按固定格式计；混合项目按文件级判定，不按项目级“一刀切”。

### Q19 FOS-002 怎么避免 `register` 注释误报？

- 先**剥离注释与字符串**（`//`、`/* */`、`'...'`、`"..."`），再按关键字/符号匹配；
- `register` 作为 C/C++ 关键字时才算；注释里的 “register the callback” 不算；
- OpenFOAM 中大量 `register` 是注释/普通词，不能直接 `rg` 计数；
- `auto_ptr` 同理：OpenFOAM `src` 实为 **0 命中**，原始计数含注释/文档，不能当正样本。

### Q20 FOS-006 与标准注释正则的边界到底在哪？

- 标准 `calc_dead_code` 的注释正则只匹配 `/* ... if/for/class/return ... */` 这一形态；
- `//` 单行注释、`#if 0` 块、`<!-- -->` 等**不在标准正则内**；
- v0.3 把这些统一归 **FOS-006**：成块注释按行数分级（>10 行 WARNING，≤10 行 INFO）；
- 标准侧只保留备份文件，不再抢注释代码。

### Q21 FOS-004 跨语言死代码为什么是 KNOWN_HOLE？

- Fortran/C/C++ 符号映射不完整（名字修饰、`extern "C"`、链接脚本、动态加载）；
- 静态引用图可能把“被脚本/配置调用的函数”误判为死代码；
- 因此 FOS-004 只做**同语言引用图**的高置信部分；跨语言死代码列为 **FOS-013 KNOWN_HOLE**，不评分。

### Q22 FOS-011 的 SQALE 比率为什么只是“代理”？

- SQALE 需要“规则 → 修复成本”的映射；化石形态没有行业统一的修复工时基准；
- 设计依据用“违规密度 × 代理成本”估算，不是真实项目核算；
- 因此 FOS-011 标为中低置信、candidate；不单独触发 ERROR，只用于排序/预算参考。

### Q30 什么是 ABI？为什么化石代码会导致 ABI/跨平台失效？

**一句话**：**ABI（Application Binary Interface）是编译后二进制模块之间的“契约”**；API 是源码级契约，ABI 是机器级契约。API 断了，改代码重编译通常能修；ABI 断了，重编译仍可能链接失败或运行时崩溃。

#### 1. API vs ABI

| 层面 | 约定内容 | 断裂表现 | 修复方式 |
|:--|:--|:--|:--|
| **API**（源码） | 函数名、参数/返回类型、类/结构定义、语义 | 编译失败 | 改代码、重编译 |
| **ABI**（二进制） | 调用约定、名字修饰、内存布局/对齐、异常/RTTI、vtable、运行时库、符号版本 | 链接失败、运行崩溃、数据错 | 重编所有依赖，或保持二进制兼容 |

#### 2. ABI 具体包含什么

- **调用约定**：`cdecl`/`stdcall`/`fastcall`、SysV AMD64 vs Windows x64、参数寄存器/栈、栈对齐。
- **名字修饰/符号名**：C++ mangling、Fortran 下划线后缀、`extern "C"`、符号可见性/版本。
- **数据布局**：`struct`/`class` 大小、对齐、padding、位域、vtable 布局、基类偏移。
- **基础类型大小**：`long`（LP64 vs LLP64）、`size_t`、`wchar_t`、`long double`、枚举底层类型。
- **异常/RTTI**：异常表、`type_info`、栈展开（unwind）。
- **运行时/标准库**：`std::string`/`vector`/`list` 的 ABI、分配器、`_GLIBCXX_USE_CXX11_ABI`。
- **链接/加载**：符号版本、TLS、ELF/PE/Mach-O、动态库搜索路径。
- **语言互操作**：Fortran `COMMON`/数组描述符/名字修饰、C 原型/默认实参提升。

#### 3. FOS-001~003 如何引发 ABI/跨平台失效

**FOS-001（F77/`COMMON`/`IMPLICIT`）**

- `COMMON` 块的**布局/对齐/类型大小**由编译器决定；两侧 `REAL*4` vs `REAL*8`、`INTEGER*4` vs `INTEGER*8`，或 `-fdefault-integer-8`/`-fdefault-real-8` 不一致 → 偏移错、数据损坏。
- Fortran 名字修饰（gfortran 默认下划线）、字符串隐藏长度、数组描述符因编译器而异 → 与 C/C++ 互操作时符号找不到或参数错位。
- `IMPLICIT` 让类型由首字母推断；换编译器/`IMPLICIT NONE` 后类型变化 → 接口二进制不匹配。

**FOS-002（废弃 C++ API）**

- `auto_ptr` 若出现在公共接口，替换为 `unique_ptr` 会改变类型/签名/mangled name → 源码/ABI 双断。
- `std::string` 的 GCC 5 双 ABI（`_GLIBCXX_USE_CXX11_ABI=0/1`）：混用 → 链接错误或运行时崩溃。
- `throw(type)`/`throw()` 主要影响源码与异常表/调用边界；`register` 是存储类，**主要源码级**（C++17 移除），不直接改 ABI。
- `strstream`/`bind1st` 移除 → 源码断；若库符号也移除 → 链接断。

**FOS-003（K&R C/非标准方言）**

- 无原型的老式函数定义触发**默认实参提升**（`float`→`double`、`char`/`short`→`int`）；调用方/被调方一方有原型、一方没有 → 参数宽度/寄存器错位。
- 隐式 `int`、`__attribute__((packed))`、位域、结构体对齐因编译器/平台而异 → 布局不匹配。
- GNU 扩展（`typeof`/`__attribute__`）换编译器即不可编译或语义变化。

#### 4. 跨平台失效的典型场景

| 场景 | 现象 | 原因 |
|:--|:--|:--|
| Windows vs Linux | `long` 32 vs 64 位，结构体大小不同 | LLP64 vs LP64 |
| 大端/小端 | 二进制文件/网络数据读错 | 字节序 |
| `char` 符号 | 比较/哈希结果不同 | x86 有符号、ARM 常无符号 |
| `wchar_t` | Unicode 乱码/截断 | Windows 2 字节、Linux 4 字节 |
| `long double` | 精度/大小不一致 | 80 位 x87 vs 128 位 vs double |
| 结构体/位域 | 字段偏移错 | 对齐/padding/位域实现 |
| Fortran `COMMON` | 数据错位/越界 | 布局、类型大小、编译器选项 |
| 调用约定 | 链接失败/栈错 | `__stdcall`/`__cdecl`、名字修饰 |

#### 5. 为什么叫“编译器升级阻塞”

- **源码级**：API/关键字被移除（`auto_ptr`、`register`、`throw(type)`）→ 编译失败；改代码可修。
- **ABI 级**：预编译库/插件按旧 ABI 编译 → 新编译器/新标准库下链接失败或运行崩溃；必须重编所有依赖，或保持兼容层。
- **跨平台**：同一份源码能编译，但二进制布局/调用约定不同 → ABI 边界、序列化数据、插件接口失效。

#### 6. 工程上怎么防

1. **公共接口用 `extern "C"` + 不透明指针/PIMPL**，避免 STL 类型跨 ABI 边界。
2. **固定宽度类型**：`<cstdint>` 的 `int32_t`/`int64_t`；`static_assert(sizeof(long)==8)`；C++20 `std::endian`。
3. **Fortran**：`bind(C)` + `ISO_C_BINDING` + `integer(c_int32_t)`；用 `MODULE` 替代 `COMMON`；`IMPLICIT NONE`。
4. **C**：强制原型（`-Wstrict-prototypes`），禁止 K&R 定义。
5. **ABI 检查**：`abidiff`/`abi-compliance-checker`；符号版本；`_GLIBCXX_USE_CXX11_ABI` 全仓一致。
6. **序列化**：固定布局/字节序，禁止直接 dump 结构体。
7. **CI 矩阵**：Windows/Linux、32/64 位、多编译器；ABI diff 门禁。

#### 7. 与本评估的映射

- FOS-001/002/003 是 **ABI/跨平台风险的信号**，不是 ABI 检查器本身；它们回答“有没有旧形态”，ABI 工具回答“二进制是否兼容”。
- FOS-011 的 SQALE 成本代理可包含 ABI 整改成本；报告建议增加 `abi_risk` 标签（阶段 C 可选）。
- 有意保留 ABI 的旧接口，用 `@fossil_legacy_ok` 显式登记；但 >30% 会触发滥用告警。
- **ABI 自动比对目前不是独立 FOS 规则**，属已知增强项；可在阶段 C 后评估是否新增规则/门禁。

### Q31 FOS-004 的“符号引用图 + 入口点/FFI/插件白名单”具体怎么做？

**一句话**：FOS-004 不是“搜不到调用就算死代码”，而是**先建符号引用图，再从入口点/白名单出发做可达性分析**；从根不可达的符号才是候选，且只给中低置信度、需人工复核。

#### 1. FOS-004 在评什么

- **对象**：未被引用的**函数、全局变量、文件/编译单元**。
- **赋分**：50（死代码子维中最高）；**置信度中低**。
- **输出**：候选（WARNING），带 `定义位置 file:line` + `未发现引用` 证据；确认后才扣 50。
- **与 FOS-005 的边界**：同一符号既“未引用”又“含不可达分支”时，**只扣 FOS-004（50）**，FOS-005 记 INFO，不双扣。

#### 2. 符号引用图是什么

**节点**：函数、方法、全局变量、文件/模块（可选类/结构体）。

**边**（A → B 表示 A 引用了 B）：

| 引用形态 | 例子 | 说明 |
|:--|:--|:--|
| 直接调用 | `foo();` | 最常见 |
| 取地址/函数指针 | `&foo`、`cb = foo;`、`std::bind(foo)` | 必须算引用 |
| 成员/虚函数 | `obj.run()`、`base->run()` | 虚函数要保守标记 override |
| 函数指针表 | `{foo, bar}` | 表被调用时，全部标记可达 |
| 注册宏 | `REGISTER_PLUGIN(foo)` | 宏/注册表算引用 |
| 字符串动态查找 | `dlsym("foo")`、`GetProcAddress("foo")` | 字符串要映射到符号 |
| 绑定/FFI | `pybind11::def("foo", &foo)`、JNI、P/Invoke | 声明/绑定算引用 |
| 配置/清单 | `plugin=foo`、`class=LegacySolver` | 配置驱动算引用 |
| Fortran | `CALL foo`、`EXTERNAL foo`、`bind(C)`、`USE mod` | 名字修饰/模块要处理 |

**建图步骤**：

1. **符号表**：解析每个文件的定义（函数/全局变量/文件），记录 `file:line`、可见性、语言。
2. **引用点**：解析调用、取地址、成员访问、函数指针赋值、注册宏、字符串、配置、FFI 声明。
3. **连边**：引用者 → 被引用者；跨文件/跨语言尽量连。
4. **根集合**：入口点 + 白名单（见 §3/§4）。
5. **可达性**：从根做 BFS/DFS；**不可达 = 候选死符号**。
6. **过滤**：third_party/generated/build/examples/tests（按规则）；条件编译/宏/模板保守处理。

#### 3. 入口点（root）有哪些

入口点是“程序/库本来就会被调用的地方”，必须作为可达性起点：

| 类型 | 例子 |
|:--|:--|
| 可执行程序入口 | `main`、`wmain`、`WinMain` |
| 动态库入口 | `DllMain`、`JNI_OnLoad`、`PyInit_*` |
| 导出 API | `extern "C"`、`__declspec(dllexport)`、`visibility("default")`、`.def`/`EXPORTS` |
| 插件入口 | `create_plugin`、`plugin_init`、`register_*`、工厂函数、`REGISTER_PLUGIN` |
| 语言运行时 | Fortran `PROGRAM`、Python 模块初始化、JNI 注册 |
| FFI 入口 | `bind(C)`、ctypes/cffi/pybind11/JNI/P/Invoke 声明 |
| 测试/工具 | 测试 `main`、benchmark、CLI 工具（**单独标记**，见 §5） |

> 关键：**入口点不是“所有 public 函数”**。把所有 public 都当根，会让 FOS-004 失效；只把真正的入口/导出/插件/FFI 约定当根。

#### 4. FFI/插件白名单是什么

白名单是“静态引用图看不到、但运行时会调用”的符号清单，来源必须**可核实**：

| 来源 | 例子 | 处理 |
|:--|:--|:--|
| 导出声明 | `extern "C"`、`dllexport`、`visibility`、`.def` | 自动加入根 |
| FFI 声明 | `bind(C)`、`ctypes`、`cffi`、`pybind11::def`、JNI、P/Invoke | 自动/半自动加入根 |
| 插件注册 | `REGISTER_PLUGIN`、`plugin_init`、工厂/配置 | 自动加入根 |
| 配置/清单 | `plugin=foo`、`class=LegacySolver` | 解析配置加入根 |
| 动态查找字符串 | `dlsym("foo")`、`GetProcAddress("foo")` | 字符串映射加入根 |
| 人工注解 | `@fossil_not_dead: reason` | 显式白名单，reason 必填 |

**反滥用**：

- 不允许“整个目录/整个命名空间”一键白名单；
- 白名单要有证据（导出表、FFI 声明、配置、注解）；
- 人工注解占比过高要告警（与豁免体系一致）。

#### 5. 为什么置信度是“中低”

静态引用图有天然盲区：

- **间接调用**：函数指针、回调、虚函数、事件/信号、注册表；
- **动态加载**：`dlsym`/`GetProcAddress`、插件、反射；
- **跨语言**：Fortran/C++ 名字修饰、JNI/Python/C# 绑定；
- **宏/模板**：宏展开、模板实例化、条件编译；
- **测试遮蔽**：测试调用了某函数，不代表生产在用（应标“test-only”，不直接算生产可达）；
- **生成代码/第三方**：应排除或单独处理；
- **链接器优化**：`--gc-sections`/LTO 可能已删，但源码仍在。

所以 FOS-004 **不能设 ERROR**，只能 candidate + 人工/LLM 复核；跨语言死代码进一步列为 **FOS-013 KNOWN_HOLE**。

#### 6. 算例

**正例（候选）**：

```c
static void legacy_init(void) {   /* 定义；无调用、无取地址、未导出 */
    /* ... */
}
```
→ 图中无入边、非根 → FOS-004 候选（50，WARNING，中低）。

**负例（不触发）**：

```cpp
extern "C" __attribute__((visibility("default")))
void api_init(void);              // 导出 API，自动入根
```
```cpp
REGISTER_PLUGIN("legacy", create_legacy);   // 注册宏，入根
```
```cpp
// 通过 dlsym("api_init") 调用 → 字符串白名单
```

**虚函数/回调**：

```cpp
struct Base { virtual void run(); };
struct Derived : Base { void run() override; };
```
→ `Base::run` 可达时，`Derived::run` 保守标记可达（避免误杀 override）。

**Fortran FFI**：

```fortran
subroutine umat(...) bind(C, name="umat")
```
→ `bind(C)` 导出，入根；被外部求解器调用，不能判死。

#### 7. 在工具里怎么落地

- `FileIndex` + 解析器（tree-sitter/ctags/正则）建符号表；
- `rg`/AST 收集调用、取地址、函数指针、宏、字符串、配置；
- 哈希表建图（O(n)），从根 BFS；
- 白名单：导出表/FFI 声明/插件注册/配置/`@fossil_not_dead`；
- 输出：`FOS-004` 候选 + `file:line` + “无入边/非根”证据 + 最近根；
- 大仓库：排除 third_party/generated/build，分片/缓存；
- 误报处理：人工确认 → 真死则删；动态引用则加白名单/注解。

#### 8. 一句话总结

**符号引用图回答“谁引用了谁”，入口点/FFI/插件白名单回答“哪些符号本来就会被外部调用”；两者结合，才能把“没搜到调用”从“死代码”降级为“候选”，避免把导出 API、插件工厂、FFI 入口误杀。**

### Q32 克隆检测：token 哈希/winnowing/SimHash 怎么识别 Type-1/2/3 克隆？

**一句话**：三者都是“把代码变成指纹再比对”，但粒度不同——token 哈希看**连续 token 片段**，winnowing 看**局部指纹集合**，SimHash 看**整个函数/文件的近似指纹**。

#### 1. 先分清克隆类型

| 类型 | 特征 | 例子 | 主要检测 |
|:--|:--|:--|:--|
| **Type-1** | 完全相同，仅空白/注释/格式不同 | 复制后改缩进 | token 哈希（精确） |
| **Type-2** | 标识符/字面量/类型重命名 | `flux_a`→`flux_b`、`0.85`→`0.85f` | 归一化 token 哈希 |
| **Type-3** | 近似克隆，有增删改/语句插入 | 复制后加一行日志、删一个分支 | winnowing + 相似度 |
| **Type-4** | 语义相同、写法不同 | 循环 vs 递归、不同算法同语义 | 静态难判（FOS-014 KNOWN_HOLE） |

#### 2. 总体流程

```text
源码 → 词法分析（token）→ 归一化 → 片段化（k-gram/函数）
     → 指纹（token hash / winnowing / SimHash）
     → 候选检索（哈希表/LSH）
     → 相似度验证（token 序列/指纹交集/Hamming）
     → 克隆对（file:line + 相似度）
```

#### 3. Token 哈希

**做什么**：把 token 序列切成固定长度 `k` 的连续片段（k-gram），对每个片段算哈希；相同哈希 → 候选相同片段。

- **token 化**：关键字、标识符、字面量、运算符、标点；去掉注释/空白。
- **归一化**：
  - Type-1：保留原 token；
  - Type-2：标识符→`ID`、字面量→`LIT`、类型→`TYPE`，保留关键字/运算符；
  - Type-3：归一化后仍需容忍增删，单靠精确哈希不够。
- **k-gram**：如 `k=5`，`a b c d e` 是一个片段；滑动一位得 `b c d e f`。
- **滚动哈希**（Rabin-Karp）：`h = (h - old×base^(k-1))×base + new mod M`，O(n) 算完所有片段。
- **比对**：哈希表存 `hash → 位置列表`；相同哈希即候选；碰撞需回验 token 序列。

**优点**：快、精确、易实现。  
**缺点**：对重命名/插入敏感；Type-2 需归一化；Type-3 易漏。

**例子**：

```cpp
// A
double flux_a(double u, double v) { return u * v + 0.5 * (u - v); }
// B（Type-2：改名）
double flux_b(double x, double y) { return x * y + 0.5 * (x - y); }
```
归一化后 token 序列相同 → Type-2 命中。

#### 4. Winnowing（局部指纹）

**做什么**：不保留所有 k-gram 哈希，而是每个“窗口”只选一个最小值作为指纹；用少量指纹覆盖全文，仍能保证一定长度的匹配被检出。

- 参数：`k` = k-gram 长度；`w` = 窗口大小（连续 k-gram 个数）。
- 步骤：
  1. 算所有 k-gram 哈希；
  2. 用长度 `w` 的窗口滑动；
  3. 每个窗口选**最小哈希**（并列取最右）；
  4. 去重得到指纹集合。
- **保证**：若两段代码有长度 ≥ `k + w - 1` 的公共 token 子串，则至少有一个共同指纹被选中。
  - 例：`k=5, w=4` → 保证 8 token 的匹配；想保证 10 token，可取 `k=5, w=6` 或 `k=8, w=3`。
- **相似度**：指纹集合的 Jaccard/containment；如 `|A∩B| / min(|A|,|B|) ≥ 0.80`。
- **优点**：对插入/删除/移动更稳（Type-3），指纹量小、可索引。  
- **缺点**：小于保证长度的克隆可能漏；窗口/k 选择影响召回率。

**例子**：A/B 复制后 B 多了一行日志；k-gram 大部分相同，winnowing 指纹大量重叠 → Type-3 候选。

#### 5. SimHash（整体近似指纹）

**做什么**：把整个函数/文件压成固定长度（如 64 位）指纹；相似内容的指纹 Hamming 距离小。

- 步骤：
  1. 取特征（token/ngram/行）；
  2. 每个特征算哈希；
  3. 对 64 位每一位，按特征权重累加 `+1/-1`；
  4. 符号位 → 0/1，得到 64 位 SimHash。
- **相似度**：`1 - HammingDistance / 64`；近重复通常距离 ≤3~5。
- **检索**：LSH 分 band，先找候选再精确比 Hamming。
- **优点**：整文件/函数级近重复快；对少量修改不敏感。  
- **缺点**：局部小克隆会被大文件“稀释”；不适合精确定位克隆片段；需要配合 winnowing。

**例子**：两个 500 行文件 95% 相同，SimHash 距离很小 → Type-3/近重复；但若只复制了 20 行，SimHash 可能看不出来。

#### 6. 三者对比与 FOS-007 映射

| 方法 | 粒度 | 擅长 | 局限 | FOS-007 用途 |
|:--|:--|:--|:--|:--|
| token 哈希 | 连续 k-gram | Type-1/2 精确匹配 | 插入/删除敏感 | 快速召回精确克隆 |
| winnowing | 局部指纹集合 | Type-1/2/3，抗增删 | 小于保证长度会漏 | 主力相似度 |
| SimHash | 整个函数/文件 | 近重复、Type-3 | 局部克隆稀释 | 文件级预筛 |

**FOS-007 当前口径**：token 哈希/winnowing，相似度 ≥0.80；识别 Type-1/2/3；Type-4 语义克隆列 **FOS-014 KNOWN_HOLE**；赋分 50、置信度中低、候选 WARNING。

#### 7. 参数与误报控制

- 最小克隆规模：如 ≥20 token 或 ≥6 行，避免 `get/set` 样板误报；
- 归一化强度：太强 → 不同语义误判；太弱 → Type-2 漏；
- 排除：third_party/generated/build/templates/宏展开；
- 去重：同一克隆对只报一次；同一函数多片段合并；
- 阈值：0.80 为默认，阶段 C 用真实样本校准；
- 误报来源：样板代码、license 头、自动生成、常见 idiom、测试夹具。

#### 8. 一句话总结

**token 哈希找“完全一样的片段”，winnowing 找“局部指纹大量重合的片段”，SimHash 找“整体很像的函数/文件”；三者组合，才能覆盖 Type-1/2/3，而 Type-4 语义克隆仍需 AST/PDG，当前列为 KNOWN_HOLE。**

### Q33 举例解释“词法分析（token）”

**一句话**：词法分析（lexing/tokenization）是把源码字符流切成**有类型的 token 序列**，并丢掉空白/注释；它是克隆检测的第一步——后面的 k-gram、哈希、winnowing 都基于 token，而不是原始字符。

#### 1. 一个 C++ 例子

源码：

```cpp
// legacy flux
double flux_a(double u, double v) {
    return u * v + 0.5 * (u - v);
}
```

词法分析后（注释/空白被丢弃）：

| # | token 类型 | 词素（lexeme） | 位置 |
|:-:|:--|:--|:--|
| 1 | keyword/type | `double` | 2:1 |
| 2 | identifier | `flux_a` | 2:8 |
| 3 | punct | `(` | 2:14 |
| 4 | keyword/type | `double` | 2:15 |
| 5 | identifier | `u` | 2:22 |
| 6 | punct | `,` | 2:23 |
| 7 | keyword/type | `double` | 2:25 |
| 8 | identifier | `v` | 2:32 |
| 9 | punct | `)` | 2:33 |
| 10 | punct | `{` | 2:35 |
| 11 | keyword | `return` | 3:5 |
| 12 | identifier | `u` | 3:12 |
| 13 | operator | `*` | 3:14 |
| 14 | identifier | `v` | 3:16 |
| 15 | operator | `+` | 3:18 |
| 16 | literal | `0.5` | 3:20 |
| 17 | operator | `*` | 3:24 |
| 18 | punct | `(` | 3:26 |
| 19 | identifier | `u` | 3:27 |
| 20 | operator | `-` | 3:29 |
| 21 | identifier | `v` | 3:31 |
| 22 | punct | `)` | 3:32 |
| 23 | punct | `;` | 3:33 |
| 24 | punct | `}` | 4:1 |

> 注释 `// legacy flux` 不进入 token 流；空白/换行也不进入（Python 例外，见 §5）。

#### 2. 词法分析器在做什么

```text
for each char:
  skip whitespace/comments
  if identifier start: consume [A-Za-z_][A-Za-z0-9_]*
  if digit:           consume number (int/float/hex)
  if quote:           consume string/char with escapes
  if operator/punct:  match longest
  emit token(type, lexeme, line, col)
```

产出 token 对象：

```text
Token { type, lexeme, file, line, column, offset }
```

常见 token 类型：

| 类型 | 例子 |
|:--|:--|
| keyword | `return`、`if`、`implicit`、`program` |
| identifier | `flux_a`、`u`、`v` |
| literal | `0.5`、`"abc"`、`.true.` |
| operator | `+`、`*`、`==`、`**` |
| punctuation | `(`、`)`、`{`、`}`、`;`、`,` |
| EOF | 结束 |

#### 3. 为什么克隆检测要用 token

- **去掉格式噪声**：缩进、空格、换行、注释不影响 token → Type-1 更容易命中。
- **稳定序列**：token 流比字符流更适合 k-gram/哈希/winnowing。
- **可归一化**：标识符→`ID`、字面量→`LIT`、类型→`TYPE` → Type-2。
- **保留结构**：关键字/运算符/标点保留，避免把不同语义归一成一样。

#### 4. Type-1 / Type-2 的 token 例子

**Type-1（仅格式不同）**：

```cpp
double flux_a(double u,double v){return u*v+0.5*(u-v);}
```

与上面的多行版本 token 序列完全一致 → Type-1。

**Type-2（改名）**：

```cpp
double flux_b(double x, double y) {
    return x * y + 0.5 * (x - y);
}
```

归一化后：

```text
double ID ( double ID , double ID ) { return ID * ID + LIT * ( ID - ID ) ; }
```

与 A 的归一化序列一致 → Type-2。

**Type-3（插入一行）**：

```cpp
double flux_c(double x, double y) {
    log("flux");
    return x * y + 0.5 * (x - y);
}
```

token 流多了一个 `log ( "flux" ) ;`，但其余 k-gram 大量重合 → winnowing 仍可检出近似克隆。

#### 5. 不同语言的词法差异

| 语言 | 词法要点 | 对克隆检测的影响 |
|:--|:--|:--|
| C/C++ | 注释 `//`/`/* */`、预处理 `#include`/`#define`、字符串转义、原始字符串、模板 `>>` | 需处理预处理/模板；宏未展开会漏克隆 |
| Fortran 固定格式 | 第 1 列 `C/*` 注释、第 6 列续行、空格不敏感、`REAL*8` 可拆 token | 必须按列切；否则注释/续行解析错 |
| Fortran 自由格式 | `!` 注释、`&` 续行、`::`、`=>` | 按自由格式 lexer |
| Python | 缩进产生 `INDENT`/`DEDENT`、`#` 注释、f-string、换行 `NEWLINE` | 不能简单丢换行；缩进是语法 |
| C | K&R 旧式定义、隐式 `int`、宏 | 词法上仍是 token；语义/ABI 另判 |

**Fortran 固定格式例子**：

```fortran
      IMPLICIT REAL*8 (A-H,O-Z)
```

token 可能是：`IMPLICIT`、`REAL`、`*`、`8`、`(`、`A`、`-`、`H`、`,`、`O`、`-`、`Z`、`)`。  
若词法器不按列处理，可能把第 1 列 `C` 当代码，或把续行当新语句。

#### 6. 词法分析 vs 语法分析

| 阶段 | 产出 | 克隆检测用途 |
|:--|:--|:--|
| 词法分析 | token 流 | Type-1/2/3 的 k-gram/哈希/winnowing |
| 语法分析 | AST | Type-4 语义克隆、结构比对 |
| 语义分析 | 符号表/类型/数据流 | Type-4、跨语言、死代码 |

> FOS-007 用 token 流即可覆盖 Type-1/2/3；Type-4 需要 AST/PDG，当前列 **FOS-014 KNOWN_HOLE**。

#### 7. 常见坑

- **宏未展开**：`#define SQ(x) ((x)*(x))` 词法只看到 `SQ`，看不到展开后的克隆；
- **模板 `>>`**：`vector<vector<int>>` 可能被 lex 成 `>>`，需要 lexer 模式/parser 处理；
- **字符串/注释**：转义、原始字符串、嵌套注释要正确跳过；
- **Unicode 标识符**：`变量名` 在不同 lexer 支持不同；
- **生成代码**：token 流可能是模板生成，需排除/标记；
- **归一化过度**：把所有标识符都变 `ID`，可能把不同语义的代码判成克隆。

#### 8. 一句话总结

**词法分析把“字符”变成“带类型的 token”；克隆检测再把 token 变成 k-gram/指纹。没有可靠的 lexer，后面的哈希/winnowing/SimHash 都是在错误的序列上比对。**

### Q34 “第 1–6 列标签/续行，第 7 列起代码；或 -ffixed-form”怎么理解？

**一句话**：这是 Fortran **固定格式（fixed-form）**的列规则——第 1–5 列放语句标号，第 6 列放续行标记，第 7–72 列才是语句正文；`-ffixed-form` 是编译器选项，用来**强制按固定格式解析**，覆盖扩展名默认规则。

#### 1. 固定格式的列布局

```text
列:   1 2 3 4 5 | 6 | 7 ................ 72 | 73–80
      [ 标号  ] [续行] [ 语句正文 ......... ] [序号，忽略]
```

| 列 | 用途 | 说明 |
|:--|:--|:--|
| **1–5** | 语句标号（label） | 1–5 位数字；如 `100`、`  10`；也可空白 |
| **6** | 续行标记（continuation） | 非空白且非 `0` → 本行是上一行的续行；常用 `&`、`+`、`1`–`9` |
| **7–72** | 语句正文 | 代码从第 7 列开始；第 7 列前不能写正文 |
| **73–80** | 序号区 | 传统打孔卡序号，编译器忽略 |

> 注意：第 7 列是“正文起点”，不是“必须紧贴第 7 列”；正文可以在 7–72 列内任意位置，空格在字符串外不敏感。

#### 2. 例子

**正常语句**（1–6 列空白，代码从第 7 列开始）：

```fortran
      PROGRAM LEGACY
      IMPLICIT REAL*8 (A-H,O-Z)
      COMMON /BLK/ X
      X = 1.0D0
      END
```

列示意：

```text
12345678901234567890
      PROGRAM LEGACY
      IMPLICIT REAL*8 (A-H,O-Z)
```

**带标号**（标号在 1–5 列）：

```fortran
  100 CONTINUE
```

`100` 在 3–5 列，第 6 列空白，`CONTINUE` 从第 7 列开始。

**续行**（第 6 列非空白）：

```fortran
      X = A + B +
     &    C
```

第 2 行第 6 列是 `&` → 它是上一行的续行；正文从第 7 列继续。

**注释**（第 1 列 `C`/`c`/`*`）：

```fortran
C     This is a comment
*     Also a comment
      X = 1
```

第 1 列 `C` 或 `*` → 整行注释，不参与编译。

#### 3. `-ffixed-form` 是什么

- 它是 **gfortran** 的编译选项：**强制把源文件按固定格式解析**，不管扩展名是什么。
- 对应 `-ffree-form`：强制按自由格式解析。
- 默认规则（gfortran）：
  - `.f`、`.for`、`.f77` → 固定格式；
  - `.f90`、`.f95`、`.f03`、`.f08` → 自由格式。
- 其他编译器选项名不同：
  - Intel：`-fixed` / `/fixed`；
  - NVHPC：`-Mfixed`；
  - IBM XL：`-qfixed`。
- `-ffixed-form` 只改**源格式解析**，不改语义；同一文件用不同选项可能编译结果不同（尤其列敏感代码）。

**例子**：

```bash
gfortran -ffixed-form legacy.f90   # 把 .f90 当固定格式
gfortran -ffree-form legacy.f     # 把 .f 当自由格式
```

#### 4. 为什么 FOS-001 要两者结合

只看扩展名会误判：

- `.f` 可能被 `-ffree-form` 编译；
- `.f90` 可能被 `-ffixed-form` 编译；
- 构建系统（CMake/Makefile）可能对单文件加选项；
- 同一项目可能混用固定/自由格式。

所以检测顺序建议：

1. **扩展名先验**：`.f/.for/.f77` 倾向固定；
2. **编译选项**：查 `compile_commands.json`/CMake/Makefile 的 `-ffixed-form`/`-ffree-form`；
3. **列启发**：第 1 列 `C/*` 注释、第 6 列续行、正文从第 7 列起、标号在 1–5 列；
4. **关键字**：`COMMON`/`IMPLICIT`/`EQUIVALENCE` 增强置信；
5. **结论**：固定格式 + 关键字 → 高置信；只有列启发 → 中置信；冲突 → 候选/INFO。

#### 5. 常见坑

- **Tab**：固定格式中 Tab 有特殊跳列规则，跨编译器可能不一致；可用 `-ftabstop`。
- **第 73 列以后**：固定格式默认只读到第 72 列，后面的代码可能被忽略；可用 `-ffixed-line-length-*`。
- **`!` 注释**：Fortran 90 起 `!` 也可注释；不要只认 `C/*`。
- **`;` 多语句**：固定格式也支持 `;` 分隔。
- **预处理行**：`#include`/`#define` 由预处理器处理，列规则可能不同。
- **`C` 在第 1 列**：固定格式是注释；自由格式可能是标识符——不能混判。
- **续行标记**：标准是第 6 列“非空白且非 0”；`&`/`+`/数字常见，`0` 不算续行。
- **正文起点**：第 7 列是起点，但代码可在 7–72 列内任意位置；不要要求“第 7 列必须非空”。

#### 6. 一句话总结

**固定格式是“按列说话”：1–5 列标号、6 列续行、7–72 列正文；`-ffixed-form` 是“强制按这套列规则解析”的编译器开关。FOS-001 要把扩展名、编译选项、列启发、关键字四者合起来判，不能只看 `.f`。**

### Q35 “赋分 30”是什么意思？和 severity/置信度/权重是什么关系？

**一句话**：**赋分 30 不是“30 分总分”，也不是“30% 概率”，而是 FOS-005 在“死代码与不可达逻辑”子维 100 分里的扣分权重**。命中一次，就从该子维扣 30 分。

#### 1. 评分链路

```text
规则赋分（FOS-005=30）
  → 子维得分（死代码子维 = 100 − Σ命中规则赋分）
  → 维度得分（死代码子维 × 20% + 其他子维 × 各自权重）
  → 项目总分（dim.fossil 按激活子集全局归一化并入）
```

#### 2. 死代码子维的分值分配

| 规则 | 内容 | 赋分 |
|:--|:--|:-:|
| FOS-004 | 未引用函数/变量/文件 | 50 |
| **FOS-005** | **不可达分支** | **30** |
| FOS-006 | 成块注释代码 | 20 |
| **合计** |  | **100** |

所以 FOS-005 的 30 是**子维内的相对权重**：它比 FOS-004（50）轻，比 FOS-006（20）重。

#### 3. 算例

假设其他 3 个子维都是 100：

| 命中情况 | 死代码子维 | 化石维度总分 | 说明 |
|:--|:-:|:-:|:--|
| 只命中 FOS-005 | 100−30 = **70** | 70×0.20 + 100×0.80 = **94** | 化石维度掉 6 分 |
| FOS-004 + FOS-005 | 100−50−30 = **20** | 20×0.20 + 100×0.80 = **84** | 掉 16 分 |
| FOS-004 + FOS-005 + FOS-006 | **0** | 0×0.20 + 100×0.80 = **80** | 死代码子维清零 |
| 同符号同时命中 FOS-004/005 | 100−50 = **50** | **90** | 互斥：只扣 FOS-004，FOS-005 记 INFO |

> 若按 `dim.fossil` 权重 0.15 折算（未归一化前）：化石维度从 100 掉到 94，项目总分约掉 `6×0.15=0.9` 分；掉到 84，约掉 `16×0.15=2.4` 分。

#### 4. 它不是什么

| 容易误解 | 实际含义 |
|:--|:--|
| “30 分总分” | 不是；只是死代码子维 100 分里的 30 分 |
| “30% 概率是死代码” | 不是；是扣分权重，不是概率 |
| “30 行代码” | 不是；与行数无关 |
| “severity=30” | 不是；severity 是 MEDIUM（概念严重度） |
| “置信度 30%” | 不是；置信度是“中”，描述检测可靠性 |

#### 5. severity / 置信度 / 赋分 的分工

| 字段 | FOS-005 | 作用 |
|:--|:--|:--|
| **severity** | MEDIUM | 概念严重度：不可达逻辑的风险等级 |
| **置信度** | 中 | 检测可靠性：静态可判，但宏/模板/平台分支有边界 |
| **赋分** | 30 | 子维内扣分权重：命中一次扣 30 |
| **子维权重** | 20% | 死代码子维在化石维度中的权重 |
| **维度权重** | 0.15（候选） | 化石维度在项目总分中的权重 |

四者互不等价：**severity 高不等于赋分高，置信度高不等于权重高**。

#### 6. 命中一次 ≠ 按出现次数累加

- 同一规则在一个项目内**只扣一次赋分**（FOS-005 命中 1 处和 100 处，都是扣 30）；
- 出现次数/密度写入报告，用于排序和工单拆分；
- 这是“存在性评分”口径，避免大仓库因出现次数多而被过度惩罚；
- 阶段 C 会评估是否按密度缩放（默认不缩放）。

#### 7. 候选 vs 确认

- FOS-005 置信度“中”，默认 candidate（WARNING）；
- **候选也计入风险分**（扣 30），但**不触发等级封顶/BLOCK**；
- 人工/LLM 复核确认后，才按 MEDIUM 进入 WARN/封顶逻辑；
- 若复核判定误报，撤销该命中（30 分退回）。

#### 8. 豁免

- FOS-005 **不适用** `@fossil_not_dead`（该注解只给 FOS-004）；
- `@fossil_deferred` 只降 `output_level`，**不改变 30 分扣分**；
- 平台条件编译（`#ifdef`）本身不算 FOS-005，这是规则边界，不是豁免。

#### 9. 为什么是 30，不是 50/20

- FOS-004（50）：未引用符号/文件，删除价值最高；
- FOS-005（30）：不可达分支，影响控制流理解，但通常比整符号删除轻；
- FOS-006（20）：成块注释，主要是可读性/维护成本；
- 30 是**工程经验默认值**，阶段 C 会用真实样本校准，不是永远固定。

#### 10. 一句话总结

**“赋分 30”= FOS-005 在死代码子维 100 分里占 30 分的扣分权重；命中一次扣 30，子维剩 70；再乘 20% 子维权重、0.15 维度权重，才是它对项目总分的实际影响。**

### Q36 普通项目没有源码目录时，dir_coverage 是 N/A 还是 0.0？

**一句话**：**真正的“无生产源码”应判 N/A（不适用），不是 0.0；但“源码在根目录”不是无源码，应把根目录视作 `.` 正常计算。**

#### 1. 先区分三种情况

| 情况 | 判定 | 处理 |
|:--|:--|:--|
| 源码在根目录（如 `main.cpp`） | 有源码，只是没有子目录 | `source_dirs={"."}`，正常算 L1 |
| 只有测试/文档/配置，无生产源码 | 无源码 | `test_coverage=N/A`，不参与结构质量加权 |
| D3 把遗留模块全部剔除，剩余源码为空 | 无剩余源码 | `test_coverage=N/A`；FOS-012 已计债务 |

#### 2. 为什么不是 0.0

`dir_coverage` 是“有测试的源码目录 / 源码目录”，是 0–1 的比例。  
没有生产源码时：

```text
source_files = []
source_dirs  = []
dir_coverage = 0 / 0   # 无定义
```

给 `0.0` 等于说“覆盖率 0%”，会惩罚一个**根本没有源码需要覆盖**的项目；这在语义上是错的。

#### 3. 为什么根目录源码不能算“无源码”

旧逻辑：

```python
d = os.path.dirname("main.cpp")  # ""
if d: source_dirs.add(d)
```

根目录源码的 `dirname` 是空串，被跳过 → `source_dirs=[]` → 误判为“无源码”。  
现在：

```python
if not d:
    d = "."
```

根目录源码计入 `.`，L1 正常算，不会误判 N/A。

#### 4. N/A 如何影响评分

- `calc_test_coverage()` 返回 `(None, detail)`，`detail["applicable"]=False`；
- `calc_structural_score()` 只对非 `None` 的子维加权，并**重新归一化**剩余权重；
- 报告显示“测试覆盖度 N/A（无生产源码）”，不按 0 分扣；
- `SAR-005` 低覆盖规则不会因 N/A 触发。

#### 5. D3 的情况

D3 剔除 `legacy_untested_modules` 后：

- 若还有非遗留源码：正常算；
- 若剩余源码为空：`test_coverage=N/A`，因为标准覆盖率没有可评对象；
- FOS-012 仍在债务子维计分，不双扣。

> 之前把 D3 空分母写成 `dir_coverage=1.0` 是中性兜底；更完整的语义是 **N/A**，现已统一为 N/A。

#### 6. 例子

| 项目 | source_files | source_dirs | test_coverage |
|:--|:--|:--|:--|
| `main.cpp` + 根目录测试 | 有 | `{"."}` | 正常数值 |
| 只有 `tests/` | 无 | `{}` | **N/A** |
| 只有 `legacy/`，D3 全剔除 | 无（剔除后） | `{}` | **N/A** |
| `legacy/` + `modern/`，D3 只剔 legacy | 有（modern） | `{"modern"}` | 正常数值 |

#### 7. 一句话总结

**没有生产源码 → N/A；源码在根目录 → 视作 `.`；D3 全剔除 → 无剩余源码 → N/A。`0.0` 只适用于“有源码但完全没测试”的情况，不适用于“没有源码”。**
