## 摘要

工业软件的生命周期常达 20–40 年。代码中会沉淀大量**时代特定形态**：FORTRAN 77 固定格式/`COMMON`/隐式类型、`auto_ptr`/`register`/`throw(type)` 等废弃 C++ API、K&R C 方言、死代码、复制粘贴、长期未偿还的技术债。与业务软件不同，这类形态的**危害是累积且非突发的**：它们不一定让程序崩溃，却持续抬高理解、修改、测试、编译升级与现代化成本；其价值也不体现在单点性能，而体现在**可维护性、可移植性与升级可行性**。

通用质量模型（ISO/IEC 25010:2011「可维护性/可移植性」）只给出定性目标；自动化测量标准（CK、CISQ/ISO 5055、SQALE）覆盖复杂度、结构违规与债务成本，但**不定义"F77/auto_ptr/死代码/克隆"等化石形态的可操作检查项**；标准结构维度的"演进质量"只统计趋势/债务曲线，**不做形态检测**。本文从必要性、定义、工程作用与设计逻辑四层，系统阐述「化石代码与技术债（维度⑦）」作为独立评估项的设计依据，并给出 4 子维、12 条 FOS 规则、边界裁决（D1~D3）与源码实证锚点。

## 1 建设必要性

### 1.1 通用质量模型存在目标缺口

ISO/IEC 25010:2011 的「可维护性」包含模块化、可重用性、可分析性、可修改性、可测试性；「可移植性」包含适应性、可安装性、可替换性。**（2023 版将 Portability 改为 Flexibility，Testability 移入 Flexibility；本评估沿用 2011 术语，迁移到 2023 时需同步改名。）**它们给出的是**定性目标**，但工业软件的现实是：

- **形态是时代特定的**：F77 `COMMON` 在 1980 年代是标准做法，今天则是现代化障碍；`auto_ptr` 在 C++98 合法，C++17 已移除。通用模型没有"语言时代形态"这一维度。
- **成本是累积的**：死代码/克隆/债务标记不会让程序崩溃，却持续抬高理解与修改成本；ISO 25010 没有"债务密度/修复成本"子特性。
- **升级是硬约束**：编译器/标准升级（C++17/20、Fortran 2008+）会直接淘汰旧 API；通用模型无法回答"哪些代码阻塞升级"。
- **可移植性被低估**：旧方言/扩展在跨平台/跨编译器时失效；通用模型缺少"方言依赖"检查。

ISO 25010 只告诉我们要"可维护、可移植"，却没有说明"如何识别 F77/`COMMON`/`auto_ptr`/死代码/克隆，以及如何排序修复"。

### 1.2 自动化测量标准存在适用盲区

| 标准/工具 | 覆盖 | 对化石形态的盲区 |
|:--|:--|:--|
| **CK 度量集**（WMC/CBO/RFC/LCOM，Chidamber & Kemerer 1994）| 单语言 OO 结构 | 无语言时代/废弃 API/死代码概念 |
| **CISQ / ISO/IEC 5055:2021** | 可靠性/性能/安全/可维护性规则 | 规则面向现代语言；不覆盖 F77/`COMMON`/K&R C |
| **SQALE（方法/工具）** | 规则违反映射修复成本 | 需先定义规则；无"化石形态"清单 |
| **通用 linter/静态分析** | 现代 API 弃用、复杂度、重复 | 不覆盖固定格式 Fortran/旧 C 方言；跨语言符号弱 |
| **克隆检测工具**（jscpd/Simian）| token/行克隆 | 不区分"应保留的兼容实现"与"应消除的重复" |

只依赖 CK/CISQ/SQALE 会给出**虚假的"可维护性健康"结论**：分数可能不低，但代码里仍有大量 F77/`auto_ptr`/克隆，现代化成本被低估。

### 1.3 行业工程实践形成刚性倒逼（案例按源码实证校正）

| 样本 | 观察到 | 本地锚点（可溯源）|
|:--|:--|:--|
| **BRL-CAD** | 旧 C `register` 关键字；自有固定格式 Fortran | `src/librt/vshoot.c:49` `register int i;`；`src/conv/patch/rpatch.f`、`misc/fortran_example.f` |
| **Code_Aster** | 固定格式 Fortran + 隐式类型 | `astest/umat001a.f:87` `IMPLICIT REAL*8 (A-H,O-Z)`；`astest/umat002a.f:86` |
| **OpenFOAM** | 债务标记（HACK/FIXME）| `src/conversion/ccm/writer/ccmWriterSolution.C:428` `// HACK`/`// FIXME`；`ccmReaderSolution.C:353` `#define SOLID_STRESS_HACK` |

> **校正说明**：BRL-CAD 的 `COMMON` 主要出现在 `src/libbg/geogram/third_party/liblbfgs`（第三方，应排除）；OpenFOAM `auto_ptr` 在 `src` **无命中**（原始计数含注释/文档），故不作为 FOS-002 正样本。以上为**本地 checkout 局部锚点**，阶段 B 以固定 ref 复核；原始计数含注释，检测需剥离注释。

这些形态倒逼行业承认：**化石代码/技术债不是"代码风格问题"，而是影响升级可行性、维护成本与可移植性的架构风险**，必须成为独立评估项。

### 1.4 经济、风险与合规

| 维度 | 影响 |
|:--|:--|
| **升级阻塞** | C++17 移除 `auto_ptr`/`register`/动态异常规格；Fortran 新标准淘汰 `COMMON` 用法 |
| **维护成本** | 克隆/死代码/债务标记抬高理解、修改、测试成本 |
| **一致性风险** | 同一常量多处硬编码 → 改一处漏一处 |
| **安全** | 硬编码密钥/IP（标准 `hardcode` 子集）；旧 API 缺安全修复 |
| **合规/ABI** | 保留遗留 API 可能是兼容要求；需豁免而非误判 |
| **现代化预算** | 需要可排序清单估算工时，而非笼统"债高" |

## 2 内涵定义与边界划分

### 2.1 核心概念定义

**化石代码与技术债（维度⑦）** 是指：工业软件中由**过时语言方言、废弃 API、死代码、重复实现与长期未偿还债务**构成的结构性遗留形态，以及该形态在可维护性、可移植性与升级可行性上的健康程度。它决定软件在以下方面的能力：

- **历史遗留 API 与语言方言**：是否使用 F77/`COMMON`/`auto_ptr`/K&R C 等已过时形态；
- **死代码与不可达逻辑**：是否存在无引用符号、不可达分支、大块注释代码；
- **重复代码与重复实现**：是否存在克隆、重复常量、同一算法多份实现；
- **技术债密度与可维护性**：债务标记密度、修复成本比率、遗留模块是否失控。

**与相邻概念的区别**：

| 概念 | 定义 | 与 ⑦ 的关系 |
|:--|:--|:--|
| **化石代码** | 过时语言/API/范式写成的代码 | ⑦ 的主体 |
| **遗留 API** | 已弃用/移除的接口 | FOS-002 的检测对象 |
| **死代码** | 无引用/不可达/注释掉的代码 | FOS-004~006 |
| **重复代码** | 克隆/重复常量/多份实现 | FOS-007~009 |
| **技术债** | 为短期交付留下的未来维护成本 | FOS-010~012（静态代理）|
| **演进质量** | 债务趋势/历史/增量 | 边界：趋势归演进，形态归 ⑦ |

**颗粒度定义**：

| 颗粒度层级 | 定义 | 评估方法 | 用途 |
|:--|:--|:--|:--|
| **基本颗粒度** | 化石形态出现点（文件:行）| 正则/词法、符号引用、token 哈希 | 清单/工单 |
| **辅助颗粒度** | 模块/文件年龄、依赖半径、债务趋势 | git、依赖图、SQALE 汇总 | 排序/预算 |

**四子维检查项与检测方法**：

| 子维度 | 检查项 | 检测方法 |
|:--|:--|:--|
| 历史遗留 API 与语言方言 | F77/`COMMON`/`IMPLICIT`、`auto_ptr`/`register`/`throw(type)`、K&R C | 扩展名 + 固定格式列 + 关键字/符号 |
| 死代码与不可达逻辑 | 未引用符号、`#if 0`、`return` 后、大块注释 | 符号引用图 + 控制流 + 注释块 |
| 重复代码与重复实现 | 克隆、重复常量、多份算法 | token 哈希/winnowing + 常量表 |
| 技术债密度与可维护性 | TODO/FIXME 密度、SQALE、遗留模块 | 计数 + 成本代理 + 年龄/测试 |

### 2.2 典型化石形态与架构模式

| 形态 | 示例 | 现代化方向 |
|:--|:--|:--|
| F77 固定格式 | 第 1–6 列标签、`COMMON`、`IMPLICIT`、`EQUIVALENCE` | 自由格式、`MODULE`、`IMPLICIT NONE`、`allocatable` |
| 废弃 C++ API | `std::auto_ptr`、`register`、`throw(type)`/`throw()`、`std::strstream`、`std::bind1st` | `unique_ptr`、去 `register`、`noexcept`、`stringstream`、lambda/`bind_front` |
| 旧 C 方言 | K&R 函数定义、隐式 `int` | ANSI C/C99+、显式类型 |
| 死代码 | 未引用函数/文件、`#if 0`、`return` 后语句 | 删除、特性开关、测试保护 |
| 克隆 | 函数/文件级复制粘贴 | 提取函数/模板、单一实现 |
| 债务 | `TODO/FIXME/HACK`、修复成本高 | 债务清单、预算、测试 |

> 注：`throw(type)` 在 C++17 移除；`throw()` 保留为 `noexcept(true)` 的弃用别名（至 C++20）。

### 2.3 与通用软件质量评估的本质差异（5 点）

| # | 差异 | 说明 |
|:-:|:--|:--|
| 1 | **形态 vs 趋势** | ⑦ 检测"是否存在某形态"；演进质量看"债务曲线" |
| 2 | **语言/时代特定** | F77/旧 C++/K&R C 的规则不同，不能一套正则 |
| 3 | **静态可检 vs 运行时** | ⑦ 以静态为主；不依赖运行 |
| 4 | **现代化/ABI 约束** | 保留遗留 API 可能是兼容要求 → 豁免 |
| 5 | **边界敏感** | 与演进/标准重叠，必须裁决（D1~D3）|

> 原则（`维度完备性证明与边界裁决.md §3.4`）：**同一文件同一形态只由 ⑦ 计分**；演进质量仅统计趋势，不重复扣分。

| # | 重叠 | 现行实现 | ⑦ 规则 | 建议裁决 |
|:-:|:--|:--|:--|:--|
| **D1** | 注释代码/备份文件 | `arch_metrics_standard.py:1011-1038` `calc_dead_code`：备份文件 + `/* ... if/for/class/return ... */` 注释块 | FOS-006 成块注释代码 | **FOS-006 计所有成块注释，按行数分级**（>10 行 WARNING；≤10 行 INFO）；标准 `calc_dead_code` **仅保留备份文件、移除注释块扣分**；**影响 `standard_arch_quality` 等快照，重设需程序化校验 + 迁移记录** |

## 3 体系工程应用作用

### 3.1 开发/演进

- 新代码避免引入 F77/废弃 API/克隆；代码评审可对照 FOS 清单；
- 重构时按"化石清单"排序，优先处理编译阻塞项。

### 3.2 运维/现代化

- 现代化项目需要**可排序的化石清单**（文件:行、风险、成本、影响半径），而非笼统"技术债高"；
- 支持 C++17/20、Fortran 2008+ 升级评估；
- 支持"保留 vs 重写 vs 封装"决策。

### 3.3 集成/CI 门禁

- 新增代码禁止新增 FOS 命中（增量门禁）；
- 存量按优先级 burn-down；
- 与标准/HPC/GCS 等引擎并行运行。

### 3.4 合规/ABI

- 保留遗留 API 的兼容性要求可 `@fossil_legacy_ok` 豁免；
- 供应链/安全审查可查硬编码密钥（标准 `hardcode`）与旧 API。

## 4 体系设计逻辑（四层驱动催熟模型）

### 4.1 通用质量模型明确目标缺口

ISO/IEC 25010:2011 的「可维护性/可移植性」是**定性目标**：它告诉我们要"可分析、可修改、可测试、可移植"，但没有给出"F77/`COMMON`/`auto_ptr`/死代码/克隆"的可操作定义。这一层**指明方向但留下缺口**：我们知道应"现代化"，但不知道"哪些形态、多少、先改谁、成本多少"。

### 4.2 自动化测量标准暴露能力盲区

CK/CISQ/ISO 5055:2021/SQALE 的前提是"规则可定义、代码可解析"：

- CK 基于 OO 语法树，无法表达 Fortran `COMMON` 或 C++ 弃用 API；
- CISQ/ISO 5055 规则面向现代语言，不覆盖 F77/K&R C；
- SQALE 需要先有"化石形态"规则，才能映射修复成本；
- 通用 linter 覆盖现代 API 弃用，但不覆盖固定格式/旧方言。

只依赖这些标准会**低估现代化成本**，给出虚假的"可维护性健康"。

### 4.3 行业实践梳理典型化石形态与风险（按源码实证校正）

**历史遗留 API/方言**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | F77 固定格式/`COMMON`/隐式类型、`auto_ptr`/`register`/`throw(type)`、K&R C → 编译器升级阻塞、跨平台失效、理解成本高（Code_Aster `IMPLICIT REAL*8`；BRL-CAD `register`）|
| **解决方案** | 自由格式/`MODULE`/`IMPLICIT NONE`；`unique_ptr`/`noexcept`/`stringstream`；ANSI C |
| **可提炼指标** | FOS-001/002/003 |

**死代码**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 无引用符号、`#if 0`、`return` 后语句、大块注释代码 → 理解/维护成本、误改风险 |
| **解决方案** | 删除、特性开关、测试保护、代码考古 |
| **可提炼指标** | FOS-004/005/006 |

**重复代码**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | 函数/文件克隆、重复常量、同一算法多份 → 改一处漏一处、缺陷扩散 |
| **解决方案** | 提取函数/模板、命名常量、单一实现 |
| **可提炼指标** | FOS-007/008/009 |

**技术债密度**：

| 阶段 | 内容 |
|:--|:--|
| **问题** | `TODO/FIXME/HACK` 密集、修复成本高、遗留模块无测试 → 交付速度下降、缺陷率上升 |
| **解决方案** | 债务清单、预算、测试补齐、模块退役 |
| **可提炼指标** | FOS-010/011/012；FOS-013/014 KNOWN_HOLES |

**正样本参照**：Code_Aster（固定格式 Fortran）、BRL-CAD（旧 C/自有 Fortran）、OpenFOAM（债务标记）提供形态参照；**缺陷阳性需 C 类合成样本**（如 `auto_ptr` 双实现、克隆块、`COMMON` 块），不得以健康样本充当阳性。

### 4.4 行业共识推动确立核心评估项

"催熟"：当同一类遗留形态在多软件、多团队、多年反复造成升级阻塞/维护成本，它从"个体痛苦经验"上升为"行业必需共识"。催熟三前提：**问题普遍存在**（长生命周期工业软件普遍有 F77/旧 C++/死代码/克隆）、**难以人工发现**（跨文件/跨语言/历史沉积）、**后果严重**（升级失败、维护成本失控）。

**催熟三证据**：

- **方法学/标准**：ISO/IEC 25010:2011（可维护性/可移植性）、CISQ/ISO/IEC 5055:2021（自动化质量度量）、SQALE（方法/工具，技术债修复成本）、CK（Chidamber & Kemerer 1994）、技术债（Cunningham 1992）、代码坏味道/重构（Fowler 1999/2018）提供理论基础；
- **工业界实践**：BRL-CAD、Code_Aster、OpenFOAM 等长生命周期项目持续面临遗留形态；现代化项目需要化石清单；
- **工具生态**：clang-tidy `modernize-*`/`cppcoreguidelines-*`、Cppcheck、SonarQube、PMD/Checkstyle、fprettify/flang、jscpd/Simian、lizard 等可支撑部分检测。

## 6 总体结论

化石代码与技术债成为独立评估项，本质是因为传统质量模型与测量标准假设了"新代码、现代语言、单一标准"的纯粹世界，而工业软件的现实是**20–40 年生命周期、多语言/多时代共存、升级阻塞与维护成本累积**。本文从必要性出发，论证了理论缺口、测量盲区与实践倒逼；给出了定义、颗粒度、4 子维检查项与典型形态；明确了与演进/标准/其他 8 维的边界（D1~D3）；阐述了现代化/维护/CI/合规作用；通过四层催熟模型与源码锚点揭示设计逻辑。

未来工具须内置化石形态专用分析：F77/`COMMON`、废弃 API、死代码、克隆、重复常量、SQALE 债务。其中 FOS-001/002 作为高置信核心参照；FOS-004/006/007/008/009/011/012 以 candidate 输出并交人工/LLM 复核。
