## 四、性能基线实测

### 4.1 FreeCAD src 全量（12417 物理文件 / 7590 索引文件）

| 缓存状态 | 轮次 | init(s) | generate(s) | total(s) | 换算 |
|---|---|---|---|---|---|
| **冷** | 1 | 184.7 | 17125.4 | **17310.1** | ~4.8 h |
| **热** | 1 | — | — | 14449.1 | ~4.0 h |
| **热** | 2 | — | — | 14577.5 | ~4.0 h |
| 热 P50 | | | | **14513.3** | ~4.0 h |
| 热 P90 | | | | **14564.6** | ~4.0 h |

**KPI2 判定**：冷/热均远超 KPI（FreeCAD src P90 < 10 分钟）。**不达标**。

**关键洞察**：热缓存（4.0h）与冷缓存（4.8h）差异仅 ~17%，说明瓶颈**不是首次全量 IO**，而是计算热点（超线性算法），与专家意见"性能优化不解决首次全量 IO"相互印证但结论相反 —— 真正的热点是**算法复杂度**，而非缓存。

### 4.2 5 个回归项目各自耗时（热缓存，2 轮）

| 项目 | 索引文件数 | P50 (s) | P90 (s) | 换算 |
|---|---|---|---|---|
| OpenFOAM-v2512 | 10402 | 447.7 | 453.3 | ~7.5 min |
| BRL-CAD | 3513 | 259.6 | 280.9 | ~4.3 min |
| ElmerFEM | 3234 | 314.1 | 336.6 | ~5.2 min |
| FreeCAD-CAM | 600 | 56.3 | 58.7 | ~1 min |

> 说明：此处的"各自耗时"是 `ComprehensiveReport`（5 引擎全跑）的完整耗时，即回归测试实际执行一个项目所需时间。

### 4.3 热点引擎定位

分引擎测量（FreeCAD src 全量，热缓存）：

| 引擎 | init(s) | generate(s) | total(s) | 结论 |
|---|---|---|---|---|
| standard | 6.6 | 7.3 | 13.9 | 正常 |
| **multilang** | **166–212** | **>34min 未完（多小时级）** | **多小时** | **主导热点** |
| template | 21.6 | 30.9 | 52.5 | 正常 |
| numerical | 11.1 | 242.4 | 253.5 | 中等（4.2 min） |
| solver_physics | 2.8 | 33.9 | 36.7 | 正常 |

**结论**：FreeCAD src 的 ~4h 耗时**完全由 MultilangMetrics 的 generate 阶段主导**（multilang generate 已持续 >34min CPU 仍未完成，其余四引擎合计 <6 min）。OpenFOAM（10402 文件，448s）与 FreeCAD（7590 文件，4h）对比差 32 倍，强烈指向**对特定文件分布触发的超线性（O(n²)/O(n·m)）算法**。

> 注：数值引擎（numerical generate 242s）为第二耗时，但相对 multilang 可忽略。

**疑似超线性热点（已代码定位）**，均位于 `arch_metrics_multilang.py` 与 `arch_multilang_matcher.py`：

1. `_build_ctype_edges` / `_build_cross_lang_graph`：每个 Python ctypes 调用函数 → **线性遍历全部 C/C++ 头文件**（O(py_calls × header_files)），如 `arch_multilang_matcher.py:157-161`、`arch_metrics_multilang.py:372-392`。
2. `calc_call_depth` 路径2：每个含回调注册的 Python 文件 → 遍历全部 C++ 文件，再对其遍历全部 Python（O(py × cpp × py)），如 `arch_metrics_multilang.py:871-942`。
3. `calc_call_depth` 路径4 + `_resolve_pyimport_module`：`PyImport_ImportModule` 解析对**每个 Python 文件**读取并全量内容匹配，如 `:835-851`、`:1004-1025`。
4. SWIG 绑定：`%module`/`%extend` 对全部 Python/头文件线性扫描，如 `:574-576`、`:591-594`。

这些模式在头文件/脚本密集的 FreeCAD src（1930 个 .h + 1762 个 .py）下放大为多小时级，而 OpenFOAM 分布不同故 32 倍更快。

## 六、假阳性基线（部分完成）

**状态**：本报告时间窗口内仅完成环境与工具就绪；BRL-CAD + FreeCAD 的人工抽检需在试点期（WP-8）随 KPI5 执行。当前已确认的**系统性假阳性风险**（代码级证据）：

| 规则 | 潜在系统性误判 | 代码依据 |
|---|---|---|
| MLR-003 SWIG 签名 | 头文件函数声明正则漏匹配模板/重载/返回类型复杂情形 → 可能误报"未找到声明" | `arch_metrics_multilang.py:1054-1058` |
| MLR-010 FFI | `malloc` 计数正则对注释/字符串误计；`find_malloc_tokens_in_py` 有 tokenize 缓解但 C 侧无 | `:1579-1595` |
| MLR-006/007 热点/TNT | 纯路径统计，无调用真实性校验 → 高扇入头文件可能误判热点 | 依赖图边可能过宽 |
| ctypes 兜底 | 同名函数跨头文件"先匹配即连"可能连错文件 | `arch_multilang_matcher.py:157-161` |

> 人工抽检记录（触发数/确证数/疑似假阳性）占位，将在 WP-8 试点期按规则子集补全，供 KPI5 判定（核心规则假阳性率 ≤10%）。

## 七、结论与对后续工作包的输入

1. **KPI2 当前不达标**：FreeCAD src P90 ≈ 4.0h（热）远 > 10 分钟。**WP-3 必须优先解决 multilang 引擎的超线性算法**（见 §4.3 四个热点），缓存/增量/过滤对 4h 量级收效有限。
2. **瓶颈是算法复杂度，不是缓存**：热 vs 冷仅差 17%。WP-3 的 `_read_cached`/增量扫描（为"跑两遍"场景设计）收益有限；**重点应重构 O(n²) 匹配为哈希索引**。
3. **回归基线口径已建立**：5 项目热缓存耗时（§4.2）可作为 WP-3 劣化 ≤20% 的对比基准。
4. **回归不可复现**：绝对路径清单（§3.1）确认，WP-5 需 projects.yaml + 相对路径；快照缺工具版本字段需补。
5. **假阳性风险已代码定位**（§6），供 WP-2 合成项目设计与 WP-8 KPI5 抽检参考。
