## 二、升级准则（自动记录 → 阻塞）

门禁按"先记录、后阻塞"渐进升级，避免突然阻塞阻断团队迭代：

```
阶段 1 记录（log）：门禁结果写入报告，不阻断。启用新门禁项时先在此阶段 1-2 周。
阶段 2 警告（warn）：门禁失败发警告（CI 黄色），允许合并但提示。持续 1-2 周。
阶段 3 阻塞（block）：门禁失败阻断合并（CI 红色）。稳定后固定在此阶段。
```

| 门禁项 | 当前阶段 | 升级条件 |
|:-------|:---------|:---------|
| 单元测试 | 阻塞 | 已稳定 |
| 一致性检查 | 阻塞 | 已稳定 |
| 覆盖矩阵 | 阻塞 | 已稳定 |
| 快照校验 | 阻塞 | 已稳定 |
| 性能基线 | 记录 | 稳定后升警告（KPI2 达标时）|

## 三、失败回滚流程

当门禁失败需回滚或修复：

```
门禁失败
  ↓
分类：
  A. 工具 bug（代码/算法错误）→ 修复代码，禁止改快照掩盖
  B. 预期行为变化（评分算法改进/过滤策略）→ ARCH_REGRESSION_UPDATE=1 更新快照，人工审查
  C. 项目源码演进（外部项目变化）→ 更新 projects.yaml 引用的 commit
  ↓
修复后重跑门禁 → 通过则合并
  ↓
无法快速修复 → 提交豁免（见 §四），限时修复
```

**红线**：禁止用更新快照掩盖工具 bug 或检测误报（对齐开发指南 §B3 基线更新规范）。

## 四、豁免流程

| 豁免类型 | 触发场景 | 流程 | 时限 |
|:---------|:---------|:-----|:-----|
| 临时豁免 | 门禁失败但已定位为项目源码演进（非工具问题）| 提交豁免 PR（注明规则/原因/owner/修复日）| 5 个工作日 |
| 性能豁免 | 声明机型性能波动（非代码劣化）| 提供基线数据对比，owner 确认 | 10 个工作日 |
| 外部依赖豁免 | 第三方项目 CI 获取失败（网络/授权）| projects.yaml 标注，降级为手动回归 | 长期（记录）|

豁免须在 `docs/zh/计划/门禁豁免记录.md` 登记。

## 五、Owner 职责

| 角色 | 职责 |
|:-----|:-----|
| **门禁 Owner** | 维护门禁配置（CI yaml/bat），升级准则判定，处理阻塞 |
| **规则 Owner** | 维护规则覆盖矩阵，合成项目，覆盖退化时响应 |
| **回归 Owner** | 维护 projects.yaml 与快照基线，项目 commit 更新 |
| **性能 Owner** | 维护性能基线，KPI2 监控，性能回归响应 |

当前默认 Owner：arch-quality 维护者（本仓库）。

- 门禁脚本 Windows/Linux 双平台可用
- 覆盖矩阵 + 一致性 + 快照校验全部通过
