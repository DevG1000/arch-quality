## 回归套件修复记录（2026-09-28）

**触发**：`tests/` 全量跑出 36 例失败（回归套件 30 + 通用 MLR 2 + Standard 4）。经 `git stash` 对照确认为**既有失败**，与 WP-2.5 无关。

### 根因与处置

| # | 根因 | 性质 | 处置 |
|:-:|:-----|:-----|:-----|
| 1 | 10 个 `tpl_*.json` 是**空占位基线**（`overall=null`、`cpp_file_count=0`、`required=[]`），系项目目录尚不存在时采集；现引擎已能检出这些 C++ 项目 | 陈旧基线 | 程序化校验取值范围后重生成（Eigen 为唯一既有真实基线且通过，佐证引擎正确） |
| 2 | 引擎维度键 `compile_time_coupling` → `compile_time_fanin`（对齐中文名"编译时扇入"），快照未同步 | 陈旧基线 | 随重生成一并更新 |
| 3 | `StandardMetrics.all_metrics()` 将四维暴露为**顶层键**（`structural`/`design`/`documentation`/`evolution`），而测试读 `result["dimensions"]` 恒为 `{}` → `test_dimension_scores` 对全部 5 个项目**空转通过** | **既有覆盖漏洞** | 修正取数路径，5 个 standard 快照首次填充维度基线 |
| 4 | 快照分数为 `null` 时 `assertAlmostEqual` 触发 `TypeError: float - None`，掩盖真实诊断 | 测试缺陷 | 三套件统一改为显式 None 断言 + 重生成指引 |
| 5 | `MLR-004`（Python `ctypes` 直访）与 `MLR-004b`（Tcl 命名空间）拆分后，测试 docstring 与 BRL-CAD 快照 `required` 仍指向 `MLR-004` | 陈旧期望 | docstring + 快照定向修正（计数 7751 未变，纯 ID 归属变更） |
| 6 | **`MLR-024` 环计数随 `PYTHONHASHSEED` 波动**（同一项目 seed=0/1/2 → 9/33/20）。根因：邻接表用 `set`、遍历序随哈希种子变化，叠加全局 `visited` 的 DFS 只探索每节点一次 | **引擎确定性缺陷**（ERROR 级规则） | 起点与邻接均排序 + 同一环不同旋转去重；实测跨种子恒定 |
| 7 | **`GitHistory._git` 超时后静默返回 `""`**，被当作"0 次提交"。30 s 上限在批量负载下被击穿（`git log --shortstat -30` 单独跑即需 9.2 s）→ `avg_commit_size=0` 被判为"无膨胀"而**得满分**，超时反而提分 | **引擎正确性缺陷** | 契约改为失败返回 `None`、超时放宽至 300 s；两个调用点将"查询失败"按 N/A 处理而非 0 |
| 8 | `SAR-011`/`SAR-012` 依赖 Git 滚动窗口与依赖数据新鲜度，随时间漂移，不适合做快照基线（`test_standard_sar.py` 已定义为 N/A 条件规则并有单元覆盖） | 基线设计 | Standard 套件新增 `TIME_DEPENDENT_SAR` 过滤 |

### 遗留（非缺陷，供后续参考）

- `avg_commit_size` 取 30 次提交的**均值**，遇供应商/单体库导入提交时会被单点主导（FreeCAD 一次 `12994 files changed, 8213790 insertions(+)` 将均值拖至 8.2M）。改用**中位数**更稳健，但属指标语义变更，未在本轮改动。
- `standard_arch_quality.json` 的 `file_count` 是仓库自扫描基线（218 → 247），每次提交新增文件都会漂移，需定期刷新。
