# 模板元编程与编译时依赖膨胀评估技能

本技能提供 C++ 模板元编程与编译时依赖膨胀评估的领域知识，包括 6 个评估维度定义、评分算法、12 条 MLR 规则、基线校准方法和豁免验证框架。

版本：4.0（对齐《模板元编程与编译时依赖膨胀评估指南(4.0)版》）

## 权重分配

| 维度 | 权重 |
|------|------|
| 编译时扇入 | 20% |
| 模板实例化重复率 | 20% |
| 头文件影响半径 | 15% |
| 模板嵌套深度 | 10% |
| 二进制膨胀率 | 15% |
| 不必要的模板化 | 20% |

## 维度定义

### 1. 编译时扇入（头文件编译稳定性）

衡量头文件被多少编译单元直接或间接包含。影响编译单元越多，修改该头文件触发的重编译范围越大。

**代码坏味道：热模板头文件（Hot Template Header）**
- **描述**：头文件包含大量模板代码，被 80% 以上编译单元依赖。
- **典型危害**：数学库头文件被 120 个编译单元依赖；一行注释修改触发全量重编译（耗时小时级）。
- **风险**：并行编译效率极差；CI 资源浪费；团队幸福感下降。

评分算法：

```
I = 头文件平均影响的编译单元数（通过 include 图计算，去重）
if I == 0: score = 100
else if I <= 10: score = 100 - I * 1.5
else if I <= 50: score = 85 - (I-10) * 0.7
else if I <= 100: score = 57 - (I-50) * 0.5
else: score = max(0, 32 - (I-100) * 0.3)
```
阈值说明：0~10 为优秀，10~50 需关注，50~100 应重构，>100 为危险。**基线校准**参见 8.1 节。

### 2. 模板实例化重复率

同一模板在不同编译单元中被重复实例化的程度。重复率越高，编译时间和对象体积浪费越严重。

评分算法：

```
总实例化次数 = 所有模板特化统计出现次数之和
唯一实例化数 = 去重后的模板特化数
重复率 = (总实例化次数 - 唯一实例化数) / 总实例化次数

if 重复率 == 0: score = 100
else if 重复率 <= 0.1: score = 90
else if 重复率 <= 0.2: score = 80 - (重复率-0.1)*100
else if 重复率 <= 0.4: score = 70 - (重复率-0.2)*150
else: score = max(0, 40 - (重复率-0.4)*100)
```
说明：重复率 <10% 为健康，10%~20% 可接受，>40% 为强烈重构信号。

**extern template 无效或低效场景清单**：
- 模板定义完全在头文件时显式实例化声明仍需完整解析
- 与 `-fvisibility=hidden` 同时使用时，需标注为可见符号
- 与 LTO（链接时优化）一起使用时，模板重复实例化可能被优化掉，不纳入计量
- 对于仅生成很小代码量的模板（如简单委托、类型标签），膨胀风险极低

**关键函数/性能豁免**（MLR-014 专用）：
- 对于关键性能热点（如同时使用 `Tensor<double>` 和 `Tensor<float>`）、多维模板（如 `Matrix<3,3>` 与 `Matrix<4,4>`），同一实例化应走相同算法+特化路径，可用批注 `@template_specialization_required` 标注
- 扫描到 `@template_specialization_required` 注解时，MLR-014 输出级别可从 WARNING 降为 INFO

### 3. 头文件影响半径

修改一个头文件时，通过 `#include` 传递链可能影响的编译单元总数。影响半径越大，变更成本越高。

**代码坏味道：传染性头文件（Contagious Header）**
- **描述**：头文件通过传递 #include 影响大量编译单元。
- **典型危害**：修改底层头文件导致上游大量重编译；破坏模糊测试效率。

评分算法：

```
R = 从该头文件经 #include 反向链（即被谁 include）可达的编译单元数
if R == 0: score = 100
else if R <= 10: score = 95
else if R <= 30: score = 85 - (R-10)*0.5
else if R <= 80: score = 75 - (R-30)*0.3
else if R <= 150: score = 60 - (R-80)*0.2
else: score = max(0, 46 - (R-150)*0.15)
```
注意：只统计项目内编译单元，系统头文件不统计。**基线校准**参见 8.1 节。

### 4. 模板嵌套深度

模板定义中的递归/嵌套实例化深度。深度过高导致编译时间爆炸和错误信息不可读。

**代码坏味道：模板递归地狱（Template Recursion Hell）**
- **描述**：模板递归/嵌套过深，编译时间指数级增长。
- **危害**：编译时指针 OOM；错误信息上万行不可读；IDE 补全几乎失效。

评分算法：

```
D_max = 项目最大模板实例化嵌套深度
if D_max <= 3: score = 100
else if D_max <= 6: score = 80 - (D_max-3)*5
else if D_max <= 10: score = 65 - (D_max-6)*4
else: score = max(0, 49 - (D_max-10)*3)
```
说明：深度 ≤3 为最佳，4~6 需注意，7~10 较差，>10 不可接受。

### 5. 二进制膨胀率

编译产物中模板实例化生成的代码占 .text 段总大小的比例。

评分算法：

```
膨胀率 = (模板生成的代码字节数) / (总 .text 段字节数) * 100%
if 膨胀率 <= 10%: score = 100
else if 膨胀率 <= 20%: score = 90 - (膨胀率-10)*1
else if 膨胀率 <= 35%: score = 80 - (膨胀率-20)*1.2
else if 膨胀率 <= 50%: score = 62 - (膨胀率-35)*1.5
else: score = max(0, 39.5 - (膨胀率-50)*0.8)
```
说明：膨胀率 <10% 健康，10%-20% 可接受，>35% 警告。嵌入式项目建议阈值 20%。

**关键函数/性能豁免**（MLR-017 专用）：
- HPC 场景中 30-40% 膨胀率可能是换取接近手工优化代码性能的必要支出（如 AllScale 达到 92-105% 手写 MPI 性能）
- 指南将膨胀率高于 35% 标记为"需审查"，而非直接定为"债务"
- 扫描到 `@allow_binary_bloat` 注解时，MLR-017 输出级别从 WARNING 降为 INFO（需附带性能验证数据）

### 6. 不必要的模板化（虚泛型）

一个模板如果在整个项目中只被一种类型实例化，那么它本不需要模板，应降为普通函数/类。

评分算法：

```
total_templates = 所有模板定义数
unnecessary_templates = 只有一种实例化类型的模板（含未实例化的）
ratio = unnecessary_templates / total_templates
score = 100 - ratio * 150   # 每1%扣1.5分，上限扣100
```
扣分加强：模板且未被实例化的，额外扣 10 分（最低为 0 分）。

**预留发布扩展接口**（MLR-018 专用）：
- 对于底层预留但尚未实现支持类型的接口，开发者可用 `// @reserved_for_future_extension: float, int, custom_complex` 注解标注
- 扫描到 `@reserved_for_future_extension` 注解时，MLR-018 输出级别从 WARNING 降为 INFO

## 综合评分

```
模板元编程综合分 =
    编译时扇入 × 20% +
    模板实例化重复率 × 20% +
    头文件影响半径 × 15% +
    模板嵌套深度 × 10% +
    二进制膨胀率 × 15% +
    不必要的模板化 × 20%
```

本综合分可作为**结构质量**的增强维度，权重占比最高 15%。

### 指标重叠与得分合并处理

- **MLR-014（重复实例化）+ MLR-023（多处重复实例化）**：属于同一问题的不同维度，在计综合分时，应取两者中较严重的得分（即较低分）作为该问题的最终得分，避免双重扣分。
- **MLR-013（编译时扇入）+ MLR-015（头文件影响半径）**：底层依赖相同的数据（include 图），不自动合并。保留独立评分，但在报告中标注关联性，提示优先解决同时触犯两条规则的模块。
- **跨规则豁免协调**：若一个模板同时触发 MLR-014 豁免（性能/维护必要性）和 MLR-017 豁免（关键函数+性能验证），应**分别处理**：MLR-014 降为 INFO（豁免通过），MLR-017 仍需执行性能数据验证；若验证失败，MLR-017 维持 WARNING。
- **SME 复核机制**：综合分低于 60 时，标注为潜在债务（而非强制重构），尤其是边界情况（如 HPC 模块），应由架构师人工评审确认是否为真实债务。

## MLR 规则清单

| 规则ID | 名称 | 默认输出级别 | 豁免后输出级别 | 说明 |
|--------|------|-------------|--------------|------|
| MLR-013 | 热模板头文件 | WARNING | — | 扇入>50 |
| MLR-014 | 模板重复实例化 | WARNING | INFO（需审查） | 重复率>40%或无豁免 |
| MLR-015 | 头文件传染链过长 | WARNING | — | 影响半径>80 |
| MLR-016 | 模板嵌套深度过高 | WARNING | — | 深度>10 |
| MLR-017 | 二进制膨胀超标 | WARNING | INFO（需审查+性能验证） | 膨胀率>35% |
| MLR-018 | 虚泛型（镀金模板） | WARNING | INFO（预留接口） | 仅1种实例化或未实例化 |
| MLR-019 | 未使用 extern template 优化 | INFO | — | 低优先级 |
| MLR-020 | 头文件包含不必要模板定义 | WARNING | — | 非inline模板定义 |
| MLR-021 | 模板特化放在错误命名空间 | INFO | — | 低优先级 |
| MLR-022 | 递归模板导致实例化爆炸 | **ERROR** | — | 无限递归模板 |
| MLR-023 | 同一模板在多处重复实例化 | WARNING | — | 与 MLR-014 合并计分 |
| MLR-024 | 头文件包含循环依赖 | **ERROR** | —（有模块时LOW） | 阻塞编译 |

**输出级别定义**：
- **ERROR**：阻塞 CI 流水线；必须立即修复。
- **WARNING**：建议修复；可暂时忽略但必须记录技术债务。
- **INFO**：提供信息；不阻塞 CI。

### 豁免注解语法（4.0 扩展）

| 规则 | 注解 | 说明 |
|------|------|------|
| MLR-014 | `// @template_specialization_required: <reason>` | 标注多精度/多维/性能关键路径，豁免后降为 INFO |
| MLR-017 | `// @allow_binary_bloat: <brief reason>; performance_gain: X%; compile_time_increase: Ys; benchmark_script: <path>; threshold: gain>=N% and increase<=Ms` | 标注关键函数性能豁免，**所有字段为必填**，缺少任一字段则豁免无效（维持 WARNING） |
| MLR-018 | `// @reserved_for_future_extension: <types>` | 标注预留扩展接口，未实现类型不扣分 |

**注解字段验证**：
- `@allow_binary_bloat` 必须包含 `performance_gain`、`compile_time_increase`、`benchmark_script`、`threshold` 四个字段
- 缺少任一必填字段时，输出 `[豁免语法缺失]` 警告，MLR-017 输出级别维持 WARNING
- 性能测试程序及日志应归档到 `docs/waivers/performance_logs/`

## C++20 Modules 过渡影响

### 现实约束声明

| 维度 | 现状 |
|------|------|
| **编译器支持** | GCC 仍为 **experimental**（需 `-fmodules`）；Clang 16+ 部分支持但存在 ABI 不兼容；MSVC 成熟但数据不互通。 |
| **构建系统** | CMake 3.26+ 实验性支持，适配复杂；IDE 支持不完善。 |
| **生态系统** | 支持 Modules 的开源库占比 **<2%**。 |
| **迁移成本** | 渐进式迁移可行，但投入高、风险大。 |

### 关键维度 Modules 过渡评分调整

| 维度 | 传统头文件参考值 | Modules 过渡评分调整 |
|------|-------------------|---------------------|
| MLR-013（编译时扇入） | 扇入 >50 | 过渡期参考 100-150 作为试探值；完全迁移后应重新收集编译依赖数据 |
| MLR-015（影响半径） | 影响半径 >80 | 替换为模块导入图后，传统接口边界影响半径减小 |
| MLR-024（循环依赖） | 传统循环 | 纯模块项目：编译器直接拒绝循环，降级为 LOW；混合项目：仍保留检测 |

## 评分等级

| 综合分 | 等级 | 说明 | 建议动作 |
|--------|------|------|----------|
| ≥ 85 | ★★★ 优秀 | 编译时依赖管理良好，模板使用克制 | 保持现状，持续推进改进 |
| 70–84 | ★★ 良好 | 存在可优化的大编译时债务 | 重点关注头文件瘦身、重复实例化、关键重构 |
| 50–69 | ★ 需改进 | 多处模板膨胀问题，编译时成本可感知 | 立即修改不必要模板化、拆分热点；引入 extern template |
| < 50 | ✕ 危险 | 编译时依赖失控，严重拖累效率 | 制定重构计划：拆分头文件、显式实例化、降低模板嵌套 |

## 实施建议

1. **工具集成**：使用 `clang -ftime-trace`、`include-what-you-use`、`nm`/`bloaty` 等工具采集原始数据，再用本指南算法计算得分。
2. **门禁设置**：CI 设置综合分 <50 时警告（非阻塞）；ERROR 级别规则（MLR-022、MLR-024 无模块时）必须阻塞。
3. **重构优先级**：P0（评估 Modules 迁移可行性）> P1（MLR-013、MLR-018）> P2（MLR-014/023）> P3（降低嵌套、循环）。
4. **基线建立**：首次运行参见 8.1 节进行校准；每季度或代码量增长 >30% 时重新校准。
5. **SME复核流程**：至少两位架构师对得分 <60 的模块进行复核确认是否为真实债务。
6. **豁免审计**：按附录 B 及 8.2 节管理；每季度审计。

## 高级主题：基线校准与豁免验证

### 8.1 基线校准统计方法

默认阈值来源于大型工业项目的典型值。不同项目应基于自身数据校准阈值。

#### 8.1.1 采样模块选取

随机抽取 **20–30 个模块**，覆盖：
- 高频修改模块（修改频率前10%）
- 低频修改模块（修改频率后10%）
- 核心基础设施模块（影响编译最多的10个头文件）
- 边缘业务模块（外部接口）

#### 8.1.2 采集与统计

对每个采样模块计算扇入(I)、影响半径(R)、重复率、膨胀率、嵌套深度，得到数据集 `{x1, ..., xn}`，计算：
- 中位数 (Median)
- 四分位距 (IQR) = Q3 - Q1
- 上四分位数 (Q3)

#### 8.1.3 设定项目专有阈值

| 指标 | 默认阈值 | 校准公式 |
|------|---------|----------|
| 扇入 | 50 | `max(10, Q3 + 1.5*IQR)` |
| 影响半径 | 80 | `Q3 + 1.5*IQR` |
| 重复率 | 40% | `Median + 2*MAD`（MAD为中位数绝对偏差） |
| 膨胀率 | 35% | `min(60%, Q3 + 1.5*IQR)`（嵌入式20%） |
| 嵌套深度 | 10 | `max(5, Q3 + IQR)` |

#### 8.1.4 验证与迭代

阈值设定后应在不熟悉项目（约20个模块）中测试：
- 误报率 >10% → 放宽至 `Q3 + 2.0*IQR`
- 漏报率 >10% → 收紧至 `Q3 + 1.0*IQR`
- 每季度或代码量增长 >30% 时重新校准。

### 8.2 性能数据自动化验证

#### 8.2.1 豁免注解扩展语法（4.0 新增）

```cpp
// @allow_binary_bloat: <简要理由>;
//    performance_gain: X%;
//    compile_time_increase: Ys;
//    benchmark_script: ci/benchmarks/benchmark.cpp;
//    threshold: gain>=5% and increase<=10s
```

#### 8.2.2 CI 自动化验证流程

1. 编译两版本（特化版 vs 基线版）
2. 运行性能测试 10 次，取中位数得 `gain` 和 `increase`
3. 判断是否满足 `threshold` 条件
4. 不满足则阻塞 MR 合并，输出失败报告

#### 8.2.3 性能测试编写规范

- 确定性：固定随机种子
- 隔离性：无共享状态
- 代表性：数据规模与生产相当
- 版本控制：与代码变更同提交

#### 8.2.4 MLR-014 多精度豁免验证

比较 `double` 与 `float` 特化版本的汇编代码；若指令序列完全相同，则豁免无效。

#### 8.2.5 豁免审计增强

- 性能测试程序及日志归档到 `docs/waivers/performance_logs/`
- 每 6 个月自动重跑性能测试；条件不满足时提醒 SME 复审
- 项目豁免总数 >50 时，架构委员会季度审查
