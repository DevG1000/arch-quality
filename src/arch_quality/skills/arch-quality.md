## 二、维度定义与评分算法

每个维度包含：代码坏味道名称、检测方法、评分算法。评分算法从指南的文字描述中提取为可执行的分段函数，与工具 `calc_*_score()` 方法一一对应。

### 2.1 结构质量（30%）

#### 2.1.1 模块化（20%）

**代码坏味道：** "目录结构失衡"——平均每目录文件数偏离理想值 5 过远，模块边界不清晰。

**检测方法：**
- 统计项目唯一目录数与文件总数
- 计算 `avgFilesPerDir = 总文件数 / 唯一目录数`

**评分算法：**

```
modularityScore = 100 - |avgFilesPerDir - 5| × 10
（封顶 100，最低 0）
```

#### 2.1.2 耦合度（20%）

**代码坏味道：** "高耦合"——文件平均导入数超标，模块间依赖过密。

**检测方法：**
- 构建依赖图（import/include 语句）
- 计算 `avg = 依赖边数 / 文件数`

**评分算法：**

```
couplingScore = 100 - avg × 10
（封顶 100，最低 0）
```

#### 2.1.3 内聚度（20%）

**代码坏味道：** "低内聚"——超大文件（>1000 行）占比过高，单一模块职责过重。

**检测方法：**
- 统计超过 1000 行的文件数（依赖 `FileIndex.total_lines()` 填充真实行数）

**评分算法：**

```
cohesionScore = 100 - xlargeRatio × 200
```

#### 2.1.4 复杂度（20%）

**代码坏味道：** "高复杂度"——超过 200 行的文件占比过高，代码难以理解和维护。

**检测方法：**
- 统计超过 200 行的文件数（依赖 `FileIndex.total_lines()` 填充真实行数）

**评分算法：**

```
complexityScore = 100 - largeFileRatio × 300
```

#### 2.1.5 测试覆盖度（20%）

**代码坏味道：** "测试覆盖不足"——测试文件对源码的覆盖程度不足（4 层综合评估）。

**检测方法：**
- L1 目录覆盖：有测试的源码目录占比（模块级一一对应语义）
- L2 语言覆盖：有测试文件的语言占比
- L3 文件比：测试文件 / (源码文件 × 0.3)
- L4 绑定层覆盖：多语言项目有测试的绑定函数占比（pybind11 .def() / SWIG）

**评分算法：**

```
多语言: testCoverage = L1×30% + L2×25% + L3×25% + L4×20%
单语言: testCoverage = L1×37.5% + L2×31.25% + L3×31.25%  （L4 并入）
```

> **out-of-tree 测试根目录**：可通过 `--test-dirs` 声明外置测试目录（如 `tutorials/`），避免工业项目系统性低分。

### 2.2 设计质量（25%）

#### 2.2.1 SOLID 原则（40%，置信度：中）

**代码坏味道：** "SOLID 违反"——面向对象设计违反五大原则，降低需求变化弹性。

**检测方法（S/O/L/I/D 五原则启发式）：**
- **S 单一职责**：超大文件（>400 行）比例代理职责数
- **O 开闭原则**：接口/抽象类使用（正面）+ `new` 具体类（反面）
- **L 里氏替换**：override 不调 super 的比例
- **I 接口隔离**：接口方法数 ≤5（默认满分，接口膨胀在反模式/SAR-009 检测）
- **D 依赖倒置**：构造注入（正面）+ `new` 具体类（反面，Factory 例外）

**评分算法：**

```
solidScore = (S + O + L + I + D) / 5
```

> 置信度：**中**。依赖正则启发式，需人工复核。

#### 2.2.2 设计模式（15%，置信度：低）

**代码坏味道：** "模式缺失/误用"——代码成熟度不足，或模式使用不当。

**检测方法（12 种正则模式）：**
Singleton / Observer / Strategy / Factory / Command / TemplateMethod / Adapter / Facade / Decorator / Cache / Retry / CallbackInjection

**评分算法：**

```
patternCount = 检测到的不同模式种类数（上限 8）
diversityScore = patternCount × 10（上限 80）
correctnessScore = min(20, patternCount × 2)
patternScore = diversityScore + correctnessScore
```

> 置信度：**低**。正则匹配无法识别意图，**检测结果需人工复核**，不作为阻断性门禁唯一依据。

#### 2.2.3 架构风格（20%，置信度：中）

**代码坏味道：** "风格缺失/依赖方向违反"——系统无主导架构风格，或分层依赖方向反向。

**检测方法（目录模式）：**
layered(controller/service/repository) / mvc(model/view/controller) / modular(module/feature) / event(event/subscriber) / plugin(plugin/extension)

**评分算法：**

```
score = min(100, 60 + 主导风格命中文件占比 × 40)   # 识别出主导风格即 60 基准分
依赖方向违反（repository→controller）：每处 -5 分
```

#### 2.2.4 反模式（25%）

**代码坏味道：** "设计债务"——God Class/Long Method/硬编码等常见有害设计。

**检测方法：**
- God Class：**类块** >300 行且方法 >10 个（测试文件除外）
- Long Method：连续同缩进块 >100 行
- 硬编码：IP/密钥/密码等魔法值直接写死

**评分算法：**

```
smellDeduction = min(30, GodClass×10 + LongMethod×5 + hardcode×5)
antiPatternScore = max(0, 100 - smellDeduction)
```

### 2.3 文档质量（20%）

#### 2.3.1 README 完整性（25%）

**检测方法：** 正则匹配 README.md 章节标题（任意级 `#+`）

**评分算法：**

```
README.md 存在 → 20
包含简介 → +15；安装 → +15；使用 → +15；功能 → +15；配置 → +10；贡献 → +10
```

#### 2.3.2 CHANGELOG 完整性（15%）

**检测方法：** 正则匹配版本号/日期/变更分类

**评分算法：**

```
CHANGELOG.md 存在 → 30；版本号 → +20；日期 → +20；变更分类(Added/Fixed等) → +30
```

#### 2.3.3 ADR 覆盖率（20%）

**检测方法：** 统计 `.opencode/templates/` 模板 + `docs/adr/` 记录数

**评分算法：**

```
有模板且记录>0: score = 40 + 60 × min(1, 记录数 / min(5, 文件数/200))
无模板无记录: score = 0
```

#### 2.3.4 代码注释密度（15%）

**检测方法：** 统计注释行数 / 代码总行数（源码文件，排除测试）

**评分算法：**

```
<5% → 20；5-10% → 40；10-15% → 60；15-25% → 100（健康区间）；25-40% → 80；≥40% → 40
```

#### 2.3.5 JSDoc 覆盖率（15%）

**检测方法：** 统计 TS/JS 公共 API（export）上方是否有 `/**` 注释块

**评分算法：**

```
≥80% → 100；60-80% → 70；40-60% → 40；20-40% → 20；<20% → 0
（无公共 API → 100）
```

#### 2.3.6 架构文档完整性（10%）

**检测方法：** 扫描 `docs/`、`architecture/`、`.opencode/` 下 Markdown

**评分算法：**

```
文档存在 → 20；目录结构 → +15；模块职责 → +15；数据流 → +15；依赖关系 → +15；设计决策 → +20
```

### 2.4 演进质量（25%）

#### 2.4.1 历史可追溯性（16%）

**检测方法：** Git 提交频率（3 月/1 月/7 天）+ 贡献者数

**评分算法：**

```
有 Git → 20；3 月内有提交 → +20；1 月内 → +20；7 天内 → +20；多贡献者 → +10
（无 Git → None，权重按比例重分配）
```

#### 2.4.2 技术债务趋势（20%）

**检测方法：** 对比 `history.json` 历史结构分与当前

**评分算法：**

```
有基线 → 20；改善 → +40；持平 → +10；腐化 → -20
（无历史数据 → 20 基础分）
```

#### 2.4.3 依赖过时程度（16%）

**检测方法：** 静态解析 package.json / requirements.txt / **pyproject.toml** + lock 文件存在性

**评分算法：**

```
无依赖清单 → None（跳过）；有 lock → 80；无 lock → 60（版本未锁定风险）
（过时/漏洞精确判定需 npm audit 集成，标记 needs_external_tool）
```

#### 2.4.4 废弃代码比例（12%）

**检测方法：** 备份文件（.bak/.old）扫描 + 注释代码块正则

**评分算法：**

```
从 100 起扣：备份文件 -10/个；注释代码块 -5/处（上限）
```

#### 2.4.5 增量质量（16%）

**检测方法：** `git log --shortstat -30` 平均提交变更行数

**评分算法：**

```
<50 → 100；50-100 → 80；100-300 → 60；300-500 → 30；≥500 → 0
（无 Git → None）
```

#### 2.4.6 问题扣分（20%）

**代码坏味道：** "综合健康度不足"——跨包循环、大文件、高耦合、低内聚、测试不足、文档不足。

**检测方法：** **从 SAR 违规派生**（单一事实源，避免双重计分）：

| SAR 触发 | 扣分 |
|:---------|:----:|
| SAR-002 高耦合 | -3 |
| SAR-003 低内聚 | -3 |
| SAR-005 测试不足 | -3 |
| God File（>1000 行）| -5/个 |

**评分算法：**

```
problemScore = max(0, 100 - highIssues×5 - mediumIssues×3)
```

## 三、基线校准

评分阈值根据验证案例集（1.3 版）的实测数据校准。校准方法参照指南 §9 和数值 Skill §三。

### 校准数据来源

| 数据源 | 类型 | 用途 |
|:-------|:-----|:------|
| 46 万行单体系统（案例集 §1.1）| 模块化失衡 | 校准 SAR-001 阈值 |
| OpenFOAM Tensor.H（案例集 §1.2）| 高耦合 | 校准 SAR-002 阈值 |
| FreeCAD Document.cpp（案例集 §1.3）| 低内聚 | 校准 SAR-003 阈值 |
| 金融交易系统（案例集 §1.4）| 高复杂度 | 校准 SAR-004 阈值 |
| 开源 ERP 系统（案例集 §1.5）| 测试覆盖不足 | 校准 SAR-005 阈值 |
| Apache Commons DBCP（案例集 §2.1）| God Class | 校准 SAR-006 阈值 |
| 开源项目（案例集 §3.x）| 文档缺失 | 校准 SAR-010 阈值 |
| 不活跃 GitHub 项目（案例集 §4.1）| 项目不活跃 | 校准 SAR-012 阈值 |

### 校准方法

与模板元编程 skill §8.1 一致的统计校准流程：

```
1. 收集案例集的阳性案例（通过）的评分数据
2. 收集阴性案例（违规）的评分数据
3. 计算阳性案例评分分布的 5% 分位数作为及格线
4. 计算阳性案例评分分布的均值作为基准分
5. 验证阴性案例的评分是否全部低于及格线
```

## 四、豁免注解体系

### 4.1 注解类型

参照模板元编程 skill 和数值精度 skill 的豁免注解设计。标准架构质量 12 条 SAR 规则**默认不支持豁免**（结构/设计/文档/演进维度为基础质量，无业务豁免场景）。若项目确需豁免（如遗留系统迁移期），按组织豁免审批流程记录。

| 注解 | 适用规则 | 必填字段 | 说明 |
|:-----|:--------|:---------|:------|
| `@legacy_approved` | 全部 SAR | `reason`, `owner`, `approval_date` | 遗留系统迁移期的豁免审批标记 |

### 4.2 `@legacy_approved` 格式

```
@legacy_approved(
    reason = "遗留系统迁移期，重构排期 2026-Q4",  # 必填：豁免理由
    owner = "arch-team",                          # 必填：责任人
    approval_date = "2026-08-21"                  # 必填：审批日期
)
```

### 4.3 验证规则

- 豁免注解必须包含所有必填字段，缺失任一字段 → 不降级
- 字段值为空 → 视为缺失
- 豁免注解仅在同文件内生效，跨文件引用不作用

## 五、12 条 SAR 内置规则

每条规则包含：编号、名称、`output_level`、`severity`、代码坏味道描述、检测条件、豁免可能性。详细定义见指南第七章。

| 规则 | 名称 | output_level | severity | 代码坏味道 | 豁免 | 检测条件 | 指南§ |
|:-----|:------|:------------:|:--------:|:-----------|:----:|:---------|:-----:|
| SAR-001 | 模块化失衡 | **WARNING** | MEDIUM | 目录结构失衡 | 否 | `avgFilesPerDir` 偏离 5 过远 | §3.1 |
| SAR-002 | 高耦合 | **WARNING** | MEDIUM | 平均导入数超标 | 否 | `couplingScore < 60` | §3.2 |
| SAR-003 | 低内聚 | **WARNING** | MEDIUM | 超大文件占比过高 | 否 | `cohesionScore < 60` | §3.3 |
| SAR-004 | 高复杂度 | **WARNING** | HIGH | >200 行文件占比高 | 否 | `complexityScore < 40` | §3.4 |
| SAR-005 | 测试覆盖不足 | **WARNING** | MEDIUM | 测试覆盖不足 | 否 | `testCoverage < 50` | §3.5 |
| SAR-006 | God Class | **WARNING** | HIGH | 类>300行且方法>10 | 否 | 反模式 GodClass > 0 | §4.4 |
| SAR-007 | Long Method | **WARNING** | MEDIUM | 函数>100行 | 否 | 反模式 LongMethod > 0 | §4.4 |
| SAR-008 | 分层依赖方向违反 | **WARNING** | MEDIUM | 低层依赖高层 | 否 | layered 风格得分 < 60 | §4.3 |
| SAR-009 | 接口膨胀 | **INFO** | LOW | 接口方法数>5 | 否 | SOLID I < 80 | §4.1 |
| SAR-010 | 文档缺失 | **WARNING** | HIGH | 文档严重不足 | 否 | `docScore < 50` | §五 |
| SAR-011 | 依赖严重过时 | **ERROR** | HIGH | 依赖版本过时 | 否 | `depScore < 40` | §6.3 |
| SAR-012 | 项目不活跃 | **ERROR** | HIGH | 近3月无提交 | 否 | `no_commit_3m` | §6.1 |

**注意**：`output_level` 与 `severity` 解耦（与 NVR/MLR 体系一致）。SAR-011/012 用 ERROR（确定性检测，可作 CI 阻断）；设计/文档类规则用 WARNING/INFO（启发式或置信度中，需人工复核）。

## 六、跨规则协调

### 6.1 SAR ↔ 6.6 问题扣分（单一事实源）

SAR 规则是**唯一检测层**，演进质量的问题扣分（§2.4.6）从 SAR 违规派生，避免双重计分：

```
SAR-002 高耦合 → problemDeduction -3
SAR-003 低内聚 → problemDeduction -3
SAR-005 测试不足 → problemDeduction -3
God File（>1000 行）→ problemDeduction -5/个
```

### 6.2 与结构质量子维度的对应

SAR-001~005 分别对应结构质量 5 个子维度（模块化/耦合/内聚/复杂度/测试覆盖度）的阈值触发。子维度得满分时不触发规则，得低分时触发——保证"评分得满分时规则不触发、得分低时规则触发"的一致性。

### 6.3 N/A 守卫

| 规则 | 守卫条件 |
|:-----|:---------|
| SAR-011 | 无依赖清单（package.json/requirements.txt）→ 跳过 |
| SAR-012 | 无 Git 仓库 → 跳过 |
| SAR-009 | 无面向对象代码 → 跳过 |
| SAR-008 | 未识别 layered 风格 → 跳过 |

## 八、启用条件

标准架构质量评估是**基础维度**，对所有项目自动启用（无需检测触发），权重占主评分的 30%。它是唯一始终启用的维度，其他增强维度（多语言/模板/数值/物理场）按检测结果叠加。

| 基础维度 | 权重 | 说明 |
|:---------|:----:|:-----|
| 结构质量 | 30% | 始终启用 |
| 设计质量 | 25% | 始终启用 |
| 文档质量 | 20% | 始终启用 |
| 演进质量 | 25% | 始终启用 |

**与其他增强维度叠加时的权重调整**（多语言/模板/数值/物理场激活时）：

| 激活维度数 | 基础结构质量 |
|:-----------|:------------|
| 0 | 100% |
| 1 | 85% |
| 2 | 70% |
| 3 | 60% |
| 4 | 55% |
